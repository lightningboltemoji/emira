# The capture plane's cost model, measured

> Change `1785301362` — 2026-07-28

## Goal

Establish where a transition's head latency actually goes, and cut it. The capture batch sits in front of
every covered scroll — nothing has moved and nothing is covered while it is out — so it is the whole of
what a keypress feels like before the motion starts.

## Implementation

No behavioural change. Two comments and one `IMPLEMENTATION.md` paragraph asserted a cost model that
measurement contradicts, and the corrected model is the deliverable; two optimizations derived from the
old model were implemented, disproved and reverted.

**The model.** Against ScreenCaptureKit on a 120 Hz, 2× display:

```
T ≈ 10 ms (SCShareableContent)  +  12 ms fixed  +  10.3 ms × number of captureImage calls
```

Measured base + n stills: 22.7 / 32.3 / 42.3 / 53.7 / 62.9 ms for n = 0…4, holding slope to n = 16
(187 ms). The window server **serializes** screenshot requests; `withTaskGroup` buys about 45% overlap
against fully serial, not parallelism. Ruled out as artefacts: main-actor isolation on the capture
function, `Task.detached` onto the global pool, and capturing distinct windows versus one window n times.
So scope size *is* the latency, linearly.

The requested output size does not enter into it — a window captured at 1/32 of its pixel dimensions costs
the same as at native (19.7 vs 19.7 ms). Cost is per call, not per pixel.

**What this overturned.** `SCKCapturer`'s header claimed the batch "fans out, costing the slowest still
rather than the sum", and `IMPLEMENTATION.md` §3 rested the shoulder's placement in the head batch on that
same claim ("nearly free where it is paid"). Both are replaced. `CaptureService.defaultDeadline`'s
"~1.8× the observed worst case" is replaced by the model, which puts the 250 ms bound at ~22 windows —
headroom that shrinks linearly with scope rather than a fixed margin.

**Rejected: deferring the shoulder to a post-raise batch.** If the shoulder is ~10 ms per window at the
head of every scroll, and it only insures against a *further* command, issuing it once the cover is up
looks free. It is not. `theCoverNeverShowsAHoleHoweverFastTheCommandsArrive` fails immediately:
`focus` left/right opens a **126 pt** hole at 10-frame press intervals with 8-frame captures, and
`move-window` reaches 151 pt. The stills land after the layers have crossed into the newcomer. The
shoulder is load-bearing at ordinary key-repeat rates and stays in the head batch; only the *reason*
recorded for it was wrong.

**Rejected: caching `SCShareableContent`.** Worth ~10 ms of every batch, and emira observes every window
create/destroy/move already. But `SCWindow` is a **snapshot, not a live proxy**: `.frame` never updates
after the fetch, so a cached token yields the wrong capture dimensions and a wrong `CapturedSurface.frame`
for any window that has since moved. Worse, a token whose window has *closed* still returns an image
rather than failing — a ghost on the cover, silently. A safe version needs invalidation on the geometry
observations, which our own teleports generate, so the cache would be cold at exactly the keypress it
exists to serve unless a debounced background re-warm is added too. Not worth that machinery for 10 ms.

**Characterized but unused: one call for many windows.** `SCContentFilter(display:including:)` renders N
windows in a single capture — 22.2 ms for four, against 53 ms as four calls — onto a genuinely transparent
background (the desktop and dock are excluded by default). Crops out of it are **pixel-identical** to
`desktopIndependentWindow` captures (|Δalpha| and |Δrgb| both 0.000), rounded corners and their alpha ramp
intact. The crop rect is `(window.frame.origin − union(includedFrames).origin) × scale`; `filter.contentRect`
reports the full display and is a red herring. Two constraints keep it from being a straight win: the
capture is display-bounded, so a window clipped by the screen edge comes back truncated and a parked
column comes back as its sliver — both still need their own call — and overlapping included windows bake
their occluder into each other's crop. Its value therefore scales with how many columns sit *fully* inside
the viewport, which is layout-dependent and zero for a wide column with bleeding neighbours.

## Observations

The floor this leaves is ~45 ms for any cover: one content fetch, one base, one still. Going below it
means not capturing on the critical path at all — speculative pre-capture while idle — which trades
against stale stills and the display link's "an idle emira pays nothing" property.

Not measured: whether the ~10.3 ms per call is a compositor frame boundary (8.3 ms at 120 Hz plus
overhead) or a fixed IPC cost. If the former, the model would differ on a 60 Hz display and every number
here is machine-specific. `CaptureReport.elapsed` already logs the real thing per batch, so the daemon's
own output is the check.

The deferred-shoulder experiment suggests a narrower variant nobody has tested: shoulder only the
*leading* side of the sweep, halving its cost, since continuing in one direction is far commoner than
reversing past the start. `worstHoleWhileSpamming` spams a single command and so exercises only the
leading shoulder — a reversal case would have to be written before that could be trusted.
