# CI on GitHub Actions, and a release scheme with one version authority

> Change `1785196403` — 2026-07-27

## Goal

emira built and tested only on the machine it was written on, and the version it claimed lived in
`Resources/Info.plist` as a literal — a number nothing enforced and everything could contradict.
Publishing a build meant assembling one by hand. The question this answers is not "how do we run
`swift test` in the cloud" but "what is a version, who decides it, and how does a release become
impossible to publish twice".

## Implementation

**The git tag is the only version authority.** No file in the tree carries a number now: the
`Info.plist` in `Resources/` reads `0.0.0`/`0` and `make app` stamps the bundle's *copy* from
`git describe --tags --match 'v[0-9]*'` plus the commit count. Drift is not prevented, it is
unrepresentable — there is no second place to bump. The alternative considered and dropped was a
version file that CI verifies against the tag, which is a consistency check standing in for a
consistency property. `emira --version` reads the stamp back out of `Bundle.main`, which for an
executable inside `Contents/MacOS` resolves to the bundle around it, so the CLI and the daemon
report one string with no codegen and no build plugin; outside a bundle it says `dev`.

**Two channels, and machines never pick a version.** `release.yml` fires on both a push to `main`
and a `v*` tag. Main updates the long-lived `tip` prerelease — tag force-moved, release edited in
place, asset clobbered under a stable name so its URL is a permalink. Deleting and recreating the
release reaches the same state and was rejected because creating a release notifies watchers, which
on a per-push channel is a reason to unwatch the repository. A tag cuts the real thing, guarded
before the build: the tag must be `vMAJOR.MINOR.PATCH`, must not already be released, and must be an
ancestor of `main`. Publishing the same semver twice therefore fails twice, at the guard and again at
`gh release create`. `tip` is a prerelease so `/releases/latest` and a Homebrew cask cannot see it.

**Signing is plumbed but unexercised.** `CODESIGN_IDENTITY` defaults to ad-hoc and the workflow
supplies a Developer ID when the secrets exist, bringing `--options runtime` and `--timestamp` with
it; notarization and stapling run under the same gate. `make zip` was deliberately split from
`make app` because notarization runs between them and a prerequisite would re-sign the bundle after
stapling and throw the ticket away.

Builds are arm64. A universal build was tried and abandoned: the toolchain warns that x86_64 is
deprecated at this deployment target, and macOS 26 is the last release to run on Intel at all.

## Observations

The signing and notarization steps have never run — they are skipped entirely until six secrets
exist, so their first real execution is their first test. Until then a *downloaded* build is
ad-hoc-signed: Gatekeeper refuses it, and because an ad-hoc signature is identified by a cdhash that
changes every build, every tip update re-asks for Accessibility and Screen Recording. That is the
thing standing between this scheme and a release anyone else can install (open item 3).

The Makefile's Swift Testing detection probes for the CommandLineTools plugin path and assumes an
Xcode-active machine does not have it. That assumption has only ever been tested against
CommandLineTools; the first CI run is what checks the other branch.

`EmiraShellTests` links AppKit. The runner has a logged-in GUI session so this is expected to work,
but nothing here has proven it.

The README's install section still points only at the releases page, and the Homebrew cask is still
bumped by hand — the workflow writes the archive's sha256 into the job summary so that bump is a
copy, not a computation. Pushing the cask from CI needs a token for the tap repository.
