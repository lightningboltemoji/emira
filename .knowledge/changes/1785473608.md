# A config broken at launch holds the desktop rather than replacing it

> Change `1785473608` — 2026-07-30

## Goal

A broken config file changes nothing — that is the reload rule, and it is right because there is
always something to change nothing *from*: the settings that were running a moment before the file
broke. At boot there is nothing. The daemon read the file, failed, fell back to `Config()` and went on
to adopt the entire desktop under it — every window snapped onto a gapless, full-width strip, laid out
by numbers the user never wrote, with none of their own keys bound to undo it. The `!` in the menu bar
was the only trace, and the menu under it said "emira is running with the last settings that loaded",
which in this one case was a lie. From the outside it is indistinguishable from emira working as
intended, which is the worst version of this failure: the user has to already know what their config
was supposed to do to notice that none of it happened.

## Implementation

The daemon's boot is now two phases. Everything up to and including the menu bar item runs
unconditionally; adopting the desktop is behind `startManaging()`, a latch called at boot only when
the config file parsed, and otherwise by the first save that makes it parse. Held, the truth plane is
never started (no `screensChanged`, no enumeration, no observers) and no keys are bound — so a held
emira is not a window manager that decided to do nothing, it is one that never began.

The grants still come first and both are still asked for. `OnboardingModel.live(wantsCover:)` reads
the user's *intent*, and a file we could not parse is a file whose intent we do not have, so a boot
diagnostic forces `wantsCover` rather than letting the invented `Config()` answer for the user. That
is behaviour-preserving today — `Config().transitionMode` is `.smooth` — and the point is that it stays
right if the default ever moves. A grant is also the one thing a later reload cannot go back and
collect: the process would have to restart, which is what onboarding exists to avoid a second time.

`StatusModel.configError: String?` became `configStatus: ConfigStatus` — `.loaded`, `.broken`,
`.neverLoaded`. Two failures, not one, because the sentence under the diagnostic is the entire
difference between them and a `String?` cannot carry it: `.broken` still says emira is running with
the last settings that loaded, `.neverLoaded` says it starts managing when the file parses. It also
takes the workspace address out of the `.neverLoaded` tooltip, which was naming a workspace holding no
windows. The enum makes the daemon's two call sites read as the decision they are, and makes the state
that cannot happen — a diagnostic with no consequence — unrepresentable. A failed *reload* while held
stays `.neverLoaded`: a save that does not fix the file has not given emira any settings either.

`ConfigLoader` is untouched, and one property it already had is now load-bearing enough to have a
test: `lastLoaded` is set only on success, so a failed boot read leaves it `nil` and the first parse
that works is always reported — including when what finally parses is `Config()` itself, which is the
case the "a config identical to the live one is not reported" suppression would otherwise swallow.

Rejected: falling back to the *example* config, which is a third set of settings nobody chose; and
refusing to boot at all, which throws away the menu bar item that is the only thing telling the user
what is wrong and the only way they have to open the file and fix it.

Also removed a duplicated `open config file` block in `menuNeedsUpdate` — two `let config`
declarations in one scope, so `main` had not compiled since the previous change.

## Observations

Verified against the running daemon on a scratch config: broken at boot logs "not managing windows
until it parses" and quits with "no managed windows to place"; a save that is still broken logs "still
not managing windows"; the first clean parse logs the keys, then the enumeration, then the columns, in
that order. The three menu strings are covered by `MenuBarTests`, but the latch itself lives in
`main.swift` and is wiring — the daemon run is what checks it.

The socket server starts either way, so a held emira answers the CLI with an empty world: `emira focus
left` does nothing rather than failing. That is honest — the daemon *is* running — but it is not
*informative*, and a `Reply` that said "not managing; the config file is broken" would be better. It
needs a wire error case, which is more than this change should carry.

Nothing re-reads the file on a timer, so a held emira depends entirely on the directory watch. If
`ConfigWatcher.isWatching` is false — the config directory could not be opened — a held emira stays
held for the life of the process with no way out but a relaunch. That is already true of hot reload
generally; being held makes it matter more, and nothing currently reports it.
