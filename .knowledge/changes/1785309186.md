# `fullscreen` expels, and undoes

> Change `1785309186` — 2026-07-29

## Goal

`fullscreen` was a width and nothing else, so it did neither half of what the verb promises. A window
with stackmates got a maximized *column* — both windows still on screen, at half height — and the
second press only handed the width back, leaving the strip wherever the first press had scrolled it.
Toggling twice from `[w1] [w2 w3] [w4]` with the first two columns in view left the third column in
view instead.

Make it a reversible **window** operation: the window ends up alone and full-screen, and pressing again
puts the strip back the way it was.

## Implementation

Fullscreen is now two layers, and only the new one is new. `isFullscreen` stays the width shadow it
was — over `widthOverride`, over the ladder — so the width underneath still comes back exactly, still
re-resolves against whatever the presets say at that moment, and still needs nothing stored. What
shadowing cannot carry is **structure** and **scroll**, and those are all `ColumnLayout.fullscreen`
(a `Fullscreen?`, replacing the `Bool`) holds: the stack the window left as a `ColumnId` + row, and
the viewport as a `ColumnId` + a distance.

**A window with stackmates is expelled first.** That is what makes it full *height* as well as full
width; the alternative the original change ruled out — a per-window height selection — is not needed
if the window simply gets a column. The branch is the one `move-window` and `consume-or-expel` already
make (alone in its column ⇒ the column resizes; with stackmates ⇒ it pops out), so `enterFullscreen`
splits on exactly that and the solo path is the old code path untouched. It pops out **in place**, the
column it leaves sliding right, so the anchor it will be restored against does not move under it.

**The viewport is an anchor, not an offset.** A stored scroll offset is a number in strip space that a
column opening, closing or resizing to the *left* silently re-points — it would put the strip back
somewhere it never was. A column and a distance from the content area's left edge survive all three,
because the left edge is re-read from the live strip at restore time. `theViewportAnchorSurvivesAColumnResizingToItsLeft`
is the difference: a `grow` on column 0 while fullscreen, and the anchor comes back to 100 where a
remembered offset says 0.

The restore **clamps into the strip**, and that is not hygiene. When what the distance was measured
across is gone, it asks to look past the strip's origin; clamped, the column gives the distance up and
comes to rest flush, which is the only reading that means anything — there is nothing to its left to
show. It cannot be left to `emitPlacements`' resting re-clamp, which catches the snap path and not the
animated one: the scroll would travel past the origin and `closeTransition` would snap to the target it
was handed. Confirmed by removing it, which is invisible under `smoothTransitions: false` and 500 pt of
empty margin with it on.

**Staleness is unrepresentable rather than detected.** Both halves name a `ColumnId`; ids are never
re-issued, so a surviving match is that column and not a coincidence, and a half whose column has gone
is simply not applied. There is no fingerprint of the arrangement, no validity predicate and no expiry
— and every way it can degrade lands on precisely what `fullscreen` did before this change: the window
keeps the column it is in at its own width, and the strip reveals it the ordinary way. A fingerprint
was considered and rejected for being both more machinery and *worse*: it invalidates on a window
opening at the far end of the strip, which the user cannot see and does not care about.

**The growth rides the structural edit, not the width spring.** The popped-out column is born at 100%
and never resizes, so what animates is the expelled window's displacement from the slot it left, which
`finishStructuralEdit` already seeds — one animator with an opinion about that width. Routing it
through `animateColumnWidth` *as well* was the first attempt and double-counts: `finishStructuralEdit`
diffs the two geometries at `old.widths`, which has no entry for a column the edit just minted, so the
whole ⅓ → 100% growth already lands in the displacement. Going the other way — dropping the width
spring on the solo path too, and letting displacement carry every fullscreen — loses the
`SizeCorrection` spring-back, since `handlePlacementCorrected` retargets the *width* animator when an
app refuses to be as wide as we asked.

Two callers needed an offset that is not a reveal, so `finishStructuralEdit` and `resizeFocusedColumn`
each gained a `framedAt:` override (defaulted, so no other call site moved). `resizeFocusedColumn`'s
"nothing to look at" guard was deliberately left alone rather than taught to ask whether the viewport
moves: `framedAt` reaches it only from un-fullscreening a column whose window never left it, and a
column that gets there at one width is one already at 100%, whose single resting place under both
reveal and center is flush — so the anchor it restores is the offset it is already at. The guard for it
was written, found to be unreachable, and removed.

`extract` and `adopt` inherit the fullscreen **width** and not the record (`Fullscreen.plain`), so an
expel out of a fullscreen column, or a move to another workspace, keeps the size the user asked for
out loud without two columns claiming one origin.

## Observations

- Not exclusive, as before. Two fullscreen windows each carry their own record and undo independently,
  in either order.
- A `consume` *into* a fullscreen column leaves it holding two windows with the record intact; the
  undo then merges the fullscreened window home and leaves the consumed one behind. Deliberately not
  given a rule of its own — it is reachable only by asking for it out loud, and the outcome is
  defensible — but it is the one arrangement where "a fullscreen column holds exactly one window" is
  briefly untrue.
- The restore is only ever attempted on the strip the window is on. A record whose columns are on
  another workspace degrades through the same "column has gone" path as everything else, which is why
  the cross-workspace case needed no code.
- `ColumnLayout`'s encoded shape changed (`isFullscreen: Bool` → `fullscreen: Fullscreen?`), so a state
  dump reads differently. Nothing persists across restart, so there is no migration.
- **The anchor is read off `viewportOffset.target`, not `.current`.** A press landing mid-scroll should
  remember where that scroll was coming to rest, not the frame it happened to be passing through; at
  rest the two are the same number, so only an interrupted scroll can tell them apart, and
  `fullscreenLandingMidScrollRidesTheOpenTransitionAndAnchorsOnItsDestination` is the one that does —
  it fails by ~250 pt against `.current`.
- The four decisions worth distrusting were each checked by breaking them and watching the suite: no
  expel (6 tests), no anchor restore (2), anchor off `.current` (1), no clamp on the restore (1 —
  and only after that test was moved onto the animated path, where it is the sole authority).
