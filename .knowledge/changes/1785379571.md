# One onboarding window, live, that boot waits on

> Change `1785379571` — 2026-07-29

## Goal

First launch was a fatal path with a message on it. Each missing grant produced an alert naming one pane,
with a button to open it and an instruction to launch emira again — two grants meant two alerts and, in the
worst case, two relaunches, and the alert opened in the middle of the screen, which is exactly where macOS
puts its own grant prompt. The two covered each other, and the one the user could act on was the one they
couldn't see.

Two grants that must both be in place before anything works are *one* piece of setup. So: one window, both
grants in it, with the state live, boot waiting rather than giving up, and **one** restart at the end
instead of a relaunch per grant.

## Implementation

`Sources/EmiraShell/Onboarding/` splits the way `MenuBar/StatusItem.swift` does — `OnboardingModel` is the
policy (which grants are asked for, the copy, when boot may proceed, where the window opens),
`OnboardingWindow` the AppKit wiring. The daemon's whole permissions section is now four steps: build the
live model, log what is outstanding, `OnboardingWindow.gate(_:)`, exit if it had to open a window. `die`'s
`settings:` parameter went with it — the remaining two fatal paths (no displays, an unbindable socket) never
had a pane to offer.

**The policy is unchanged and deliberately so.** Every row is required; asking for the cover
(`smooth-transitions`) is still what makes Screen Recording a row at all, so a config that waived it is
never asked. That made satisfaction "all rows granted" and let the notion of an optional row disappear
instead of being modelled — the optional grant is the one that isn't there. A "start anyway" button was
rejected on the same grounds: a waiver granted to one session leaves no trace, and `applyEnvironment`
already ANDs the live grant into the preference, so the config file is the only place that can record the
decision. Closing the window quits.

**The copy bills both grants as required and never mentions the waiver.** An earlier draft spent its second
paragraph on `smooth-transitions = false`, which is an argument against the feature the user just installed
emira for; the setting stays, undocumented in the window, for the few who want it. The status line also
lost its "emira starts as soon as it's granted" — the window closing itself and emira appearing says that
better than a sentence promising it. The paragraphs are asserted *whole* in the suite, not by substring:
they are assembled from string fragments to stay inside the column, and a space lost at a seam is a typo in
the first sentence anyone reads of emira.

**A Screen Recording grant cannot be read by the process that wants it, so a subprocess reads it.**
`CGPreflightScreenCaptureAccess` is computed per call but caches its *answer* for the life of the process —
the row stayed ❌ through a grant given in front of it, which is the same cache behind macOS's "Quit &
Reopen". That prompt is also the evidence for the fix: a relaunch working at all says a new process reads
the truth. So `Permissions.probeScreenRecording` relaunches something small — the daemon's own executable
with `--probe-capture`, which preflights, exits with the answer as its status, and touches nothing else,
before `NSApplication` exists. Same binary, same signature, same bundle identity, which is what TCC records
a grant against; ~200 ms per probe, one in flight, so the row lands within about half a second of the
switch. Two things follow: `GrantRow.refreshed()` had to become **monotonic**, because the in-process read
would otherwise revert the probe's answer on the next tick; and `emira-daemon` now takes one argument or
none and exits 2 on anything else, since the fall-through is a window manager adopting the whole desktop —
which is what a stale `dist/` binary and a typo'd flag produced while testing this.

**And onboarding ends with a restart, which is the shape the whole flow settled into.** A grant given to a
*running* emira turns out to be only half a grant, in three ways: the process cannot read the Screen
Recording answer it was just handed (above), the capture client behind that answer is stale the same way,
and its menu bar item never appears. Each was worked around separately and every workaround was then
removed. An in-place `execv` — macOS's own "Quit & Reopen", performed rather than requested — did fix the
two capture problems, and did nothing for the indicator, which reports itself *present* while being nowhere
on screen. So the window ends by asking for the one thing that fixes all three and needs no mechanism at
all: **quit emira, then open it again**, said in the status line and carried by a `quit emira` button that
appears exactly when it becomes the thing to do. `Outcome.restart` covers both ways out — the button and
the close box — because the daemon's move is the same either way. The saving is not small: three mechanisms
(an exec, a relaunch-loop guard, a log file to observe them with) came out, and what replaced them is one
sentence and one button.

**The button is drawn to be pressed** (`PulseButton`): centred, in the wordmark's greens, with a glow that
breathes and a highlight that washes across its face and then rests, and the reason for it directly beneath
at the size of the paragraphs above — the same kind of sentence, so the same type. This is the only control
emira ever asks anyone to press, and a window that says "quit, then open it again" over a plain grey button
reads as an error rather than an instruction. `NSButton` keeps the click, the target/action, the key
equivalent and first responder; the drawing is all ours, because a layer-backed button draws its cell into
the layer's own contents, which any sublayer of ours would cover — so the title is a subview label and
everything beneath it is layers. Two things were checked rather than assumed: Core Animation is driven by
the render server, so both animations really do run while the app sits in `runModal` (sampled off the
presentation layer — `shadowOpacity` 0.42 → 0.73, the sheen sweeping and then resting), and
`accessibilityDisplayShouldReduceMotion` turns them off. The window grows when the button appears, so
`place` runs again and re-derives the corner: sizing alone would grow it upward, out of its inset and under
the menu bar.

The highlight is **wider than the button on purpose**. Three stops peaking at 34% white over 40% of the
width is a *line* travelling through the button, which is what it looked like; the fix is not a slower line
but a broader, fainter one — five stops peaking at 13%, spanning 1.2 of the width, so at mid-sweep the whole
face is inside the band and no edge of it is ever visible. The extra pair of stops exists because a gradient
interpolates linearly, and a bare triangle has a visible corner at its peak. Half the 3.2 s cycle is rest: a
shimmer that never stops reads as a progress indicator, and a fast one reads as a warning.

**Four further mechanisms were measured rather than assumed** (`scratchpad/modal.swift`, `markup.swift`):

- A `DispatchSourceTimer` on `.main` *does* fire inside `NSApp.runModal(for:)` called before
  `NSApplication.run()`, at the cadence asked for, and the run loop is still usable afterwards — which is
  what makes the wait a modal session and lets the daemon's boot stay straight-line. The loop needs exactly
  one exit: a `stopModal` arriving after the session ends is remembered and would close the next one, hence
  the `hasStopped` latch the close box and the button share. It also fixes an ordering — the system prompt
  is fired from the first drain rather than before the call, so the thing that explains the prompt is on
  screen before the prompt is.
- **Two TCC prompts fired together are one prompt.** Asking for Accessibility and Screen Recording in the
  same turn put up the Accessibility sheet and dropped the other request entirely — a clean run showed one
  prompt, not two. So the window asks for the first outstanding row only and lets the next grant landing earn
  the next prompt, which also puts that prompt up while the user is already in System Settings. The
  subprocess probe waits its turn on the same reasoning: before Accessibility lands, a probe per tick is a
  process per tick for a grant nobody has been asked about.
- `Heartbeat`'s fixed one-second leeway would have swallowed a 300 ms poll whole, so it is now a third of
  the period — which is the same 1 s at `WorldWatcher`'s 3 s interval, i.e. today's behaviour with the
  argument stated in the form it actually takes.
- `AttributedString(markdown:)` parses the blurb's `**bold**` and `` `code` `` spans into
  `inlinePresentationIntent` runs, but `NSAttributedString(AttributedString)` carries *no* `.font` attribute
  across, so an `NSTextField` would draw it all plain. Foundation does the parsing; the fonts are applied
  per run by hand. No hand-rolled parser, no guessing.

**The wordmark is a resource of the target that draws it**, not of the app bundle: `Bundle.module` resolves
both from `Contents/Resources` and from a bare `swift build` tree, so the first-launch window looks the same
however emira was started. `make app` copies the bundle inwards and signs it before the outer seal,
alongside the nested CLI. The asset is the README's own file — the **animated** WebP, not a still of it,
since the animation is the wordmark. Its green was already chosen to carry against either appearance, so
the alpha does the light/dark work and there is no variant to pick.

**Animating it is a chain, not an animation object.** Measured: 101 frames, alpha intact, ~1 ms to decode
one at the size the window draws, ~35 MB to hold all of them — and holding all of them is exactly what a
`CAKeyframeAnimation` over `contents` requires. So `Wordmark` decodes a single frame and schedules the next
on the delay that frame declares, which the asset forces anyway: 40 ms per stroke, then 2.48 s of stillness
at the end (6.88 s a loop). One property made that cheap rather than fiddly, and it was checked rather than
assumed — ImageIO composites animated WebP frames **whole**, every frame decoding to the full 472×192, so
WebP's blend and dispose rules never come up. The chain ends with the view, since nothing else holds its
closure; `DelayScheduler` has no cancellation and needs none.

**Placement is where the guessing had to stop, and it took two goes.** First, none of it applied:
`runModal(for:)` centres a window it has to show itself, so every computed frame was discarded and the
window opened wherever AppKit put it — which is *the same place the system prompt goes*, because
`NSWindow.center()` is 75% of the free space and a system alert is centred by the same rule (measured at
three heights). Two windows obeying one rule cannot help but collide, and no arithmetic in
`OnboardingPlacement` could have moved a frame that was being thrown away. Ordering the window front before
the modal session is the fix (`scratchpad/place.swift`: an origin of y=24 came back as y=555).

Second, with the frame finally honoured, the vertical rule was still the wrong shape. Clearing a *centred*
prompt on the y axis means knowing its height, and "two thirds down", then "two thirds plus 200 pt", were
both guesses at it — the measured alert spans y 606…906 of an 1800×1130 working area, but nothing says the
next one will. So the window opens in the **top-right corner**, inset `cornerMargin` (80 pt) on both axes:
beside the prompt rather than above or below it, which no prompt height can defeat, and where emira lives —
a few points under the menu bar item this window hands the user over to. On `NSScreen.screens.first`, for
the same reason the compositor picks that display over `NSScreen.main`: it is the one the strip and the menu
bar are on. `visibleFrame` puts it below the menu bar with no arithmetic of its own, and the clamp keeps a
window larger than the working area reachable, since the close button is the only way to decline.
`.floating`, so System Settings opening over the top doesn't hide the row the user is about to change.

## Observations

- **Confirmed end to end on real first launches** (`make install`, both grants reset): the prompts arrive one
  at a time, the rows land live — Screen Recording through the subprocess probe — and the window ends on the
  restart.
- **The window is verified by launching it, not by a test.** The model, the copy and the placement are
  unit-tested; the view is not, matching `MenuBarItem`. `tccutil reset Accessibility zip.tanner.emira` (and
  `ScreenCapture`) then opening `emira.app` is the real first-run path.
- The probe's answer is attributed by TCC to the **responsible** process, which is `emira.app` for a bundled
  daemon and the *terminal* for one started by `swift run` — so a dev build can be told it holds a grant that
  belongs to Ghostty. Harmless where it happens, confusing if forgotten.
- The config is read once, before the window. Editing `smooth-transitions = false` while it is up therefore
  changes nothing until the next launch, even though `ConfigLoader` could watch it — the loader isn't started
  yet, and starting it early to serve a path nobody takes is the wrong trade.
- **Still unexplained, and now routed around rather than fixed: a status item created on the launch that goes
  through the grant flow never appears.** It is there on every launch afterwards, which is what the closing
  restart makes certain. Recorded so nobody re-runs the search:
  - The daemon *reaches* `MenuBarItem()` — the socket and the hotkeys are wired after it and both work — so
    the item is created and never shown.
  - Six things were tested and are **not** the cause: a modal session before `NSApplication.run()`, an
    `execv`, a spawned successor, an item created before the run loop starts, a bare binary versus a bundled
    `LSUIElement` app, and a LaunchServices launch versus a shell one (`scratchpad/menu.swift`, `reg.swift`,
    `modalitem.swift`, `bundled.swift` — the last builds a signed `LSUIElement` bundle and `open`s it, which
    is what clicking the icon does).
  - **`AXExtrasMenuBar` is not the oracle it looks like.** Read against our own pid it needs no grant and
    reports a child — a button, a title, `isVisible` true — for an item that is demonstrably not on screen.
    It answers "the app has an extras menu bar with something in it", not "the user can see it". Two probes
    were built on that misreading before a real launch disproved it.
  - Everything built to chase it came out again: the `AXExtrasMenuBar` read, a second-status-item retry, a
    boot-time check at 1 s and 6 s, and `~/Library/Logs/emira.log` (a file sink for a bundled app's stderr,
    which is connected to nothing — worth revisiting on its own merits, but not as a debugging aid kept for a
    bug that is no longer chased).
- **Unrelated, and found by an accident while testing: a second daemon rearranges the desktop before it
  discovers it is second.** `SocketServer.start()` is the last thing boot does, well after `watcher.start()`
  has enumerated and placed every window, so the "another copy may already be running" refusal arrives after
  the damage. Binding the socket before the truth plane starts would fix it and is a boot-ordering change,
  not part of this one.
- Two rows is the whole table, and `OnboardingModel.list` is written for more anyway; a third grant would
  need no new mechanism, only a row.
