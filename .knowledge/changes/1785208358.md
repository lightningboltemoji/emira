# The cask bump, pushed by an app, out of one environment

> Change `1785208358` — 2026-07-27

## Goal

A tagged release published an archive and then stopped: the tap's `emira` cask was edited by hand
from the sha256 the job printed into its summary, which is a copy nobody is going to make reliably
at the one moment it matters. Automating it needs a credential `github.token` cannot be — it is
scoped to this repository and the tap is another one — and that is the actual question here. Not
"how does CI push to a second repo", but what the release pipeline is allowed to hold, for how long,
and on whose behalf.

## Implementation

**The bump runs in the release job, after the release.** `brew bump-cask-pr --write-only --commit`
rewrites `version` and `sha256` and nothing else, then `brew style --cask` and `brew audit --cask
--online` gate the push; both run because they catch disjoint things — audit passes a cask whose
`desc` style fails, and only `--online` fetches the published URL to check the checksum against it.
The wrapper actions (`Homebrew/actions/bump-packages` and the third-party ones) solve a different
problem: they `livecheck` to *discover* a version and fork the tap to open a pull request, which is
what contributing to a tap you do not own requires. The checksum is already in hand from the archive
this job just built, and the tap is ours. Same job for the same reason — a separate one would
re-download the asset to hash what it had just made. The accepted consequence is that a failed bump
leaves a published release with a stale cask, repaired by re-running the job and never by re-tagging.
`tip` deliberately gets no bump: its cask is `version :latest` with `sha256 :no_check` against a
permalink, so no build can change a field in it, and pinning a real checksum there would be correct
only until the next push to main.

**A GitHub App, not a token.** The app is installed on `homebrew-tap` alone with `contents: write`
and nothing else, and `actions/create-github-app-token` mints an installation token per run — an
hour's life, revoked in the step's post-run, belonging to no person. A fine-grained PAT was the
obvious alternative and grants exactly the same access; what it does not have is any of those three
properties, and its expiry is a date nobody is watching until a release fails on it. The mint step
carries the ref conditions and the bump step gates on `steps.tap.outputs.token != ''`, because a
skipped step has no outputs — so the credential's absence is the only gate, and a repository with no
app configured skips the cask exactly as one with no certificate skips signing. The commit is
authored as the app rather than as `github-actions[bot]`, which is a claim that would now be false;
that needs the bot account's numeric id, so the step reads it from the API rather than hard-coding
the one that was pasted in for `github-actions[bot]`.

**One environment, gating on the ref.** `production` holds the six `MACOS_*`/`APPLE_*` signing
secrets and the app's client id and private key, and its deployment policy admits the branch `main`
and the tag `v*` — the two channels stated a second time, at the place the credentials live, so a run
from any other ref cannot read them. The job declares `environment: production`; without that the
secrets are simply invisible to it, and the `env.X != ''` gates read as "not configured" rather than
failing, which is a silent skip and was the state this change found. No required reviewer, on
purpose: the same job builds `tip` on every push to main, so an approval rule would tax every merge
in order to guard the one ref a human already had to tag deliberately. The tag is the gate.

## Observations

None of this has run. The app credentials exist now, so the mint is the one part that could be
exercised, but the six signing secrets still do not — that is open item 3, unchanged.

The bump's first real run will fail, and where it fails is known in advance: both repositories are
private, a cask's `url` is fetched by plain `curl` with no credentials, and so `brew audit --online`
gets a 404 for the asset. That is open item 5, and it is the reason to expect a red step on the first
tag rather than to read one as a defect in this change.

The deployment branch policy was `main` only until this change added the `v*` tag policy. A tag push
matches tag policies, not branch ones, so the first versioned release would have been rejected at job
start — before the guard, before the build — with the tag already pushed. Recoverable, since no
release gets created, but the failure would have arrived with no obvious connection to its cause.
