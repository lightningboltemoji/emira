# the schema becomes a table you can enumerate

> Change `1785393582` — 2026-07-29

## Goal

The config schema existed only by being *run*: `Config.parse` was forty-five lines of straight-line
statements, and the only way to answer "what settings are there?" was to read them. That is fine for one
consumer and it is about to have four — the reader runs the schema, the writer renders it, `emira config`
explains it, and the settings window lays it out. Three of those cannot read Swift statements.

The hand-maintained example document at the top of `ConfigSyntax.swift` was the proof this was worth
doing. It was a restatement of the reader in comment form, kept true by a careful eye and nothing else,
and it had already drifted: it documented `[keys]` and `[[window-rules]]` at a level of detail the reader
no longer matched. After this it is generated, and pinned.

## Implementation

**One `Setting` per key, and a codec is what makes the entry serve reader and writer both.** A codec
knows what a legal value is, how to take one out of a `TOMLValue`, and how to put one back; a setting
pairs it with a `WritableKeyPath` and the prose. The two halves are stored as closures because the table
is one array over values of different types. Every codec reads through `ConfigSyntax.swift`'s typed
readers rather than restating them — those became `static`s over an already-taken value, so a
table-driven setting and a bespoke section now refuse the same value by running the same code, which is
the only version of "the diagnostics don't regress" that stays true.

Diagnostic regression was the risk worth designing against rather than testing for afterwards, and the
shape that avoids it is that `Bound` carries its own sentence. `atLeast` and `greaterThan` stayed two
spellings rather than collapsing into a range, because "must be at least 0" and "must be greater than 0"
are different refusals — a gap of zero is a gap, a spring of zero is not a spring — and the entry is
where that distinction now lives, `Kind.legend` reading it back out for the generated document.
`ConfigSyntaxTests` did not change by a character.

**The three springs are one sub-schema, not three special cases.** They differ in which motion they
drive and in nothing else. Each contributes two entries whose setter reads the *running* config and
replaces one coordinate, which is what keeps a file that stiffens the scroll from silently dropping ζ to
zero — the old `spring()` reader's `default:` parameter, expressed per key instead of per table.

**What the table deliberately doesn't hold**, each read by a function named for it and called out at the
call site rather than left as whatever the loop didn't take: `outer-gap` (one value with five spellings),
`[keys]` (an open table), `[[window-rules]]` (repeating, ordered, cross-validated). They are exactly the
three that get bespoke editors in the settings window, so forcing them in would have bought a tidier list
and a worse GUI. The reader is now three passes — the table, those three, then "what was left" — and the
take-what-is-known-report-the-rest property is preserved exactly; it just takes from a loop.

`SpringParams.smooth` is the one change outside `EmiraConfig`, and the generated document is what found
it. It was `critical(frequency: √800)`, so routing k through a square root and back landed on
800.0000000000001 — which the example file would have printed as the default, and which no file could
round-trip. Respelling it as `SpringParams(stiffness: 800, dampingRatio: 1)` is the same spring, agreeing
with the old one on `damping` to the bit; only k loses its rounding. `SpringTests` already asserted the
two spellings agreed within 1e-9, so the assertion became an equality and the tolerance moved to the
`critical` spelling it now describes.

## Observations

`make test` is green at 1036, `EmiraConfigTests` at 113 — seven new, and two of them carry the change.
Both were mutation-checked rather than assumed: deleting `layout.column-gap` from the table makes the
coverage test name `columnGap`, and appending a line to the golden file fails the document test.

The coverage test builds its own config file *from the table* — every setting set to a value that
disagrees with its default, derived off `Kind` — then reads it and asserts the only field of `Config`
still at its default is `struts`. So a new field is caught by a test nobody had to remember to update,
and a new *setting* is exercised without being named. `notKeys` is the explicit list and has one entry.

`width-presets` prints as `[0.3333333333333333, 0.5, 0.6666666666666666]` and that is correct rather than
unfortunate: the default is one third, and `0.333` would be a document that lies about it. The spring
case above looked identical and was not — there the noise was accidental, and the fix was at the source.

**Where a new `[table]` header goes is still appended, not schema-ordered.** The document model left that
as a placeholder for this change to refine, and the schema now makes it possible; it is not done here
because nothing writes a new table yet and `ConfigDocumentTests` pins the current placement. Task 6's
rule editor is the first caller with an opinion.

`Kind` has four cases over sixteen settings — 9 numbers, 3 choices, 2 toggles, 2 size lists — which was
the stated tripwire — a case serving one setting
means the table has stopped paying for itself. A test asserts it, so the tripwire is armed rather than
remembered.
