# The pointer plane

> Change `1785627157` — 2026-08-01

## Goal

The pointer is the one thing on screen a cover cannot cover. It composites above every window including
our overlay, so for the length of a transition it is the only element still describing a desktop the user
has stopped looking at — a bright arrow over the third column while the strip scrolls past underneath it.
`[mouse] hide` makes a command that moves the desktop take the pointer away and the next real motion bring
it back; the plane that answers it then carries two more features, `[mouse] follows-focus` sending the
pointer after focus and `[focus] follows-mouse` sending focus after the pointer.

## Implementation

**The charter question came first.** Hiding the cursor from a background app needs private SPI, which
trips `PRINCIPLES.md` §7. The public API genuinely cannot do it: an Apple DTS engineer confirms
`cursorUpdate` is not delivered to non-active applications, which closes cursor rects, tracking areas and
`NSCursor.push`/`set`, and eight variants were tried from an `.accessory` process that is never frontmost.
`CGSSetConnectionProperty(cid, cid, "SetsCursorInBackground", true)` followed by the public
`CGDisplayHideCursor` does work, with SIP fully enabled, so §2's core decision is untouched. §7 now states
the terms: reached by `dlsym` and never linked or `dlopen`ed, because arm64 chained fixups have no lazy
binding and a linked symbol that went away would fail in dyld before `main` while a looked-up one is a
`nil` and a capability bit; it decides nothing about where a window goes; the property is set lazily on
the first hide, so a user who leaves the setting off has emira execute no private call at all; and
`CursorConnection.swift` is the whole of it, deletable in one commit.

**A hide is a standing assertion rather than an edge**, and reading it as an edge is what makes the
feature look like it does nothing. Any application becoming active *discards* a background hide — and
emira's own batch does exactly that a millisecond later, since the hide is prepended to a batch that ends
in `.focus`, whose AX write raises a window in another app. Three facts settle the shape, all measured:
absent an activation `CGDisplayHideCursor` keeps a real per-connection count, so two hides take two shows;
an activation *resets* that count rather than decrementing it; and the count floors at zero. So
`Event.appActivated` re-emits `setCursorHidden(true)` for as long as one is owed, the reducer's state does
not move on a re-assertion (nothing was decided, something was undone), and `PointerExecutor` counts its
own depth and pays the whole of it out on a show — no arithmetic on our side can predict the server's
count, and the overshoot is free while an unpaid hide is a desktop with no cursor. The *announcement*
stays edge-triggered even so: `onCursorHidden` arms the wake watcher, which re-anchors as it arms, so
announcing every re-assertion would measure an untouched pointer from wherever the last activation fell.

**That event has two sources, because `NSWorkspace` is deaf to the commonest case.**
`didActivateApplication` fires on a change of *frontmost app*, and `AXWindowWriter.focus` re-activating the
app already in front — which is what focusing the other window of the same app does, the commonest focus
change there is — discards the hide and posts nothing. So the writer reports the activations it makes
itself: `focus` gained a completion, called only when `FocusIntent` did not supersede the request first,
and `AXExecutor` acks it with `feedback(.appActivated)`. That is the shape `place` already has, and it
keeps the effect's meaning (which window has focus is still the observers' to say; this is only "an app
came forward"). The ack is deferred one turn of the main queue, which is load-bearing — the window server
re-establishes the cursor *after* `activate()` returns, and a synchronous re-assertion was measured to
lose that race. Rejected: a callback on the concrete writer wired in `main.swift`, which puts an
untestable fact where no test reaches; and skipping `activate()` when the app is already frontmost, which
removes the discard at its source but is racy against `isActive` and risks a focus that silently fails to
raise, a worse failure than a cursor that blinks for a frame.

**The decision to hide is a post-pass on the `reduce` wrapper, not a call in each verb.** A `.command`
that emitted something, with nothing already hidden, gets the hide *prepended* — so workspace switches,
structural edits and any verb added later are covered by construction, while a window opening by itself is
not, and a read like `dumpState` or a `focus left` into the wall needs no naming. Both gates ask **who
asked**, not what moved: a rule drawn around window movement looks right and is wrong, because focus
crossing between two on-screen columns emits `.focus` alone. The executor may not decline what the
reducer recorded — the capability is a config question, answered once by `applyEnvironment`, and an
executor that returned early after the reducer had already recorded the hide left the two permanently out
of step, with no announcement, no armed watcher and so no way back for the session.

**We only hide because we can see the motion that ends it.** The capability has two conjuncts —  the
private symbols resolve, *and* the pointer's motion monitor installs — and refusing a state with no exit
is better than any timeout, which would also unhide on someone who is merely reading. The monitor is
therefore probed by installing it and taking it straight down, before the config is finished; it is then
installed for either setting that wants samples, so a desktop that asked for neither pays no standing idle
cost. Motion is three masks besides `mouseMoved`, since moving with a button held posts `*MouseDragged`
and a hidden pointer must not survive a window drag. `PointerWake` anchors at the hide and reports
`Event.pointerWoke` once, four points from that anchor, then disarms: measured from the anchor rather than
summed along the path, because jitter sums to any threshold given enough seconds while a slow deliberate
drag crosses this in a few samples — and a watcher left armed would put an event through the pump on every
twitch for the rest of the session, into the inbound log, which *is* the replay log.

**`Effect.warpPointer` carries a rect rather than a point**, so "leave it alone if it is already in there"
belongs to the instruction; the alternatives were a second effect or a core that tracks the cursor, which
would be wrong between reads. Focus moving records `State.pointer.pendingWarp` in a second post-pass, and
one rule pays it — *owed, and no session open* — which covers the uncovered case at once and the covered
one when `Motion.closeTransition` clears the session, with no list of closing events to keep in step.
Waiting is the point: under a cover the reals have already teleported, but the user is watching layers
travel toward the target, and a cursor arriving 250 ms early is the flash the cover exists to prevent, one
element over. The visit is dropped rather than retried, gated on `isOnScreen` and clamped into the working
area so a half-revealed column takes the pointer to the part of itself the user can see. `follows-focus`
is a four-rung ladder because **here a column is most of the screen**: "already inside" is the common case,
so `lazy` is nearly inert and `force` is what people mean by the feature. `except-hover` is `force` minus
the one source where the warp can only lose — the hovered window is already the right one, so the
recentring's whole effect is a jump away from where the hand aimed. It gates the *owing*, never the
paying (by payment time the event is several events ago), and asks the event rather than `FocusOrigin`,
which cannot tell a hovered focus from a commanded one since both reduce into the same tail. Every focus
change re-decides the debt, including a declined one, or a visit would aim at a window focus has left.

**`[focus] follows-mouse` is the one with real design risk**, because here a focus *scrolls*: hover the
edge of column N+1, the reveal scrolls, N+2's new edge arrives under the stationary pointer, and it runs
away across the desktop. Two rules stop it and neither is an optimisation. It fires on **pointer motion
only, never window motion** — the termination argument, and why `PointerFocus` is driven by the mouse
monitor and never by `onStateChanged`. And it is **suspended while a cover is up**, since hover is an act
of the eye and mid-transition the eye is on a photograph. Suspension keeps *tracking* while it declines to
dispatch, so a cover coming down leaves the baseline as whatever is under the hand; recording nothing
would make the first twitch after every scroll a crossing. The hit test is pure and lives on `World`
(floats and dialogs before tiled windows, restricted to `isOnScreen`, which excludes parked nubs for free —
a nub sits under a hot corner). Only the crossing enters the pump as `Event.pointerEntered`: 120 raw
samples a second would fire `onStateChanged` at that rate and fill the replay log. Two orderings hold the
plane together. `PointerSamples` runs focus **before** the wake, because a hidden pointer may be sitting
over a window nobody chose and the wake is about to clear the flag focus reads. And a warp rebases *both*
readers, since it posts no event: the wake forgets its anchor without arming, and focus re-reads the hit
test, which matters because a float lying over the target's centre would otherwise take the focus the warp
was sent to deliver.

## Observations

- **Passing over the Dock brings the cursor back**, confirmed on this machine. The window server enforces
  it deliberately; it is a permanent limit of this route rather than something to work around, which is
  why `[mouse] hide`'s help sentence names it — a user whose cursor reappears at the bottom of the screen
  would otherwise file it as a bug.
- **Screenshot differencing is the anchor for every claim about the cursor**: `screencapture -x` against
  `screencapture -x -C` over a crop at the pointer, with a plain-vs-plain control. `CGCursorIsVisible`
  read from an `.accessory` process that neither is frontmost nor issued the hide tracks the real state
  exactly on macOS 27.0 (26A5388g), which makes the plane fast to probe, but it is deprecated since 10.9
  and absent from the SDK, so it stays `dlsym`-only and out of shipping code. `PRINCIPLES.md` §6 is
  corrected to match.
- **Synthetic `CGEvent` motion does not reach a global `NSEvent` monitor**, so the wake threshold cannot be
  exercised from a harness at all. It was confirmed from a live instrumented daemon instead: anchor, a
  sample 18 points away, `pointerWoke`, show — then four alternating `focus left`/`focus right` with the
  cursor hidden throughout and `State.pointer.isCursorHidden` agreeing at every step, transitions
  unaffected (44 frames, ~118 fps, cover raised at ~36 ms).
- **A warp posts no event**, verified with both a global and a local `.mouseMoved` monitor, and that is
  what makes the two follow settings compose without a guard: hover focuses, the pointer is warped in, and
  no sample is generated to report a second crossing. The same goes for `CGWarpMouseCursorPosition`
  working from a background process at all and taking top-left global coordinates. None of these is
  unit-testable — they are facts about the window server, recorded here and re-checked with a probe.
- Three things settled by running it rather than by argument, none lived with yet. **`center-focused-column
  = true`** makes every hover recentre the world under the hand; it cannot run away, but it may be
  unusable, in which case hover becomes the one focus path that scrolls nothing. **Z-order**: the core
  knows frames, not stacking, so an *unmanaged* window over a tiled one still resolves to the tiled one —
  `CGWindowListCopyWindowInfo` (~2.5 ms, the same unprivileged list the registry joins against) is the
  authoritative answer, held in reserve and payable at a crossing only. **Dwell**: nothing is implemented,
  every crossing dispatches, and sweeping across the strip to reach the menu bar may want hysteresis.
- Under `transition = off` nothing sequences the warp against the AX sets landing, so the pointer can
  arrive a frame or two before the window it is aimed at. The covered path waits for the session to close
  and does not have this problem.
- **A commands-only rung was built and dropped.** It gated on `case .command = event`, which also excludes
  a click on a background window — the honest reading of "don't fight a hand that is on the mouse", since
  a click and a Cmd-Tab are indistinguishable at the AX layer. It costs Cmd-Tab, an app raising itself and
  an arriving window, which are exactly the changes the pointer should follow. A click therefore still
  recentres under `except-hover`: a milder case, since the click has landed by the time the pointer moves
  and it happens once rather than on every sweep across the strip.
