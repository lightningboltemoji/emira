# `transition` is a three-rung ladder, and the middle rung is new

> Change `1785463092` — 2026-07-30

## Goal

`animation.smooth-transitions` was one bit holding two independent questions: *may we cover?* and *may
we animate?* Three of those four answers are worth having and one bit reaches two of them, so the
useful middle setting — cover the transition, but do not animate under it — was unreachable.

It also made the capability degradation land on the wrong rung. Screen Recording is required for the
cover's pixels, so a machine without the grant fell all the way to no cover, which is the mode that
shows the AX API's latency in full. The user who lost the grant wanted the *reliability* the cover
buys at least as much as the springs.

`[animation] transition = "off" | "snap" | "smooth"` replaces it. `off` and `smooth` are what the two
values of the flag were. `snap` covers without animating: the cover goes up painting the finished
strip, the reals teleport behind it, and it comes away the moment their AX sets land.

**Singular, to match its two neighbours.** `animation.window` and `animation.cover` each name the one
thing the key has an opinion about, and every key under `[animation]` reads as a property of *a*
transition rather than of the set of them. The label follows the same pairing — "Transition mode"
beside "Cover mode".

**The Swift field is `transitionMode`, where the key is `transition`.** The same widening the two
neighbours already do — `animation.window` is `windowAnimation`, `animation.cover` is `coverMode` — and
here it earns more than symmetry: `Config.transition` beside `Motion.transition` puts a mode and a
`TransitionSession?` under one word in reducer lines that read both.

## Implementation

**`snap` is the cover without the clock, and that is the whole mechanism.** `Motion` already treats an
absent animator as "at the value `Layout` derives" — it is why `closeTransition` *drops* the width and
displacement animators rather than snapping them, the resting value being something the layout already
knows. So snap needs no new session phase, no new `Effect` and no compositor change: open the session
and create no animator. Everything else falls out. `isSettled` is true from the session's first
instant, so `isReadyToClose` reduces to `landingComplete`; `emitLayerFrames` reads
`viewportOffset.current`, which a snapped aim has already put at the destination, so the cover's first
blit is the finished geometry.

The reducer changes are three cover gates now reading `transitionMode.covers`, and three places that
put a quantity in motion now asking `transitionMode.animates` first: `aimViewport` (new, the one place the
scroll is aimed, in motion or already arrived), the column-width animator in `resizeFocusedColumn`,
and the displacement loop in `finishStructuralEdit`.

**What a structural edit moves is a fact about the layout; putting it in motion is the mode's.**
`finishStructuralEdit` builds `moves` — the scoped windows whose frames actually changed — under every
mode, and displaces them only under one. That list is also the answer to "can anything on screen see
this edit", which is what decides whether to cover at all, so computing it inside the `animates` branch
— the obvious spelling — makes every snapped structural edit look invisible and stops covering it
entirely. `TransitionModeTests.aSnappedStructuralEditIsStillCovered` is the test that fails on that
spelling and on no other in the suite; it was written by making the mutation and watching it catch it,
and it still fails on the same mutation after the loop was split in two.

**The cover's exit is a length per mode, and the lengths were found by looking.** The 0.22 s cross-fade
at `endTransition` was the first thing that read wrong under the new mode — the longest-lasting motion
in a transition whose whole claim is that it has none, landing at the end where it is the last thing
seen. A hard cut was the obvious correction and was tried first; on screen it read as *too* abrupt. So
`snap` dissolves over 40 ms, about two frames: enough to be a seam rather than a jump, not enough to be
motion. `off` takes the same length rather than a cut of its own — it raises no cover, so the only one
it can ever price is a cover whose transition outlived a reload into `off`, and two frames is not a
thing anyone can tell from a cut. That is also what lets `Overlay.fadeOut` keep a single path: it is
never handed a zero, so the teardown that releases the stills never has to ride on whether AppKit
schedules a completion handler for an animation with no work to do.

**Every length is safe, and the reason is the close gate.** A cover is dismissed only once its
animators have settled *and* its reals have landed, so it always comes off a desktop that already
matches it. A dissolve was never hiding a geometry difference — it hides a window whose *content* went
stale while it was covered, which is a smaller thing under `snap` because the cover is up for the AX
latency alone. That is also why the number is free to be tuned by eye: nothing depends on it.

**The choice sits in `CompositingExecutor`, not in `Reconstruction` or `Overlay`.** Those two need a
window server and are below the test seam, so a duration chosen down there would ship unasserted;
`CoverSurface.dismiss` therefore takes `over:` and the executor answers it from a `transitionMode` it is
told, exactly as `Reconstruction.animation` and `CaptureService.mode` are told theirs. `Overlay` keeps
no calibrated number at all now — it fades for as long as it is asked to. That also settles which plane
owns the choice: the rule already written down twice is that a value the *core's emitted geometry is
identical under* belongs to the shell, and the core emits the same `endTransition` whatever the exit.
`Effect.endTransition` gaining a payload was the alternative, and it would have made the core name a
wall-clock quantity for the first time.

**One function applies the config to the shell.** `transitionMode` is the third value that reaches a
shell object rather than the reducer, after `Reconstruction.animation` and `CaptureService.mode`, and
three properties assigned at two call sites — boot and `ConfigLoader.onLoad` — is a drift the comment
above them could only assert against. `applyShellConfig` is that assertion made structural; the boot
call also moved below the executor's construction, which is what the "set on the executor below, which
does not exist yet" apology in `main.swift` was standing in for.

**The capability clamp is an `if`, and the ladder is not `Comparable`.** A `min` over
`off < snap < smooth` was written first, on the reading that a capability sets a ceiling. It has no
ceiling to set: both covered rungs are the same captured pixels, so the grant answers *any cover at
all*, and `min(x, granted ? .smooth : .off)` degenerates to identity on one branch and to `.off` on the
other — an `if` spelled at length, resting on a `<` that read the ladder off `allCases` and so off the
order the three cases happen to be written in. It was also the reverse of future-proof: `.smooth` sits
in it as a hard-coded top, so a rung added above one would have been clamped away on the granted
branch. `if !granted { .off }` says the whole of it, and `TransitionMode` conforms to `CaseIterable`
alone — which it owes to `Codec.word`, the config vocabulary being read off `allCases`.

**A covered-but-settled tick now emits nothing.** Every tick of a snap transition is one, and so is
the tail of a smooth one still waiting on an AX set after its motion is over — both were re-emitting a
frame identical to the last. The frame clock still runs (`Runtime` gates it on `isTransitioning`, which
is right: the session is genuinely open), so the reducer has to be inert rather than merely unused.

**`Setting.Kind.toggle` now serves one key, and stays.** `ConfigSchemaTests` asserted no `Kind` case
serves a single setting — a smell detector for a case invented per key — and moving `transition` from
`.toggle` to `.word` tripped it. What `.toggle` buys was measured rather than assumed: it is the branch
of `Kind.value(from:)` that makes `emira config set … true` write a bare `true`, and folding bools into
`.choice` would write `"true"` quoted, which the next read refuses. The suite already prices that
behaviourally in `everySettingReadsBackWhateverItPrints`, so the counting test was narrowed to what it
can actually detect — a case no setting uses — with the reason recorded there: the cases are the shapes
a TOML value comes in, and `toggle` is the bool shape whether one key or six are spelled `true`.

## Observations

- **The config change is breaking and has no soft landing.** `ConfigSyntax` has no alias mechanism, so
  an existing `smooth-transitions = true` is now an `unknownKey` error naming its line. Correct for the
  file's contract, and cheap to soften later with a special case on that one key if it is ever worth it.
- **A snapped resize is the one place the mode is visibly a compromise.** The still inside the cover was
  filmed at the old width and is painted into the new one by `animation.window`, held static for the
  duration of the AX latency rather than passing through in motion. Under `smooth` that same wrong-scale
  frame reads as animation. Not yet looked at on a screen; if it is bad, the fix is for a snapped resize
  to decline the cover rather than for `animation.window` to grow a case.
- **Capture latency is snap's felt latency.** Under `smooth` the head cost of `cover = "exact"` hides
  inside the spring; under `snap` there is nothing to hide it in, and it *is* the perceived
  responsiveness of the keypress. `snap` + `cover = "immediate"` is the natural pairing, and whether
  `snap` should bias that default is unmeasured.
- The three modes are asserted to come to rest in the same place
  (`TransitionModeTests.everyModeComesToRestInTheSamePlace`), which is the invariant that keeps a mode a
  statement about what is on screen *during* a transition and nothing else.
