# Overriding a setting for a while, without touching the file

> Change `1794893257` — 2026-11-16

## Goal

Some settings are right most of the time and in the way occasionally. The case that prompted this was
`unfocused-opacity`: a video playing next to a notes window is hard to watch through a veil. Keybinding
it was possible, but only through `exec` and the CLI's `config get`/`config set`. That route rewrote
the user's file on every press, and it held the "on" value in the binding as well as in the file,
because the file has nothing to remember it by while the setting is off. It also ran into a
`ConfigDocument` rule: setting a key to its default deletes the line, and setting it again adds it
back after the table's last key. Measured on the real file, one round trip moved a line, unless the
key was already last in `[focus]`.

A verb per setting (`veil toggle`) would have answered this one case and invited a gap verb, a blur
verb and so on. The general shape is a layer of settings changed for this run only, over a file that
is never written.

## Implementation

**`config override [toggle] <key> <value> | override reset [<key>]`.** It takes any key `config set`
takes, spelled the same way. `ConfigOverrides` (in `EmiraConfig`, pure) reads each value through the
setting's own codec, so a refusal uses the same wording as the file's. It keeps entries in the order
they were added, and replacing an entry keeps its position. A toggle matches on the value as well as
the key, so `fn-o` (opacity 1) and a `fn-shift-o` (opacity 0.8) each switch between their own value
and the file's. Values are compared by `.spelled`, the same comparison `isDefault` uses, so `1` and
`1.0` count as one value.

**It is spelled under `config`, and `config` is a verb for `override` alone.** An override changes the
config, only not the file, and the rest of `config` is already about settings rather than about the
file (`explain` describes them). So it goes in that namespace, split by where each subcommand acts:
- **The CLI keeps the file's subcommands local** and sends only `config override`. `main.swift` makes
  this one check against `OverrideIntent.word`, the single place the word is spelled.
- **The vocabulary's `config` verb accepts only `override`.** A binding to `config set …` is refused
  with the grammar, rather than sent to a daemon that has no file to write.

`config override reset` repeats `override` because `config reset` would read as resetting the file.
`--help` lists `config override` with the other `config` subcommands. `ConfigCommand.usage` writes its
line from the verb's own signature and summary, so a bare `emira config` shows it too, and
`Vocabulary.usage(of:)` leaves it out of the general command list.

The other spellings considered:
- **A bare `override` verb** keeps the CLI's `config` branch purely local. But it separates the command
  from the settings it changes, and `emira config` would never mention it.
- **A two-word verb name** (`"config override"`) would make the errors name `config override` rather
  than `config`. But the parser, the keybinding editor and the settings catalog all assume a command's
  first word is its verb.

**The layer goes between the file's reading and `applyEnvironment`, in `reconfigure`.** A reload and
an override are its only callers, and it hands one value to the reducer, the hotkeys and the shell
together, as `onLoad` already did. Because `parsedConfig` now keeps the last successful reading, a
file edit made while an override is on leaves the override in place, and a reset lands on what the
file says at that moment. The alternative was to snapshot the file at override time and restore the
snapshot. Resetting would then undo any edits made in between. Before any file has parsed (a
never-loaded boot), an override is recorded but not applied: there is nothing to apply it over, and
`applyKeys` must not bind an empty set of keys.

**The verb takes `exec`'s route through the core.** The engine returns `[.override(intent)]` and
changes nothing. `CompositingExecutor` gains a `config` plane that hands the intent to `onOverride`.
The daemon handles it on a `DispatchQueue.main.async` hop. Inside the pump, `configChanged` would be
queued while `applyKeys` and `applyShellConfig` ran first, the reverse of the order a reload uses.
The hop makes both callers run from a clean stack. Intercepting the command before the reducer was
the other option, but commands enter at two places (`RequestRouter` and the hotkey sink), and they
would have had to stay in agreement. The engine's exhaustive switch needed a case for the verb either
way.

**The core carries keys and values as strings.** It cannot validate them, since `EmiraCore` does not
see the schema. Instead the `[keys]` reader checks every `config override` binding with
`ConfigOverrides.check`, so a typo is reported with its line number. The CLI runs the same check
before dialling the socket, so `emira config override` exits 2 on a typo rather than getting `ok` and
leaving only a line in the daemon log. The daemon still validates, and logs a refusal, for anything
that reaches the socket some other way.

**`Verb.Argument.line` now carries `grammar`, `placeholder` and `hint`.** `config` has an open argument
just as `exec` does: the key is one word, and the value is everything after it, because `[0.5, 1]`
contains spaces. So it uses the same shape, which the keybinding editor draws as a text field beside
the verb. The text field's tooltip used to hard-code `exec`'s "/bin/sh" sentence, and `.line` printed
its grammar as `<placeholder>`, which can't spell a grammar with alternatives. The placeholder is now
an example that has to parse, and `CommandSyntaxTests` checks this for every `.line` verb in place of
the old `"\(verb) ghostty"`. A dedicated control (a setting popup, and that setting's own control for
the value) was considered and is not built; see below.

**The menu lists overrides; the title stays the workspace address.** A broken file takes the title as
`!` because it is a failure. An override is something the user chose, so it is listed in the menu,
at the top where diagnostics go, with **Reset overrides** under it. Reset calls `applyOverride`
directly rather than going through the vocabulary. A command that emits an effect hides the pointer
(`hidesCursor`), and a mouse click on a menu item should not do that.

`emira-daemon` now lists `EmiraConfig` as a dependency, because `main.swift` names
`ConfigOverrides`. It was reachable through `EmiraShell` already; listing it makes the dependency
explicit. The wire version stays 1: a new verb has never bumped it, since the CLI and the daemon ship
in the same bundle.

## Observations

`make test` is green. New tests:
- `ConfigOverridesTests` (7);
- parser tests for the three forms, the argv value join and the refusals;
- the `config` verb refusing each of the file's subcommands;
- the engine pass-through and the compositor routing;
- a `[keys]` binding checked against the schema;
- override cases in every Codable round-trip list.

The CLI was checked by hand. A valid `config override` with `--dry-run` encodes the request. An
unknown key, a value below its bound, and a missing argument each exit 2 with the file's wording.
`config get`, `config frobnicate` and a bare `config` stay local.

**Run against the installed daemon, through the socket and the menu:**
- **The socket:** an opacity toggle removed every veil, and toggling again brought the veils back. A
  second override (`layout.column-gap 0`) stacked independently, and a reset restored both. Throughout,
  the config file's hash did not change.
- **The menu,** read through the accessibility API: it listed "Overriding the config file",
  `focus.unfocused-opacity = 1` and Reset. Clicking Reset lifted the override, left the pointer
  visible, and removed the section.
- **The key:** a hotkey-bound override was in effect before testing began, which is evidence that the
  key path works.

**What that live run was against:** a build that spelled the verb `override` alone. The rename since
then touches the parser, the CLI and `[keys]`, and not the wire (`{"override": …}` either way) or
anything in the daemon. So `.build/debug/emira config override …` was sent to that same running
daemon, and it toggled the veil the same way.

**A binding to `config override` does not parse on a daemon without this change.** It is refused as
`'config' is an unknown command`, the file counts as broken, and the previous settings stay. A binding
can be switched from the `exec` toggle only once the running build has this change.

**What an override applies to:**
- **Only the settings in the schema table.** It covers the same set `config set` does, which leaves out
  `outer-gap`, `[keys]`, `[[window-rules]]` and `[[display]]`.
- **Not per-display gaps.** An override of `layout.column-gap` changes `[layout]`, and a
  `[[display]]` block that sets its own gap still wins on that display, exactly as it would over the
  same line written into `[layout]`.
- **Not past what the machine allows.** `applyEnvironment` clamps an override the same as a file
  value, but the "not available on this system" line is only logged at boot, so an override clamped
  away (`trackpad-scroll` with no Screen Recording grant) is dropped without a word.

**The settings window shows the file, not the live config.** With an override on, the window's
control shows the file's value while the desktop shows the override. The menu lists the override next
to the window's own item, and `PRINCIPLES.md` now names this as the one allowed difference. A note
inside the window would be better.

**Left for later:**
- Several settings in one binding (a "video" key that turns off the veil and the gaps together). The
  grammar takes one key per command, and `[keys]` binds one command per chord.
- A keybinding-editor control that offers settings from the schema instead of a free-text field.
- `config explain` and `config get` saying when a setting is overridden. Both read only the file, so
  they would need to ask the daemon.
- Showing overrides in `emira debug` or `watch`. Both report core state, and the layer lives in the
  daemon, so neither shows which settings are overridden; `debug` shows only the resulting values.
