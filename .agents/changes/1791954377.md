# A floated arrival that took focus is focused

> Change `1791954377` — 2026-10-13

## Goal

While driving probe windows for `1791953609`, a second window from an app never tiled. The cause was the
config's own rule (`smaller-than-focused = 0.6`, `from-focused-app = true`, `float = true`): a 600×432 window
opened from a focused 1760×1102 window of the same app is floated by design. Opened at 1500×1000, the same
window tiled beside the first and took focus.

The floated case showed a real defect, though. The floated window held the keyboard, but `World.focusedWindow`
stayed `nil` for as long as it was open. `close-window` reads `focusedWindow`, so it closed nothing, and every
other verb that reads focus was working from nothing.

## Implementation

**The focus report arrives before the window is bound.** AppKit posts `AXFocusedWindowChanged` for a window as
it opens, before the scan that adopts it. The registry does not know the element, so the report is
`focusMovedUnmanaged`, and the watcher's read of the app answers `.window(nil)`: a successful answer naming no
managed window, which the core folds as focus leaving every managed window. The scan binds the window a few
milliseconds later, and nothing asks again. A tiled arrival never shows this, because the core focuses a tiled
window on adoption. A floated one gets only `noteActivation`, deliberately: most dialogs and popovers take no
focus.

**The watcher now asks the active app again once one of its arrivals is bound while its own focus belief is
`nil`** (`WorldWatcher`, after a scan's `windowCreated`s). The read goes through the existing `readFocus`, so
`FocusIntent`'s staleness checks apply as they do to any read. It runs only for the active app's arrivals,
but for every scan that binds one, including one that meets its windows already open. An arrival announced
while a close or reconciliation scan of the same app is out is folded into that scan and bound as already open,
and it took focus all the same. `focus` can stand for "the last answer named nothing bound" because it is never
cleared when its window dies, so once anything has been reported, `nil` comes only from such an answer.

Rejected: having the core focus a floated arrival itself. The core cannot tell a dialog that took focus from a
popover that did not, and only the app can.

Verified live: the same floated window is `focusedWindow` once bound, and `close-window` closes it. Three
`LiveWorldTests` pin the behaviour: the re-ask and the re-ask after a coalesced scan, which both fail without
the change, and the case where focus on a managed window means nothing is asked.

## Observations

- A read answering `nil` before a window is bound and then not re-asked can still happen when the arrival
  belongs to an app that is not active. That report is not keyboard focus anyway (`isActive`).
- Where the read is asked again and the app still names the old window, the core receives a report that
  changes nothing.
