# A display can have its own gaps

> Change `1790235880` — 2026-09-24

## Goal

One `[layout]` served every display, so a laptop screen and a 27" monitor beside it got the same gaps.
Gaps that suit a large monitor waste a meaningful share of a laptop's width, and gaps that suit the
laptop look cramped on the monitor. The ask was per-display configuration, with the scope of what a
display may override left open.

## Implementation

**A `[[display]]` block is a partial `[layout]` for the displays it names.** It matches on `name` (exact)
or `name-regex` (unanchored), the matchers a window rule's `app-id` / `app-id-regex` already are, and sets
any of `column-gap`, `window-gap` and `outer-gap` (with its four per-side spellings). Blocks apply in file
order over `[layout]`, a later one winning key by key and an outer-gap edge counting as a key of its own
(`EdgeInsetsPatch`). The reader refuses a block that names no display, a block that sets nothing, and a
`[layout]` key a display may not override, the last with its own sentence, because "not per display" and
"misspelt" are different mistakes.

**What a display may override is what is resolved against its working area.** That rule is the scope, and
it comes from the code rather than from a list. `LayoutMetrics(config:workingArea:)` was already "the metrics
config asks for on a display", with five of its inputs taken from the file. Making them depend on the display
too is one line at one seam: `LayoutMetrics(config:display:workingArea:)` applies `Config.on(display:)` before
reading the five. `State.metrics(of:)` is its only reducer caller. The parameter is required, so no future
caller can skip it. Struts already vary per display, and outer gaps were already documented as "the same
arithmetic", so no new kind of event appears: a workspace changing display already re-resolved against a
different working area.

Kept out, and why:

- **`default` (layout kind):** PRINCIPLES §1 makes the kind a workspace's, "never of the display". A
  workspace materializes on whichever display is acting and migrates on a lid close, so a per-display seed
  would make an address's layout depend on where the user happened to be standing.
- **`resize-detent`, `interactive-resize`:** they are about the hand, not the screen.
- **`width-presets`, `height-presets`:** these are metrics and fit the rule, but a column stores a *rung
  index*. `PresetCycle.size(at:)` wraps, so a ⅔ column (rung 2 of ⅓/½/⅔) crossing to a display whose ladder
  is ½/1 lands on rung 0, which is ½. That needs an answer (nearest size on crossing?) before presets can be
  per display. `Engine.swift:2603` also cycles heights through `s.config.heightPresets` rather than the
  metrics, and would have to move.
- **`center-focused-column`, `fullscreen-when-alone`:** both depend on screen shape (an ultrawide is the case
  for each), but neither is a metric. Centering is read at about a dozen reducer sites, and the solo rule is a
  seed that would not re-fire when a workspace changes display.

**Standing rather than seeded**, unlike a window rule. A block is consulted every time its display is laid
out, which a window rule must not be. That is safe because a gap is not a fact about any window, so there is
no second authority to fall out of step.

**The display's name moves into the core**, as `MonitorInfo.name` / `MonitorState.name` observed beside
`isMain`. Two consequences:

- `describesSameDisplays` compares the name, because the name now decides gaps.
- `watch` reads the name off `State`. `DesktopPublisher` used to resolve names with a second
  `NSScreen.localizedName` lookup and cache them; that lookup, its cache and the `displayName` closure are
  gone. So the name `emira watch` prints is the name a block matches, by construction, and that is the
  documented way to find out what to write.

**Settings window:** `display` is on `BespokeEditors.notEditable`. The right editor is a scope switch on the
Layout tab (*every display* / *this display*) over the gap controls it already has, and that needs
`ConfigDocument` to splice into an element of an array of tables, which it cannot yet do. The mock keeps
showing `[layout]`, because that is what the controls beside it edit. A mock showing the display's override
would make the gap slider look dead on any display that overrides it.

`Setting` gained `apply(_:spelled:_:)` so a display block's `column-gap` is read by `layout.column-gap`'s own
entry, with the same bound and the same sentence, while the complaint names the key the line actually carries
(`display.column-gap`). `edgeInsets` now returns a patch, applied over the default by `[layout]` and stored
as-is by a display block. The singly-bracketed-table diagnostic is shared by both repeating tables.

## Observations

**Validated live** on a Studio Display XDR (main, 2560×1440) with the built-in display to its left. The worktree
daemon ran against a scratch copy of the real config plus a built-in block at 4 pt, and frames were read from a
separate process via `CGWindowListCopyWindowInfo`:

- **Built-in:** two Finder columns landed at x = −1796 (a 4 pt margin), 894 wide (`(1792 − 4) / 2`), 4 pt apart.
- **Studio:** Ghostty kept `[layout]`'s 20 pt margins and 8 pt top.
- **Hot reload:** editing the block to `column-gap = 30` re-laid the built-in at 881 wide with a 30 pt gap and
  left the Studio alone.
- **`move-to-monitor`:** a window moved to the Studio took the Studio's 1250-wide ½ column.

**Seen in passing, not caused here:** a Studio column scrolled partly off the Studio's left edge (Safari at
x = −1281) extends into the built-in's area, which sits to that side. It was the same under the installed
daemon before the swap.

**Follow-ups, in order of likely value:** per-display presets, once the rung-crossing question is answered;
the settings-window scope switch; possibly `center-focused-column`, which is display-shaped and read against
the acting monitor at every site that asks.
