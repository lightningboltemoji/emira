# A background app's key window is not focus

> Change `1790142242` — 2026-09-22

## Goal

Pin Safari, open four Ghostty windows, ⌃D three of them quickly, click Safari. Safari is frontmost
(menu bar, ⌘T), and the one Ghostty left stays unveiled with Safari veiled, indefinitely. The core
believes focus is on Ghostty and nothing ever tells it otherwise: Safari was already active, so no
further report comes.

## Implementation

### What was measured

Reproduced live against the daemon with `EMIRA_TRACE=1` plus temporary logging of every `FocusIntent`
request and every verdict and drop in `WorldWatcher.resolveFocus`. The script opened four Ghostty
windows from the pin on an empty workspace, closed three through Ghostty's own `close window` by
explicit id, and posted a real click on Safari. When the click landed before the last close did,
**2 of 2** runs ended in the reported state: core on Ghostty, Safari frontmost, the veil on Safari.
The pin plays no part in the cause. It is what puts Safari in view beside the strip, so the wrong veil
shows. Two paths led there, and both come from a close that lands after the click.

**The backfill arrives from a background app.** The click activates Safari, and its activation read goes
through: the core is on Safari. Ghostty then finishes the close, picks its next key window and posts
`AXFocusedWindowChanged` for it, now from the background. `resolveFocus` read this as a report that
displaced Safari, which is alive, so it probed, got "alive" and passed `focusChanged(ghostty, .system)`
on. The core moved to Ghostty, and nothing activates an app for a `.system` report. This is the exact
reported state.

**The click is judged against the closing window.** The click's activation read answers while the
Ghostty window is still closing. The displaced window is that one, so the report was asked the backfill
question. The destroy then lands, the core hands focus to its successor and issues `focus`, and the
probe comes back "dead" (and superseded): Safari's report is dropped. The successor's activation pulled
Ghostty over the click in the runs measured. Wherever that activation is refused, which
`PRINCIPLES.md` §5 says it can be, this path ends in the same state.

### The fix

**`AXFocusedWindowChanged` is admitted only from the active app** (`WorldWatcher.active`, set from
`appActivated`). The notification means "this app's focused window changed", which is keyboard focus
only while the app has the keyboard. A real move to another app is always an activation, and the
activation is its own read, so nothing the user does is lost. Only the order changes: when emira focuses
a background app's window, the echo now comes back through the activation read instead of the
notification that `makeKey` provokes first. `nil` before the first activation admits everything, as before.

**The backfill question is asked only of the app that lost the window.** A report from a different app
emits without a probe. The watcher remembers which app its `focus` was in when it was reported
(`focusApp`), because a plain close retires the id at once and the registry can no longer say whose it
was. The first version asked the registry instead, and the suite's after-the-destroy test failed on
exactly that. A quit keeps the question: `appDeparting` and `appTerminated` forget the app, so macOS's
pick of the next app is still dropped in favour of the core's successor, as before.

Rejected: reading `NSWorkspace.frontmostApplication` at report time rather than tracking activations.
On the main actor it updates from the same notification that delivers `appActivated`, so it says
nothing more. It would also be a new `ObservationSource` member, where the observation the watcher
already receives is enough and keeps the rule testable.

### After

Same desktop and script, with the click racing the last close: 0 of 8 runs inconsistent (core focus
always the frontmost app's window). With the click after the closes: 4 of 4 on Safari. A sanity pass
across app activation, `focus left`/`right`, a same-app window switch and `focus-pinned` agreed with the
frontmost app at every step.

## Observations

**A click that races a close can still lose to the close's successor.** In 5 of those 8 racing runs,
Ghostty ended frontmost and focused: consistent, but not what was clicked. Traced: Safari's activation
read is out when the destroy lands. The core, which has not heard about the click yet, picks a Ghostty
successor. Because that column crosses the pin, the fence asks for Safari, and that request supersedes
the pending read under the rule for queued reads (IMPLEMENTATION §7, *judged against the request order
it left under*). The owed focus then activates Ghostty. The supersession rule exists for a keypress
issued after a click. Here the request came from the core reacting to a destroy, which the watcher
cannot tell apart. If that activation were refused, this would be a third route to the stuck state.
Not fixed here.

**Unchanged.** Emira's own settings window is excluded from `appActivated`, so while it is active the
watcher still treats the previously active app as active. With the first activation not yet seen after
boot, every app is admitted.
