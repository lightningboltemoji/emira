# fn as a modifier

> Change `1786152670` — 2026-08-07

## Goal

Bind `fn-h` to a command. `fn` was the one modifier the chord grammar had no word for, and adding the
word alone would have been worse than refusing it: the Carbon registry accepts an fn bit and then
answers to the wrong key.

## Implementation

`KeyModifiers` gains `.function`, spelled `fn` or `globe`, canonical first in `🌐⌃⌥⇧⌘`. Everything
else in this change exists because the system registry cannot take it.

**Carbon cannot express fn, and fails silently rather than loudly.** `EventModifiers` is a `UInt16`
whose bits stop at `rightControlKey`; there is no fn bit, and `kEventKeyModifierFnMask` is absent from
the macOS 27 SDK entirely. `RegisterEventHotKey` takes a `UInt32` but matches on the narrow width, so
a chord registered with an invented fn bit returns `noErr` and then fires on the *unmodified* key.
Measured, not reasoned: registering `H + 0x20000` and `H + 0x800000` took the plain `h` key away from
the whole machine until the process was killed. That is why `carbonFlags` became `UInt32?` and returns
`nil` for fn — the danger is not a missing feature but a working registration pointed at the wrong
chord, and `nil` is what keeps it from ever reaching `RegisterEventHotKey`.

**So fn chords go through a consuming `CGEventTap`, and only they do.** `SplitHotkeyBinder` routes on
that one flag and keeps `HotkeyManager` unchanged; `FunctionKeyTap` holds the fn chords. Carbon keeps
every other chord, because it remains the better mechanism: the chord is claimed at the window server
and emira is not in the event path at all. The split gives `bind`'s `false` a second reading — Carbon
means another app holds the chord, the tap also means macOS would not give us one — so
`Outcome.summary` names both rather than the wrong one.

**A chord's release belongs to whoever took its press.** Matching key-up on the chord the way key-down
is matched does not work: `fn` is let go before the key more often than not, so by the release the
chord is over, the flags no longer match, and the focused app is handed a key-up whose key-down it
never saw. The record is keyed on the key code alone, which is exact — a keyboard has one `h` and it is
either down or not. It is cleared whenever the window server disables the tap, because those releases
were dropped with everything else and a stale record is worse than the orphan it prevents: it would
swallow the release of a *later* unmodified press of the same key, which the focused app reads as a key
stuck down. `GestureTap` resets on re-enable for the same class of reason.

**The tap runs on its own thread, which is the answer to the objection against having one.** The
standing reason for preferring Carbon is that a consuming tap that does not answer stalls every
keystroke on the machine. That is a claim about where the callback runs. Matching reads a lock-guarded
snapshot, and the hop to the main actor is `DispatchQueue.main.async` *after* the decision to consume,
so the tap thread never waits on the main actor — the one part of emira that genuinely blocks, on AX.
The tap is also created lazily on the first fn binding, so a config with no `fn-` chord never creates a
keyboard tap at all. It needs no grant beyond Accessibility: verified by running the daemon with only
Accessibility and Screen Recording granted, where `.defaultTap` was created and 39 chords bound. A
process *without* Accessibility gets `nil` from `.defaultTap` while `.listenOnly` still succeeds, which
is what a missing grant looks like from inside `install()`.

That thread runs its loop rather than polling it. A `while !isCancelled` around a timed
`CFRunLoopRunInMode` would wake a `.userInteractive` thread several times a second for the life of a
daemon that is meant to sit still, to ask whether it should still be running; `CFRunLoopRun` with
`CFRunLoopStop` from `stop()` costs no wakes and tears down at once instead of a quarter-second later.
`stop()` can beat the thread to publishing its run loop, so both sides go through the registry lock and
`adoptRunLoop` returns `false` to send home a thread that would otherwise enter a loop nobody holds a
handle to — a leak that only looks harmless because the process it leaks in is usually exiting.

**The grammar refuses fn on keys that already carry its flag.** macOS sets the fn flag on AppKit's
function-key class whether or not fn is held — a bare left arrow reports `FN+numpad` — so a `fn-left`
binding would match the bare arrow and take it, the same failure as the Carbon trap. `Key.isFunctionClass`
names that set (arrows, F1–F20, home/end/page-up/page-down, forward delete) and `KeyChord.parse` throws
`functionCannotQualify` with a line number. Physical fn+arrow is remapped in firmware before anyone sees
it — fn+left arrives as Home — so nothing is lost by refusing it. Letters, digits, punctuation and space
are the layer that is genuinely free.

**Rejected: remapping fn to a real modifier with `hidutil`.** The only targets are left/right variants
such as right-command, and Carbon's own header marks the left/right distinction "Not supported on Mac OS
X" — `fn-h` would be indistinguishable from `cmd-h`. Remapping fn to a non-modifier key instead makes it
a plain keypress, not something a chord can be built on, and costs the key its native functions.

**The tap callback is a file-scope function, and that is not a style choice.** A closure written inside
a `@MainActor` type inherits that isolation, and the compiler emits a `swift_task_isCurrentExecutor`
check as the callback's first instruction — invisible in source, no warning, passes the type checker.
On the main run loop it merely passes, which is why `GestureTap` may write its callback inline; on the
tap's own thread it traps, and the daemon died on the first key event. Two plausible causes were wrong
before the disassembly settled it: the closure stored for delivery (which had a real, separate version
of the same bug, fixed by moving the main-actor hop into `Registry.fire`) and the file-scope
`matchedFlags` global (a probe under `-swift-version 6` reads it off-main without complaint).

## Observations

No unit test covers the isolation trap, and none would have caught it — the type checker was satisfied
and only a real tap on a real thread failed. The check is now structurally absent rather than asserted
against, and the disassembly is the evidence: zero executor checks in the callback body.

The tap, once created, lives until `stop()`. Removing the last `fn-` chord from a config leaves an idle
tap behind until the daemon restarts. It consumes nothing it does not match, so the cost is a live tap
rather than any change in behaviour.

`fn` is matched exactly, like every other modifier, so `fn-h` does not fire on `fn-shift-h`. Whether
that or a hyper-style "fn plus anything" leader is the better shape for a strip is untested.

Auto-repeat is consumed but does not re-fire, which matches what Carbon does for the other chords.
Holding `fn-h` therefore scrolls one column, not many; a held `alt-h` behaves the same way.

`held` survives `unbind`, deliberately: a config reload between a press and its release still owes the
release, because the press was taken.

`Match` is reachable only through a real `CGEvent`, so the flag masking — caps lock, the numeric-pad
bit — is not under the suite. Lifting its construction to something a test can call would cover the
part carrying the risk the tap exists to manage.

Exercised against a live daemon on one built-in keyboard. `fn-h/j/k/l` fire; a listen-only tap at
`tailAppendEventTap`, behind emira's own so that anything consumed never reaches it, saw neither half
of `fn-h` released `fn`-first and both halves of an unmodified `h` — the same rule read from the side
it must not over-reach on — with an unbound F13 as the control, because a silent observer proves
nothing. The thread parks: every one of 2536 samples sat in `mach_msg`. An external non-Apple keyboard
may report the fn flag differently, and nothing here has been tried on one.
