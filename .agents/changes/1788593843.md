# The fence writes a stack, not a focus

> Change `1788593843` — 2026-09-05

## Goal

Four defects in the pin's teleport gate, all of them in the bookkeeping around the fence rather than in
the fence itself. Each was reproduced against the reducer before it was fixed, and each has a test.

## Implementation

### The fence's write is a stacking operation

`Effect.confirmFocus` is described as the same write as `.focus` under a different promise, and the shell
answers it with a literal `writer.focus`. Its AX echo came back as `focusChanged(pin, .ours)` and folded
as an ordinary focus change, so `World.focusedWindow` sat on the pin for the length of the gate — and
every verb that branches on focus read the user there. Measured, on a left pin with a column crossing its
band: a second `focus right` resolves through the pin branch as *re-enter the strip*, lands on the window
it is already on, and the press is swallowed; `focus-pinned` finds itself already on the pin and toggles
back to the strip, the opposite of what was asked.

**The record of what the user asked for is `owedFocus`, and the echo is not a second opinion about it.**
A `.ours` echo naming a pinned window the core does not believe is focused can only be the fence's, since
the two other writes onto a pin — `focusPin`, and a `restoreFocus` correction — have already moved
`focusedWindow` there themselves. That is the predicate, and it is structural rather than timed: nothing
in it depends on the fence still being in flight when the echo lands.

What the echo was carrying that *is* wanted is the activation: `StackOrder` reads `World.focusedAt`, and
a float behind the pin is buried by it. So `World.noteActivation` takes `setFocus`'s stacking half alone.
Both activations the sequence orders are written through it, at the point the core decides them rather
than when a notification happens to arrive — `askNextPin`'s, and the debt's, which reasserts a focus the
core already holds and so trips `setFocus`'s "re-asserting raises nothing" guard. Left to the echoes, the
order between two apps' notifications decides whether the record says pin < target or target < pin.

Rejected: a third `FocusOrigin`, or a `Motion.isAwaitingPin` query. The first spends a protocol case on a
distinction the shell already makes by which effect it is executing; the second is true only while the
fence is out, so a late echo would fall through to the very fold it was meant to avoid.

### A gate speaks for its own display

`settleGatedFocus` looped every display and, for any un-cleared one, removed **every** `.focus` in the
batch — no filter on where the focus was landing. On two displays, `focus-monitor right` under a gate on
display 1 had its focus stolen, recorded as display 1's debt, and the debt already owed there overwritten,
so that window was never refocused at all. `host(_:holding:)` answers which display holds a window — the
one it is pinned to, the one showing its workspace, or the acting one for a window on no strip, which is
the fallback `acting` already makes — and both the steal and the record read it.

### The hold and the pay are one predicate

The steal asked `!isPinCleared`; the pay asked `isPinCleared && clearance.isEmpty`. Between them lies the
phase the debt exists for: pin confirmed, reals teleported, landings outstanding. A focus arriving there
went out at once, putting its app back over the pin while a window was still crossing the band.

The hole was plugged by accident — a command that retargets calls `guardPins`, which re-arms the gate,
which makes the steal fire — and that is exactly the coupling worth removing: a command that opens no
transition re-arms nothing, and `focus-pinned` is a bare focus change. `Motion.isGatingFocus` states it
once, and the two callers are its two polarities.

### A departed display takes its cover shape with it

`Compositor` filters its own `clearing` on `syncDisplays`; `State.coverClearing` was not filtered
anywhere. A display leaving mid-cover never reports the cross-fade that would have released the shape, so
the record outlived the surface — and `settleCoverClearing` emits only the difference, so the returning
display's fresh, flush cover diffed equal and was never cut back out. The pin then sits under a
photograph for the whole of that display's next transition. Dropped in `setMonitors`, beside `rehomePins`,
which is the one place that knows what survived.

## Observations

All four are reducer-side and the suite covers them headlessly; nothing here changes what reaches the
window server, so the live-desktop questions the pin already had are unchanged.

Three from the same pass are **not** fixed here and stand:

- `PinFence.confirm` answers a second request for a window already in flight *immediately* rather than
  joining it to the one outstanding. Reachable when a session times out with a pin still on the wire and
  the next session asks again: that gate opens unverified. `HoistPanels` solved the same shape with a
  generation counter.
- `Overlay.setClearing` drops `isOpaque` for the whole cover when any band is cleared, though only the
  band is transparent — the largest surface on screen loses its occlusion fast path on every frame of
  every scroll. Shrinking the window's own frame to the cover rect would keep it opaque and changes twice
  a session rather than every frame. Worth measuring before believing either way.
- `settleCoverClearing` builds a `LayoutMetrics` and a scope `Set` per display per tick for the length of
  every cover, including on a desktop that has never pinned anything.

`Motion.mayPlace` carries `isReadyToClose`'s doc comment, which it was inserted in the middle of.
