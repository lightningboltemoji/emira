# A window that just opened is not behind anything

> Change `1788833969` — 2026-09-07

## Goal

Reported from IntelliJ: `Cmd-,` opens the settings window, it appears, and emira immediately draws a
hoist over it — a picture of a window with nothing in it, pinned where the real one stands, reading as
the dialog having lost focus the instant it took it.

`EMIRA_TRACE` names the whole of it in two lines. The arrival and the hoist are one batch:

```
windowCreated(WindowTag#3, "Settings – hello-world", role: standard, 900×700, wasAlreadyOpen: false)
     → setHoists([HoistBinding(window: #3, …, state: covered)])
focusChanged(nil, origin: system)          [+38 ms]
```

Two facts behind it. The window is floated by a rule — `smaller-than-focused` with `from-focused-app`,
the pair that catches an app's own dialogs — so it never joins the strip, and `windowCreated`'s
off-strip branch returned without writing anything but the float. And `World.focusedAt`, which
`StackOrder` reads to answer "what is in front of what", had no entry for it. A window with no entry
ranks `(0, 0)`: behind every window of its own app that has ever been focused. Hoisting's third rule
asks exactly that question — is a window emira placed in front of this float — and got `yes` about the
IDE window the dialog had just opened over. The still was then filmed at that instant, which is before
IntelliJ had drawn a single pixel into the dialog, and a hoisted float is never re-filmed.

The `focusChanged(nil)` is a second defect and not this one: the app's report about the new window
resolves through `WindowRegistry.id(for:)` at notification time, before the scan the sibling
`AXWindowCreated` triggers has bound the element, so it reaches the core as "focus left every managed
window". It is left standing here. It does not move the stacking record — `World.setFocus(nil)` clears
`focusedWindow` and touches neither `focusedAt` nor `lastFocus` — so the hoist stays down across it,
which the suite pins.

## Implementation

`windowCreated`'s off-strip branch writes `World.noteActivation`. One line, and the argument is which
line it is.

**`noteActivation`, not `setFocus`.** The first shape tried was the symmetric one — an arrival takes
focus whether or not it lands on the strip, which is what the desktop actually does when an app opens
a dialog. Two tests price that decision and both are right to:
`EngineArrivalTests.nonTilingWindowIsRecordedButNotPlacedOrFocused` states it outright, and
`SystemFocusEventTests.theThreeModesFormANestedLadder` builds its fixture on it. The taxonomy floats
every dialog, sheet, popover and tool palette, and most of those open without taking focus at all; a
background app's autocomplete panel moving `World.focusedWindow` would aim every verb at it. Only the
stacking half of the fact is true for the whole set, and `noteActivation` is that half — it already
exists, written for the pin fence, for the same reason.

**Gated on `isOnScreen`.** Off the strip covers three cases, not one: float, minimized, and `Cmd-H`
hidden. A window that arrives into the Dock or under a hidden app is on top of nothing, and
`isOnScreen` is the reader `hoistBindings` already uses to ask it.

**Unconditional on `wasAlreadyOpen`.** The launch scan writes ranks for its strip windows as a side
effect of `setFocus`, in enumeration order; an off-strip window skipped there would rank `(0, 0)`
against them and be hoisted at boot by the same arithmetic. Arbitrary in the same way the strip's
already is, and consistent, which the alternative is not.

Rejected: teaching `StackOrder` to treat a missing entry as *newest* rather than oldest. It reads
better at the one call site and is false everywhere else — an unfocused window is genuinely at the
bottom, which is what `aDesktopNothingHasFocusedShowsNothing` is about, and the fix belongs where the
fact enters `World` rather than where it is read back out.

Validated against the real daemon, not only the suite: the same `Cmd-,` now produces
`state: standby` at arrival — prepared, showing nothing — and the dialog renders and stays live.
Focusing the IDE window behind it still flips it to `covered`, so the mechanism is intact rather than
disabled.

## Observations

The `focusChanged(nil)` above is still emitted, and `World.focusedWindow` still ends up `nil` while a
dialog holds focus for real. Nothing on screen depends on it now, but it is a lie in the truth plane
and the ordering that produces it is a race — the trace shows both orders across two runs, the arrival
before the report and after it. The repair with the least new machinery is the one
`Event.appActivated` already uses: `WorldWatcher.readFocus(of:)` after a scan binds new windows for an
app, so the question is asked again once the answer can resolve. Untouched here.

The reported focus loop between a settings window and the file picker it opens (Project Structure →
Compiler output → browse) is unexamined. `World.lastFocus` is the anchor
`Engine.arrivalAnchor` measures the picker's `smaller-than-focused` against, and the `nil` above
leaves it naming the IDE window rather than the dialog the picker opened out of.
