# A cover that goes up on the desktop alone

> Change `1785306827` — 2026-07-28

## Goal

Take the number of columns a transition sweeps off the critical path. The measured cost model
(`1785301362`) puts a cover's head at `22.7 ms + 10.3 ms × stills`, because the window server serializes
screenshot requests — so a two-column focus is ~43 ms, a four-column one ~63 ms, and a wide sweep 187 ms,
all of it spent before anything has moved or been covered. Resolution never entered into it: a capture
costs per call, not per pixel, so a bigger display buys more columns on screen and pays for each one.

## Implementation

`[animation] cover` picks between **`exact`** (the default, and what emira did before) and
**`immediate`**, which raises on the desktop base alone — one capture, ~23 ms, whatever the strip looks
like — standing in for each window with whatever still an earlier cover left behind and sharpening each
layer as its own capture lands.

**The boundary is the point, not a compromise.** The base stays exact and the per-window stills go
cached, because the base is the one capture whose cost does not grow with the strip and it is the frame
of reference the eye judges the transition against — menu bar, wallpaper, every window that is *not*
moving. What gets approximated is exactly the thing about to be smeared by motion anyway. Pushing
further (a cached wallpaper plus cached float layers, composited ourselves, for a head of zero) would
make the menu bar and floats stale too, for a term that is already O(1).

**The blur is the memory budget, not a cosmetic.** A window at 2× is several megabytes and the cache
holds one per window on the desktop, so keeping stills at capture resolution is hundreds of megabytes.
A quarter on each axis is a sixteenth of that, and the softness an upscale back to the window's own size
produces is the disclosure: a still filmed minutes ago must not be able to pass for the window as it is
now. Implemented as a downsampled `CGImage` rather than a filter, so the refresh is a plain `contents`
swap and nothing runs on the hot path. Reduction happens in a detached task at `clearStore`, which is
where every still passes on its way to being freed — `discard` is not that point, since a cover can also
lose its stills to the next transition claiming the store.

**Size is the whole of freshness.** A cached still is usable iff it was filmed at the size the window is
at now: one that merely moved is showing the pixels it was filmed with, while one the app re-laid-out is
not, and painting those into the new rect distorts them (`stretch`) or leaves the extent unfilled
(`crop`). Only the core can tell those apart, so `Effect.capture` carries the size — `World`'s recorded
frame, written optimistically at placement, rather than `WindowRegistry.frame`, which is deliberately
lossy and only updated on drag reads. A miss costs the capture that would have been paid anyway, so a
cold cache is precisely the old latency and a wrong answer is only ever possible in the safe direction.
Nothing invalidates on a window's death: `WindowId`s are never reused, so a dead entry is unreachable
rather than wrong and the byte budget collects it — one coupling the capture plane does not have to
hold.

**The teleport did not move.** The tempting version of this raises the cover early *and* teleports early,
which would let a window's own still be captured after the window had gone — content-identical for a
scroll, and for `cycle-width` a capture of the app mid-reflow at its new size, painted into a layer still
at the old one. Reals teleport when their stills are in, exactly as before; only the *raise* moved
earlier. The truth plane's sequencing, the landing wait and the hold timeout are untouched, which is why
this change is confined to the presentation and capture planes.

**The atomic batch had to go, and what it was protecting is now said outright.**
`CaptureService`'s rule 2 answered a whole batch at once, reasoning that per-window acks would let the
core count down to a raise the base was not ready for. That reasoning is about the base, not about
batching — and answering as a unit charges every cover the full serialized cost of its scope, which is
the thing being removed. So `SurfaceCapturer` hands pieces back as they land (`CapturePiece`), and the
service **holds every ack until the base is in**. Same guarantee, stated as the rule it always was, and
it applies to `exact` too, where streaming newly makes a still-before-base possible. `SCKCapturer` also
queues the base task first, since it is first in the gate.

**The core barely moved, and never learns about a base.** `Motion` is untouched: `isReadyToRaise` is
still "every scoped window acked", because what `CoverMode` changes is when a window is deemed to *have*
pixels, not what the core does once every scoped one does. That is what kept ~40 existing reducer tests
from needing an edit, and it is the right seam — a base is capture-plane mechanism. The two additions
are `Event.captureRefreshed` → `Effect.refreshLayer(LayerId)`, a `contents` cross-fade at whatever rect
the last tick left the layer at. Routed through the core rather than shell-to-shell for symmetry with
`extendCover`, which is the same event (a late still) for a window that has *no* layer yet; a refresh
naming a window with no layer is silently nothing, because the raise reads the store and finds those
pixels already there. It settles no gate, so it cannot raise, extend or close anything, and
`CompositingExecutor` does not count it as a blit — a transition whose stand-ins all resolved would
otherwise read as smoother than the identical one that never needed them.

`Reconstruction.refreshLayer` deliberately does not re-state the clip's corner radius or the layer's
`natural` size, both measured off the stand-in: the size match guarantees fresh pixels could only move
them by a rounding error, visibly, since the radius is a hard edge and `natural` anchors every subsequent
`place`.

## Observations

**The base is awaited before the window group opens, and that is load-bearing rather than tidy.** Queuing
it as the group's first task is not the same thing: `addTask` order is not execution order, so a base
merely queued first can be taken last by a window server that serializes, which puts the gate back at the
end of the batch. The mode then does nothing at all *and looks like it is working* — every stand-in is
overtaken by its own capture before the gate opens, so the cover is built from exact pixels and the only
symptom is the absence of the artifact it was supposed to trade for. Awaiting costs the overlap the base
had with the first still (~3 ms of an already-serialized batch).

**`stoodIn` counts matches; `standing` counts layers.** That distinction is the instrument for the failure
above, and the first version of this change did not have it — `CaptureReport` reported cache hits at
request time and the elapsed cost of the *whole batch*, neither of which moves when the gate does. It now
carries `gate` (when the batch stopped blocking the raise — the head latency), `base` (when the base
landed, which the gate can never precede) and `standing` (stand-ins not yet overtaken at the gate). A
`standing` of zero against a high `stoodIn` is the signature of a mode buying nothing.

**Capture order within the batch is still arbitrary.** Base first is now a fact; ordering the *windows* so
the ones on screen sharpen before the shoulder is not, and it is the rest of the mitigation for the one
visual risk here — the spring starts at rest, so there is a 1–2 frame window where the cover is up,
blurred, and has not visibly moved. Not free: `session.windows` order *is* the cover's z-order, so it
needs a separate capture order rather than a re-sort.

**A late piece after the deadline is dropped rather than merged.** The 250 ms deadline resolves a batch
and acks whatever is outstanding; stills arriving afterwards are discarded, as they were before, so a
timed-out batch produces holes rather than layers that sharpen late. Adding a second resolution path
there is complexity for a case that already means something is badly wrong.

**The cache is warmed only by use.** Staleness is bounded by how long since a window was last scrolled
past, which is exactly what the blur discloses and nothing measures. An idle re-capture a beat after a
transition settles would make the common case (scrolling back from where you just landed) nearly always
fresh, at the cost of "an idle emira pays nothing" — untested, and the honest next thing to try before
reaching for the persistent `SCStream` that removes staleness and head latency together.
