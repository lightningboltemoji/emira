# Waiting for answers that were never coming

> Change `1788236418` — 2026-08-31

## Goal

Quitting an app left a hole in the strip for as long as the app took to die. Reported on Infuse: the
window hides, the layout does not move, and half a second later the process finally goes and emira
closes the column and focuses its neighbour — one late lurch that reads as lag.

Measured on the reporting machine, from `terminate()`:

| fact | Infuse | TextEdit |
| ------------------------------------------------- | -----: | -------: |
| window off screen, `activationPolicy` `.prohibited` | 22 ms | — |
| AX element dead | 646 ms | — |
| gone from the window list | 654 ms | — |
| `isTerminated` — what `appTerminated` rides | > 2 s | 24 ms |

Every signal emira listened to was downstream of the app's actual exit. `didTerminateApplication` is
the only thing that closed the layout, and `reconcile` could not have helped either — the window does
not leave the list until 654 ms.

Closing a window had the same shape for a different reason. `vanish` holds a destroyed window's *id*
until a scan says whether a native tab took its place — but that scan is a round trip into the app that
just tore the window down, the process least able to answer it. Traced on a bare-launched TextEdit,
whose launch window is the XPC-hosted Open panel: the destroy lands at ~65 ms and issues the scan, the
scan answers at ~330 ms, and `successionGrace` retires the window at ~320 ms. A quarter second of empty
column, then the close and the focus that follows it arriving together — and *erratic*, because a
250 ms grace against a ~264 ms blocked round trip is a coin flip over which one settles the window.

⌘H was worse than late: nothing reported it at all. A hidden app's windows keep their window-list
entries (only `kCGWindowIsOnscreen` goes), AX goes on describing them, and no destroy notification is
ever posted — so reconciliation's "absent from the list entirely" never becomes true and the column
sits on the strip forever.

## Implementation

`WorldObservation.appDeparting` / `.appHidden` / `.appUnhidden`, from KVO on `NSRunningApplication`.
Change `1788227630` established LaunchServices as the register that knows; this watches it instead of
only asking it when a write happens to be going out.

**Why an observation and not a read.** The obvious shape — check these facts when a focus report
arrives, where `resolveFocus` already probes the displaced window — does not work: the report lands
~1 ms into a quit and `.prohibited` is 21 ms behind it. Any read at that moment says the app is
healthy, and any read placed later is a delay chosen to beat a teardown, which is the constant change
`1788227630` rejected wearing a different hat. As edges the facts need no such choice: `.prohibited`
at 25 ms, `isHidden` at 23 ms, and both silent when an app merely loses focus (checked against a
plain activation steal, which fires neither).

**A departure retires; a hide borrows.** They are one predicate for `AXWindowWriter.canHoldFocus`,
which only wants to know whether to write, and three different facts for the world model:

- `.appDeparting` → `retire` per window, and deliberately not `vanish`: what a succession scan settles
  is whether something took the window's place, and an app on its way out has no successor to offer.
  The app itself stays tracked — observer, lane, scan target — so a `.prohibited` that turns out not
  to be a quit costs one reconciliation rather than going silently unmanaged.
- `.appHidden` → the **minimize** pair, not a destroy. These windows are coming back, and
  `windowDestroyed` would return them as fresh columns having forgotten their width and their place.
- `.appUnhidden` → exactly the set the hide took, which is why `WorldWatcher` now tracks `minimized`
  and `hidden`. A window the Dock already held is not restored by an unhide, so claiming it at hide
  time would promise a return that never comes.

**The succession wait becomes a question.** A window nothing could have succeeded has no answer worth
waiting for, and both halves of "could it" are needed. A tab group is several window-server entries
standing on **one** rectangle with exactly one of them on screen, so a candidate is another entry of
the app on this window's own frame — `couldBeSucceeded`, a synchronous read of a list already held,
reusing `WindowIdentity.sameFrame` so there is one definition of the rectangle. That alone is unsafe:
a *newly made* tab is described by AX before the window server lists it (measured on Ghostty at ⌘T:
AX ~4 ms, window server ~116 ms), and in that gap a real successor is invisible to the rectangle. So
`pendingArrivals` latches what a scan could not account for. The report already carries it —
`mayHaveMissedAnArrival` — but only for the instant it lands, and the destroy arrives later; making it
a per-app latch is the whole addition, and it closes the hole that `scanning`/`rescan` leave open,
which is the 150 ms between a scan returning incomplete and its retry going out.

`isTerminated` is left alone. A fast app never publishes `.prohibited` at all — TextEdit goes straight
to terminated at 24 ms — so `appTerminated` is not a fallback here but the whole signal for that half
of the world. The two are complementary; whichever arrives first takes the windows.

The KVO hop is a `Thread.isMainThread` branch rather than a bare `MainActor.assumeIsolated`. Every
sample of both facts lands on the main thread, but KVO promises only the thread that mutated the
property, and the gap between measured and guaranteed is a trap in a release build.

`AppWatch` is a class rather than a struct, and that is a crash rather than a preference.
`NSKeyValueObservation` holds its object weakly and `NSRunningApplication(processIdentifier:)` mints a
fresh one per call, so the app has to be held beside its tokens; but holding it is not enough, because
the invalidation has to happen while it is still alive. Written as `removeValue(forKey:)?.tokens
.forEach { $0.invalidate() }` it does not: ARC ends the temporary's lifetime at the `tokens`
projection, releases the app, and invalidates against a dead object. That path segfaults on the retry
`watch(app:)` takes when an app is too busy to be observed first time — which is the ordinary case for
an app that has just launched. A `deinit` cannot get the order wrong, and makes releasing the watch
the whole of unregistering it by any route, teardown included.

Rejected:

- **Swapping `resolveFocus`'s oracle** from the AX liveness probe to the window server. It looked like
  the unifying fix and it is a regression: on an ordinary ⌘W the ranking inverts — the AX element dies
  at 101 ms while the window server holds the entry until 395 ms — so the probe would have started
  admitting the backfilled focus report that change `1785477519` exists to suppress. AX is the right
  oracle for a window dying inside a living app; LaunchServices is the right one for a window dying
  because its app is. Neither dominates, and the probe keeps the one that suits it.
- **Shortening `reconcileInterval`.** The fact it reads is itself 654 ms late on a slow quit, so no
  interval reaches the window in time, and every app on the desktop pays for the attempt.
- **Watching `isTerminated` by KVO** beside the other two. It is the same edge
  `didTerminateApplicationNotification` already delivers.

## Observations

- Measured end to end, driving the real `WorldWatcher` over the real `AXObservationSource` against
  Infuse, timed from the gesture — ⌘H `windowMinimized` at 8 ms and the unhide's `windowDeminimized`
  at 4 ms, neither of which was reported at all before; ⌘Q `windowDestroyed` at 27 ms against ~650 ms.
- The gap is now bounded by LaunchServices rather than by the app. What remains is an app that gives
  up its windows without touching either fact, which none of the three departures tested does.
- `canHoldFocus` in `AXWindowWriter` is untouched and still load-bearing. The focus report that
  provokes a refusal arrives ahead of every fact here, so the correction still goes out and is still
  the writer's to withhold.
- One review finding from `1788227630` is left open: `AXWindowWriter.focus(_:correcting:)` mints its
  `FocusIntent` ticket before the late `canHoldFocus`, so a correction that bails has already
  superseded an in-flight `focus` command and that command's activation is dropped. `FocusIntent` has
  no way to withdraw a request, and the ticket is legitimately owed to the `makeKey` that did go out,
  so the fix is not a one-liner and is not attempted here.
- Closes measured end to end through the real `WorldWatcher`, destroy notification to
  `windowDestroyed`: the bare-TextEdit Open panel 251–254 ms → **2 ms** (4/4), and an ordinary close
  with a survivor 15–24 ms → 2–6 ms. Succession checked on the other side by driving ⌘T then ⌘W at
  20/40/80/150/400 ms against a real Ghostty tab group: the id is kept at every delay, before and
  after.
- The window server is authoritative about a *settled* tab and says nothing about a newborn one. Both
  readings are true and they are different moments — which is why `couldBeSucceeded` is not allowed to
  answer on its own, and why the fixtures under "the destroy that waits for one answer" now carry a
  `backgroundTab`: without one, a window in those tests is not something a succession could reach.
- `successionGrace` is now reached only by a window something could have succeeded. Its value is
  unchanged and still untuned — nothing here makes it shorter, only rarer.
- Investigated and rejected on the way: `AXEnumerator.join` refuses to read departures out of an
  answer describing no windows (`answer.windows.isEmpty`), which looked like the cause. It is not —
  the vanishing loop settles an empty answer through `mayHaveMissedAnArrival` instead, and traces show
  it retiring at 76 ms when the app answers promptly. Removing the clause changed nothing measurable.
- Also rejected: `couldBeSucceeded` alone, without the latch. It reintroduces exactly the race
  `anIncompleteScanSettlesNothingAndTheRetryIsWhatFindsTheSuccessor` pins, and the ⌘T/⌘W measurement
  above is where that stopped being a matter of taking the test's word for it.
- `.accessory` still passes everywhere `.prohibited` is read — an agent with a window is a legitimate
  place for focus to sit, and only the app's own statement that it cannot be activated counts.
- An app that converts itself to `.prohibited` while continuing to run loses its windows for one
  reconciliation interval and gets them back. No app tested does this.
- Untested by construction: which facts KVO actually reports and when. Those belong to a live desktop,
  like every other system read below `WorldWatcher`. What `LiveWorldTests` pins is the shape of each
  response — retire versus borrow, and that an unhide returns neither more nor less than its hide took.
