# The guide, greenfield

> Change `1786606834` — 13 August 2026

## Goal

The guide was **drawn twice** — once by `GuidePanel` in the shell, once by `DesktopView.place(guide:)`
in the settings window — off two layouts that shared only `GuideModel.projection`. The preview was
therefore not a wrong drawing of the guide; it was a different object that resembled it. It had no
separators, no tile radii and no separation inset, and every cosmetic in the real one was an absolute
point count — `panelRadius 20`, a 1 pt border, a half-point rule — drawn into a ribbon the preview
scaled to a quarter, so the frame was four times too heavy for what it framed. `SettingsStyle.guideRadius
= 10` was a patch over that arithmetic rather than a fix for it.

Three faults, one root, and no restyling could have closed it: adding a second guide would have meant
forking both drawings. So this makes one model, one renderer and two hosts, and then adds the names
guide on top of it.

## Implementation

**`GuideInput` replaces `State` as what a guide is drawn from.** `GuideModel.layout(for:on:)` took a
`State`, and `ImportFenceTests` forbids `EmiraSettings` from naming one — the fence is right, and the
signature is what had to move. The shell builds an input from the truth plane (`GuideSubject.swift`) and
the settings window builds one from a mock desktop (`GuideFrame.swift`); both then run the same layout,
and the preview inherits separation, separators, corner concentricity and the ring for free. `GuideTrigger`
moved to the shell with the adapter: its workspace name and scroll target are State-shaped, so a type in
the core would have been a value split from its only constructor.

**`GuideLayout` is column-structured**, and the separators fall out of it rather than being a second
derivation from the same frames. That is the change that made a second style cheap. A `GuideColumn`
carries its *unseparated* rect because that is what a rule is measured between; the stack boundaries are
taken from the separated tiles instead, which is the midpoint of the band actually left empty and
identical for any tile tall enough for the separation to reach its full 1.5 at both ends.

**`EmiraGuide` is a new target between `EmiraCore` and `EmiraSettings`**, and `scale` is the whole fix.
Every cosmetic multiplies by it — radii, borders, separator width, font size — so the daemon passes `1`
and the settings window passes its mock's own scale, and the preview is the same object seen smaller.
`CosmeticScaleTests` renders one input at `1` and at `k` and requires every frame, radius, stroke, path
box and point size in the tree to differ by exactly `k`; it asks it of every style, since a second
renderer is a second place to write a number down. It is the regression that let the preview drift, and
the one test that could not have been written before there was a single renderer to ask. The palette stays a
parameter because higher contrast over a mock wallpaper is a real requirement, but it is one struct of
colours rather than a second layer tree.

Two deliberate departures from "pixel-identical at `scale = 1`". A tile's picture layer now sets
`minificationFilter = .trilinear`, which the settings preview always had and the real guide did not — a
full-window still downscaled into a 30 pt tile wants it in both hosts, and keeping two filter settings is
exactly the drift this removes. And the preview's viewport indicator moves: `GuidePreview` offset it by
the scroll, which put the indicator a screen to the right of where you actually were.

**The config is per-guide tables.** `GuideStyle`'s `off`/`placeholder`/`preview` ladder collapses into
`enabled` + `content`, and `[guide]` itself holds nothing — two guides cannot share a position without
overlapping, and once position is per-table, splitting the rest across two levels is arbitrary.
Compatibility is not kept; the file breaks and says so. `Setting.table` already derived the header from
the dotted key, so this cost no grammar and no writer work.

**The settings panel splits a section into sub-tabs where its main surface spans sub-tables.** A heading
was the first answer and it is the wrong one: fifteen guide settings in one scrolling list put `Position`,
`Width`, `Gap` and `Duration` on screen twice, and a heading four rows above the one you are reading is
not there when you need it. A tab is a place you go and a heading is a label on a run of rows, so the two
guides get a tab each and the rows on screen are one guide's, whole. The advanced tables keep headings —
they arrive already inside a disclosure, and a third level of tabs under one would be a place you go to
inside a place you went, which settles the plan's open question in the same breath. Both are derived from
the key by `ControlSlab.tables(of:)`, so neither is a second list to drift.

The sub-tab row costs the scroller **exactly one row pitch**, which is not a spacing choice. The panel's
"half a row is the affordance" rests on where the fold cuts a row, and a first attempt at 34 pt slid the cut
into the gap between two rows: the Guide tab then ended on a whole row with nothing under it and read as a
section with four settings rather than seven. A whole pitch is the one height that leaves the fraction where
it was, and `ScrollFadeTests` now measures a sub-tabbed section as well as the default one.

**The names guide measures its words, through a seam the host supplies.** `GuideFace` is two closures —
a word's width at a size, and the line box that size sets on — and `GuideTypeface` in `EmiraGuide` is the
one implementation both hosts pass. Two other shapes were available and both fail. Putting the packing in
the renderer, where AppKit already is, is circular: the settings window needs the panel *before* it draws,
to frame a camera and to seed a movement spring, so the answer would arrive back through `PreviewState`,
`Camera` and `PreviewMotion` a frame late. Counting characters against a monospaced advance is only the
same arithmetic for a face whose every glyph is one advance wide, and `GuideNames` resolves the
**localized** name: the system monospaced face sets `カレンダー` at 56.97 pt where a character count
packs 51.60, so a Japanese Calendar would be cut to `カレンダ…` in a cell the model thought roomy.
Taking the measurement as an argument inverts the dependency instead of choosing between those — it
happens inside `model()`, at the moment the host calls it, and the host is AppKit in both cases. The
precedent was already in the signature beside it, `name: (String) -> String`. What it buys past
correctness: no monospace constraint, so a `font-family` setting is a setting rather than a rewrite, and
`NamesModelTests` measures through a stub of its own, so the packing's tests cannot fail because Apple
reflowed a face.

**The cells tile**, so the gutter between two words is shared rather than each cell holding its own
padding with a gap on top. Three quantities on one distance is what put the focus fill's edge nowhere in
particular: it stopped short of a strip of ribbon belonging to neither neighbour, and focus crossing the
row read as jumping over gaps rather than moving from one word to the next. With the gap gone a cell is
its word plus half a gutter, the fill's edge is exactly the midpoint of the two words it comes between,
and the interior spacing (1.2 × the type size) matches the end inset (1.1). `NamesTypeTests` is where the
packing meets the face it will be set in: that a measurement is never *short* of what will be drawn — in
Kana, Hangul, an emoji and a combining mark as well as in Latin — and that a name in any script gets a
cell it fits in. Widths are rounded up to a half point, which is the whole of the slack.

**A row has a width, and past it the cells share what there is.** Without one `NamesModel` summed its
cells and handed `GuideModel.place` a size it cannot argue with, so a row wider than the display was
clamped to `area.maxX - size.width` and hung off the *left* edge, losing the columns nearest you: on a
1512 pt working area, sixteen columns named `activity monitor` placed a 2147 pt panel at `x = -635`, and
twenty-four short names already filled the screen. The minimap is bounded by construction —
`min(width, 1) / span` — which is what made the asymmetry the tell. So `names.width` is a fraction of the
working width defaulting to 1, clamped to the gap it is held off the edge by, and the two tables now rhyme
on the word. Past the ceiling `share` divides the row **max-min fair**: each cell takes what it asked for
while there is enough to go round, and what is left splits evenly between those that asked for more. It is
one sort and one pass rather than rounds converging — walking narrowest first, the first cell over its
share of the remainder settles every cell after it, since they all asked for at least as much. Taking the
overflow off one end is what the bug did.

**The rhyme is then a key written once.** Both guides mean the same thing by `width` — the most of the
working width this one may take — and differ only in how each concedes past it, which is `span`'s
sentence and the row's own truncation rather than the width's. So it joins `position`, `gap` and
`duration` on the one generator over `GuideTable`, and what stays written per guide is `enabled`, whose
sentence is which guide it turns on. The `sizeList` reading — "≤ 1 is a fraction, anything larger is a
point count" — was declined rather than missed: it would let a row of names be capped at 600 pt on every
display rather than at a share of each, for a `Kind` case and a control serving the one key
`guide.*.width`, and it would cost `PreviewGuideSettings.scale` its standing as a property of the
settings alone, since `min(width, 1) / span` needs the working width in hand to resolve a point count.

**A cell is two runs, and only the name truncates.** The count is measured separately and placed after
it, because one run makes `ghostty²` truncate to `ghost…` — losing the mark that says the column is
stacked, which is the cheaper information to keep and the one a reader cannot reconstruct. The model
hands the renderer two rects and `NamesGuideRenderer` measures nothing; cutting the string is left to
`CATextLayer`, which keeps graphemes, combining marks and emoji right without any of that reaching the
core.

**The floor is a crowding rule, and elision is what it falls back to.** Under about six characters a name
is not recognisable and the row has stopped naming anything — the elision counts and the focus chip's
position already say "there are many, you are in the middle" — so a cell may not be squeezed below
`4 × font-size` of text, and where the share would go under it `max-columns`' own elision drops the
columns furthest from focus instead. Rendering both settled the number: at two ems a sixty-column strip
draws nineteen cells of `sa…`, and at four it draws nine whole names between two marks. It applies **only
to a row that overflows** — nineteen short names that fit are not cut for a floor none of them is pressed
against, which is a different rule from `max-columns` and pinned separately.

`GuideModel.place(size:within:position:gap:)` is the nine-anchor arithmetic factored out of `projection`.
The preview guide derives its size from `scale` and the names guide from its own type; both put themselves
in a corner with the same function, and it stays purely testable. **A model bounds its own panel before it
places one**, because `place` is handed a size and can only anchor what it is given —
`GuideDrawingTests.neitherGuideOutgrowsTheWorkingArea` asks it of every style at one column and at two
hundred, which is the shape of claim that catches a guide walking off the display.

**Both hosts drive N styles, and `GuideStyle` is what they count in.** It is in `EmiraCore` beside the
models rather than in either host, because everything that comes in one-per-guide keys off it: a renderer,
a spring, a camera, a table of settings. `allCases` is the drawing order — the minimap under the row of
names — and `GuideStyle.renderers(contentsScale:)` is the only list of which class draws which, so the two
hosts cannot come to differ about either. The shell's `GuidePanel` shrank to a window plus a host layer
and adopts a renderer root per style, each fading on its own; `PreviewState` carries `[GuideFrame]`,
`PreviewMotion` keeps a spring per style, and `Camera.guidePanel`/`guideCorner` take the style they
frame — a lens that framed "the guide" would push in on the minimap while the user was editing the row
of names. `Camera.guidePanel` is also where the life-size ceiling gets its exception back: the minimap
may magnify because nothing read at it is a length, and the names guide may not, because everything read
on it is type.

**A `GuideDrawing` is the model already run, and it is what a host hands its renderer.** The settings
window needs a panel *before* it draws — to frame a camera and to seed a movement spring — so a renderer
that ran the model itself and answered where its panel went made that host derive the same expression
twice, off a `switch` over the styles that a third guide would have had to be taught. `GuideDrawing.of`
is that switch, once, next to the models; `GuideFrame` is what a host owns and nothing else. Which is
also what makes `nil` mean one thing: **a guide with nothing to draw shows nothing**, in both hosts. The
settings window leaves that style out of its frame and the shell hides its root, where before it skipped
the style and left the layer up — so a display switched to an empty workspace kept naming the columns of
the workspace it had left, for as long as the dwell ran.

**A dwell is one guide's.** Two guides answering *where am I* in two corners are two settings, so each
style is armed for its own table's `duration` and leaves on its own. `GuideSettings.table(of:)` is where
a style becomes a field and `enabledStyles` is what a host builds a frame from, so neither host switches
on the style again to ask how long a guide stays. One dwell over the longest any *enabled* guide asks
for was the first answer, and it is the *window's* answer rather than the guide's: it holds a row of
names up for the minimap's sake, and the only thing forcing it was fading the pair on one window's
alpha. Fading each renderer root instead makes two clocks representable, and the window is then simply
up while any of them is. The daemon re-arms on every drain that finds the desktop still moving, so a
dwell starts when everything stops rather than when the key went down — which is also what keeps a guide
up for the whole of a trackpad scroll. `Guide` also took a `GuideSurface` seam, for `CoverSurface`'s
reason: everything above is a decision, and `GuidePanel` is the only part that needs a window server.
`GuideShowTests` drives the controller over a recording double.

**A close framing and a life cycle turned out to be exclusive.** Every guide setting first played
`guideLife` — the loop that raises a guide, holds it for `duration` and lowers it — and the close-framed
ones played it under a lens pushed in on the panel. `Camera.guidePanel` resolves against the guide that is
*drawn*, so for the two thirds of each loop with no guide on the desktop the subject was `nil` and the shot
fell back to the whole display: every close-framed setting pumped between 0.52× and its own framing
every 4.2 seconds. The fix is not machinery but the rule the top of `Catalog.swift` already states and this
section had been ignoring — a setting that *is* geometry needs no script, because `PreviewModel` re-derives
from the draft on every change. So `enabled` and `duration`, whose subject is the life cycle, keep the loop
and play it **wide**; the other eleven are still takes, which keeps the guide up for as long as the pointer
is on the row and holds the lens still. `GuideLifeTests` pins both halves — nothing framed close raises and
lowers a guide, and exactly four settings loop — so a future take cannot reintroduce it.

**`guidePanel` frames the panel and nothing around it.** It had a 35% margin, and a margin is not slack: for
a corner-positioned guide the frame is clamped to the display's own corner anyway, so what the margin
actually did was widen the shot — which is `maximumScale`'s job, and the two fought. The names guide lost:
its `maximumScale` of 1 is a *floor* on frame width, and a panel plus 35% exceeded life size, so `font-size`
was framed at 0.93× and the claim that twelve points draws twelve points was false by 7%. Deleting the
margin leaves one rule deciding how close a shot goes, and the names framings now land at exactly 1.000.

**A guide's exit is one pair of numbers, in `EmiraGuide`.** With `duration` reframed the preview spends
most of that take showing a guide arrive and leave, and it was cutting the guide away where the daemon
fades it over 350 ms — the setting beside it being *how long it stays*. `GuideFade` states the asymmetry
once (instant up, because a guide answers *where am I* about the thing that just moved, so any rise is
late; gentle down, because nothing is hidden behind it) and both hosts run it on the renderer root's own
opacity — the shell's window is a binary gate behind that, following the last guide off. The preview's
guides moved off `isHidden` onto the same remembered-opacity fade the cue badge uses, one memory per
style, since two guides can be on their way out at once.

`SettingsStyle.guide*` is now one `GuidePalette`, `GuidePreview.swift` and the guide branch of
`DesktopView` are gone, and `ImportFenceTests` scans `Sources/EmiraGuide` as well: a renderer that could
read a `State` would be one only half the hosts could use.

## Observations

**The names guide's focus fill does not travel.** The preview guide's ring animates because the core hands
it `focusRingDisplacement` in screen space; a names cell's position is text-derived and the core cannot
know it, so the fill jumps. A spring over cell geometry is the obvious follow-up and would want the
displacement expressed in cell space rather than screen space.

**Two guides in one corner overlap.** Nothing stops a user putting both at `top-right`; the renderers are
drawn minimap-first and names over it, and that is the whole of the policy. A layout that stacked them
would need one of them to know about the other, which is the coupling per-guide tables exist to avoid.

**The daemon path has not been watched by eye.** The settings harness verified both guides drawn together
in two corners, the Guide tab's sub-tabs, the minimap framed close at 1.6× and the names row framed at
life size — separators, tile radii, the separation inset, the ring and the superscript are all present.
The row was read again through `CALayer.render(in:)` at four widths and in four scripts, which is what
settled the floor. `GuideShowTests` drives the controller's decisions over a recording surface, so what is
left resting on nothing is the part that needs a window server: `GuidePanel` hosting two renderer roots
over a real desktop, fading them on their own clocks and putting the window down behind the last of them.

**The preview's dwell and the daemon's are two rules rather than one.** The daemon re-arms while
`Motion.needsFrames`, so a guide leaves `duration` after the desktop *stops*; `PreviewModel.raised`
measures from the beat that started the motion, because a take is a pure function of `t` and the mock's
springs settle downstream of it in `PreviewMotion`. So the preview draws a guide for `duration` where the
desktop draws it for the transition **plus** `duration` — on the one setting whose whole subject is time.
Closing it wants either a settle allowance stated as a number beside `coverHead`, or a raise the model can
ask about once the springs have run.

**The fade was verified through the presentation layer, not by eye.** A screen recording of the mock could
not settle it: the band the guide sits in also carries the windows the same beat is moving, so its
brightness trace is dominated by the strip and reads a 350 ms fade as a cut. Probing
`CALayer.presentation()` frame by frame showed the ramp, and `GuideFadeTests` pins the animation's
duration and that the frames after it do not restart it — but nobody has looked at a guide fading on a
mock desktop and said "yes, that is 350 ms".

**A crowded preview may lose a glyph the real guide keeps.** The model measures at the type size and the
renderer sets at `size × scale`, so a settings window at `k ≈ 0.3` sets type whose advances need not be
exactly `k` times the measured ones. Half a point of round-up absorbs the ordinary case, and what is left
is a preview truncating one character early at three-point type. Measuring per scale would fix it and
would make a model's output depend on the host's zoom, which is worse.

**The elision marks are not held to the floor.** A mark is one glyph and asks for less than a word, so
what is guaranteed is that every *named* column clears it. Nothing states what a row of nothing but marks
would look like, because `fitting` cannot produce one.

**`GuideSources.name` is a channel nothing reads.** Names reach the model through `GuideDrawing.of`, and
`GuideFace` now sits beside it; `NamesGuideRenderer` takes `sources` and uses none of it, while
`DesktopView` supplies the same function by both routes. The two want collapsing into one words argument,
which is a change to both hosts.

**The names panel sets a border colour it never draws.** `restyle` assigns `palette.panelEdge` and pins
`borderWidth` to zero, so the minimap wears a hairline and the row of names does not. Whether the two
guides should agree about that is a design question rather than a leftover.

**`GuideInput.passing` has no test in the shell.** The adapter fills it from windows the shown strip does
not place, which is a workspace switch in flight; `GuideModelTests` covers the model's half with a
hand-built input, but nothing drives a real switch and reads the result.
