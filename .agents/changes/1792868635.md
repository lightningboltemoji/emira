# A main window moving is a focus report where no other came

> Change `1792868635` — 2026-10-24

## Goal

Clicking between two Ghostty windows side by side on one display moved the keyboard but left the veil behind.
The core's `focusedWindow` stayed on the window clicked away from, so it kept that window unveiled and veiled
the one being typed in. `focus left`/`right` between the same windows worked, because the core writes its own
focus as it asks for it. To find out why, a probe ran in a separate process: its own `AXObserver` on Ghostty,
`NSWorkspace` activations, the app's `AXFocusedWindow`, and `emira debug` polled every 50 ms. It showed that a
click posts `AXMainWindowChanged` and no `AXFocusedWindowChanged`, while `AXFocusedWindow` does move. An AX
`AXMain` write does the same. This was Ghostty tip `b699ea79f` (build 18090) on macOS 27.2, relaunched on the
morning this was found. On the same system a control AppKit app posts both, focus first, whether
`makeKeyAndOrderFront` or an AX write moves key. emira took in-app focus changes from `AXFocusedWindowChanged`
alone. It dismissed `AXMainWindowChanged` naming a managed window as a plain raise, and kept that notification
only for the native-tab rescan (`ad5a1fd`).

## Implementation

`AXMainWindowChanged` naming a managed element is now `WorldObservation.windowBecameMain(id)`. An unmanaged
element is still the native-tab rescan. The watcher treats it as a focus report only where it is news. It must
come from the active app, through the same `isActive` gate as `focusMoved`, and name a window other than
`focus`, the last report's. The second clause is what makes an app that posts both cost nothing, since AppKit
posts the focus change first and `focus` already names the window by the time main does. After that it is
`readFocus`, the question a sheet already asks. Everything downstream is the existing path. `FocusIntent`
still tells our own echo apart, so `focus right` on Ghostty now comes back `.ours` through the read. The
backfill question still drops a close's replacement window, because ⌘W makes the next window main before the
destroy lands.

Rejected: believing the main window as the focused one, `focusMoved(id)` straight from the notification. That
saves a lane round trip, and it is wrong while a panel holds key over its document window. Also rejected:
reading on every main-window change. That costs a round trip per focus change in every app, for an answer the
focus report has already given.

Validated live with the same probe. The installed daemon, built from the same parent commit, held
`focusedWindow` on the window clicked away from through two real clicks and an AX drive. The worktree build
followed an AX drive in both directions within one sample (the sampler's ~80 ms resolution), veil included,
and the user confirmed that clicks are now followed.

## Observations

- Whether this is a Ghostty regression, and since when, is unknown. Plain AppKit posts
  `AXFocusedWindowChanged` by itself on a key-window change, so something in Ghostty's accessibility
  implementation is likely suppressing it. Not investigated, and possibly worth an upstream report.
- An app that posted main *before* focus would pay one read and report the same focus twice. A repeat report
  is already something the core absorbs (`resolveFocus` passes one that changes nothing). No app has been seen
  doing it.
- Native tab switching in a Ghostty tab group whose newly shown tab is a managed element now goes through the
  read too. That is covered by the unit tests' logic, but not exercised live.
