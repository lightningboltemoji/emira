# our own focus, arriving late

> Change `1785299886` — 2026-07-28

## Goal

Spamming `focus left`/`focus right` across a strip holding Chrome, two IntelliJ windows and Ghostty
produced an occasional mid-animation **bounce**: the scroll briefly reversed, pulled back toward a
column one or two presses behind, then carried on. Most often with IntelliJ, never reliably.

The commands were never out of order — `Runtime` is a strict FIFO and `Engine.reduce` is synchronous.
What was out of order was emira hearing about its *own* focus changes. `Effect.focus` provokes the
same `AXFocusedWindowChanged` a Cmd-Tab does, and it returns by a different route than it left: the
app's notification, plus an `NSWorkspace` activation that `AXObservationSource` answers with a second
read on that app's lane, plus `resolveFocus`'s liveness probe on the *displaced* window's lane. Three
async hops across up to three per-app serial queues — the same queues carrying the transition's
placement writes — and `AXClient` says outright that there is no order between them. A JVM lane
delivers its news after a terminal's, naming a window the user has already moved off, and the core
reads it as the user asking to go there.

Two separate damages, and the second is worse than the bounce. The late **report** retargets the live
transition, because `reveal` mid-session redirects rather than snaps. The late **activation** brings
the wrong app forward *for real*: `AXWindowWriter.focus` defers `activate()` until `makeKey` returns
on the lane, so two focus commands to two apps are two lanes with nothing between them.

The design had already recorded the assumption that failed. `MockExecutor` acks `.focus` with
`focusChanged` and says the core absorbs its own echo because a reveal of an already-revealed window
is a no-op — true, but only while the echo is *current*, which a synchronous mock cannot fail to be.

## Implementation

`FocusIntent` is the shell's record of the focus changes it caused: the windows it asked for inside a
grace, and which of them it asked for last. One instance per daemon, shared like `WindowRegistry` —
written by `AXWindowWriter` where the asking happens, read by `AXWindowWriter` before it activates and
by `WorldWatcher` before it believes a report.

**The two questions are answered by two fields, and collapsing them breaks it.** `isCurrent(ticket)`
keys on a monotone counter that is never rewound; `resolve(id)` keys on a list the grace clears. A
ticket must stay current after its report arrives, because the write's completion and its echo take
two different hops onto the main actor and either may land first — retire the ticket on the report and
an echo that beats the completion cancels the activation, leaving the app the user asked for behind
the one they didn't.

**The suppression is per window, not a deafness for the length of a burst.** A verdict of `stale`
requires the report to name a window *we asked for and then changed our mind about*; anything else is
`external` and reaches the core untouched, so a Cmd-Tab landing between two focus presses still
reveals. `nil` is external by construction — it names no window, so it can be nobody's echo, and
swallowing it would leave the core focused on something the user has stopped typing into.

**The record is append-only within its grace, and the grace is what expires it.** Consuming an entry
when its echo lands is wrong twice over: one request can produce *two* reports (the app's notification
and the activation read), and a newer request's confirmation arriving first would otherwise retire an
older entry whose echo is still in flight — the exact reordering this exists to catch. So nothing is
removed one at a time; a deadline armed per request clears the whole record 500 ms after the last one,
with a generation check so a superseded timer cannot wipe a record still in use (`DelayScheduler` has
no cancellation, by design). The bound is not optional: a record that never expired would make emira
permanently deaf to real focus changes on every window it had ever focused.

**A stale report is swallowed rather than passed on, because it carries nothing.** `handleFocus`
writes `World.setFocus(target)` optimistically when it emits the effect, so the echo can only confirm
that or corrupt it. This also makes `Event.focusChanged`'s existing doc comment — "focus moved and we
did not move it" — true, where before it named two different things.

**`focus` is not advanced by a swallowed report.** It names the window a *new* report displaces, and a
window we stopped considering focused two presses ago is not that; advancing it would make the next
real report ask its liveness question about the wrong window.

**An `expected` verdict skips the liveness probe**, and that is correctness before it is a saved round
trip: a report naming exactly the window we asked for cannot also be macOS covering for one that died,
because we named the replacement ourselves. The old path would have dropped it when the *displaced*
window happened to be closing.

**`makeKey` is left to run on a superseded request; only `activate()` is dropped.** It cannot bring an
app forward on its own, its own lane already orders it against that app's other writes, and the echo it
may post is what the record exists to recognise on the way back. Gating it would need the check to run
off the main actor, where the answer does not live.

## Observations

- `AXObservationSource.activated` still spends a lane round trip reading the focused window for every
  activation, including the ones we caused. Skipping it when the activation is ours looks free and is
  not: an app that comes forward without its focused window changing posts no AX notification at all,
  so that read is the only signal, and dropping it would go blind exactly where `PRINCIPLES.md` §5 says
  not to.
- One report can still be wrongly swallowed: a Cmd-Tab back to a window emira focused and superseded
  within the last 500 ms. It is the genuinely ambiguous case — the two are byte-identical — and the
  cost is one lost reveal, recovered by the next focus change.
- The reducer half is untouched and deliberately so. A genuine external focus change mid-scroll *should*
  retarget the transition (`PRINCIPLES.md` §4a); the defect was never that it did, but that it was being
  handed the past and told it was the present.
- Reproduced headlessly at the reducer before the fix — two `focus left` presses with the cover up, then
  the first press's echo — and the viewport verifiably reversed and settled a full viewport from where
  the user aimed. The regression tests landed at the `WorldWatcher` boundary instead, where the fix is;
  the reducer behaviour they would have pinned is behaviour we intend to keep.
- The activation half is established from the code and is not covered by a test: it needs a real
  `NSRunningApplication` and two genuinely contended AX lanes. Whether it is what was being seen in
  practice wants a look at the running daemon.
