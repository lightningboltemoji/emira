# An empty AXWindows is a question, not an answer

> Change `1786003637` — 2026-08-06

## Goal

Finder stops being managed. A new Finder window is not adopted, and Finder is absent from
`emira debug`'s `world.apps` altogether — not listed unbound, not rejected by a rule, simply not
there.

The classifier was the suspect, and it is innocent: Finder's windows never reach it. Finder's
application element answers `kAXWindowsAttribute` with an **empty array** — `.success`, count 0 —
while the same window elements are still listed under `AXChildren`, with `role=AXWindow`,
`subrole=AXStandardWindow`, correct titles and frames, and `AXFocusedWindow`/`AXMainWindow` both
resolving to a real one. Safari and Ghostty answered `AXWindows` correctly in the same pass, so it is
not systemic. `killall Finder` clears it.

`AXApplication.windows()` read only `AXWindows`, and an empty list there is exactly what an app with
nothing open looks like — so the app contributes no windows, which is why Finder leaves `World`
rather than showing up as a failure.

## Implementation

`windows()` re-asks an **empty** answer as `AXChildren`. The two lists were checked for identity
rather than assumed equal: across Finder, Safari and Ghostty the window-role children are the *same
elements* as the `AXWindows` entries by `CFHash`, and the only extra child is the menu bar.

A **failed** read is deliberately not re-asked. `copyAttribute` collapses every `AXError` to `nil`,
and the common one is the 250 ms messaging timeout — a second round trip there would double what a
hung app costs its serial lane, which is the one thing `AXClient`'s whole design exists to bound.
Distinguishing the two is free: `nil` is the failure, `[]` is the app answering with nothing.

Nothing filters the children before the classifier, on purpose. `WindowRole.init?` already declines
an unrecognized role — it is what drops Finder's desktop `AXScrollArea` out of `AXWindows` — and a
menu bar is the same kind of fact. One authority over what counts as a window, not two. The cost is
that a menu bar pays `snapshot`'s first three round trips before being dropped, and only for an app
that answered empty.

This bends §7's "never walk children", and the wording there now says what the rule always meant:
never descend *below* a window, because that is what spins up a Chromium/JVM accessibility engine.
Naming the application element's own children is one round trip that descends into nothing.

## Observations

Verified against the live desktop by linking a harness to the built `EmiraShell` and calling the
shipped `AXApplication.windows()` → `AXWindow.snapshot(bundleId:)` path. Both branches were exercised
for real: with `AXWindows` populated, output is unchanged; with the read forced empty in a scratch
build, all three apps recover every real window with correct role, title and frame and decline
exactly one element each — the menu bar. Under the daemon, Finder's windows are adopted, Finder
leaves `World` cleanly when its last window closes without a menu bar standing in, and a reopened
window is adopted again. Suite green at 1474 tests.

**What causes Finder to drop its `AXWindows` is still unknown**, and this change treats the symptom.
Hide/unhide, minimize/unminimize, and close-all-then-reopen cycles were all tried against a freshly
restarted Finder without reproducing it; the Finder that was wedged had been running for a long time.
Worth another attempt at a trigger if it recurs, since a cause might be something emira does.

A caution for whoever tries: this was investigated across a screen lock, and a **locked session
collapses every app's AX tree** — every window in every app answers with the application element's
attributes (`role=AXApplication`, the app's title, frame `(0, screenHeight) 0×0`), through every
client including System Events. It looks exactly like a spreading AX wedge and is nothing but the
lock. Check `CGSessionCopyCurrentDictionary()["CGSSessionScreenIsLocked"]` before believing a
degenerate AX read.
