# A stand-in nobody placed

> Change `1787276849` — 2026-08-20

## Goal

`emitLayerFrames` ended in a `compactMap`, so a binding whose window it had no frame for produced no effect
at all. That is not "no layer": `Reconstruction.makeLayer` builds each layer at `surface.frame`, so a skipped
binding leaves a stand-in standing at the frame its capture was filmed at, for the life of that cover — and
under `CoverMode.immediate` a kept still's frame is explicitly an old origin, which `SurfaceCache` documents
as "not a position: a cover places every layer from the core's own geometry in the transaction it raises in."
`Effect.extendCover` asserts the same invariant from the other side ("immediately followed by a
`setLayerFrame` for every binding"). Neither was enforced anywhere.

The symptom is a window's image, refreshing its contents as the real window changes (`refreshLayer` swaps
pixels and repositions nothing), parked somewhere it does not belong while everything else animates normally
and the real window is exactly where it should be.

It is reachable. A scope is decided when a session opens; workspace ownership is not.
`handleMoveWorkspaceToMonitor` hands an address to another display, and its windows' geometry goes with it —
so a cover already up on the source display is left bound to stand-ins that display can no longer place. A
probe over the reducer showed three bindings and zero effects on the source screen.

Not reachable through `screensChanged`, which was the first suspicion: `State.setMonitors` closes every
surviving display's cover on any report that changes displays, so the re-home always lands with no session
alive. The route needs two displays attached and a command, not a reconfiguration.

## Implementation

**`Effect.hideLayer(LayerId)`, and the emission is a `map`.** Every binding gets exactly one effect per pass.
The alternative shapes were both worse: un-binding abandons a layer and a teleport mid-flight (`Motion` says
so), and `setLayerFrame(layer, .zero)` still runs `place`, which rewrites the clip and the shadow path for a
zero-size layer. `Reconstruction` hides the root and `place` clears the flag, so the two calls are inverses
and the core never has to remember which state a layer is in.

**A cover scopes only what its display can draw.** `scopeUnion` gained `drawnBy:` — the acting display's own
workspaces, which are exactly what `emitLayerFrames` derives frames from — and `carrying:`, the one window an
edit hands across the desktop, which the display it left draws on purpose. This closes the case where the
ownership change lands *before* the session opens; the totality above closes the one where it lands after.
Both are needed, and the tests fail independently for each.

**The edit emits its own frame.** Ticks skip a settled display, and a workspace hand-over changes what a
raised cover draws while leaving the source screen's viewport and animators exactly where they were — so
without this the hide would wait for a tick that never comes. It sits last in `finishStructuralEdit`'s
per-display pass, after `elevate` and `carry`, or a carried window would be hidden and re-placed a frame
later.

**Two independent findings, both one-liners.** `SurfaceCache.removeAll()` documented invalidation for "the
display changed under us" and had no call sites, which matters under `immediate`: size is the whole of
freshness, and a display change moves every working area at once, so a window returning at the size it left
at stands in with pixels from a desktop that no longer exists. `CaptureService.forgetKeptStills` is called
from the daemon's display-change hook. Separately, `handleMoveWorkspaceToMonitor` took its snapshot *before*
writing the travelling address's live scroll, so the destination's before-geometry placed the arriving strip
at a stale remembered offset and the arrival slid in diagonally; the write is hoisted above the snapshot.

**What was considered and rejected: re-keying displacements per (window, display).** The nicer departure —
the outgoing workspace sliding off the source while the incoming slides onto the destination — needs it,
because `Motion.windowAnimators` is keyed by window alone and the hand-over's one animator per window is
already committed to the arrival (measured: the source's pass seeds nothing, the target's seeds the whole
delta). Giving the source its own vertical departure means two journeys for one window. That contradicts a
documented decision ("deliberately **not** per monitor") and the property that decision buys — a window
crossing displays drawn as one continuous journey, which has a test. So the source cuts, which is what it
already did whenever no cover happened to be up, and the two paths now agree.

## Observations

The trigger that produced the original screenshot is still unidentified. The mechanism above accounts for a
stand-in frozen at a stale rect and for its contents staying live, but the reported trigger was connecting
and disconnecting a display, and that path takes every cover down. Either there was a moment with both
displays attached — a lid-open plug-in, where the command routes are live — or there is a second route. The
totality makes the symptom impossible regardless of route, which is why it was worth doing before the trigger
was pinned.

The same screenshot also showed a correctly-placed rounded rectangle filled with `.crop`'s scrim and no still
inside it. `place` anchors the still at the rect's own origin inside a `masksToBounds` clip, so a placed
layer always shows its still in that corner: all-scrim-no-still means either a blank capture or a second
layer for one window, and neither follows from anything here. Unexplained.

Not exercised against a live desktop. The reducer's output is pinned by tests on both routes and on both
displays, and the shell plumbing by the compositor suite, but nobody has watched a workspace hand-over on
two real screens with this build.
