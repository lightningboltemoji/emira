# The window server checks the order hoists are decided by

> Change `1793164256` — 2026-10-27

## Goal

Whether a float is buried is answered by `StackOrder` over `World.focusedAt`, the stacking reconstructed
from focus reports, and the window server was asked only on the way down. The reconstruction's mistakes
stood until something else changed, and both directions were seen:

- **A picture over a window in front.** A JVM lifts an owned, non-modal dialog to the floating level (`L3`)
  over its frame while the app is active, so focusing the frame left the core calling the dialog covered and
  a frozen picture of it over the live dialog — indefinitely, since no further report was coming. Zoom's
  dialogs sit at `L3` too.
- **A buried float with no picture** — the report "it correctly cuts the veil, but we never hoist". The veil
  is cut from the window server's own z-order, so it was right. The hoist was not, because IntelliJ posts
  **no focus report** when a click raises its frame over a dialog that keeps the keyboard, and Zoom posts
  none for a click between two of its windows; an activation whose focus read times out twice is, by
  design, nothing at all.

## Implementation

**Read in the shell, decided in the core.** `StackProbe.windowsOver` takes one `optionOnScreenOnly` window
list off the main thread (`optionAll` is ordered by window number, not z-order — checked) and answers, for
every float, the managed windows drawn over it. `HoistPanels` audits a moment after each burial, after each
click and activation (`WorldWatcher.onRestacked`, `restackSettle` after the press), when a cover comes down,
and every `auditInterval` (1.5 s) while any float is on screen. It reports only a disagreement — `.covered`
with nothing over it, `.standby` under something — as `Event.stackRead(id, over:)`, once per distinct reading.

**The core corrects its record with the primitive it already has.** `foldStackRead` writes
`World.noteActivation` on the side that is wrong: the float, when nothing emira placed is drawn over it; or
the placed window drawn over it that the record ranks beneath it. Rule 3 holds against the reading — a window
emira never placed is no burial. Rejected: letting the shell reveal and conceal on its own reading, which is
the second opinion about what is on the screen that the hoist plane's own release fence already declines to
be; and a new record of "held above", which would be a second authority on stacking beside `focusedAt`.

**Three guards, each against a reading that is behind the record**, which is the one way this can make
things worse: never while a transition paints (the read waits on our own commits); never while a focus of
ours is still in flight (`FocusIntent.isQuiet` — the server shows the old order until the app answers); and a
reading is dropped if a new set arrived while it was out.

## Observations

Owner click with the non-modal probe dialog: covered at +12 ms, `stackRead(…, over: [])` at +335 ms, standby,
concealed. Real IntelliJ: frame clicked over its prompt, no report, hoist up on the audit (+0.94 s on the
periodic round; ~0.1 s once clicks trigger it). Under load: 120 random `focus left/right` with all cores pegged,
then the core's hoist state against the window server — consistent in every round; idle cost with a float on
screen ~0.1 % CPU.

A JVM's owned dialog still flashes a picture for ~0.3 s whenever its frame takes focus, since the reading has
to wait for the activation to land before it can say the dialog stayed in front. `noteActivation` on a float
ranks its whole app newest, which is coarse for a float at the floating level of an app that is not active.
