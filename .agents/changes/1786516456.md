# Take the capture batch one still at a time

> Change `1786516456` — 2026-08-11

## Goal

The capture head is the whole of what a keypress feels like before anything moves, and `SCKCapturer`
was spending more of it than it had to. The batch fanned its window captures out through a task group
on the reasoning that the window server serializes screenshot requests anyway, so a group costs nothing
and buys partial overlap. The first half is true. The second is not: overlapping requests does not merely
fail to help, it inflates each one.

## Implementation

The window stills are now taken in a plain `for` loop, in scope order, and delivered as each lands. The
task group, the `Piece?` optional element type it needed, and the `nonisolated(unsafe)` on the per-window
filter all go with it — that annotation existed only because `addTask` is an isolation crossing, and
without a child task the filter never leaves its own task.

Measured before committing to it, with a purpose-built harness (an `.accessory` app so its windows are
invisible to `AXWindowSource.applications()`, which filters on `.regular`, and so count and size are the
harness's to choose rather than whatever is on the strip). 252 timed batches — 2 window sizes × 3 batch
sizes × idle and under load × 7 interleaved trials:

- One capture alone costs ~25 ms; the same capture with anything else in flight costs ~41 ms. That is
  1.55–1.90× on the batch, and serial won all 12 cells.
- The penalty **grows under CPU load** (1.60× → 1.90×), which is when transitions happen.
- **Bounding the group to two in flight pays the penalty in full** (74.9 ms against 74.1 ms unbounded at
  n=2), so there is no concurrency width to tune. Overlap itself is the cost, not queue depth.
- Pixel dimensions do not enter into it: 500×400 and 1100×800 windows both cost ~25 ms. Scope size alone
  is the latency.
- Ordering is a strict improvement, not a trade: at n=8 the first piece is a tie (25.7 ms against
  26.8 ms) and every later one lands sooner, the eighth at 197 ms against 350 ms. This matters because
  the extend gate acks per window and `CoverMode.immediate` gates the raise on the base alone.

Confirmed end to end against the daemon, driving a fixed sweep of `focus` commands over a 12-window
strip under `cover = "immediate"`, comparing batches of equal size:

| windows | before (`done at`) | after (`done at`) |
| ------- | ------------------ | ----------------- |
| 3       | 232 ms             | 172 / 192 / 195 ms |
| 4       | 259 / 260 ms — deadline | 201 / 208 / 208 / 212 / 221 ms |
| 5       | 260 / 262 ms — deadline, 1 missing | 241 / 246 / 247 / 247 ms |

Four of five steady-state batches hit the 250 ms deadline before; none of twelve did after. The `before`
figures for 4 and 5 windows are censored by that deadline rather than measured, so the true gap is wider
than the table shows.

The deadline overruns were not merely slow, they were losing pixels. A batch of 5 where 4 windows have a
kept still and the fifth does not is gated on that fifth window's own capture; the group pushed it past
the deadline, so `CaptureService` acked it with nothing (`raise at never`, `1 missing`) and the cover
raised with a hole where that window should have been. Taken in order it lands comfortably inside the
budget. **A window that has just opened is exactly this case** — a fresh `WindowId` can never hit
`SurfaceCache` — so the arrival path was paying the worst of it.

## Observations

- Measured on one display and one machine, in batches up to 8. Serial scaling is dead linear
  (46 / 98 / 200 ms at n=2/4/8), which makes extrapolation past 8 reasonable, but it is extrapolation.
- Two covers on two displays are two batches, and by this result they interfere with each other. That is
  unchanged here — the batches were never in one task group — but it means the per-display independence
  §D7 buys is costlier than it looks.
- The 5-window case still lands at ~246 ms against a 250 ms deadline, so the budget is not comfortable,
  merely no longer exceeded. Two things sit behind that and neither is capture: `SCShareableContent` is
  ~11 ms warm at the head of every batch, and `CapturedSurface.measuredCornerRadius` runs per still on
  the main actor, drawing and scanning a 96 pt block each time.
- `IMPLEMENTATION.md`'s shoulder cost is corrected from ~10 ms to ~25 ms a window in the same pass.
