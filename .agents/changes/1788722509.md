# A lone window takes the whole strip

> Change `1788722509` — 2026-09-06

## Goal

A window opening onto an empty workspace landed on the width ladder's first rung — ⅓ of the screen under
the defaults — with nothing beside it and the rest of the display empty. A rung is a *share*, and a share
of a strip nobody else is on is the wrong quantity: the ladder answers "how much of this do you want the
others to have", and there are no others yet.

So: **while a strip holds exactly one window, that window takes the whole strip.** Open a second and both
fall back to the ladder; close one and the survivor takes the strip again. On by default, off with
`layout.fullscreen-when-alone`.

## Implementation

### It is the shadow `fullscreen` already raises, not a fourth rung

`ColumnLayout.fullscreen` sits *above* `widthOverride` and `widthPreset` rather than beside them, so
raising it stores nothing and costs nothing to undo — the rung underneath is never touched, and coming
off is exact rather than a guess at which preset a full-width column was nearest. Both width verbs
already clear it, and outside `handleFullscreen` nothing in the daemon reads `isFullscreen` at all:
every other consumer resolves through `Layout.resolvedWidth`. The rule therefore needed no new geometry,
no new width case, and no new consumer — which is most of why it is small.

What it did need is a way to tell the two apart. `Fullscreen.Origin` is that: `asked` is the user's verb
and outlives a neighbour arriving, `solo` is this rule and is lifted the moment the strip has company.
Without the discriminator the feature would silently change what `fullscreen` means for everyone who has
it on — a column the user asked to be full would drop out of full when the next window opened.

### Exactly one *window*, not one column

A single column holding two stacked windows keeps its width. Widening it would mean either expelling a
window to preserve the property that a fullscreen column holds one — `handleFullscreen` maintains it — or
representing a fullscreen column with a stack in it, which nothing else in the layout expects. Either
way emira would be rearranging a stack the user built with `consume` and did not ask to have undone. The
waste argument applies to a lone column as much as to a lone window; the answer is that the user already
chose that arrangement, and a rule that overrides a choice is the leash §4 forbids.

### Seeded at population changes, and deliberately not derived

The first design was a derivation: resolve a solo column to the content width and store nothing. It is
smaller, it is self-maintaining, and it is wrong — `cycle-width`, `grow`, `shrink` and `fullscreen off`
all become dead keys on a lone window, because every width they can express resolves to the same full
width. A user with one window who wants it at ½ could not have it. "A rule seeds a window; it never
leashes one" is exactly this, and a derived width is a leash by construction.

So the rule runs only where a strip's window set changes, and between those moments the layout holds
whatever the user last said. The escape is not permanent: the next arrival or departure hands the column
back to the rule, which is what keeps it a standing property of the strip rather than a one-shot at
launch.

Because it is edge-triggered it cannot live in `Workspaces.reconcile`, which every handler calls
defensively and which would re-assert it over a chosen width on the next event. It also cannot live in
`Engine.reduce` beside the focus-ring warp — the other cross-cutting difference between two states —
because the width has to be written *before* `finishStructuralEdit` reads the new geometry, or the
incumbent's shrink snaps while everything around it animates. That leaves the four sites where a strip's
population actually moves, and each names the strips it touched:

| `arriveOnStrip` | create, de-minimize, `float off`, unpin | acting |
| `departFromStrip` | destroy, minimize, `float on`, pin | acting |
| `moveToWorkspace` | `move-to-workspace`, `move-to-monitor` | source + destination |
| `arriveOnWorkspace` | a window rule's `workspace` | destination only |

The last row is the one with a trap in it. `Workspaces.reconcile` admits every newcomer to the strip in
view before `State.move` carries it off, so the acting strip briefly holds a window that is on its way
elsewhere. A pass over the acting strip there would read that transient as company, lift the incumbent's
shadow, and then — with the population back where it started and nothing left to re-fire the rule —
leave a lone window on a rung. Naming the destination alone is the fix, and it is also the argument
against putting the rule anywhere that fires on every membership edit.

### Nothing outranks it, and there is no boot case

**A seed chooses the rung; a verb clears the shadow.** That is the whole of the precedence, and the three
sources of a seeded width — the ladder, a window rule's `width`, the launch scan's `keepExistingWidth` —
are the same kind of thing under it. None of them is exempt, and nothing in the rule knows what a boot is.

The line is one call's position. `seedWidth` writes a `widthOverride`, and `setWidthOverride` clears
`fullscreen`, so running the rule *before* it silently exempted every seeded column. Written that way
first, to give a window rule's `width` precedence — and the launch scan, which goes through the same
mutator, was exempted along with it. The justification offered for that (§4's quiet boot) does not hold:
boot already resizes what it adopts, clamping the width to the working area and giving every window the
full column height, so "keeps the size it had" was never the promise. `EngineArrivalTests`' own comment
that the arrival "never resizes a window the user did not ask to resize" was already false on the height
axis.

Running the rule *after* `seedWidth` removes the exemption without a branch: the seed lands on the rung
and the rule shadows whatever rung the column ended up on. `fullscreen off` then gives back the adopted
or rule-given width exactly, since it was never overwritten.

The consequence for a window rule is deliberate and is a behaviour change from the first cut: `width =
0.5` on a window that is alone resolves to full, and to 0.5 the moment a second window opens. A rule's
width describes how that app sits *among others*; alone, half a screen is the same empty half the whole
feature exists to close.

a reload is what the user is watching for. Turning it off lifts every shadow the rule raised and leaves
the verb's standing.

### `fullscreen on` over the rule adopts it

A lone window is already full, so `handleFullscreen`'s "nothing to do" guard made `fullscreen on` a
no-op — and the next window opened would then drop it out of full, because the record was still the
rule's. There was no way to say "full, and *stay* full" about a window that was already full. `on` over a
`solo` record now rewrites it as `asked` and emits nothing, which is the only place the two mechanisms
touch.

### Test fallout

Sixteen existing tests opened a single window and asserted a ladder width; every one of them is about the
width stack, the resize verbs or the `fullscreen` verb rather than about this rule, and a lone window
filling the strip answered their question before they asked it. `EngineFix.laddered(_:)` turns the rule
off by name at each, so the reason is visible at the call site rather than inferred from an argument.
Reverting the default to `false` fails 26 assertions in the new suite, which is what says the suite is
testing something.

## Observations

Not run against a live desktop. The headless check is `theIncumbentsShrinkRidesTheArrivalsOwnCover`,
which asserts the invariant a raise pops without — `natural(after) + displacement(0) == natural(before)`
on every layer of the arrival's first frame, with the incumbent going 1000 → ⅓ inside it. What that
cannot answer is the §3 cost floor: the incumbent is *resizing*, so only its app can produce the new
pixels, and what the user sees for the length of the transition is a stretched or cropped still of a
full-width window. `cycle-width` has always had this and the trade is the same one, but this rule fires
without anybody pressing a key — every second window opened now resizes the first — so it is the one
place the feature could read as worse than the ladder it replaces. Worth watching on a slow app.

**A multi-window boot now places its first-adopted window twice.** Measured on a three-window launch
scan: window 1 is placed at 1000 (alone, so full), then at 300 when window 2 arrives and lifts the
shadow — one extra AX resize, which is the expensive kind, and settled after the second arrival rather
than repeated per window. It is zero on the single-window boot the rule is actually for.

That cost is not the price of removing the exemption; it is the launch scan being **N sequential
`windowCreated` events**. `WorldWatcher.absorb` has the whole set in `report.snapshots` and fans it out
one event at a time, so an edge-triggered rule cannot see that four more windows are coming: the first
one is genuinely alone at the moment it is asked about. Batching the scan into one adoption would remove
it; exempting boot again would only hide it. Reported not visible on a real desktop.

**Measured before believing it, and the case for batching is weaker than it looks.** An eight-window
boot under the default config: placements are bounded by the *viewport*, not by the window count — the
per-arrival count plateaus at four once the strip is wider than the screen — so the whole fan-out is
24 `setFrame`s against a batched 8, on a quantity that does not grow with the desktop. What does grow is
one `capture` per arrival, eight of them, which §5 says the window server serializes — and the focus
announcement, now suppressed for an adoption, which was the only user-visible half of it. Against that,
`windowCreated` is the reducer's most policy-dense event — rules for float, workspace and width, the
taxonomy, two distinct anchors, focus, and the arrival animation — and a batched twin either restates
all of it or becomes a transaction around N folds, which is a change to how the reducer is *driven*
rather than a new event.

A pin narrows the strip and the rule follows it for free: `fullscreen` resolves against `contentExtent`,
the clear viewport, so a lone window beside a pinned chat fills what is left rather than the display.
Untested on a live pin.

`Layout.applySoloFullscreen` walks every column to clear stale `solo` records, though only a strip that
just stopped being solo can carry one. The walk is O(columns) on an edit that is already O(columns), and
the alternative — tracking which column held the record — is a second opinion about a fact the columns
already carry.
