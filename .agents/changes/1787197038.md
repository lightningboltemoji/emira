# The TOML reader scans scalars, not lines

> Change `1787197038` — 2026-08-19

## Goal

The reader was written as a subset — the grammar emira's own config happens to be spelled in — and its
header said so. Compliance with TOML 1.0.0 is the goal instead, so the subset is a gap list rather than a
design.

Measured against the spec, the reader had three classes of defect. It **rejected valid TOML**: multi-line
strings and arrays, nested arrays, the `\b` `\f` `\u` `\U` escapes, literal-quoted keys, underscores in
numbers. It **accepted invalid TOML**: any Unicode letter or digit as a bare key, NBSP as separator
whitespace, leading zeros, a decimal point with digits on only one side, raw control characters. And it
**misread valid TOML**: splitting lines on `Character.isNewline` cut a string in half at U+0085, U+2028 or
U+2029 — scalars `basic-unescaped` explicitly admits — and reported it unterminated.

All three trace to one decision: the reader iterated `text.split(whereSeparator: \.isNewline)` and parsed
each line, so its character classes were Swift's rather than the ABNF's, and no production could span a line.

## Implementation

`TOMLScanner` is a cursor over the text's Unicode scalars with one method per production. Scalars because
that is the unit the ABNF is written in, and because `Character` cannot tell a bare CR from a line ending —
`"\r\n"` is one grapheme and two scalars. `ws` is space and tab; `newline` is LF or CRLF; a bare key is ASCII
`A-Za-z0-9_-`. Every class is spelled as a scalar range, because every Swift property that reads like the
right question answers a Unicode-wide one.

The scanner counts its own lines, which is what a line-based reader got for free and what multi-line values
make load-bearing: a `"""` string and a wrapped array both carry line breaks belonging to the value rather
than ending the statement.

**`TOMLSpan.line` becomes `.statement`.** It meant "the whole line carrying this value", and a multi-line
value has several. `ConfigDocument.remove` splices over the statement, so unsetting a wrapped array takes
every line of it and the comment inside it. Nothing else in the edit model moved — `set`, `rename` and
`insert` were already expressed as ranges, and the invariant they need is that a span is contiguous, not that
it is short.

**The writer moved with the reader.** `spell(key:)` shares the reader's bare-key predicate, so emira can no
longer write `café = 1` unquoted. `spell(_:quoting:)` gained `\b`, `\f` and a `\uXXXX` fallback for the
control characters the reader now refuses — without it, a stricter reader turns `emira config set` into a
way to write a file emira cannot open. A round-trip test pins the two halves together.

**`inf` and `nan` are grammar, and finiteness is schema.** Both are legal TOML floats and the reader now
takes them; no setting has a use for either, and they pass every range check the schema has — `inf` is at
least anything — so `TOMLTable.number` refuses non-finite values on its own rather than leaving it to bounds
that cannot catch it.

**A bare key that ends early names the scalar that ended it.** `café` used to reach the caller as `expected
'key = value'`, pointing at the missing `=` rather than the `é`. The key scanner now reads on to the next
scalar that may legally follow a key and reports `invalid key 'café'`. The case this is really for is a
non-breaking hyphen or space pasted from a web page, which is invisible in an editor.

`keyPath` returns where the last segment was written rather than letting a caller find it again, because
finding it again means a second, subtly different reading of the same grammar. (Moved here from the
declaration, which the comment ceiling had outgrown.)

Numbers stay `Double`. Radix integers were rejected rather than read, because `0xFFFFFFFFFFFFFFFF` does not
fit one and a lossy accept is worse than a refusal — that, the integer/float distinction, inline tables and
the date-times are the same change, not four, and it is the next one.

## Observations

Verified by a 92-case conformance battery over the spec's own examples (all pass), the 1,897-test suite (all
pass, two assertions updated where they pinned limits this removes), and the real CLI: `emira config set` on
a file carrying a wrapped array with a comment inside it changes one value and no other byte, and replaces
the array itself in one splice.

What the spec still says that emira does not, all of it needing a `Payload` case the flat document model
cannot carry:

- Inline tables, the four date-time types, hexadecimal/octal/binary integers — each refused by name.
- The integer/float distinction. Every number is a `Double`, so `9223372036854775807` reads back as
  `9.223372036854776e+18`, and a `1.0` rewritten by `config set` comes back as `1` — a float that became an
  integer.
- `[a.b]` after `[[a]]` belongs to the array's last element; it is filed at `a.b` instead, and the schema
  then reports a correctly written key as unknown.
- An array-of-tables index shares a namespace with real keys, and TOML permits all-digit bare keys, so
  `[[a]]` and `[a] 0 = 1` collide.
- Duplicate `[table]` headers merge silently, and a key defined both as a value and as a table is accepted.
  Duplicate *keys* are refused, so this is the same user mistake with two different answers.

`BurntSushi/toml-test` is the suite that would turn that list into a number. It wants an executable reading
TOML on stdin and emitting the suite's tagged JSON, which the value-model change is a prerequisite for.

Multi-line strings preserve CRLF as written rather than normalising it to LF. The spec says other whitespace
and newlines "remain intact" and does not spell out the CRLF case; implementations differ.
