# An app is asked until it answers

> Change `1793950456` — 2026-11-05

## Goal

`1793866083` audited the reads the tighter AX bound had turned into wrong answers, and left three. Reproduced on a
real daemon against a stalling AppKit fixture, every check run against `b815024` as well:

- **A focus change inside one app was lost for good if the app then stalled for 0.6 s.** `confirmAlive` got two
  attempts where the read it replaced waited 1.5 s, and silence failed toward "dead". The window with the keyboard
  stayed veiled and the one without it stayed clear, past every heartbeat: `noteFocus` had already advanced, so
  `windowBecameMain` took the report for one it had seen. The comment said this "only drops a reveal".
- **One window that reads slowly unmanaged its whole app.** With a healthy app and one window whose `AXSubrole` takes
  300 ms, no attempt at the short bound can succeed, and the `break` that ends a pass took every window behind it.
- **A registration that timed out was retried every heartbeat, forever.** It lands all the same, so the retry answers
  `.notificationAlreadyRegistered`, which `watch(windows:)` counted as a failure and rolled back. Its notifications
  worked throughout.

`appTerminated` also left `overdue` holding the windows of an app force-quit while hung, for one more read.

## Implementation

**Asking is cheap and waiting is not, so the two are spent differently.** A call against a silent app costs one
message, and between calls a write can get onto the lane; a call that waits holds the lane with that app's writes
behind it, and a held write holds the veil. So retries got generous and waits did not. `maxUnansweredAttempts` (20,
about 5 s) replaces `maxFrameReadAttempts` and governs frame, liveness and focus reads alike, and past it the question
goes to the heartbeat rather than being given up on: `overdue` for frames, `owedFocus` for focus, which is one slot
because a newer question is about a newer report. 5 s is therefore how fast emira notices recovery, not whether.

**A long retry needs a staleness check, which the short one had got away without.** A liveness answer is about one
report, so it is dropped unless `focus` still names that report's window. A focus read's answer is current however
late it comes, so it is dropped only once its app has lost the keyboard. Both would otherwise pull focus back to
where the user had left.

**Polling covers a stall; it cannot cover a slow call.** A read that always takes 300 ms is never answered by asking
at 250, however often. So a scan's last attempt waits (`AXClient.patientTimeout`, 1.5 s, the bound window elements had
before `1793851899`). It is set on the window element and lifted after, since that element is the one writes go
through: measured at 1510 ms under it and 260 ms after, against a stalled app.

**That attempt was unreachable.** A retry landing while a scan was out was coalesced and replayed from attempt 0, on
the reasoning that a replay is a new request. For an app slow enough that `register` fails too, the scan's retry and
the watch's collide every round, so the budget restarted forever: an unbounded scan loop, 74 reads in 45 s, that
`theRetryIsBoundedRatherThanARepeatingScanOfTheUsersDesktop` could not see. `rescan` now carries the attempt, merging
toward the lowest: a retry keeps its place and a request still starts over.

**`FocusedWindowRead.unanswered` is new, split from `.unreadable`.** `.unreadable` meant both silence and an app
answering that nothing has focus, and only the first is worth polling: the second is every activation of an app with
no windows open. It keeps its existing second ask, which nothing here measured.

**`resolveFocus`'s comment was cut to its constraint.** What it carried is in `PRINCIPLES.md` §4, `IMPLEMENTATION.md`
and `ObservationSource.isAlive`, except that this path never synthesizes a `windowVanished`, which would drop a real
window off the strip.

| | `b815024` | this change |
|---|---|---|
| focus change in one app, then a 0.6 to 12 s stall: core follows | 0/9 | 9/9 |
| the user leaves during a 2.5 to 8 s stall: focus stays with them | not run | 3/3 |
| one window's `AXSubrole` takes 0.3 or 0.6 s: windows adopted | 0/3 | 3/3, and at 1.2 s |
| rollbacks of one window's registration in 16 s | 7 | 1 |
| veil behind focus, 1 and 3 hung windows on the display | 1.03, 2.58 s | 1.03, 2.58 s |
| overlap clear of a neighbour's veil during a stall | yes | yes |

Removing each of the 12 guards fails the suite. One test passed with its guard removed until it was rewritten:
`min` and `max` agree until a retry is already waiting when the request arrives.

Rejected:

- **A deadline instead of a count.** A process that has gone answers `.cannotComplete` instantly, so 5 s of it is a
  busy loop on a lane, where 20 attempts is 20 hops.
- **5 s of patience on the waiting attempt.** It would add up to 5 s to a write to that app, and so to the veil on its
  display, on every scan chain. Reasoned from the lane, not run.
- **Patience on `AXWindows` as well.** Added on a diagnosis that was wrong, and adoption is the same without it.
- **Dropping a retry that finds a scan out**, simpler than carrying the attempt. It loses the `alreadyOpen` merge.

## Observations

- **The veil's lag behind focus is unchanged**: about 1 s per hung window, on every focus change on that display, for
  as long as the app is hung. It is now the largest error left in the mask, and releasing the held set is the
  question `1793851899` left open.
- **The focus-read budget was not shown to fix anything live.** Activating an app that then stalled, 1 to 7 s, was
  right on `b815024` as well. It is pinned by tests only.
- **A window past `patientTimeout` still takes the windows behind it.** At 2 s the app adopts nothing and stops
  asking. `b815024`'s parent adopted all three, with that window misfiled as `.other`.
- **A slow call stays slow everywhere else.** Only the scan waits, so a window whose `AXPosition` always outlasts the
  bound never answers a frame read, and its writes always report `axFailed`. Provoked for `AXSubrole` alone.
- **An abandoned read still runs in the app.** At most five, by its port's depth, but a slow app does that work again
  for each one.
- **`checkFullScreen` still drops an unanswered read.** The same class, unprovoked and left.
- **How often any of this happens is unknown.** Only fixtures were run, with Finder and one browser open, on one
  60 Hz display. A count of `.cannotComplete` per app, over days of use, would answer it.
