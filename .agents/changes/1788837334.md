# A departure unwinds the stack, not just the strip

> Change `1788837334` — 2026-09-07

## Goal

Reported: open a settings dialog (it takes focus), open a file picker out of it (it takes focus), close
the picker — and the settings window does not come back. Focus lands on the tiled window behind both.

Not a missing stack. `World.focusedAt` is a monotonic focus clock keyed by window, total over every
managed window, already kept for `StackOrder`; with the picker up it read

```
focusedAt: {4: 6, 3: 4, 2: 2, 1: 1}
   4 picker · 3 settings dialog · 2 the tiled window · 1 another app
```

which is exactly the order the return wants. `Engine.successor` simply never asked it. Its third clause
— the one a window with no column reaches — went to `Engine.stripAnchor`, and that function answers only
with a window that *holds a column*. So a departing float could never hand focus to another float, and
the unwind skipped the middle of the stack every time.

Nor was it passive. `World.remove` clears `focusedWindow`, `departFromStrip` sees `nil`, and emits:

```
windowDestroyed(WindowTag#4)
     → focus(WindowTag#2)
     → setHoists([#3 … state: covered])
```

emira took focus to the tiled window, which buried the settings dialog and hoisted it — a frozen picture
over a window the user was about to type in, the same visible failure as change `1788833969` reached by
a different route. Afterwards `focusedAt` read `{1: 1, 3: 4, 2: 7}`: emira's own write had inverted the
stack it needed to read.

## Implementation

`World.lastFocusedOnScreen(on:)` is the stack's top, and `successor` gains a `recent:` clause that
consults it before `anchor`. The two positional clauses are untouched, so a tiled window closing still
takes its neighbour rather than the stack.

**On screen and on one display.** `focusedAt` outlives its window being minimized, `Cmd-H` hidden,
parked on a workspace the user has left, or scrolled off the viewport, and none of those is somewhere a
departure can hand focus — `isOnScreen` is the same reader hoisting already asks. The display test is
`World.monitor(at:)` on the frame's centre, hoisting's idiom again, and it is not decoration: without it
closing a dialog could move focus to another screen while `Monitors.focused` stayed put, since
`departFromStrip` writes focus directly rather than through the reveal a `focusChanged` gets.
`stripAnchor` survives behind the new clause for the case the stack declines and it does not — a strip
place that has since scrolled out of view.

**The empty strip falls through to the same clause, deliberately.** A strip losing its last column has
no positional answer and no strip memory, so it now hands focus to a float standing in the open. That is
a behaviour change beyond the reported bug and was agreed rather than inherited: it is the only thing
left to focus.

**`move-to-monitor` staying behind passes `recent: nil`.** It reaches the same clause when the move
empties the strip, but the placement pass is what retires the moved window from `World.placedOnScreen`,
and it has not run yet — so the stack would answer with the window just sent away and focus would follow
it off the display. The one call site where the stack is not yet true.

Rejected: emitting nothing for an off-strip departure and letting the app restore focus, which macOS
does naturally for a modal panel. It reads well against "emira declines an opinion about a window it
does not place", but it leaves the core with no focus at all when the app declines too, and it discards
a stack emira is already paying to maintain.

Each of the three new tests was checked against the unfixed code: two fail without the `recent` clause,
and the third fails with the clause but without its `isOnScreen` filter. Validated against the running
daemon as well — closing the picker now traces `→ focus(WindowTag#3)` with no `setHoists`, and the
dialog stays real rather than becoming a photograph.

## Observations

The stack is global to the acting monitor, not per app. Closing a dialog therefore returns to the newest
window that screen is showing even if it belongs to another app — which is the honest reading of "where
was I", and is what the user asked for, but is worth knowing before someone reads it as same-app
nesting.

The stale `focusChanged(nil)` noted in `1788833969` and `1788835822` is still unrepaired. It is harmless
to this path — `setFocus(nil)` leaves `focusedAt` alone, so the stack survives it — but the moment where
emira believes nothing is focused is still there.
