# The refusal asks whether the window can still take focus

> Change `1788227630` — 2026-08-31

## Goal

An app alone in a workspace could not be quit or hidden. ⌘Q on Infuse left it running and frontmost with a
freshly rebuilt window; ⌘H left it visible. Quitting emira and pressing the same key worked, and so did the
same key with a second window on the strip.

The cause is `[focus] system-events = "on-screen"` (also `ignore`) doing exactly what it says. An app giving
up focus makes macOS activate a successor, and with one window in the workspace that successor is always
somewhere the user is not looking — a parked column, another workspace. The report is refused, the refusal
re-asserts the focus the core still believes in, and the window it names belongs to the app that is halfway
through leaving. Bringing that app forward is enough to cancel a quit outright: measured with
`NSRunningApplication.activate()` and again with an `AXFrontmost` write, both resurrect Infuse, which then
rebuilds the window it had just torn down. The correction went out 1 ms after the report.

Nothing about that is Infuse-specific — ⌘H reproduces on the same path, and every app pays the pointless
re-activation on the way out. Infuse is only the app that treats it as a reason to stay.

## Implementation

`Effect.restoreFocus` splits the refusal's write away from `focus`. Same AX work, different promise: a
command is owed its write whatever the app is busy doing, while a correction — which names a window nobody
chose — is owed only to a window that can still hold focus.

**The question is answerable, and AX is the one place that cannot answer it.** Sampling every published fact
about a departing app at 2 ms says so plainly. At the moment of the focus report, and 100 ms later, AX still
lists the app's windows, names a focused one, and answers about live elements:

| fact | quit (Infuse) | quit (TextEdit) | ⌘H | another app steals focus |
| --------------------------------- | ------------: | --------------: | ----: | -----------------------: |
| `activationPolicy` → `.prohibited` | 5–7 ms | — | — | never |
| gone from LaunchServices | 450 ms | 2 ms | — | never |
| `isHidden` → true | — | — | 3 ms | never |
| off the window server | 26 ms | 1 ms | 12 ms | never |
| AX still describes it as healthy | ≥ 100 ms | — | yes | yes |

So `canHoldFocus` asks LaunchServices and the window server, and never the app. The last column is what makes
it a *question* rather than a guess: none of those facts moves when a window merely loses focus, so a refusal
that should bounce still bounces, immediately.

**`AXWindowWriter` asks it around its own write, twice, because one asking cannot do both jobs.** Before
`makeKey`, because that write alone brings a hidden app back — the very thing ⌘H asked for. Again in its
completion, immediately before activating, because the answer arrives a few milliseconds after the report
being corrected, and the lane round trip is what carries the question past it — time that stretches with the
teardown being raced, since the lane belongs to the departing app. Measured over the reliable repro (the app
alone in a workspace): the early asking alone quit 6 of 8, the late one alone 15 of 15, both together 10 of
10, with ⌘H sticking 6 of 6.

It is `AXWindowWriter`'s and not `AXExecutor`'s because both instants are inside one write, and a seam above
the writer could only ever hold the early one. That leaves the answer untested, which is the honest place for
it: the four reads are a live desktop's to answer, like every other system call below `WindowWriter`. What
the executor still decides — and what `WritePathTests` still pins — is *which* windows are asked about at
all: a correction takes the asking route, a command never does.

Rejected:

- **Waiting.** Hold the correction for a grace and drop it if the window has left the screen by then. It
  works, and it is a constant tuned on one machine for a race whose two sides — an AX round trip to identify
  the window, and another process's teardown — nothing keeps in proportion across hardware. It also charges
  every *legitimate* refusal, a Dock click onto another workspace among them, the same wait with the keyboard
  in the wrong app.
- **Never bouncing** — refuse the reveal, leave the keyboard where macOS put it. That is the case the policy
  exists for: a reminder taking focus from another workspace would leave the user typing into a window they
  cannot see.
- **A gentler write.** Neither route to the front is gentle: AppKit activation and `AXFrontmost` were tested
  separately and both cancel the quit. `makeKey` is not the culprit and could not be — a Catalyst window
  reports `AXMain` as unsettable, so that half of `focus` is already a no-op there.
- **Waiting for emira's own destroy**, which arrives behind the succession scan, seconds later.

## Observations

- No latency is added anywhere. A refused report is corrected as immediately as before; the difference is
  four cheap reads on the way.
- What remains is a race rather than a constant: if emira activates before LaunchServices has marked the app,
  the correction lands and the app is resurrected that once. Asking twice makes it narrow, and the second
  asking widens with the departing app's own slowness.
- `activationPolicy == .prohibited` is the app's own statement that it cannot be activated. `.accessory` is
  not that and must keep passing — an agent with a window is a legitimate place for focus to sit.
- An app that gives up focus without touching any of the four facts would still be re-activated. None of the
  three departures tested (quit fast, quit slow, hide) is that app.
- `[focus] system-events = "respect"` never refuses, so it never had the bug and is unaffected.
