# A window away comes back where it stood

> Change `1795408183` — 2026-11-22

## Goal

`1795405786` gave a window back from native full screen its column's width and left the Dock and ⌘H out. The
user wants all three to return a window as it left: its width, its place on the strip and its workspace.
Measured in the VM before this change, all three lost the width (850 pt, the ladder's first rung). A middle
column came back one place to the right. Every return landed on the workspace in view, so an app hidden on
workspace 2 and unhidden from 1 came back on 1 and left 2 empty.

The work also turned up an older ⌘H bug. The shell reports a hide one window at a time. When the focused window
left first, the strip handed focus to its sibling, which was still standing. That focus write unhid the app
19 ms later. Reproduced on a baseline build from `HEAD`.

## Implementation

**One notion of away.** `World.awayWindowIds` is every live window that is minimized, hidden, or in full
screen. `Workspaces.reconcile` takes it as `away`, and now runs in four steps:

1. Record where each departing window stands.
2. Remove departures from every strip.
3. Rejoin each returning window to its own place.
4. Admit what is left onto `home` beside the anchor, as before.

A place is an `AwayPlace`: the workspace plus a `Layout.Spot`, which holds the column as it stood, the row,
and the strip's window order.

`Layout.rejoin` puts the window back into its column at its row if that stack outlived it. Otherwise it gets a
column at the width it left with, beside the nearest window in the recorded order that is still on the strip,
looking left first. Failing that, it goes at the end. `ColumnLayout(id:window:like:)` is now the single rule for
a column taking another's width, shared by `adopt` and `rejoin`.

**The order has the windows already away spliced in** (`Workspaces.remembering`). Without that, two adjacent
windows that leave one after the other come back reversed in one of the four leave/return orders. The
neighbour test fails exactly that case when the splice is disabled. Rejected: storing a left and right
neighbour pair. Whichever side is tried first, one departure order defeats it.

**Returns.** `Engine.returnFromAway` serves `windowDeminimized`, `windowUnhidden` and `windowFullScreen(false)`.
On the strip in view, a return is the ordinary arrival. Out of view, the desktop switches only for the window
the user is in.

- A Dock restore and a full-screen exit take focus and are followed.
- An unhide follows its app's focus report, which can arrive before the return or after it.
  - If the report came first, the return finds the window focused.
  - If it came second, `revealAcrossWorkspaces` finds the window back on its strip.

That needed a new event, `windowUnhidden`. The shell had sent ⌘H undone as `windowDeminimized`, which takes
focus once per window: an app with three windows would steal focus three times, and switch workspaces as often.

Rejected: dropping the focus grab on every return and following reports alone. An app that posts no focus
change on a restore within the active app would never be followed. Under `system-events = on-screen`, the
report for a window still in the Dock is refused.

**⌘H departs on its own event, `windowHidden`.** It folds like a minimize. `departFromLayout` passes over the
hidden app's windows when it chooses a successor; `Engine.successor` takes the set to skip and walks to the
nearest column beyond them, rightward first. With nothing skipped, it answers exactly as before. A minimize
still hands focus to a sibling, which is what macOS does too.

Rejected, after trying it in the VM: ordering the shell's hide so the focused window leaves last. The watcher's
belief about focus diverged from the core's. emira's own `focus left` echo never came back as a report, so the
watcher still named the window it had booted on. The successor is the core's choice, so the fix belongs there.

`RulesTests.theRuleIsNeverConsultedTwice` asserted the old behaviour: restored from another workspace, a window
"lands where the user is". It now asserts that the window goes back to where it was put and the user follows.

## Observations

Verified in a Tart VM (macOS 27.2, Safari, TextEdit, Terminal) on release builds, through `emira debug` and
`EMIRA_TRACE`:

- Safari at 41% in the middle column came back in the middle at 41% after a minimize with Dock restore, after
  ⌘H with unhide, and after ⌃⌘F twice. After further rearranging it came back between the two TextEdit windows
  at 73.6%, on the final build.
- Hidden on workspace 2 and unhidden by activating Safari from 1: Safari returned to 2, and emira switched
  there. The same for a minimize on 2 with a Dock restore from 1.
- TextEdit with two adjacent windows at 27% and 36%, the left one focused, then ⌘H. The baseline unhid at once.
  Now focus went to Safari, TextEdit stayed hidden, and the unhide restored both in order and width, with focus
  on the app's key window.

Not exercised: a second display; an unhide whose app focuses a window on a workspace shown on another display.

Known by reading, not observed:

- When a focus report reaches the core before a Dock restore that switches workspace, focus already sits on the
  away window. The outgoing workspace's remembered focus is then cleared, so returning there focuses its first
  window.
- A place lives in daemon state, so a restart forgets it. A window minimized at boot has no place and arrives
  as before.
- The ⌘H pass-over goes by bundle id, so a second instance of the same app is passed over too.
- A minimize that never posts its notification is still invisible, as before this change.
