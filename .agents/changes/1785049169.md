# Window identity under a burst — the ghost columns

> Change `1785049169` — 2026-07-25

## Goal

Fix three reported symptoms from pressing ⌘N four times in Ghostty and then focusing the results: a
column with no window in it, one Ghostty window left unmanaged on the desktop, and focus that stops
responding so the far-right columns are unreachable.

## Implementation

Four defects, each pinned by a test that first asserted the broken behaviour.

**The identity join was re-run for windows that already had an identity.** Both sides of the join are
snapshots of a moving system — AX frames read on the app's serial lane, the window list read later on
the main actor — and placement writes queue on that same lane, so the system moves between the two
reads. Under a burst the stale read reports window A at the frame window B has since taken; A matches
B's entry uniquely, so the join reports success. The registry then minted a second `WindowId` for A's
element (the empty column), moved `idByElement` onto it (so A's destroy and move notifications resolved
to a nonexistent window), and spent B's window number, leaving B unadopted. Three rules now: a known
element skips the join, an entry already bound is not a candidate, and `adopt` returns `nil` rather
than binding an element carrying a different number.

**The reverse direction had no signal.** `unbound` names a window AX described that the list did not;
nothing named a window the list showed that AX did not. That covers both the "asked too early" race
from the other side and a window whose AX attributes timed out and was dropped before the join. Both
now feed the same bounded retry via `Report.unclaimed`, which counts **on-screen** entries only:
ordinary apps carry several off-screen layer-0 entries that are not windows (four `1800×39` strips at
the origin for Ghostty, Safari and Finder), and counting them marks every scan of those apps incomplete
permanently.

**Scans are coalesced per app**, as frame reads already were. Four ⌘N presses produced four concurrent
full re-scans of one app, each seven AX round trips per window, on the serial lane placement writes
share. This is upstream of the join: less lane pressure is less skew between its two reads. A
window-level `AXObserverAddNotification` failure now rolls back instead of leaving `watchedWindows`
optimistically marked, which had made a registration a busy app refused both permanent and silent.

**Focus off the strip was a dead end.** `handleFocus` guarded on the focused window having a column and
returned `[]`, so once `World` recorded focus off the strip — routine, since activating an app surfaces
whichever window is `AXMain` — every direction no-oped until a mouse click. Off the strip is now an
entry condition: `right` re-enters at the leftmost column, `left` at the rightmost.

**A window adopted mid-transition was never placed.** `reveal`'s transitioning branch retargeted the
viewport and emitted no effects, and nothing re-asserts placement at `closeTransition`. It now calls
`driveTransition`, the path the command cases use. Consequence: `armLandings` must grow rather than
replace, since a re-teleport that moves nothing would otherwise clear the wait for sets still in flight
from the previous batch. Only the initial teleport replaces.

## Observations

- The failure class was untestable by construction: every `WindowSource` double answered synchronously,
  so two overlapping scans of one app could not be expressed. The stub can now hold a scan open.
- The `adopt` guard exposed a fixture flaw — several tests gave two windows of one app the same
  `AXUIElement`.
- `axFailed` now records that the window's position is unknown (`World.unverified`) and the next real
  event re-issues the set. Nothing is scheduled, so a hung app costs one extra set per event rather
  than a busy loop, and nothing gives up on a window that never answers.
- Verified in the product: 10 windows, 10 columns, every frame byte-identical to
  `CGWindowListCopyWindowInfo` read in a separate process, focus walking the full strip both
  directions.
