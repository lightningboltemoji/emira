# A cover's content read has to carry everything the cover draws

> Change `1789275372` — 2026-09-12

## Goal

A report from a two-window strip wider than the viewport — Safari at ⅔, a terminal at ½ — that
`focus left` / `focus right` animated wrongly: on `focus right` a large gap opened between the two
windows and closed again; on `focus left` Safari visibly slid over its neighbour; and under fast
alternating presses only Safari moved at all while the second window stood still.

Those three descriptions are one fact. The strip travels 280 pt either way, so a gap opening on the
way left and an overlap on the way right is one window travelling and one standing still — and the
standing one is *drawn under* the moving one, which is where in the cover it must be. A stand-in is
above the base; only the base holds still. So the second window was being painted by the desktop
photograph while everything else animated over it.

## Implementation

### What can put a scoped window in the base

`grab` derives two lists from one `SCShareableContent` read: the windows to photograph, and the
windows the base must have a hole where. Both are `content.windows.filter { windows.contains(…) }`,
so they agree by construction — but only over the windows that read actually carries. A scoped number
absent from it is filtered out of *both*: never filmed, so no layer, and never excluded, so the base
keeps it. The cover then raises with a `LayerId` minted for a window that has no `CALayer`, and the
photograph underneath shows it at the frame it had when the cover went up, for the length of the
transition, while the stand-ins slide past. Nothing in the path notices, and nothing logs it.

The read was `onScreenWindowsOnly: true`. The comment justifying that reasoned about the one case it
had in mind — a parked column keeps a ~1 px sliver and stays listed — which is true and is not the
whole set. `IMPLEMENTATION.md` already says so a few paragraphs earlier, about the registry: absence
from the window list is a death certificate, `isOnScreen` is not, and an ordinary desktop carries far
more off-screen entries than on-screen ones, each of them a live window. The capture plane was making
exactly the mistake the removal direction is written to avoid.

Measured on this desktop: 6 windows in the on-screen answer against 41 in the whole list, and the 35
recovered include a minimized window at its last frame and several layer-0 entries per app. Any of
those, bound to a managed window, is a window emira scopes and cannot see. `SCContentFilter(desktop`
`IndependentWindow:)` photographs one perfectly well — confirmed against an off-screen 1252×775
window, which came back at full size — so the read is the only thing standing between the scope and a
correct cover.

### Read the whole list only when the short one is short

The obvious fix — always ask for everything — was measured before being believed, and it costs. The
content read is 29 ms against 39 ms, ten times over; in the daemon that showed up as a capture head
of 54–66 ms against 36–49 ms, about 20% on the one latency the user waits through with nothing on
screen moving. The exclusion list growing from 3 to 38 costs a further ~4 ms on the base shot, inside
the noise.

So the short read stands until it comes up short: if the scope is not a subset of what came back, the
whole list is read and everything downstream is unchanged. The ordinary desktop pays nothing — head
latency after the change is 36–46 ms, indistinguishable from before — and the second round trip is
spent only where the alternative is a torn strip. A window that is missing from *both* reads is gone,
and a hole is then the truthful thing to draw.

Rejected: abandoning the cover (`coverUnavailable`) when the scope cannot be resolved. It costs
nothing and degrades honestly, which is the house pattern for a missing base — but it trades a
correct animation for no animation at all, permanently, for as long as a window is bound to a number
the short read omits. The extra read buys the animation instead.

## Observations

**The reported bug is not reproduced, and this is not proven to be its cause.** It stopped
reproducing before it could be caught: it had been reliable across daemon restarts, which rules out
accumulated daemon state and points at a property of the desktop, which is the shape this failure
has. What was established instead is that everything upstream is sound — the reducer's emitted
geometry holds the two layers exactly one column gap apart on every frame of every direction, cold,
warm, and under a 70 ms alternating burst, with the focus echo modelled and with a terminal answering
back a quantized size; and on the live desktop both windows were filmed, layered and blitted
correctly every time, measured off the `setLayerFrame` stream and off the pixels at ~30 ms. This is
the only mechanism found that produces the reported artifact in both directions with the right window
underneath, and it was unguarded.

**Untested, and structurally so.** `SCKCapturer` is the one file `CaptureTests` deliberately does not
reach — "ScreenCaptureKit itself is untestable and holds no decisions — that is what `SurfaceCapturer`
is for". The second half of that had stopped being true: which windows the content read carries is a
decision, it is the one that broke, and it lives on the far side of the seam. Moving it behind
`SurfaceCapturer` would make it testable and would mean handing the protocol a window-server concept
it currently has no need of.

**The identity side is untouched and is the other half of this.** `WindowIdentity.bind` will hand a
window a `WindowListEntry` the window server calls off screen whenever that entry is the unique frame
match for its pid — `isOnScreen` is consulted only to break a tie between several. For a minimized
window that is deliberate and stated; for a window AX reports as live it is a mis-bind, and every
consumer of the number inherits it. Narrowing it means refusing to bind a window on another Space,
which is a behaviour change with nothing measured behind it, so it is left alone. After this change
its cost is no longer a torn cover.

**`keepExistingWidth` records `width / nominalArea.width`** where every other point-to-intent
conversion goes through `Extent.proportion(of:)`, which is `(points + gap) / (span + gap)`. A window
adopted at exactly a preset width therefore does not round-trip — 1105 pt comes back as 1098 and the
launch scan resizes it by 7 pt. Unrelated to this, and left alone.
