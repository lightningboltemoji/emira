# What the focus record swallows is asked again

> Change `1790146681` — 2026-09-22

## Goal

`1790142242` did not fix the reported case. With Safari pinned, open a handful of Ghostty windows and
press ⌃D repeatedly while clicking Safari. Safari takes the keyboard and the menu bar, but the veil stays
on it, and the veil does not come off it again.

## Implementation

### What was measured

The case was reproduced on the user's machine on `ace320e` with temporary logging in the shell's focus
path: every `FocusIntent` request, every verdict and drop, and every activation result. There were three
open-and-close cycles, and the last one reproduced. In that cycle:

- **930.31.** A new Ghostty column arrives across the pin. The fence asks for Safari, which puts the
  pin's window on the record. macOS refuses the fence's `activate()`; it did so every time in the log,
  and the `AXFrontmost` fallback carried it.
- **930.84–931.37.** The closes land, and each hands focus to a successor: four more requests. The
  grace is re-armed per request, so the pin's entry stays on the record throughout.
- **931.49.** The user clicks Safari. The activation read answers with the pin's window, and the verdict
  is `stale`, because the pin's window is on the record behind newer requests. The click is dropped.
- **931.85.** The record clears. Nothing asks again, and the core stays on Ghostty.

`1790142242`'s edits are all past the verdict, so they could not reach this. The same record also
explains the rest of the family. A click on the pin while the fence's request is the *newest* is
`expected`, and the core ignores an echo of its own onto a pin. An activation of ours that macOS refuses
leaves a core focus whose app never came forward.

### The fix

**When the record clears, the active app is asked once, and the answer is passed on as it stands**
(`FocusIntent.onCleared` → `WorldWatcher.settleFocus`). The record exists to make emira briefly deaf to
its own echoes. Being deaf is the right trade only if hearing resumes, and until now nothing re-asked:
a swallowed report was lost for good, because the app it came from was already frontmost and would not
report again.

The read bypasses `resolveFocus`. Its two filters, the record and the backfill question, are about a
report arriving in the middle of something. At the clearing the record is empty, and the backfill
question can only drop the one answer this read exists to deliver. A read overtaken by a new request is
dropped under the same queued-read rule as any other, and that request's own clearing asks again.

Most clearings follow an ordinary `focus` command, and the read then names the window the core already
holds: a `.system` report for the current focus, which no policy refuses and which reveals nothing new.
It costs one AX read on the active app's lane per burst of requests, not per request.

Rejected, **taking the fence off the record.** Its activation's echo has to be absorbed somehow, or the
core is put on the pin for the length of the gate. By window id, that echo and a real click on the pin
are the same report, so any record that absorbs one absorbs the other. What was missing was a second
look once the ambiguity passed.

Rejected, **expiring entries one at a time.** That would have shortened this trace, since the pin's
entry was 1.2 s old at the click. But a click inside 0.5 s of a fence ask is still swallowed, so this
fix would still be needed. Worth doing separately if the visible delay is a problem (see Observations).

## Observations

**Not yet verified live with the fix.** It was built after the trace, and the machine this was written
on was locked, so the daemon could see no windows. The suite covers the mechanism: a stale click reported
at the clearing, a settle read overtaken by a request, and no read before any activation. The live
check is the user's reproduction on this build, which still carries the temporary logging, to be
removed after.

**The veil can be wrong for up to one grace after the last request.** In the traced case, that is
~0.36 s from the click to the clearing. During a longer burst of requests it lasts for the rest of the
burst. Expiring entries one at a time would shorten the common case.

**The watcher's `focus` can be stuck on a window that died with no report after it.** In the same log,
Ghostty's backfill never came and our echo was not posted, because Ghostty was already active. A later
click on another Ghostty window was then dropped as a backfill, 7 s after the close. It was harmless
there, since the core had already moved to that window. With no request in flight, no clearing follows
to correct it.

**Emira's own settings window** is excluded from `appActivated`. While it is frontmost, `active` still
names the previous app, and a clearing reads that app's focus.
