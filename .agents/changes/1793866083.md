# A read that timed out is not an answer

> Change `1793866083` — 2026-11-05

## Goal

Change `1793851899` made `AXClient.defaultTimeout` real for window elements, which had been waiting the system's
1.5 s while everything around them assumed 0.25. That was right, and it is what made the veil work against a hung
app. But `AXAccess` collapsed every `AXError` to `nil`, and a stall of 0.26 to 1.5 s, which used to be waited out,
now arrived as an answer. Reproduced on a real daemon, each for good until something else happened:

- **A window that moved itself and stalled stayed where it went.** The read timed out, `nil` meant "closed
  mid-drag", and the core was never told. 12 of 12 such moves were put back before `1793851899` and none after it.
- **A window whose subrole read timed out floated for life.** `nil` subrole is `.other`, and a role is decided once.
- **A focused sheet whose `AXParent` read timed out became focus on nothing** (`focusChanged(nil)`, 3 of 3). The veil
  held, on `World.lastFocus`, but the core believed no window had the keyboard, and nothing reports the sheet leaving.

## Implementation

**One new fact, at the bottom.** `.cannotComplete` becomes `AXUnanswered`, thrown by the reads that decide
something. `copyAttribute` stays for callers with nothing to do about it, so the write path is unchanged.

**A description is all-or-nothing, and the pass ends at the first silence** (`snapshot`, `ScanAnswer.isComplete`):
one timeout against a hung app rather than one per window. The flag is load-bearing. A window missing from a scan is
a departure unless the window server still shows it, and a minimized window is off screen, so a partial answer would
have retired live windows. It joins the two existing reasons an answer is not a picture to judge absence from.

**A frame read is asked again** (`FrameRead`, `maxFrameReadAttempts`, `overdue`), because that report was the only
one coming: six in a row, about the 1.5 s that used to be waited out, then once per reconciliation for as long as it
takes. No answer opens no stillness wait: `windowSelfPlaced` read from the frame `World` already holds writes nothing.
A write going out takes the question over, since its read-back answers it and a read landing inside it would put a
frame in the middle of a write.

**`isAlive` is asked once more and still fails toward "dead"**, which `resolveFocus` chose on purpose: that drops a
reveal, and the opposite mistake moves focus off a closing window. **`parent` only counts where it decides**: a
timeout on a window the registry knows is still focus on that window, so it is `.unreadable` only for one it does not.

Rejected:

- **Reverting the timeout**, the one-line fix. It gives back the write bound that `1793851899` was for.
- **Asking the window server when the app does not answer.** A window moved in the same run-loop turn as a stall is
  not on the server until the turn ends, which is the case that loses a move.
- **Retrying on a paced timer without a bound.** The heartbeat already is one, at one read a beat, and a faster loop
  against a hung app is what the write path declines to be.
- **Timing a read to tell a timeout from an instant `.cannotComplete`.** A dead process answers that in 0 ms, and
  it is no more an answer than a timeout is. Every error from four real apps was absent-or-success, so nothing needs it.

Checked on a real daemon, every check run against `1793851899` as well:

| | before | after |
|---|---|---|
| moved itself, then stalled 300 to 1400 ms: put back | 0/12 | 12/12, as the stall ends |
| the same, 2 to 4 s (2 s failed before `1793851899` too) | 0/6 | 6/6, within 2.3 s, by heartbeat |
| stall on the subrole read, 300 to 1000 ms: `.standard` | 0/9 | 9/9, adopted within 20 ms of recovery |
| stall on a sheet's `AXParent`: spurious `focusChanged(nil)` | 3/3 | 0/3 |
| plain stall from opening, 300 to 2000 ms: adopted | 27/27 | 27/27 |
| overlap clear of a neighbour's veil during a stall | yes | yes |
| focus transitions, median fps | 63 | 63 |

Chrome and IntelliJ cold launches behave identically on both. Removing each of the 12 guards fails the suite, one
by the recursion an unbounded retry makes of the synchronous test double. `IMPLEMENTATION.md` said a `nil` focus draws
the strip see-through, which `World.lastFocus` has long prevented, so that clause went too.

## Observations

- **How often any of this happened is unknown.** Every failure above needed a stall placed on purpose, and busy-opening
  fixtures and real launches never showed one, so the role and the sheet are narrow races with lasting results. A lost
  move needs the stall within about a millisecond of the move, which a same-turn `setFrame` meets.
- **`.cannotComplete` is taken at its documented word.** An app answering it instantly and forever for one attribute
  would leave its window unmanaged, with `scan gave up` in the log, where it used to be misfiled. None did, across 60
  reads of Ghostty, Finder, Chrome and IntelliJ: four apps.
- **A stall from opening past about a second can wait for the heartbeat**, up to 3 s after recovery, on both builds.
  Three attempts fit in that long, and none of the reads that timed out there were a snapshot's.
- **Idle sleep looks like this bug.** One run of the adoption check took 1 of 9 windows and is left out above: the
  display went off a second before the first failed scan, and AX listed no windows until the machine woke. Windows
  opened meanwhile at one frame then stayed `ambiguous`, which is the fixture's doing. Keep a measured machine awake.
- **`checkFullScreen` still drops an unanswered read**, the same class, unprovoked and left. `Scrims.expectMovement`
  still pushes `settleLimit` on every report, so that is not the cap the comment on `settleInterval` says it is.
- **A write to a hung app gives up per window.** 2.67 s for three, so a focus change on a held display waits that long.
- **Six attempts hold a lane for 1.5 s per moved window**, about the one 1.5 s read they replace.
- **Multi-display was measured at 60 Hz only**, on `1793851899`, with a virtual display: no cost from the watch.
