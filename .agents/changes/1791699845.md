# Film what the gate waits on first, and paint what lands late

> Change `1791699845` — 2026-10-10

## Goal

Two faults in the head of a transition, from `ASSESSMENT.md` P1 and P3.

**The batch was filmed in ScreenCaptureKit's enumeration order.** `grab` filtered `content.windows` by
membership, so the order was neither scope order (as its comment claimed) nor priority. Under `immediate` most
windows already have a stand-in. The one or two without one are what the raise waits for, and they queued behind
refreshes of windows that already had pixels: a `move-window` raised at 256 ms because the mover, resized by
the previous `cycle-width`, was filmed last of four.

**A still landing after the deadline was stored and never painted.** `receive` recorded it, then returned on
`guard let batch`, so no `captureRefreshed` went out. On a 5K display the 250 ms deadline cut 25 of 46 head
batches in the assessment's run. That left the last one or two stand-ins at quarter resolution for the rest of
the transition and the cross-fade, while the cover stayed up another 300–500 ms.

## Implementation

**The capturer films in request order; `CaptureService` chooses the order.** `grab` takes `[CGWindowID]` and
looks each up in the content read. `CaptureService.capture` puts the windows no stand-in answers for first, in
scope order, and the stood-in ones after them. Cover z-order is untouched, because it comes from the session's
window list and not from the request. This is the "separate capture order rather than a re-sort" that change
`1785306827` named and left open.

**A batch the deadline settles keeps a `Trailing` record until its capturer reports `done`.** A window still
that lands then is recorded, pinned to the cover if the cover is live, and sends `captureRefreshed` for a
stand-in. A late base is dropped. Its batch either had one already or abandoned the cover without it.
`1785306827` had decided to drop late pieces, on the grounds that a deadline expiry "already means something is
badly wrong". On a 5K display it is ordinary, so that rationale no longer holds.

**Entitlement now also needs the cover to be open (`isLive`).** Before, it needed only the generation to match.
Without this, a still landing after `closeCover` (in the cross-fade, or after `discard`) would be pinned at full
resolution to a cover that no longer exists, and nothing would release it until the next head batch on that
display. For a pending head batch this changes nothing, because its cover is open by construction. Two tests that
asserted a late still is "not adopted" by a cover still up now assert the opposite. They were written to the
decision this change reverses.

**The deadline is 0.4 s, up from 0.25.** Re-measured with per-shot timing in `grab`, on the Studio Display XDR
(5120×2880 backing):

| piece | measured | median |
| --- | --- | --- |
| `SCShareableContent` | 16–38 ms | ~23 |
| base, 5120×2880 | 27–50 ms | ~38 |
| window, 1172×976 px | 28–51 ms | |
| window, 2500×2748 px | 40–57 ms | ~50 |
| window, 3830×2748 px | 65–68 ms | |

The old figure was ~10 ms a capture, and the SCK header's was ~25 ms "whatever its size". Pixel size does enter
at this resolution. A four-window batch is 23 + 38 + 4×50 ≈ 260 ms, so under the default `exact` every strip of
four or more lost its last window to the deadline: a hole in the cover for the whole transition. 0.4 s bounds
about six windows. It adds latency only to batches that would otherwise have been cut, because a batch that
lands sooner opens its gate sooner. Under `immediate` the deadline now matters only for windows without a
stand-in, and those are filmed first.

**Validated live** with the release daemon, `immediate`, on 4–6 windows (TextEdit ×3, Finder ×2, Ghostty,
Chrome):

- Ordering. An arrival filmed `[8222 (new), 8084, 8210, 8220]` and raised at 118 ms (content 21 + base 39 +
  57). A `cycle-width` filmed the resized window first and raised at 100 ms.
- Late refreshes. A six-window batch hit `DEADLINE` at 253 ms, and `captureRefreshed` followed at 273, 307 and
  355 ms, each a `refreshLayer` on the live cover. Before this change those three layers stayed reduced.

## Observations

- **Boot is not fixed by this.** A scan is one batch per window, all flushed in one turn, and `SCKCapturer.run`
  starts each as its own `Task`. They overlap. At boot seven batches ran concurrently, every still took
  ~140 ms, and the head batch's window landed after its deadline. The first transition then raised without
  it, a hole, because it had no stand-in to refresh. The fix is ordering *across* the turn's batches, for
  example running them sequentially with the opening batch first. That is new mechanism, not policy.
- **The serialization claim deserves a re-test at 5K.** Those seven overlapped batches finished, base
  included, within ~236 ms. Run serially that would be ~400 ms. The SCK header's "overlapping hides nothing"
  was measured at smaller sizes, and the trade may differ when each still costs ~50 ms.
- A window acked by the deadline with no pixels and no stand-in still has no layer: `refreshLayer` repaints only
  existing layers. Building a layer from a late still would need `extendCover`'s path for a window that is
  already bound. Not attempted.
- Not measured: a cover on two displays at once, and the `exact` mode run live. The `exact` arithmetic above
  is from the per-shot timings, not from a traced `exact` session.
