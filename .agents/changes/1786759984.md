# Floating the small window an app opens beside the one you were working in

> Change `1786759984` — 14 August 2026

## Goal

A "go to line" prompt, a find sheet, a rename box — a window an app opens tiny because tiny is what it
is for. emira tiled it: the column took `width-presets[0]` and the prompt was inflated to a third of the
screen while the window that spawned it was pushed aside. Nothing emira can read identifies a dialog —
plenty of them arrive as `AXStandardWindow` — so no predicate over the window alone could name them.

The signal is the frame the window opens at, **read against the window that had focus**. Not because
size identifies a dialog, but because the ratio measures how violently the window would have to be
distorted to tile it. A window that opens at 400×120 and is given 853×1440 has been transformed into
something its app never asked for; a second project window that opens at 1100×900 and is given the same
has barely been touched.

## Implementation

Two matchers on `WindowRule`, `smaller-than-focused` and `from-focused-app`, AND'd with the existing
four and with each other. Matchers rather than a `[general]` setting so that scoping, precedence and the
merge come for free: `app-id` narrows the same rule to one app, a later rule overrides an earlier one
field by field, and `float` stays the one action, written through the path `Command.float` already
writes. `hasMatcher` counts them, so a rule carrying only these is legal rather than refused as a
match-everything wildcard.

**`WindowArrival` is what a rule is now shown**, replacing the `bundleId`/`title` pair on both
`WindowRule.matches` and `WindowRules.outcome`. Four bare parameters was the alternative and it costs
more than it looks: the anchor is optional and the two facts inside it (bundle id, frame) have to travel
together or not at all, which is a type rather than a convention. It also gives the subtlest part of the
change one documented home — what an anchor is, and the two places there isn't one. It is the pair to
`RuleOutcome`: what the rules are shown, and what they decided.

**An arrival has two anchors, and `World` grows a field for the second.** `stripAnchor` answers "which
column does this open beside" and insists on a column, because `insertingAfter:` has nothing to do with a
window that isn't in one. `arrivalAnchor` answers "what did this window open out of", and that question
needs a window on screen and nothing more — so a float and a native full-screen window are anchors, even
though nothing opens beside either.

Live focus cannot answer it. It is `nil` at exactly this moment, and not occasionally: `AXWindowCreated`
delivers `.windowAppeared(pid)` and the snapshot only arrives when the re-scan returns, while the app's
own focus notification resolves through an unbound element to `nil` in between. Every arrival watched on
a live desktop read `focus=nil`, so a `focusedWindow ?? stripAnchor` anchor *is* `stripAnchor`, and
`World.setFocus` records `lastStripFocus` only for strip participants — leaving a prompt from a
full-screen editor, or from a window floated by hand, measured against a window the user left behind or
against nothing at all. Watched: the prompt out of a floated parent read `anchor=nil` and took a column.
It also made the two config keys lie, since neither anchor is the focused window in those states.

So `World.lastFocus`: the last window focus rested on, whatever kind it was, which is `lastStripFocus`
with the one constraint that belongs to placement removed. The anchor's *frame* is live truth
(`windowFrameChanged` keeps it in step with AX), so the ratio is against the window as it is on screen,
not as it first appeared.

Widening it costs one thing: the anchor can now be something small — a popover, a sheet, another prompt.
That direction fails closed. A small window against a small anchor is not a small *ratio*, so the rule
does not fire, which is the same silence every other abstention here produces.

**Both dimensions, not area.** A window that is short but full-width, or narrow but full-height, is a
shape the strip can hold; only something small in both directions is a window a column would have to
invent size for. **`from-focused-app` exists because a float is not placed** and a foreign window is
never re-levelled, so floating a surprise window from a background app can leave it stuck behind a tiled
one with no way to raise it.

**No anchor fails the rule rather than abstaining**, which is the one place these two behave unlike the
other four. An unset matcher says nothing because the author said nothing; a set one with nothing to
read has been asked a question that has no answer, and the safe answer is not to float. That covers the
first window on a workspace and, deliberately, every window the launch scan adopted: at boot the anchor
would be whichever window the scan reached first, so the comparison would be against noise.
This keeps the asymmetry `PRINCIPLES.md` already states — emira sorting a desktop nobody asked it to
sort assumes as little as it can.

The fraction is read with the same bounded-number reader everything else uses, `greaterThan: 0`. No
upper bound: a value at or over 1 says something unusual but not nothing, and `number` has no `atMost`
to express one without a new parameter on a shared reader.

`0.2` is what the example file carries. A ~400×120 prompt against a full-screen 2560×1440 window is
0.156 × 0.083 and floats; the same prompt against a ⅓-width column (853×1440) is 0.47 × 0.083 — the
width fails and it tiles, which is the right answer, since with that much screen unclaimed a column
beside the window costs nothing.

## Observations

**The anchor is the focused window, not the window that spawned the arrival.** AX offers no parent link
for a standard window, and focus is the best stand-in — it is wrong only when an app opens a small window
while a *different* window of the same app holds focus, where the ratio is read against the wrong sibling.
Both windows are the same app's, so `from-focused-app` still holds and only the scale is off.

**The threshold does not catch a large modal, and should not.** IntelliJ's Settings dialog opens around
1000×700; against a full-screen 2560×1440 editor that is roughly 0.4 × 0.5, and it tiles. Catching it
needs about 0.55, which also catches a second project window. Large modals want a `title` or
`title-regex` rule, which is what those matchers are for.

**The settings window has no rules editor**, so the two keys reach a user through `emira.example.toml`
and through the documentation the `window-rules` bespoke surface carries. `window-rules` is on
`BespokeEditors.notEditable` because file order is precedence and `ConfigDocument` splices single values
rather than moving blocks; nothing here changes that.

**`from-focused-app = false` is representable and reaches only unit tests.** It reads as "a surprise
window from a background app", which is a real thing to write a rule about, but no rule anyone has run
uses it and it has not been watched on a desktop.

**`0.2` cannot fire against a tiled anchor on a wide display.** The ladder's widest rung is ⅔, so on a
2560-point display the largest column an anchor can be is 1706 and a matching prompt has to open under
341 × 288. A 400-wide prompt is 0.23 there and 0.47 against the ⅓ rung it usually opens beside — both
tile, which was watched. The number is written for a *full-width* anchor: a `width-presets = [1.0]`
desktop, a window floated at its natural size, a full-screen editor. A default-ladder desktop that wants
this wants something nearer 0.5, and 0.5 against a ⅓ column also catches a second project window — so
the honest reading is that the ratio is a good signal only where the anchor is not already a narrow
column.

**A window that goes full screen after emira adopted it keeps `role: standard`.** Roles are read once, at
adoption, so such a window stays in its column and anchors as an ordinary window (correctly — it is one).
Only a window already full screen when the scan reaches it is adopted `.other`, which was confirmed on a
live desktop; that is the window `lastFocus` is there to keep as an anchor.

**Watched on a live desktop**, with the daemon on this branch and an app opening standard windows at
controlled sizes: a 400×152 prompt out of a 1600-wide parent floats at the frame its app opened it at,
and the parent keeps its column and its width; a 1100×932 second window takes a column; the same prompt
from a background app takes a column; and the same prompt out of a parent floated by hand floats, where
before the anchor read `nil` and it tiled. What is still untested by eye: the full-screen anchor end to
end (the fixture never produced a focus report on the full-screen window, and the launch scan's own
adoption is `wasAlreadyOpen`), and `from-focused-app = false`.
