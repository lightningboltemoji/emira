# Focus on a window not yet bound lands on it when it binds

> Change `1793164263` — 2026-10-27

## Goal

One IntelliJ prompt in six left the core focused on nothing while the prompt held the keyboard. A window that
takes focus as it opens is reported before any scan has bound it — `AXFocusedWindowChanged` naming an element
the registry does not know — and the read that was meant to ask again once the arrival binds can time out
against a JVM, which is "nothing at all, never nil" by design. Keyboard verbs that act on the focused window
(`close-window`, `move-to-workspace`) then did nothing.

## Implementation

The report already had the answer in hand: the element. `WorldObservation.focusMovedUnmanaged` carries it
(defaulted, so the tests that build the case without one are unchanged), and the watcher keeps the newest
(`unboundFocus`) — replaced by the next such report, dropped by any report naming a managed window, by an
activation, or by a read that answered with one. When a scan binds a window to that element, that window is the
focus, passed through `resolveFocus` like any report. The read stays behind it for the case the element is not
a window at all, a sheet.

## Observations

Four IntelliJ prompts in a row: `focusChanged(prompt, system)` 3 ms after each `windowCreated` — faster than
any read could have answered. The test that pins it fails with the path disabled.
