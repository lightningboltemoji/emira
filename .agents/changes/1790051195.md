# A corner radius survives the part of a window its app never painted

> Change `1790051195` — 2026-09-21

## Goal

Zoom's stand-in has been taking a visibly wrong silhouette under `crop`, and the cause is one probe
making an assumption a strip can break.

`measuredCornerRadius` reads the top-left `96 pt` block and treats every transparent pixel in it as
corner. That holds for a window whose capture is transparent only outside its own rounding. It stops
holding the moment a still is transparent for some other reason — and a window hanging off the side of
the display is exactly that case for an app that rasterizes only what is on screen. The block then
carries a full-height band of nothing, and the area inverts to a corner that was never there:

| unpainted at the left edge | reported radius (true answer 17.1 pt) |
| --- | --- |
| 0 pt | 17.1 pt |
| 1 pt | 25.9 pt |
| 2 pt | 32.7 pt |
| 4 pt | 43.6 pt |
| 8 pt and beyond | `nil` → the caller's fallback |

Both halves are silent. Under 8 pt the answer is a plausible radius and the silhouette is simply too
round; past it the measurement refuses and every such window draws at `Scrims.fallbackCornerRadius`,
which is a floor and not that window's rounding. On a strip with a column wider than the gap between
them, one of the two windows is hanging off an edge at all times, so the wrong answer is the resting
state rather than a transient.

The capture plane is not what is losing the pixels. Measured with `SCContentFilter(desktopIndependentWindow:)`
at up to 70% off-display, against a plain `CALayer`-backed window, a `CAMetalLayer` one (Ghostty), a
WebKit one (Safari) and Zoom's own: the image comes back at the full requested size with alpha 1.00
across all twenty column bands, and `SCWindow.frame` and `SCContentFilter.contentRect` both report the
whole rect including a negative `x`. The window server hands over what the surface holds. What is
missing is what the app never put there.

## Implementation

**Two probes, the top-left and the top-right, and the lesser answer wins.** The strip scrolls
horizontally, so a window hangs off the left or the right and not both at once, which makes two corners
the whole of the candidate set. And the error has a sign: transparency the probe did not ask about can
only *add* to the alpha deficit, so a contaminated corner reads too big and never too small. That is
what licenses `min` rather than a threshold on how much of a block a corner is allowed to be — one
honest corner carries the answer on its own, and the other needs no diagnosis, only to lose.

`compactMap` before `min` is load-bearing in the wide case: past ~8 pt of unpainted window the block
trips the existing `radius <= probe / 2` bound and answers `nil`, and dropping it is what lets the
painted side answer alone.

**The measurement is unchanged** — same block size, same `r²(1 − π/4)` inversion, same bound. It moves
into a private helper taking the image's `x` offset, `0` for the left corner and `probe − width` for the
right; the `y` offset, and the bottom-left-origin reasoning under it, stay exactly as they were, so the
suite's existing guard against reading the bottom corner keeps its teeth.

**Rejected: cropping the block out of the image first.** It reads better — the corner becomes a crop
rect, the draw is always `(0, 0, probe, probe)`, and the flip argument disappears because a block's
total deficit does not care which way up it was drawn. It is also 10× slower, because `CGImage.cropping`
copies: 0.146 ms a corner against 0.014 ms for the offset draw, on a 2556×2090 still. Both routes were
checked to produce the same deficit before the cheaper one was kept.

**Rejected: all four corners.** The two extra buy nothing — an unpainted band runs the window's full
height, so it contaminates a side's corners together — and the bottom pair is where the offset draw gets
expensive: four corners cost 2.219 ms against 0.028 ms for the top two.

Both probes together are 0.028 ms, against ~25 ms for the capture they are measuring.

## Observations

**A column too wide for the viewport is not served.** It hangs off both edges, no reveal brings one
whole into view, and with both corners contaminated there is nothing honest left to take the minimum
of — the answer inflates exactly as one probe's did. `unpaintedEdgesNeverUnderReport` pins what still
holds there: the answer may inflate or refuse, never shrink.

**The radius is the visible half of something larger, and this change does not touch the other half.**
The same unpainted band is in the stand-in's own pixels, so a window filmed while hanging off the
display animates across the screen with that band empty — the `crop` wash where its content should be —
until the cross-fade lands on a real window that has since painted itself. What would fix that is a
rule in `SurfaceCache`: it orders every write by `mint` alone, so the newest film always wins, and a
newer film with a hole in it should lose to a held film without one. The detector is cheap — a 20×4
resampled alpha scan is 0.004 ms and reads 0.00 in the unpainted bands against 1.00 everywhere else,
where a whole-image scan would be 7.3 ms — but the ordering rule is the file's spine, so it is a
decision and not a tidy-up. Not attempted here.

The film schedule already holds what such a rule would need: a window is filmed at the *head* of each
transition it is scoped into, which is the resting state the previous one ended in, so bouncing focus
between two columns films each of them complete on the transition that takes focus away from it, one
transition before the incomplete film. An end-of-transition capture would be the same photograph of the
same resting state, one cross-fade earlier, at ~25 ms a window of window-server time spent while the
cross-fade lands.

**The Zoom case itself was not reproduced here.** The machine it happens on cannot be instrumented, and
four apps' captures on this one all come back whole — including Zoom's own, whose renderer evidently
paints the whole window for the login sheet it shows when signed out. The synthetic images stand in
their own right: whatever leaves a band of a still transparent, the old probe read it as corner and this
one does not.
