# A window back from full screen is the width it left

> Change `1795405786` — 2026-11-22

## Goal

Reported: a strip of `[100%, 25%, 75%]` with Safari last, a YouTube video taken full screen and back, and
Safari returns at about 40%. Two defects produce that one symptom.

**Coming back started a new column.** Entering native full screen is a departure (`departFromLayout`), which
destroys the column, and leaving is an arrival (`arriveOnLayout`) into a fresh column on the ladder's first
rung. Whatever width the column had was gone. This is deterministic for any window that goes full screen
itself — ⌃⌘F, the green button.

**WebKit's player could be missed entirely.** Safari's element full screen does not put the browser window into
full screen. It makes a second window at the display's size, and that window enters full screen without
changing its frame. emira adopts it as a tile and writes a column frame to it. The only report the full-screen
check ever saw was WebKit moving the window back after that write, so detection depended on emira's write
landing before the transition finished. When the transition won, the write was refused, its move reports were
dropped as echoes (`FrameWrites`), and the landing that read back the display-sized frame was never asked.
The player then stayed a tile. emira re-placed it, was refused, and re-placed it again for as long as the
video ran, the write storm `1793164261` fixed. Worse, the watcher never knew the app had a window in full screen, so
`isElsewhere` did not cover the browser window: once AX described only the player's Space, the browser
window was retired, and on exit it was re-adopted under a new id at whatever width adoption gave it.

## Implementation

**The width is remembered by the container that owns membership.** `Workspaces.reconcile` takes an `away` set,
the windows that left every strip and are coming back. A window leaving for it has its column recorded in
`awayColumns` before the removal, and a newcomer with an entry adopts `like:` that column. That is the rule
`Workspaces.move` already uses to carry width across workspaces, so a fullscreen column returns as `.plain`
of its origin and a grown one as its override. Entries are pruned to `away` on every reconcile: one is read
once and gone, and a window that closes while away leaves nothing behind. Height intent survives being away
for the same reason. `Layout.adopt` now takes its source per newcomer, which is what lets one reconcile
admit a returning window and a new one together. `State.reconcileTiling` passes `World.fullScreen` as `away`.

Rejected: keeping the window in its column while in full screen. Every reader of a layout would have to learn
that a member can be absent, which is a larger change than the bug. Rejected: recording in the
`windowFullScreen` handlers. Pruning on close would then be another site to remember, where `reconcile`
already maintains `lastFocus` and heights against membership.

**Minimize and ⌘H are not away**, and come back on the ladder as before. Whether they should is a product
question this change does not answer. The height comment in `reconcile` already names minimize as a
departure that drops intent.

**Every frame the watcher learns asks the full-screen question.** `checkFullScreen` was called only from a
frame read caused by a move report. It now also runs on each write's landing (`FrameWrites.onLanded`, wired
in `main.swift` to `WorldWatcher.landed`) and on each adoption, after the `windowCreated` it qualifies. The
guard is unchanged: only a frame filling a display, or one of a window already in full screen, costs the AX
read. The adoption check covers a window that is already full screen when a scan first describes it. That
window classifies as `.other`, is never written, and so has no landing to read either. Rejected: observing
`NSWorkspace.activeSpaceDidChangeNotification`. It is the edge macOS does announce, but it names no window,
and the frames already on hand do.

## Observations

Verified in a Tart VM (macOS 27.2, Safari, 1760 pt display, the reporter's gaps and `[½, ⅔]` ladder) on release
builds, against a baseline built from `HEAD`. The strip was `[100%, 27%, 76%]`, read through `emira debug` and
`EMIRA_TRACE`.

- ⌃⌘F on Safari: the baseline returned it at 850 pt (½) every time. Fixed: 1294 pt (76%), 3 of 3, same id and
  same place.
- Element full screen in the VM, no interference: both builds were correct in 10 of 10 rounds. emira's write
  landed about 300 ms after adoption, and the transition about 250 ms after that.
- The first cold round of the session, on the baseline, went wrong. The player stood tiled at 1720 pt, a
  size correction learned from a refused write. Safari returned as a new id at 850 pt.
- To force that ordering, a diagnostic-only build delayed every write by 1 s. Baseline: the player tiled in
  4 of 4 rounds. With a 20 s stay the browser window was retired mid-video and came back as a new id.
  Fixed: the first landing produced `windowFullScreen(true)` 0.6 ms later, in 6 of 6 rounds plus 2 of 2 with
  20 s stays. One already-queued write is still refused before the loop stops.

The reporter's real hardware was not tested. That a fast GPU makes the transition win the race is an inference
from the VM's timings and the cold-run failure.

Position is not remembered. A middle column that goes full screen comes back one place to the right, because
the arrival inserts after `lastTiledFocus` and the departure moved that to the column that took its place. The
baseline does the same. A window adopted already in full screen stays `.other` after it leaves, which was
also true before.
