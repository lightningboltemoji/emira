# A window the list cannot see is one we ask about forever

> Change `1788835822` — 2026-09-07

## Goal

Reported from IntelliJ: open a file picker out of a dialog — Project Structure, the browse icon beside
Compiler output — and the picker takes key, flashes its buttons blue, then goes grey. Clicking it does
the same thing again. Focus lands back on the dialog behind it, every time.

emira caused it, which the A/B settles rather than argues: with the daemon killed the picker's Open
button is blue and stays blue; with it running the same button is grey within a frame. And the reduce
trace shows emira emitting **no effects at all** through the whole sequence — no `focus`, no `raise`,
no `restoreFocus` — with the focus reports arriving as `origin: .system`, so it is not emira's own
write echoing back either. Whatever emira was doing, it was doing below the effect layer.

An `AXUIElementSetAttributeValue`/`PerformAction` trace at the AX boundary answers it. emira performs
**zero** AX writes here and one read, over and over:

```
focusChanged(nil)                      picker takes key; unbound, so it reads as "focus left"
AX READ AXWindows pid=10590            +0.7 ms
focusChanged(#3)                       +18 ms — key is back on the dialog
AX READ AXWindows pid=10590
AX READ AXWindows pid=10590   … once a second, forever
```

`kAXWindowsAttribute` on the IntelliJ application element is what knocks key off the panel. The panel
lives in `com.apple.appkit.xpc.openAndSavePanelService` and is only proxied into the app's AX tree, and
this app answers the enumeration by re-asserting its own window.

The read repeats because the picker cannot be bound:

```
scan gave up: 2/3 windows bound across 1 apps; unbound: com.jetbrains.intellij.ce "Select Path" (noCandidate)
```

`WindowListEntry.current()` admitted `kCGWindowLayer == 0` only, and an open/save panel is presented at
the modal-panel level, 8. The window server lists it under the app's own pid, on screen, at the frame AX
reports — a clean unique match, filtered out before the join ever saw it. So the scan was permanently
incomplete, "every on-screen window is managed" was unsatisfiable, and the heartbeat did what it is
built to do: ask again every interval for as long as the app lives. Each ask was another read, and each
read another bounce.

## Implementation

`WindowListEntry.windowLevels` is the level set the list is read at: `0...CGWindowLevelForKey(.modalPanelWindow)`,
which is normal, floating and modal panel. Dock (20), main menu (24), status bar (25) and pop-up menu
(101) stay out.

**Widening is the safe direction, which is why it is a range and not a special case for panels.** The
join's invariant is that a match must be unique in both directions, so an extra candidate can only ever
turn a match into a rejection — and the file already argues that a rejection is visible and recoverable
where a mis-bind is permanent and invisible. The two entries at the picker's frame are a live example:
one owned by IntelliJ, one by the panel service, and `byPid` separates them before uniqueness is even
asked.

**The picker binds as a `.dialog`** (`AXDialog`, `AXModal`), so the taxonomy floats it: emira records it,
never places it, and never hoists it — `isFloatedByChoice` is false. Confirmed against the running
daemon rather than assumed, since binding a picker that classified as `.standard` would tile a file
chooser into the strip, which is worse than the bug.

Rejected: bounding the re-ask. Cheaper, and it treats the heartbeat's unbounded repair as the defect
when the repair is deliberate — a window that cannot bind now may bind later, and giving up strands it
forever. The incompleteness was the defect; with the picker bound there is nothing left to repair, and
the read loop stops on its own.

Measured after the change, with the picker open: `scan gave up` count zero, `READ AXWindows` steady at
9 over ten seconds where it had been one a second without end, `World.focusedWindow` resting on the
picker, and the Open button blue.

## Observations

The read's effect on the app is a fact about `kAXWindowsAttribute` and this toolkit, not about the
level filter — anything else that leaves a scan incomplete for a live app will reproduce it. What is
fixed here is the one cause that was making it happen every second.

The stale `focusChanged(nil)` from change `1788833969` is still present and still unrepaired: the
picker's first focus report resolves against a registry that has not bound it yet, so the core sees
`nil` before it sees the arrival. It now settles — the next report names the picker and focus rests
there — but the sequence still passes through a moment where emira believes nothing is focused.
`WorldWatcher.readFocus(of:)` after a scan binds new windows is still the repair with the least new
machinery.
