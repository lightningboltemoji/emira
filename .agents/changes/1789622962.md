# Lift the veil while a window is in the hand

> Change `1789622962` — 2026-09-16

## Goal

A float over an unfocused window cuts a hole in that window's veil, and the hole stays put while the float
moves. Drag the float and the hole stays where it was picked up. Shrink it and the hole is left bigger than the
window. The mask is cut against the window server's stacking once per `setScrims` (or `restack`). Dragging a
focused float changes no binding, so the core never emits a new set and nothing repaints until something
unrelated does.

## Implementation

**The veil is lifted, not tracked.** `State.scrimBindings` returns nothing while `Drag.subject` is set, so the
scrim fades out as the window starts moving and fades back in at `dragEnded`. Tracking was rejected at the
user's request, and it would be expensive anyway: a window list and a display-sized mask per frame report, and
the hole would still trail the window by an AX round trip wherever it crossed another window.

**The set-down is the trap, and `dragEnded` is what avoids it.** The returning set is usually identical to the
one that was lifted, because the windows underneath did not move. Only the stacking moved, and `Scrims.apply`
reads that fresh on every `setScrims`, so the mask is recut against where the float is now. The mouse-up would
be too early. An app is still draining a resize when the button comes up, and `WorldWatcher.beginSettle` holds
`dragEnded` until the frame reports go quiet. The lift and the set-down are both "a veil that moved", so both
fade (`Scrims.drawn` goes from `[:]` to the set, and back). By the set-down the fade-out has cleared
`ScrimWindow.cut`, so the new mask is painted before the window fades back in, never dissolved from the old one.

**`Drag.subject` now latches any on-screen window, and the adoption gates moved to `adoptDraggedSize`.** Before
this change the latch refused a window that does not tile, and refused everything under
`interactive-resize = false`. Both are questions about adoption, not about the hand. The veil needs the plain
fact, so `driftedUnderHand` keeps only its three impostor checks (button down, nothing latched yet, actually
moved), and `adoptDraggedSize` now checks `interactiveResize` and `participatesInTiling`. The alternative was a
second latch, or a `Drag` case for "moved but not adoptable". That puts two records of one fact side by side
and splits `isArmed` between them. Two tests in `EngineHandResizeTests` stated the old gate and now state the
new one: a float is latched but adopts nothing, and the setting refuses at adoption.

Tests: `ScrimTests` covers the lift, the hold through `dragReleased` and the frames still draining, the set-down
at `dragEnded`, a click that moves nothing, and a tiled window with `interactive-resize` off. `ScrimPlaneTests`
checks that the returning set is cut against the moved stacking. The three core tests that lift or set down the
veil fail with the guard removed.

## Observations

Not yet checked live. The report and the reasoning come from the user, who is checking it on a real desktop.

**The lift fades, so the stale hole shows for `ScrimWindow.fadeDuration` (0.12 s)** as the veil goes. It fades
with everything else rather than standing still, but a fast drag can show it trailing for those frames. A cut on
the lift is a one-line change in `Scrims.apply` if that reads better.

**A hand resize that re-tiles its neighbours sets the veil down early for them.** `dragEnded` adopts the size,
and `reassertTruthPlane` writes the neighbours with no cover over them. The `setScrims` in the same batch is cut
before those AX sets land, and an uncovered placement is never restacked afterwards. Where a neighbour's new
frame overlaps where another window still stands, the overlap can be stamped opaque until the next set. This
predates the change: the same set was emitted at `dragEnded` before. It applies to any uncovered placement,
not just this one.

**A window emira does not manage is never latched**, because nothing reports its frames. Dragging one still
leaves its hole behind.

**The wider latch has two small side effects.** A float or pin that moves first under a press now takes the
latch, and a tiled window moving later in that press is not adopted. Per the latch's own rule, the second
mover is being pushed. Also, any managed window whose frame report under a press differs from `World` now lifts
the veil until the release, where before only a tiled one could latch, and only with `interactive-resize` on.
