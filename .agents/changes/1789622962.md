# Lift the veil while a window is in the hand

> Change `1789622962` — 2026-09-16

## Goal

A float over an unfocused window cuts a hole in that window's veil, and the hole stays put while the float
moves. Drag the float and the hole stays where it was picked up. Shrink it and the hole is left bigger than the
window. The mask is cut against the window server's stacking once per `setScrims` (or `restack`). Dragging a
focused float changes no binding, so the core never emits a new set and nothing repaints until something
unrelated does.

## Implementation

**The veil is lifted, not tracked.** `State.scrimBindings` returns nothing while `Drag.subject` is set, so the
scrim comes off as the window starts moving and fades back in at `dragEnded`. Tracking was rejected at the
user's request, and it would be expensive anyway: a window list and a display-sized mask per frame report, and
the hole would still trail the window by an AX round trip wherever it crossed another window.

**The lift is a cut, and the core marks it.** Checked live, a faded lift still showed the old holes for a frame
or two: the dissolve and the alpha fade both run for `ScrimWindow.fadeDuration`, so the stale mask stays on the
glass while it goes. `Effect.setScrims` now carries `lifted`, set by `settleScrims` while `Drag.subject` is
set. `Scrims.apply` calls `ScrimSurface.lift()` for a display a lifted set leaves empty. `ScrimWindow.lift`
clears the mask and drops the window's alpha to 0 through a zero-duration animator write, which replaces a fade
still in flight, the same way `HoistPanel.setAlpha` does. Nothing is rasterized on the way out. A display the
set still veils (a capture head's hold) takes the ordinary path. The flag lives in the core because the plane
cannot tell the cases apart: an empty set looks the same whether a hand emptied it or focus landed on the last
veiled window, and that second case should still fade. Rejected: a plane-local rule to cut whenever the stacking
has moved since the last paint. It would reach the lift without the core's help, but whether a focus change
faded would then depend on whatever else happened to move on the desktop in between.

**Coming on is the focus change's dissolve, and the window's alpha is only a gate.** The user reported that the
return after a strip resize looks nothing like the veil moving on a focus change, although both were 0.12 s. They
were different mechanisms. A focus change between columns already on the glass dissolves the mask's
`contents`. A scrim coming on faded its window's `alphaValue` through `NSAnimationContext`. A probe window,
sampled every 4 ms, showed AppKit stepping that alpha on the main thread at 60 Hz along a front-loaded curve:
0.41 at 17 ms, 0.66, 0.83, 0.92, 0.98, 1.0 at 100 ms. Stalling the main thread for 80 ms delayed the whole fade
by 90 ms. Next to a linear dissolve drawn by the render server, that reads as a cut. `ScrimWindow.present` now
flips the window's alpha at once and makes every visible change a dissolve: on from `ScrimWindow.empty` (a 1×1
clear image stretched over the display), off to a mask with nothing see-through, with the gate closing in the
dissolve's `CATransaction` completion. Two Core Animation facts were checked by rendering offscreen with
`CARenderer` rather than assumed. A mask layer with no contents shows nothing, so `lift` cannot flash the
unmasked photograph. A `contents` animation from `nil` is a cut, while one from the 1×1 clear image ramps
linearly (0, 38, 77, 115, 153 of 153 at 0, 30, 60, 90, 120 ms). The first fact is also why a scrim coming back
from no mask never dissolved before this change. `ScrimWindow` has no unit tests: none of the shell tests
build a real window, and the behaviour it depends on is the Core Animation behaviour above.

The work before the cut was measured, not assumed. On the development display (3420×2214), the window list
`apply` still reads takes about 0.5 ms (median), and a full mask takes 1.8 ms. Neither is a frame, so the
window list is still read up front rather than restructured around. What is left between a hand and a lift is
the AX notification plus one frame read on the app's lane, before the core can tell the report from an echo.

**The set-down is the trap, and `dragEnded` is what avoids it.** The returning set is usually identical to the
one that was lifted, because the windows underneath did not move. Only the stacking moved, and `Scrims.apply`
reads that fresh on every `setScrims`, so the mask is recut against where the float is now. The mouse-up would
be too early. An app is still draining a resize when the button comes up, and `WorldWatcher.beginSettle` holds
`dragEnded` until the frame reports go quiet. The set-down is an ordinary set and fades in. The lift records
the display as drawing nothing (`Scrims.drawn[monitor] = [:]`), which is what makes it an event, and it left
`ScrimWindow.cut` empty, so the new mask is painted before the window fades in, never dissolved from the old
one.

**`Drag.subject` now latches any on-screen window, and the adoption gates moved to `adoptDraggedSize`.** Before
this change the latch refused a window that does not tile, and refused everything under
`interactive-resize = false`. Both are questions about adoption, not about the hand. The veil needs the plain
fact, so `driftedUnderHand` keeps only its three impostor checks (button down, nothing latched yet, actually
moved), and `adoptDraggedSize` now checks `interactiveResize` and `participatesInTiling`. The alternative was a
second latch, or a `Drag` case for "moved but not adoptable". That puts two records of one fact side by side
and splits `isArmed` between them. Two tests in `EngineHandResizeTests` stated the old gate and now state the
new one: a float is latched but adopts nothing, and the setting refuses at adoption.

Tests: `ScrimTests` covers the lift (marked `lifted`), the hold through `dragReleased` and the frames still
draining, the set-down at `dragEnded` (not marked), a click that moves nothing, and a tiled window with
`interactive-resize` off. `ScrimPlaneTests` covers: a lifted set lifts the surface without painting a mask; an
empty set with no hand still dissolves; a display that still holds a set is not lifted; and the returning set
is cut against the moved stacking. The three core tests that lift or set down the veil fail with the core guard
removed, and two of the plane tests fail with the lift path in `Scrims.apply` removed.

## Observations

The user checked the first version live (lift and return both fading). They found the return after a strip
resize visibly unlike a focus change, which is what led to the gate. Neither the cut lift nor the dissolve-in
has been checked live yet.

The user also reported floats fading at both ends and strip windows at neither. The return took the same
window-alpha fade for both kinds, and nothing in this change branches on a window's kind. So whether that
difference survives the dissolve-in is for the next live check. Candidates outside the scrim remain. At release,
a strip window re-places instantly in the batch that brings the veil back. A float floated by choice gets a
hoist picture that appears at once when a strip window moves in front of it (`HoistPanels`).

**Two other planes fade a window's alpha the same way.** The cover's exit (`Overlay.fadeOut`, 0.22 s under
`smooth`) and `HoistPanel.conceal` (0.12 s) are stepped by AppKit on the main thread at 60 Hz along that same
front-loaded curve. This change leaves both as they are.

**A hand resize that re-tiles its neighbours sets the veil down early for them.** `dragEnded` adopts the size,
and `reassertTruthPlane` writes the neighbours with no cover over them. The `setScrims` in the same batch is cut
before those AX sets land, and an uncovered placement is never restacked afterwards. Where a neighbour's new
frame overlaps where another window still stands, the overlap can be stamped opaque until the next set. This
predates the change: the same set was emitted at `dragEnded` before. It applies to any uncovered placement,
not just this one.

**A window emira does not manage is never latched**, because nothing reports its frames. Dragging one still
leaves its hole behind.

**The wider latch has two small side effects.** A float or pin that moves first under a press now takes the
latch, and a tiled window moving later in that press is not adopted. Per the latch's own rule, the second
mover is being pushed. Also, any managed window whose frame report under a press differs from `World` now lifts
the veil until the release, where before only a tiled one could latch, and only with `interactive-resize` on.
