# `grow` and `shrink`

> Change `1785056899` — 2026-07-26

## Goal

`cycle-width` can only reach the rungs a config declares, so there is no way to resize a column by an
arbitrary amount. Add two verbs taking an explicit delta: `emira grow 100px`, `emira shrink 10%`.

## Implementation

Both route through `Engine.resizeFocusedColumn`, the body `cycle-width` already uses — the animated
column width, the transition opened over a viewport that never moves, the two-geometry scope, the
no-cover degradation. The verbs differ only in a closure writing the new width intent. No new `Effect`,
`Event` or subsystem, and nothing downstream of `Layout.resolvedWidth` changed, so the truth plane, the
sweep, the scroll targets and the presentation plane picked it up together.

- **A percentage is of the working area, not of the column's current width.** Compounding drifts the
  step size with each press, and `grow 10%` followed by `shrink 10%` lands 1% short (0.9 × 1.1 = 0.99).
  Against the working width the steps are uniform, the verbs are exact inverses, and the unit matches
  the ⅓/½/⅔ presets.
- **The intent is stored in the unit it was asked in** (`ColumnLayout.widthOverride: PresetSize?`).
  `grow 10%` leaves a proportion that tracks the monitor; `grow 100px` leaves a fixed point count.
- **The override is a second field beside `widthPreset`, not a case unioned into it.** `cycle-width`
  clears the override and takes the next rung after wherever the ladder was left, so no rule is needed
  for which preset a grown column is nearest.
- **The delta is measured from the column's resolved width, not its stored intent.** From the intent, a
  refused shrink banks invisible presses and the next grows in the other direction do nothing. From the
  resolved width the sequence converges.

## Observations

- The clamp can stop a resize but never reverse one: each bound widens to the current width when the
  column is already outside it, so `grow` on a column a config made wider than the screen is a no-op
  rather than a shrink to fit.
- The floor is a bare constant (`Engine.minimumColumnWidth`) and the only number here not discovered.
  The real lower bound is whatever the app answers; the constant covers apps that accept any size.
- Safari refuses below 574 pt and answers 574 to every request under it, leaving the column holding a
  width no window in it can achieve. Not corrected here.
- Verified in the product: `grow 10%` on an 1800 pt working width walked a column 700 → 880 → 1060, a
  180 pt step each time, with the neighbour moving by what the column gained; two `shrink 10%`s
  returned it to 700.
