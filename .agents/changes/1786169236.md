# The surfaces the table can't describe become a list

> Change `1786169236` — 2026-08-07

## Goal

`ConfigSchema` names three things it deliberately doesn't tabulate — `outer-gap`, `[keys]`,
`[[window-rules]]` — and then leaves every consumer to decide what to do about them by hand. The
generated document placed three named constants; the coverage test spelled three fragments into a
string literal and called itself "the list of what claims a field"; the settings window did nothing at
all. Three hand-placements is not a decision anyone made once, and it showed: **`layout.outer-gap` had
no control in the settings window**, was not on the previous change's Observations, and could only be
found by grepping. The schema's own header claimed all three had editors, present tense, which was
false for all three.

Also: `[springs]` was a tab whose every entry was `advanced`, so it opened on a disclosure triangle and
nothing else.

## Implementation

**`ConfigSchema.bespoke` is the list.** One `Bespoke` per surface, carrying what a consumer needs to
place it: a label, a sentence, a section, the documentation block the example file writes, a sample
fragment that disagrees with the default, and the reason the table cannot hold it. The reason is data
rather than a comment because it is the only question the list provokes.

It is not a `Setting` with holes in it. Each of the three fails a *different* requirement of the table —
one value with five spellings, an open table of invented names, an ordered repeating block — so none
has the `(read, write, default)` triple every entry rests on. What they share is being something a
consumer must place, and that much is a list.

Where a surface goes is one field, `after`, and both surfaces that place one read it: outer gaps follow
`layout.window-gap` in the generated document *and* in the panel, so the three gaps are together in
both. Spelling that twice is exactly how the two orders would come to differ. A surface with no `after`
falls to the end of its table, or opens a header of its own — which is how the coverage test decides
whether its sample needs a header too. The prose blocks moved from `ConfigExample` onto the entries: a
block kept next to the code that prints it is a block that can be printed for a surface the schema no
longer has.

The example file's only diff is the outer-gap block moving up ten lines, which is the move.

**`setOrUnset(_ key:to:)` is `set(_ setting:to:)`'s rule for a key whose default is not a constant.**
An `outer-gap-top` is redundant when it matches the `outer-gap` two lines up, and what it would be
redundant *with* is not knowable from the key: the only way to ask is to remove the line and read
again. That costs one re-parse of a page-long file, which is what every edit through `ConfigDocument`
already costs. A removal the schema won't read is simply not made and the line stays — a `[keys]` entry
is the shape that could do it, since a chord's absence is one fewer binding rather than a default.

**The outer-gap editor writes a per-side key, never the base one.** Writing `outer-gap` would silently
move the three edges the user didn't touch. Reading is off `Config.outerGaps`, so the five spellings are
one value to the control exactly as they are to the reducer. Four edges on one row rather than four
rows: the file spells one value five ways and four rows of "Outer gap top" would say the opposite, as
well as pushing the rest of Layout off the first screen.

**`PanelRow` and `SettingControl` split** because a bespoke editor has no `Setting` to be about. A
`PanelRow` shows a draft; a `SettingControl` is a `PanelRow` that is exactly one setting. `Draft.Edit`
is the other half: two cases, because the two surfaces disagree about what a file should contain, and
one edit path in the window rather than two that have to stay in step across four steps each.

**`BespokeEditors.notEditable` names the two with no editor and why** — `CatalogTests.notDemonstrable`'s
shape one rung up, and `BespokeTests` requires an editor or a reason. `[keys]` needs a field that holds
⌘Q and ⎋ without either reaching the app (hotkeys being suspended behind the scrim is half of that, and
already true). `[[window-rules]]` needs to move whole blocks, which `ConfigDocument` deliberately
cannot: it splices single values and refuses a positional index rather than making one public by
accident.

**The springs are eight advanced dials of `animation`**, and `Setting.Section` has no `springs` case.
The `settings` array order is untouched, so the document and `explain` are unchanged; only the tab bar
and the section switch in `Catalog` are. A test now pins the general rule — no tab whose every setting
is behind the disclosure.

**The panel says it scrolls twice, and neither is a scroll bar.** The geometry was doing the opposite:
258 pt of scroller against a 52 pt row pitch is 4.96 rows, so the fifth row's bottom edge landed two
points above the fold and eight rows of Layout read as five — a whole number of rows is the strongest
claim a list can make that it ends there. `viewport` is now `rowPitch × 4.5` and the panel's height is
`chrome + viewport`, so a row is always cut. Over that, a gradient mask on the clip view dissolves the
end that has more into the blur behind the slab — and **only** that end, since a fade at an edge with
nothing beyond it is decoration; a list that fits is not masked at all. It tapers over the last 20 pt
of travel rather than switching off on the final pixel, which would read as a flicker at exactly the
edge being watched. `ScrollFade` is the arithmetic and is tested at every position; the layer is
plumbing over it, written inside a disabled `CATransaction` because a gradient that animates its
locations turns each scroll tick into a cross-fade that lags the content.

The half row is taken off the panel rather than added on. The mock, the gap and the slab are one
centred stack whose height is already close to a scaled display's: at 1352 × 878 — "Larger Text" here —
today's 380 pt slab puts that stack two points over the screen. Buying one more visible row would have
made that worse everywhere, so the panel is 24 pt shorter instead.

**The fade also came up missing on a freshly opened panel and grew one at the first nudge**, which is
one hole with two lips. `updateFade` skipped its work whenever the numbers matched what it last wrote,
and the first pass wrote `.none` off a viewport that had not been laid out — so a remembered value said
"already correct" while the scroller carried no mask, and only a change in value could dislodge it. A
remembered value standing in for the layer is the bug; the layer is the fact, and writing four numbers
on every pass is cheaper than the bookkeeping that avoided it. The other lip is that the content's
height was never watched at all: it settles a layout pass *after* the rows go in, so `rebuild()` asking
for the fade asks about a height that has not been resolved. The document view's frame is observed now
alongside the clip view's bounds — two inputs, two observers.

**The fade came out at the wrong end first, and it was found by scrolling to the top and seeing one
there.** AppKit sets `isGeometryFlipped` on the backing layer of a flipped view, and an `NSScrollView`
is flipped when its document view is — so inside it the gradient's axis *already* runs downward and
`(0.5, 0)` is the top edge. Setting `isGeometryFlipped` on the mask as well, meaning to say so
explicitly, cancelled it: the stops were spelled top-down over an axis that had been turned upside
down, so every fade drew at the opposite edge. Measured rather than argued in the end — a probe
sublayer at layer-y 0 inside the scroller converts to the scroller's *top* edge in the slab — and the
measurement is now a test, because if that ever stops being true the fade inverts silently and nothing
else would say so. The mask also moved from the clip view to the scroller, whose bounds do not travel:
the frame is set once per layout instead of on every tick.

Rejected: a permanent scroll bar (what was being asked away from); the slab's own 1 pt border as a
position rail via `strokeStart`/`strokeEnd`, which gives position but needs arc-length math on a
rounded rect and ends up a scroll bar in a costume; and a nudge-and-settle when a section with overflow
opens, which `PRINCIPLES` rules out — the mock moves when a value moves and otherwise holds still, so a
slab animating itself would compete with the desktop above it for the same glance.

**The row layout is stacks, not a chain.** The first version pinned four captioned fields
leading-to-trailing across both edges of a fixed 260 pt well whose intrinsic widths add to 244, which is
unsatisfiable: a constraint broken at runtime and a row that looks nearly right. `.equalSpacing` has the
same intent and cannot be. `BespokeTests` lays the slab out headlessly and checks the four fields are
ordered, non-overlapping and inside the well, which is the failure a test catches and an eye doesn't.

Two claims were corrected rather than built. `PRINCIPLES.md` and `Draft.init` both said a file that
does not parse opens the window read-only; it doesn't — `SettingsWindow.open` throws, the menu reports
it, and the file is one click away.

## Observations

Not verified on screen. The daemon running on this machine is the previous debug binary, and the one on
disk has been rebuilt — restarting it re-asks for Accessibility and Screen Recording, which is a cost
worth someone choosing. What is verified is headless: the row lays out, the four fields fit, the
scroller is still half a row short of a whole number of them, and every edit path is driven through the
real control.

The stack overflows a short display, and did before this. At 1352 × 878 a 0.52-width mock, the 44 pt
gap and the panel come to two points more than the screen; the panel being 24 pt shorter now makes it
fit, but nothing *clamps* it, so a narrower `mockWidthFraction` or a shorter screen would put it back
over. The mock's width is chosen from the display's width alone and never asked whether the stack fits.

While the changed-on-disk banner is up it takes 30 pt from the scroller, which puts it back near a
whole number of rows. The banner is a transient alarm and is the thing to look at while it is there, so
the peek losing its edge under it is not worth a second geometry.

`[keys]` and `[[window-rules]]` are named and file-only, so their sections are still not tabs. A tab
that showed the surface's sentence and sent the user to the file would be more honest than silence and
was not built: the window covers every display at shielding level, so an "open the config file" button
has to dismiss first, and it owns neither the path nor any I/O.

`ConfigExplain.summary` still walks `settings` alone, so `emira config explain` says nothing about the
three surfaces. It is the one consumer of the schema this change did not convert.

A GUI edit to a file spelling `outer-gap = 8` adds a per-side line rather than rewriting the base —
correct under the no-rewriting rule, and it means the two spellings accumulate in a file edited both
ways.
