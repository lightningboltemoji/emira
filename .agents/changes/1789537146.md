# The veil waits for the cover

> Change `1789537146` — 2026-09-15

## Goal

Reported as windows flashing between transparent and solid at the start of an animation. What the glass
actually shows is a step: on a covered focus change the veil moves at the *command*, which is a capture head
before any cover exists, so two windows change appearance over a desktop that is standing perfectly still
and only then begins to move.

Filmed from a third process at ~58 fps, the whole screen scored in 24 vertical bands, the reported number
being the largest single-band change between consecutive frames. Five covered `focus` transitions under
`cover = "exact"`:

| run | veil step | motionless frames after it | motion begins |
| --- | --------- | -------------------------- | ------------- |
| 1   | 44.1      | 4                          | +133 ms       |
| 2   | 42.2      | 3                          | +133 ms       |
| 3   | 44.1      | 4                          | +132 ms       |
| 4   | 42.2      | 3                          | +131 ms       |
| 5   | 44.1      | 4                          | +133 ms       |

Forty luminance levels in one frame, then three or four frames reading 0.00 — nothing on the display moving
at all — and the transition starting an eighth of a second later. The step is the whole of the effect: the
same region measures 37 solid against 77 veiled, so what steps early is the entire veil.

## Implementation

**The set was the only part of the scrim not already gated.** `State.scrimBindings` reads three things, and
`writeTruthPlane` holds two of them for a display whose cover is not on the glass: the window frames are not
written, and that display "contributes what it was already showing" to `placedOnScreen`. The third is
`world.focusedWindow`, which a command moves at once — so during a capture head the set is the old geometry
carrying the *new* focus, and it is emitted, and the shell paints it. The mask is a cut rather than a fade
(`1789534267`), so it lands in one frame.

So the gate is finished rather than invented: `settleScrims` splices, keeping each held display's share of
the set it is already drawing and taking the fresh answer for the rest. A scrim is appearance and D8 is
already the rule for when appearance may change — the phrasing in the code is "a display whose cover is not
on the glass moves no window, and a scrim is appearance, which is the same claim".

What lands where, after: the set is emitted at `coverOnScreen`, in the same batch as `teleportBehindCover`'s
`setFrame`s, so it is painted under the cover; `restack()` re-reads the window server at `dismiss` and
repaints, still under the cover; and the cross-fade reveals the new veils with the new geometry, which is one
event rather than two. The same five-run drive with the gate in, and a sixth pair:

| run | largest step | motionless frames after it | motion begins |
| --- | ------------ | -------------------------- | ------------- |
| 1–6 | 21.7 – 44.8  | 0                          | +17 ms        |

The step does not go away and should not: a cover coming up *is* a step. What goes away is the stillness
after it — six runs for six, the very next frame is the transition moving.

**It also makes an existing claim true.** `Reconstruction.veil` reads `Scrims.veil(of:)` when a layer is
built, documented as "a stand-in stands for the window as it was filmed". It did not: the shell's applied set
had already been replaced at the command, a hundred milliseconds before the raise, so stand-ins carried this
transition's focus change. Held, the plane still holds the filmed answer at build time and the claim reads
correctly. `theVeilIsStillTheOldOneWhenTheCoverIsBuilt` is what pins it.

Two alternatives were rejected. **Holding the whole set while any display is mid-transition** is three fewer
lines and wrong for the reason the plane exists: a scrim belongs to one screen, and one display's cover says
nothing about what another looks like. **Doing the hold in the shell** puts it where the appearance is, but
`Effect.setScrims` carries the whole desktop's set, so the shell would have to take it apart per display
against a phase it does not own — and the reducer is where every other "may this display be written to"
question is already answered.

### Validation

Two builds of this worktree differing only in the gate, the same drive, the user's own config with
`cover = "exact"` so every transition takes a full head. A probe on `Scrims.setScrims` timestamped against
the command confirms the mechanism directly rather than by its picture: ungated it arrives ~26 ms after the
command with the cover still 80 ms away; gated it arrives at +125 ms, a few milliseconds after the raise.

## Observations

- **A window the transition did not scope loses its veil for the length of the cover.** The base is captured
  with `owningApplication?.processID == mine` excluded, which drops the scrim along with the overlay, so an
  unfocused window that is in the base rather than on a layer is photographed solid. Independently found by
  the `unfocused-blur` work at the same time. It is the same family as this — the cover and the desktop
  disagreeing about when — and it is not fixed here.
- **A window arriving during a transition arrives solid.** It is not in the held set, so its stand-in is
  built at veil 0 and takes its veil from the cross-fade at the end. That is the documented reading of "as it
  was filmed" applied to a window that was parked when it was filmed, and it may not be the one the eye
  wants.
- **A cover that never reaches the glass holds the set until `holdTimeout`.** The truth plane is held the
  same way and for the same second, so this adds no new failure, only another thing waiting on it.
- **`ScrimBinding` array order is still unused.** Carried forward from `1789531974`. The splice preserves
  each display's own run, so if the order ever starts being read it is preserved rather than invented.
