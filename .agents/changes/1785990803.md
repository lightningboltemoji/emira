# A released drag waits for the window to stop moving

> Change `1785990803` — 2026-08-05

## Goal

A window resized quickly by its own handle kept only a fraction of the drag, and left the strip tiled for a
column it had outgrown. Measured on a live desktop: a 163 px pull on a Ghostty edge adopted 19 px of it —
`widthOverride` `.fixed(986)` against a window 1130 wide, its neighbour placed at 1026, a 124 px overlap. A
focus change appeared to fix it, because `reassertTruthPlane` then wrote the window back to 986 and the layout
became self-consistent at the under-adopted size.

The frame the adoption read was a frame from the middle of the drag. The first guess — that our own read
pipeline lags a finished resize, so the fix is to re-read at the end — is wrong, and measuring it is what says
so. Sampling the window server every 10 ms from the mouse-up:

```
MOUSE-UP
WSLIST+  0ms  1320   ← the pre-drag width
WSLIST+ 20ms  1339
read-answer   1520   ← +33 ms, final
WSLIST+ 40ms  1520   ← and flat for the next 350 ms
```

**At the mouse-up the resize has not happened yet.** The app is still draining its own event queue, and the
window server — the authority a beachballed app cannot keep quiet, and the one this file already leans on for
death — reports the old frame too. There is nothing to read, because nothing has decided the answer. Waiting on
outstanding reads does not reach it either: in one trace the *first* `AXWindowMoved` of the whole drag arrived
8.7 ms after the button came up, with nothing in flight and no dirty bit, so a drain would have completed
instantly and adopted the pre-drag frame.

## Implementation

**`Event.dragEnded` is now later than the mouse-up it stands for, and the watcher owes it that.** A press
releases into a *settle*: `beginSettle` holds the event, every frame read that answers restarts a wait for
quiet (`dragSettleQuiet`, 60 ms), and the release goes through once the reports stop. Measured tail is 0–37 ms
across Ghostty and Chrome, four drag speeds and both edges, so the wait is not a bet on an app being fast — it
is the definition of stopped, and there is no deterministic end-of-resize signal to use instead. AX has no such
notification and the window server has no event.

`dragSettleLimit` (250 ms, one `AXClient` round trip) is the backstop for a window that never goes quiet — one
animating its own size — since the wait would otherwise hold the core's drag latch open indefinitely. A settle
capped out adopts the last frame that did arrive, which is what *every* release did before this change.

**The watcher, not the core.** The core has no clock — `Event.tick` runs only while a transition is open — and
`Drag`, the subject latch and `adoptDraggedSize` are all untouched: they simply run against a `World` that has
caught up. The defect was an ordering violation at the seam, and the seam is this file's, which already owns
the coalescer whose lag this is and one bounded deferral of the same shape (`vanish`/`successionGrace`).

**Nothing is written while a settle is open.** The adoption and its placement are both `dragEnded`'s, so the
reports the wait listens to carry no echoes of our own — which is what keeps "the last observed frame is the
intent" honest across the wait, and is why the alternative was rejected: keeping a `.settled` latch in the core
that re-adopts frame changes arriving *after* `dragEnded` would be adopting them alongside our own re-place and
an app's clamp of it, which is the hole the mouse-down gate exists to close.

`waitForQuiet` stands down rather than closing when a read is out on a lane: the answer restarts it, so a
window mid-report is never cut off by a wait that expired while the question was still in flight. A read that
comes back *empty* restarts it too — the window closed mid-drag, which reports no frame but must still stop
holding the release.

A fresh `mouseDown` closes an open settle before arming, so brackets stay sequential rather than nesting;
`DelayScheduler` does not cancel, so both timers carry a stamp and a superseded one expires silently.

The left-edge compensation is fixed by the same change without touching it: it reads `observed.minX`, which
lagged exactly as the width did (`1130x1102@808` where the settled frame was `@650`).

## Observations

Verified live, both edges, on two apps across four drag speeds including one faster than a hand can move: the
column's `widthOverride` and the window's own width agree after every drag, and the full stroke lands where
before a fast one kept 12% of it. The four behavioural tests were each checked to fail with `beginSettle`
stubbed back to a bare `emit(.dragEnded)`; the two that only assert the bracket arrives whole keep passing
there, which is what makes them the invariant rather than the fix.

`ManualScheduler` grew `fire(after:)`. With no clock, `fire()` cannot say which of two deadlines came first,
and a settle holds two at once whose *difference* is the behaviour under test — a quiet wait that closes the
release against a limit that overrides it. Note that `dragSettleLimit` and `successionGrace` are the same 0.25
s, so a future test with a vanish in flight would fire both.

Every mouse-up now costs a scheduler wake, and a click that moved nothing delivers its `dragEnded` 60 ms later
than it used to. Both are invisible: that `dragEnded` was already a no-op, and the only visible deferral is a
move-drag's snap-back.

Two things left standing, neither reached by the suite. A command landing inside the settle — a keybinding
within 60 ms of releasing a handle — re-places the strip before the adoption runs, and `adoptDraggedSize`
compares observed against *target*, so both axes come back equal and the drag is silently dropped rather than
corrupted. Closing the settle on a command would need the watcher to hear about commands, which is a coupling
this does not earn. And the subject latch is now open for the length of the settle, so an app resizing itself
in that window is marginally likelier to be adopted — the same hazard the original change recorded, with a
wider mouth and now a cap on it.
