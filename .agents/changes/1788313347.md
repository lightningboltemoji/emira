# The poll that waited on our own frames

> Change `1788313347` — 2026-09-02

## Goal

Name the thing that blocks the main thread for ~190 ms mid-transition, which `1788248980` made survivable
without identifying. It is `WorldWatcher.reconcile`, and what it is waiting for is emira.

`CGWindowListCopyWindowInfo` does not simply read a list. `SLWindowListCopyWindowInfo` opens with
`SLSConnectionSynchronizeSLSCATransaction`, which blocks until the window server has taken **this
process's own** pending Core Animation commit — so the call costs what *we* have in flight, not what the
desktop is doing. Idle it is 3 ms. Against a cover committing a frame every 8 ms it was measured at 447.

The reconciliation heartbeat fires every 3 s and knows nothing about that. A close animation is ~400 ms,
so roughly one interval in eight lands inside one — which is the whole of "one in four closes in one
batch, none in the next twelve". Nothing about ⌘W was ever involved: the poll is on a timer, and ⌘Q
looked clean because it drew a different card.

Attributed with `StallProbe` (below), over 20 bare-launch-TextEdit closes of its Open panel:

```
windowList[succession]   0.9 ms        ⌘W lands; the close path's own list read, before any cover
capture: 3 windows — raise at 46 ms    the cover goes up
windowList[reconcile]  166.1 ms        the heartbeat fires mid-transition
=== main-thread stall: 174.6 ms ===
transition: 40 frames in 500 ms (80 fps)
```

| main-thread `CGWindowListCopyWindowInfo` | n | p50 | max | over 30 ms |
| ---------------------------------------- | --: | ---: | ----: | ---------: |
| `reconcile` (a blind 3 s timer) | 34 | 3.1 ms | 447.4 ms | 3 |
| `couldBeSucceeded` (the destroy path) | 16 | 1.0 ms | 1.7 ms | 0 |

The two sites make the same call and differ only in *when*. The close path asks before its cover exists
and never pays; the timer asks whenever.

## Implementation

`reconcile` skips its list read while `Motion.needsFrames` is true, through a `WorldWatcher.isPainting`
reader the daemon points at the core — `PointerFocus`'s shape, for its reason: the watcher holds no core
state, and this is not a question about the world it watches but about whether *we* are mid-frame.

Only the read yields. The notification half above it — re-registering an app whose observer failed — is
AX work on that app's own lane and costs the main thread nothing, so it still runs every interval; an app
deaf to us must not stay deaf because another display is animating.

Skipping outright rather than deferring, because this is the level-triggered backstop: a round missed
costs three more seconds before the standing invariants are re-checked, and it is already the thing that
waits for answers measured in seconds. A round *taken* costs the animation a fifth of a second.

**Rejected: moving the read off the main thread**, which is what `AXClient`'s rule would suggest and what
`AXWindowSource.windows(of:)` already does with the same call on an app's lane. It relocates the wait
instead of removing it. `SLSConnectionSynchronizeSLSCATransaction` holds the connection's transaction
lock while it waits, and our own frame commit needs that lock on the way through
`SLSConnectionSetLastSLSCATransaction` — so the block reappears in `CA::Transaction::commit` under
`os_unfair_lock_lock_slow`. Measured over 24 closes: the `mach_msg` wait vanished from the main thread and
seven blocks of 106–125 ms took its place. Cheaper than 447 ms and still the same defect, for a protocol
change and a restructured `vanish`. The lock is per connection, so no thread makes this call cheap while
we are painting; the only fix is not to make it.

**Rejected: gating `couldBeSucceeded` the same way.** It cannot be deferred — it decides whether a
destroyed id is retired now or held for a scan, and holding it means a dead window on the strip for the
whole transition. The measurement says it does not need to be: it runs at the destroy notification,
before the cover it is about to cause exists, and never exceeded 1.7 ms.

`StallProbe` is the instrument, kept because it is the one `1788248980` asked to have again and because
two main-thread blocks below are unfixed. A background thread watches a heartbeat the main run loop
writes; when it goes stale while the loop is not parked in `beforeWaiting`, it signals the main thread to
`backtrace` itself. Off unless `EMIRA_STALL_PROBE=<ms>` is set. The obvious instrument — `sample` at
1 ms — cannot find this one: it keeps the process warm enough that 24 closes under it produced no stall
at all.

Measured over 65 closes of the reported repro, 129 transitions:

| | stalls in `SLWindowListCopyWindowInfo` | transitions under 110 fps |
| ------- | -------------------------------------- | ------------------------- |
| before | 3 per 20 closes, 151–447 ms | 3 per 20 (45, 63, 80 fps) |
| after | 2 per 65 closes, 83 and 116 ms | 0 per 65 (min 114 fps) |

## Observations

**The two that survive are the same race, and cost no frames.** A reconciliation that passes the gate and
*then* has a transition open under it still pays: the read starts idle and the raise commits during it.
Both landed at the head of a transition, before the first tick, so they are head latency rather than lost
animation — and closing the window would mean gating on something the watcher cannot see without new
coupling to the capture plane. Worth revisiting only if head latency is what is being chased.

**`SurfaceCache.reduced` blocks the main thread for 50–66 ms on every cover dismissal** — 126 of them over
the same 65 closes, the largest main-thread block emira still owns. `unpin` redraws each released still at
cache resolution inside `discard`, and `CGContextDrawImage` of a capture-resolution image is a GPU
read-back (`CGSImageDataLock`, plus an ABGR→RGBA conversion the destination bitmap format asks for). It
lands after the cross-fade, so nothing was painting and no transition in these runs lost a frame — but a
key pressed inside that window pays it. The fix is the one the code already names: `reduced` is
`nonisolated` "so the scale-down is callable off the main actor", and `unpin` calls it on the main actor
anyway. Not taken here because `unpin` is documented **synchronous** — the next head batch releases the
outgoing cover a line before it reads the store — and making the reduction asynchronous changes what a
stand-in raised inside that window is made of, which three tests in `CaptureTests` pin deliberately. Its
own change.

**A third block is not ours.** `CA::Context::commit_transaction` does a `dispatch_sync` that costs ~25 ms
once per transition (48 over 65 closes), entirely inside QuartzCore, at the same rate before and after
this change. Presumably the raise uploading the stills.

**The gate is a check, not a lock,** and `isPainting` reads `needsFrames` — which is false through the
0.22 s cross-fade, where the compositor is still committing. No reconciliation was observed to be caught
there, but nothing prevents it.
