# An app with no bundle is still an app

> Change `1791605843` — 2026-10-09

## Goal

A bare executable that puts up ordinary windows (`FiberUIHarness`, run out of `.build/out/Products/Debug`)
was never managed. Its windows were not tiled, placed or captured. The veil still cut around them, because
the veil reads the window list and has no app filter.

## Implementation

**The cause was a missing bundle identifier.** LaunchServices reports the process as `.regular`, with both
windows readable over AX (an `AXStandardWindow` and an `AXSystemFloatingWindow`). But
`NSRunningApplication.bundleIdentifier` is `nil`, and all three ways an app enters management (the boot sweep
`applications()`, the evidence path `target(for:)`, and `appLaunched`) required one. The core groups by it,
so an app without one had no key and was skipped as a whole.

**The key is now `appId`: the bundle identifier, or else `executableURL.path`.** It is defined once, in
`AppId.swift`, and all three entrances read it, so they cannot disagree about which apps exist. The path was
chosen over the alternatives:

- `localizedName` merges two different binaries that share a name.
- A pid changes on every relaunch, which breaks rules, and the core is never given one by design.

A bundle identifier admits only alphanumerics, `-` and `.`, so a leading `/` says which spelling a key is.
`AppId.location(of:)` relies on that to find the app on disk again, for the guide's names and icons. Without
it, a path key falls through `urlForApplication(withBundleIdentifier:)` to the dotted-segment fallback. That
splits a build directory at `.build` and names the app `build/out/Products/Debug/FiberUIHarness`.

The core's field keeps its name, `bundleId`. Renaming it means touching 160-odd sites and the `bundle` key of
the `watch` schema, for a value whose meaning, the app-grouping key, has not changed. Its comment now states
both spellings.

**Validated live** against the running harness with the patched daemon:

- Before: nothing in `emira debug` named it.
- After: boot enumerated 4/4 windows across 4 apps. The main window became a column and was parked, then
  resized to its column (1280×820 → 1275×1102). Two `focus left`s brought it to (20, 47), inside the gaps,
  with captures of 3/3 windows.
- `watch` names it `FiberUIHarness`, with the path as its `bundle`.

## Observations

- `AppIdTests` covers the reverse mapping: a path names and finds itself, and a bundle identifier is still
  asked of LaunchServices. Which processes get a key is LaunchServices' answer, so that part was checked live
  rather than in a test.
- Unbundled processes that share one executable (several apps run by the same `java`) now share one key, and
  so are one app to the core. This is the same one-instance-per-app assumption a bundled app already makes,
  and it is still not disambiguated.
- A rule for such an app has to spell out the whole path. `app-id-regex = '/FiberUIHarness$'` is the
  practical form, and the config documentation now says what `app-id` matches for an unbundled app.
