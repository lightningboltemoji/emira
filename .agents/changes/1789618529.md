# Round the veil by each window's measured radius

> Change `1789618529` — 2026-09-16

## Goal

The scrim rounded every see-through window by `Scrims.cornerRadius`, a constant 12. The capture plane
already measures a window's radius off every still it takes (`CapturedSurface.measuredCornerRadius`), and
on macOS 27 that measurement is 17.15 pt for Ghostty, Finder, TextEdit and a standalone alert. The veil
guessed a number the daemon already knew.

## Implementation

**The radius is kept beside the photographs, not in them.** Reading `SurfaceCache.anySurface(for:)?.cornerRadius`
was the obvious wiring, the way the guide reads `still`, and it misses on the default config. A photograph
outlives its cover only while `keepsStills` is on (`cover = "immediate"`, or a `stills` preview guide).
Under the default `exact` the last cover to let one go forgets it, and the scrim draws at rest, after that.
The budget, a display change and turning `keepsStills` off drop photographs too, and a radius is one number.

So `SurfaceCache.record` also writes `corners[id]`: the radius and the batch that measured it. It is ordered
by that batch rather than by the photograph's, because the photograph may be gone, and a film whose pixels
could not answer (`nil`) leaves the last answer standing. Nothing collects it: rule 3 holds, and it is a few
bytes per window ever filmed.

`Scrims` takes `cornerRadius: (WindowId) -> Double?`, `identify`'s shape, and the daemon passes
`surfaceCache.cornerRadius(of:)`. `regions` resolves every region's radius through it, falling back to
`Scrims.fallbackCornerRadius`, the renamed 12. Occluders carry the same lookup, though the mask still
paints them square.

## Observations

Validated live with a temporary log line in the daemon's lookup, since removed. Under `cover = "immediate"`
every veiled window read its measured 17.15. Under `exact`, set for the test and restored byte-for-byte
after, radii survived the config change's `removeAll()`. A window opened then was measured on arrival, its
photograph dropped when the cover came down, and the veil still read 17.15 when focus left it. Across both
runs no veiled window ever reached the fallback: an arrival is a transition, and the transition films it.

**A first measurement can be wrong.** A new Ghostty window measured 22.76 on its arrival film and 17.15 on
the next film two seconds later, most likely because it was shot mid open-animation. The alpha-deficit
measure is sensitive to any transparency in the probe block. The veil keeps the wrong answer until the
window is filmed again, and a veil over-rounded by that much leaves a thin unveiled crescent inside the
window's corners. In the run it happened in, the window was re-filmed before it was ever veiled. The cover's
stand-ins read the same measurement and always have.

A window with a translucent background will likely measure too large, or `nil`, for the same reason. Not
tried.

`Reconstruction.fallbackCornerRadius` and `SettingsStyle.paneRadius` are still constants. The first is used
only when a still's alpha cannot answer. The second draws the settings window's mock panes and touches no
real window.

Occluders are still square: a focused float standing on a veiled tile leaves small unveiled corners
around it. The radius they need is now on hand.
