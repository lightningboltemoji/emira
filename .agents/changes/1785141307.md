# Window rules can set float and width

> Change `1785141307` — 2026-07-27

## Goal

Extend `RuleOutcome` from a workspace assignment to the two other properties a window can start with:
`float` and an initial `width`.

## Implementation

Two fields and their arms in the reducer. Each action writes state a verb already owns: `workspace` is
`move-to-workspace`'s move, `float` writes the tri-state `Command.float` toggles, and `width` sets the
`widthOverride` `grow`/`shrink` set and `cycle-width` clears. So the first press of the corresponding
verb returns the window to normal handling, and no rule holds state of its own.

- **`float` is read before the tiling guard**, in both directions, because it decides that guard's
  answer. It was already tri-state (needed so `float off` can tile a window macOS classed as a dialog),
  so the rule sets `World.floating` and `participatesInStrip` does the rest.
- **A rule's `width` outranks the width a boot-adopted window arrived with.** They meet on one window:
  one emira found already open that a rule also names. The explicit value wins, since `wasAlreadyOpen`
  infers a width from what happened to be on screen. One helper (`seedWidth`) holds the precedence so
  both arrival paths use it.

## Observations

- A rule may not both float a window and assign it a workspace: a floating window has no column, so the
  second clause does nothing. Refused at parse time. The check is per rule, not on the merge — two
  rules that each make sense and combine into this get the same silence a dialog with a `workspace`
  already gets.
- The first-sight title-matching limit now applies to three actions rather than one.
