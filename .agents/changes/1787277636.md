# The main display carries the workspace, and a reconfiguration never strands focus

> Change `1787277636` — 2026-08-20

## Goal

Docking a laptop to a display that macOS makes **main** left the user's workspace on the internal
screen, and closing the lid then hid it entirely. Traced through the reducer, the second half is worse
than a placement annoyance: with the internal gone, `Monitors.reconcile` hands its addresses to the
first survivor as `owned` — preserved, but not shown — while `World.focusedWindow` still names a window
on that strip, which is now a parked nub. emira ends in the state `PRINCIPLES` §4 promises it will not:
focused on something the user cannot see.

The design already contained the right principle and applied it in exactly one place. `unattached.shown`
beats `detached[id].shown` on the way back from a zero-display state because "what the user was looking
at outranks what that particular screen happened to be showing" — a rule written *for the lid close*
that only fires when **every** display leaves. A clamshell with an external attached never passes
through zero displays, so the rule written for the lid close was the one the lid close could not reach.

It was not specific to that sequence. The same hole swallowed the strip when a non-main display the user
was working on was unplugged, and when the heir was showing an occupied workspace. A third instance sat
next door: `follows-mouse` across displays moved `World.focusedWindow` and left `Monitors.focused`
behind, so the next verb acted on the screen just left. The common root is that emira keeps two records
of *where the user is* — a window and a display — and only some paths kept them in agreement. §1 applies
that discipline rigorously to where a window is; nothing applied it to where the user is.

## Implementation

**What the probe settled.** Logging `CGDisplayRegisterReconfigurationCallback` and
`NSApplication.didChangeScreenParametersNotification` side by side across a real unplug and replug
decided the shape of the rule:

- `SET-MAIN` arrives in the **same flag word** as `added`/`removed`
  (`added+enabled+moved+SET-MAIN+mode+shape`). A display arriving and the role moving are one event, not
  two, so there is no ordering window in which they disagree and no two-step to sequence.
- The **first** AppKit report of each transition already carries the whole consistent truth — list, main
  and geometry agree. So main-ness rides the single `AttachedDisplays` read, which is where "one read,
  several consumers" already says it belongs. It matters: at the window server's `begin` phase
  `CGMainDisplayID()` had already flipped while `NSScreen.screens` had not, so a second read taken later
  can name a display the list does not contain.
- The transition repeats: 2 reports on an undock, 3 on a replug, the last 2.3 s late. All byte-identical,
  so `describesSameDisplays` swallows them — and a rule keyed on "main differs from the main we last saw"
  is self-idempotent across them, which is why nothing here needs the debounce that `1785729910` left
  open.

**`isMain` lives in `World`, not `Monitors`.** Observation refreshes it, which is the whole of what
decides that split — and it is what lets `setMonitors` read the *previous* main out of `World` before
folding the new report over it, so `Monitors` needs no memory of its own. `bankViewports` already runs on
that ordering for the same reason. Read from `CGMainDisplayID()` rather than `screens.first`: AppKit
documents that ordering loosely, which `ScreenGeometry.current()` already distrusts when it picks the
primary by its origin. As it happens `screens[0]` *was* the main display in every reading, and
`records[0]` is therefore already the departure heir — but nothing should rest on that.

**Why the rule is keyed on the role moving, not on a display arriving.** Arrival is the wrong lever
twice over. A second screen is more screen, not a relocation: taking the strip off the screen you are
looking at is the one thing plugging something in must not do, it would re-lay-out every window at the
new metrics at the moment the desktop is least stable, and a portrait reference monitor is the identical
event with the opposite wish. Sharper: moving the *acting monitor* on arrival would have
**reintroduced** the clamshell bug — the acting display would then be the Studio, the laptop would depart
as a non-acting display, and its strip would park again. Anchoring on the role and on the focused window
is what makes the pair hold.

**And only when the user was on the display that held the role.** The rule is *from one main to another
main*. A menu bar arriving on a screen nobody is working on says nothing about the screen they are, and
hauling a third display's strip across the desktop is not what dragging it asked for. That deliberate
narrowness is exactly what the reveal below is total over.

**The pair trade rather than the loser falling back.** `Monitors.exchange` moves both `shown` values in
one step. Two `show`s were the first shape and they left litter: the first strands the old main, and the
`repairShown` fallback that repairs it claims a *third* address — which the second call then makes
pointless, but which `State.show`'s own `materializeShown` has already given a strip. Every dock left a
spare workspace owned and materialized behind it, visible in the probe as `owned=[2, 3]`. A trade needs
no fallback at all, because neither display is ever without an address.

**The reveal is the backstop, and it reuses the switch.** `revealAcrossDisplays` is `switchWorkspace`
with an empty before-geometry, which is its own unanimated path — right here for the reason `setMonitors`
already closes every cover rather than retargeting them. It composes with the viewport banking for free:
`bankViewports` stored the departing display's scroll against the *address*, so the survivor comes up on
that strip at the offset the user left it at. Silent with no display attached, and not as an
optimisation — there is no screen for a reveal to happen on, and a switch there would overwrite the very
address `unattached` went to the trouble of choosing.

**A fixture that built an unreachable state.** `MonitorSessionTests.aLidCloseReturnsTheFocusedDisplaysScrollAndNotAnothers`
used `Monitors.focus(right)` to move the acting monitor, which no reducer path does: probed, it leaves
`World.focusedWindow` on a window living on workspace `1` while the acting monitor shows `2`, where
`focus-monitor 2` leaves focus on a window on `2`. The reveal is obliged to repair the first, so the test
was asserting against a state the system cannot reach. Switched to the verb, and moved ahead of the
scroll because the switch re-seats the destination's viewport. What the test is actually about — the
focused display's scroll coming back rather than a survivor's — is untouched.

## Observations

**Reopening the lid pulls the workspace back to the laptop.** `detached`'s reclaim is unconditional, so
the returning internal takes its addresses back and the Studio falls back. That is the documented D12
behaviour and the zero-display path already resolves the same tension the same way ("a display whose
address it really was takes it back"), so it is left alone — but a user who has worked on the Studio for
hours may not want the lid opening to move anything. If it turns out to grate, the fix is a rule about
the reclaim, not about this change.

**The main-follow does not fire for a departed old main that the user was not on.** Covered by the reveal
whenever focus is on a window; a display showing an *empty* workspace departing still hands the survivor
nothing to reveal, and the survivor keeps what it was showing. That is correct as far as anything can
tell — there is nothing the user was looking at — but it is the one corner neither rule speaks to.

**`isMain` joined `describesSameDisplays`.** Belt and braces rather than load-bearing: a main change
always moves at least two frames, since the new main takes origin `(0, 0)`, so the gate already opened
for it.

**Still owed: the visual check under a running daemon.** Dock and undock a real display and confirm the
workspace lands on the main screen, that the cover comes down on the screen that left, and that the
strip resumes at the scroll it was banked at.
