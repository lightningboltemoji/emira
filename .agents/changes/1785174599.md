# Two places AX silence was read as a departure

> Change `1785174599` — 2026-07-27

## Goal

Two defects in the tab-group change, both the same misreading: an app declining to describe a window
was treated as the window being gone. Neither was reachable from that change's tests, because a stubbed
`WindowSource` answers completely and a stubbed desktop posts notifications in the order the test
writes them.

## Implementation

**An orphaned departure is corroborated against the window list** (`AXEnumerator.finish`).
`WindowIdentity.succeed` refuses to guess, but its orphans went to `windowDestroyed` on the strength of
an app's silence. `AXWindow.snapshot` is seven round trips under the 250 ms messaging timeout, so one
failed read drops a live window out of its app's answer and is indistinguishable from a backgrounded
tab. The error is unrecoverable: no second `AXWindowCreated` arrives for a window that never closed.
The corroboration is free, since `entries` is already read for the first join, and a window still
listed **on screen** is alive whatever AX says — a background tab is ordered out and a closed window is
not listed. Such a window becomes `Report.undescribed`: kept on the strip, and `isIncomplete`, so the
existing retry asks again.

**A destroy notification waits for one scan** (`WorldWatcher.vanish`). `AXUIElementDestroyed` proves an
element died; ⌘W on a tab group destroys the selected tab while the group continues under the next one,
so the `WindowId` may still have a successor, and only a scan can find it. Retiring synchronously loses
that race — the scan is asynchronous and the registry has released the id by the time it answers, which
is why `closingTheSelectedTabKeepsTheColumnTheGroupWasIn` passed as a unit test and failed in the
product. The id now enters `vanishing` and is retired by whichever comes first:

- the scan rebinds it onto a successor (`report.succeeded`) — the column survives and the core is not
  notified;
- the scan rules a successor out — retired immediately, including an app that answers with no windows,
  which is what closing an app's last window looks like;
- `successionGrace` (0.25 s) fires, for a scan that settles nothing.

Two scan results settle nothing: one that still **lists** the window read AX before the element died,
and one that `mayHaveMissedAnArrival` has failed to look rather than ruled a successor out. Both wait
for the next scan, delivered by the existing 150 ms retry chain ahead of the deadline.

**Only the id waits.** `isLive` is false from the notification onward, so no frame read, focus report,
minimize or move about that window reaches the core in the interval, and `resolveFocus` keeps its free
answer about a displaced window already dead.

## Observations

- Only orphans are corroborated. A succession has a window standing on the departed one's rectangle,
  which is stronger evidence than a window-server flag that may not have been updated yet.
- The guard is one-directional by construction: it can prevent a retirement, never cause one, so its
  worst case is holding a column one retry interval too long.
- It cannot distinguish a backgrounded tab from a minimized window, since both are off screen. It does
  not have to — AX keeps listing minimized windows, so they are `rebound` and never reach this path.
- Not run on a real desktop.
