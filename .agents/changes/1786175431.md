# The front, when AppKit will not give it

> Change `1786175431` — 2026-08-08

## Goal

Focus stopped moving between two windows. With Ghostty and Safari on the strip, `focus right` scrolled the strip,
teleported Safari's real window to the right place and moved the core's focus onto it — and left Safari in the
background, keystrokes still going to Ghostty. `focus left` worked every time, a third window on the strip made
the symptom go away, and clicking Safari by hand restored it until the next press. It read as one app refusing
focus, which is why the first three suspects were all emira's: a `.focus` effect dropped for want of a registry
record, a superseded `FocusIntent` ticket swallowing the activation, and the cover fence withholding a truth-plane
write for a cover that never came.

None of them. Instrumenting `AXWindowWriter.focus` against a live desktop in the broken state:

```
focus(#2) pid=58456 requested; front=Ghostty
  makeKey(#2)=true  isCurrent=true
  activate(#2) app=Safari -> false
  +400ms front=Ghostty
```

The effect is emitted, the record is found, the AX write succeeds and the ticket is current.
`NSRunningApplication.activate()` returns `false`. macOS refuses.

## Implementation

**The refusal is per caller, not per target.** A freshly launched process activated the same Safari in 17 ms while
emira could not, and emira's own `activate(Ghostty)` returned `true` even when stealing the front from Safari. So
emira could bring exactly one app forward: the terminal it was a child of. That also explains every shape of the
report — a daemon started from a Ghostty tab is stuck on Ghostty, a detached one is not, a third window only
appears to help because it moves the front off Ghostty first, and a click is the user's own hand doing what emira
was refused. The rule macOS applies is not documented anywhere we can cite; what is reproducible is the refusal
and its `false`.

**`AXFrontmost` is the second answer, and it is not a duplicate of the first.** AppKit activation is the thing
being withheld; the Accessibility API is a grant emira already holds, and writing `AXFrontmost` on the application
element brought Safari forward in 22 ms from the caller that had just been refused. It is a standard attribute of
the AX application role, settable on every app surveyed.

**It goes out only on a refusal, and that ordering is the whole design decision.** Making the AX write primary
was the tempting shape — one mechanism, one plane, and `makeKey` and the raise ordered by the app's own serial
lane instead of by a deferral. It was rejected because the ticket check cannot follow it there. `FocusIntent.isCurrent`
is `@MainActor` and the lane job is not, so an AX-first `focus` either performs the raise before the ticket is
consulted — which is exactly the late activation bringing the wrong app forward that the ticket exists to
prevent — or pays a second round trip on every focus to check it first. Keeping AppKit primary costs the common
path nothing: same latency, same ordering, same guarantee.

**A refused activation is now recorded rather than assumed.** `activate()`'s result was discarded, so `focus`
called its completion either way and `AXExecutor` reported `.appActivated` for an activation that had not
happened. The completion now fires only when something actually came forward, which is `PRINCIPLES.md` §4's
"a write an app refuses is recorded as _unknown_ rather than assumed" applied to the one write that was exempt
from it. `.appActivated` re-asserts a cursor hide the front discards, so claiming one that never occurred was
also a hide re-asserted for nothing.

## Observations

The fallback dispatches to the lane after the ticket check rather than under it, so a newer focus arriving in that
one hop can leave a stale `AXFrontmost` in flight. `makeKey` has always run unguarded for the same reason and is
harmless because it cannot bring an app forward on its own; this one can. The window is a single lane hop on a
path that only runs when AppKit has already been refused, and closing it needs the ticket readable off the main
actor — which is a change to `FocusIntent`, not to this file.

Untested by construction: both routes, which need a real desktop and a system willing to refuse one of them. The
suite covers the contract around them — that a `focus` the writer declines to activate schedules nothing
(`WritePathTests`), which is now reached by two paths rather than one.

The survey of `AXFrontmost` settability covered only the apps that happened to be running. It is a standard AX
application attribute, so the risk is a toolkit that grows its own AX tree and omits it; such an app would be
reachable only through AppKit activation, which is the route that is tried first anyway.

Why macOS grants activation to some callers and not others is unresolved. The daemon's successes and failures in
one session are separated in time — the first several seconds work, everything after is refused — which looks
like a launch-time eligibility that expires, but that is reconstruction from two sessions' logs and nothing here
depends on it being right.
