# A cut that is not moving a veil leaves its fade alone

> Change `1790050825` — 2026-09-21

## Goal

The veils come back at full strength the instant a resize drag is released, where every other way they
arrive is a fade. Taking them away at the grab is a cut on purpose — `Engine.settleScrims` sends
`.cut` while `drag.subject` is latched, because a mask is cut once per set and a moving window's hole
would stay where it was picked up. Putting them back is not: the same line sends `.dissolve` the moment
the hand is off, and it does reach `ScrimWindow` as one. The fade starts, and something kills it a frame
later.

That something is the settle. `Scrims.watch` re-reads the window server every 1/60 s for up to 0.4 s
after every set, because an app's move reaches the server 8 to 42 ms after the AX write that caused it
and nothing announces the moment it does. Each re-read that finds the desktop somewhere new repaints,
as a `cut` — the veils are the ones already on the glass and only the rectangles under them moved. But
`ScrimWindow.set` took `cut` to mean *stop whatever this layer is doing*: it removed the `veil`
animation before writing an opacity the layer was already on its way to. The first re-cut inside the
fade's 120 ms therefore snapped every veil to full, and a release is exactly when the desktop is still
moving — the adopted width reflows the strip, so the veiled neighbours are travelling for several
frames after the set that describes them.

It is not a resize bug. Any fade over a moving desktop was cut short the same way, a focus change that
scrolls the strip included. A focus change between two columns already on screen looked right only
because nothing moves under it: the re-reads cut an identical mask, `Scrims.paint` finds nothing to
paint, and the surface is never called a second time.

## Implementation

**A cut names a destination, and a veil already bound for that destination is not moved by one**
(`ScrimWindow.set`). One guard, at the layer, where the two facts needed to decide it — where the veil
is going and where this cut wants it — are both in hand. Every caller's meaning survives it: a hand's
lift names `0` against a standing veil and still goes at once, a correction that moves a veil still
refuses to fade, and a re-cut that moves only shapes stops being a veil instruction at all. Both file
headers already promised this ("cutting again costs a shape's path and nothing else, so a veil fading
through it is undisturbed"); the promise is now kept rather than restated.

Rejected: a third `ScrimChange` for the shell's own re-cut. `ScrimChange` is the core's vocabulary for
why a set changed, and a re-cut has no such reason — it would be a case the core could never send, and
the plane would still have to decide per layer what it means. Rejected too: a separate path on
`ScrimSurface` for a geometry-only repaint, which duplicates `setVeils` to carry one bit that the
opacities already carry.

**The same rule on the way out**, in the two places a shape is dropped. `setVeils` dropped an unnamed
layer the moment a `cut` arrived, and `settled` dropped one whose *model* opacity had reached zero —
which it does the instant a fade-out is scheduled, not when it lands. So a re-cut arriving under a veil
that was fading away yanked its layer out of the tree, and the completion block of any transaction
committed during the fade did the same from the other side. Both now wait on the animation itself.

## Observations

- `ScrimWindow` had no tests before this; the mask is where the defect lived and nothing could see it.
  `ScrimMaskTests` is the first, off-screen against the layer tree in the manner of `SmearLayerTests` —
  the look is the render server's and is not asserted. `veils` is `private(set)` to let it read the
  shapes. Reverting each of the three lines fails a test and no other, and the three that assert the
  unchanged behaviour (a dissolve fades up, a cut that moves a veil takes it at once, a hand's lift
  takes the shapes with it) pass against both.
- `settled` can now leave a layer behind, if the animation is still attached to it when its own
  completion block runs. The next set drops it: the model is at zero, the animation is gone by then,
  and a cut naming zero against zero is the case the new guard returns from before the drop is decided.
  A stray shape at zero opacity draws nothing and is re-adopted as itself if the window comes back.
- Live-validated in **pixels**, off an `SCStream` of the veiled window's own rectangle — which delivers
  a frame only when one changes, so the frame count is the animation. A synthetic grab-handle resize
  drives it: a posted mouse-down, an AX size written in steps, a posted mouse-up.

  | | veiled window pushed | veiled window still |
  | --- | --- | --- |
  | before | 2 frames, 11 ms | 7 frames, 96 ms |
  | after | 7 frames, 93 ms | 7 frames, 96 ms |

  The split across that top row is the whole defect, and it is the one a hand can feel: a release that
  re-tiles snapped, a release that moved nothing faded, and nothing about the veil differed between
  them. What differed was whether the desktop moved under the mask afterwards and so whether a re-cut
  reached the surface at all.
- `Scrims.paint` carried its "a window management has let go of" comment twice, from a paste; one copy
  is gone.
