# The focus we wrote is not news at the clearing

> Change `1790221127` — 2026-09-23

## Goal

Press `focus-workspace` 1, 2, 3 quickly, where 3 is empty. You end up on 3, and about half a second
later emira switches back to 2 (or to 1, whichever came last before 3). This started with
`1790146681`.

## Implementation

### What was measured

Reproduced live against the daemon, using `1790146681`'s logging still in the tree. Notes was alone
on workspace 2, TextEdit was on 1, and 3 was empty, with the switches scripted through `emira`. On
`151ee23`, **20 of 20** runs ended back on 2, at both 120 ms and 40 ms between presses. The same
sequence every time:

- `focus-workspace 2` requests Notes, and its echo is `expected`.
- `focus-workspace 3` sets the core's focus to `nil` and asks for nothing. Notes stays the key app,
  and that is expected.
- The grace runs out, and `settleFocus` reads Notes, which answers Notes.
- The read is passed on as `focusChanged(notes, .system)`, and `revealAcrossWorkspaces` switches back
  to 2.

It only happens with quick presses because the clearing only follows a request made within the grace.
A slow switch to 3 has no clearing still to come.

### The fix

**A clearing read that names the focus the core last wrote is dropped.** The settle read exists to
recover a report that the record swallowed. If the answer is the core's own newest request, still
holding the keyboard, nothing was swallowed. The desktop is in the state the core put it in, and
anything the core has decided since then, including leaving that window, is newer than the read.
`FocusIntent.onCleared` now hands over that window (`held`). `settleFocus` compares the answer with it
and still notes it as the watcher's `focus`.

**The record now knows which of its requests are focus** (`FocusIntent.Purpose`). The pin fence's
`confirmFocus` is the same AX write as `focus`, and its echo still has to be absorbed, so it stays on
the record. But the core never holds the pin it raises, since it ignores that echo. Comparing against
the newest request of any kind would drop the case `1790146681` listed next to the swallowed click:
the fence's request is the newest (its owed focus went with a window that closed) and the pin keeps
the keyboard. So the fence now writes through `WindowWriter.bringForward`, which records the request
as `.stacking`, and `held` tracks only `.focus`. This follows `restoreFocus`: which writer method the
executor reaches for is the claim.

Rejected: **settling only when a report was actually dropped as `stale`.** With quick presses, our own
echoes of the earlier switches are `stale` too (the echo of 1 lands after 2 was requested), so this
reproduction would still settle.

Rejected: **comparing against the watcher's `focus`** (the last report passed on). It does not track
what the core believes. After an activation of ours that macOS refused, `focus` still names the window
the desktop holds, so the read would match it and the refusal `1790146681` covers would go unhealed.

### After

The same desktop and script on this build gave **0 of 16** jumps (8 runs at 120 ms, 8 at 40 ms). The
log shows the clearing read answering Notes with `ours` = Notes, and nothing emitted. The suite adds
two tests: a clearing that reads our own standing focus emits nothing, and a pin the fence brought
forward is still reported at the clearing. The fence's route to that second case was not exercised
live.

## Observations

**The clearing can still take the user to another workspace when the answer is not ours.** If the last
focus request's activation was refused and the previous app kept the keyboard, the read names that app's
window, and the core follows it, even onto another workspace. This is `1790146681`'s refused-activation
heal working as designed. The question is whether a refused activation should instead be retried
(`restoreFocus`).

**`1790146681`'s temporary logging (`dbg`) is removed here.** It served this investigation too. The pin
case it was left in for was never confirmed live on the machine it was reported on, so a recurrence
there means putting it back, and git has it.
