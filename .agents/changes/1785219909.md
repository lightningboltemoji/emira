# `exec`: handing a chord back to the system

> Change `1785219909` — 2026-07-27

## Goal

emira takes a bound chord from every application on the machine, and had no way to give one back. The
practical consequence is that anyone using it has to keep a second hotkey daemon running for
`alt-space = open a terminal` — two registries racing for one modifier space, where whichever
registered first wins and the loser fails silently, across two config files.

## Implementation

**In `Command`, and through the pump.** The alternative — a second kind of `[keys]` binding that
`HotkeyManager` runs itself, never touching the core — is smaller by every measure and costs the
property the hotkey subsystem is built on: _a press produces `Event.command`, full stop, so the
keyboard is a surface and never a code path_. It would put a verb-identity branch in front of a pump
whose value is being total, give `[keys]` values two types, and make the CLI unable to spell the
thing. Through the pump, the reducer returns `(state, [.exec(line)])` — no state, no session, no ack
— which is `close-window`'s shape exactly, and `ConfigSyntax.swift` needed **no change at all**,
because `[keys]` values already go through `Command.parse(line:)`. The event log gets it for free,
and replays safely: `MockExecutor` records effects rather than running them.

**One verb, shell-form, taking the rest of the line.** An argv-form `exec` beside it was considered
and rejected as strictly weaker, not merely redundant: `parse(line:)` has no quoting, so an argv form
cannot express `osascript -e 'tell application "Ghostty" …'`, which is the case the verb exists for. A
verb that parses but cannot reach its motivating example is the inert verb §2 warns about. That means
the grammar's "verb, then at most one word" premise had to bend exactly once — `Verb.takesRawTail`,
one branch in `parse(line:)`. Round-tripping survives because `parse(words:)` re-joins the tail with
single spaces: the user's own shell has already done the only splitting that was theirs to do, so
`emira exec open -a Ghostty` and `alt-space = "exec open -a Ghostty"` land on the same string.

**A fourth plane, not a corner of the truth plane.** `Effect.exec` shares nothing with AX — no window,
no per-app lane, no enhanced-UI toggle, no ack — so `CompositingExecutor.Plane` gained `.system` and
routes it to a `ProcessLauncher`. Being a plane means the existing run-splitting keeps it in emission
order with no new machinery. `ShellLauncher` spawns `/bin/sh -c` and never waits, because the pump is
main-thread and a synchronous child would freeze the window manager for as long as it ran.

**Two decisions about the environment, and the second exists because of the first.** `/bin/sh`, not
`$SHELL -lc`: a login shell would source the user's profile and make the PATH problem vanish, at the
cost of a shell startup per keypress and of emira's behaviour depending on a file it does not own. The
escape hatch needs no mechanism — the config line is already a shell line (`exec /bin/zsh -lc
'ghostty'`). But that leaves a real trap, since a bundled daemon inherits launchd's bare `PATH` and
not the user's, so `exec ghostty` fails for a Homebrew binary. Hence the reporting: `ShellLauncher`
logs a failed spawn, a nonzero exit and a signal, and _only_ those — both command surfaces already log
the request, so what a log line adds is whether it worked. Exit 127 carries the fix in its text.
Capturing the child's stderr into the report was rejected: a pipe nobody drains blocks the child at
64 KB, and the diagnostic is reachable anyway through `emira exec …` from a terminal, which runs the
same line in the same environment with the output in front of the user.

## Observations

**A spawned child may inherit emira's TCC responsibility, and this is not verified.** macOS attributes
privacy grants to a _responsible process_, and a directly-spawned child is by default attributed to
its parent — which would mean a script launched from a keybind can act under emira's Accessibility
grant without prompting for its own. If that holds, launching through `open(1)` breaks the chain and
would be the safer default for `ShellLauncher`. It was not measured here. It widens nothing that isn't
already reachable — the socket is `$TMPDIR/emira.sock`, per-user and `0700`, so anyone who can send an
`exec` can already run the command themselves — but "the same command, with a grant it wouldn't
otherwise have" is a different claim from "no new privilege", and only one of them has been checked.

**A child launched from a terminal-run daemon dies with it.** `Process` puts the child in emira's
process group, so Ctrl-C on a daemon running out of `.build` takes any spawned app with it. It does
not arise for the shipped path, where the daemon is a bundled app with no controlling terminal, and
detaching would need `posix_spawnattr` flags `Process` does not expose.

**Untested against the real daemon.** The reducer, the grammar, the plane routing and `ShellLauncher`
itself are covered (a real `/bin/sh` spawn, its exit status, its signal, and a line with a space in it
proving nothing splits it). What has not been run is a keypress reaching a live daemon and opening a
Ghostty window — the arrival path it lands in is unchanged, but the claim that a spawn needs nothing
from the layout side is an argument, not yet an observation.
