# Native tab groups are one window on the strip

> Change `1785172515` — 2026-07-27

## Goal

Reported as blank columns: open Ghostty, press `⌘T` four times, and the strip grows an empty column per
tab, with the one real window sliding into whichever placeholder has focus and swapping tabs on
arrival.

## Implementation

The classification premise is false and measuring it was the fix. **`kAXWindowsAttribute` reports
exactly one window per tab group: the selected tab.** Ghostty with four tabs answers `AXWindows: 1`, as
does a synthetic four-tab `NSWindowTabGroup` app built to iterate against. AX collapses the group
already, so there was no tab in the taxonomy to misclassify.

The accumulation is emira's, via a notification that misreports. Selecting a tab the group has never
displayed posts **`AXWindowCreated` for a window that already existed** — observed on the synthetic app
at t+2.04, +5.04 and +8.04 s while `AXWindows.count` stayed at 2. emira answers `windowAppeared` with a
re-scan, the newly selected tab is unknown, it binds to its own `CGWindowID`, and a column is created.
The tab it replaced is never destroyed, so no `AXUIElementDestroyed` arrives and `absorb`, which only
added, kept it. The live daemon held four Ghostty ids for one window, three with empty titles at park
slivers, and `CGWindowListCopyWindowInfo` confirmed those parks had landed: **a background tab accepts
geometry writes and applies them to itself alone**, which is why focusing a placeholder dragged the
visible window into it.

`AXEnumerator` gained a **second join**, on the same scan and the same two lists. `WindowIdentity.bind`
asks which window-list entry an AX window is; `WindowIdentity.succeed` asks which arriving window
stands where a departed one stood. Both are pure, take value types, return indices, and refuse a match
that is not unique in both directions.

The evidence is the frame only. A tab that becomes selected takes the group's geometry, which covers a
switch, a `⌘T`, and closing the selected tab — where the element is already dead and nothing else about
it survives. "One window left and one arrived, so they are the same" would also pair an app that closes
one window while opening another, and the cost of that error is a window inheriting another's column
permanently.

`WindowRegistry.rebind` is the only code that re-points a binding, so `Record.number` is no longer for
life. Keeping the `WindowId` is what makes a tab switch unobservable to the core, so the column, width
override, workspace and float state survive one without an `Event`. Three maps move together or the
seam leaks: `idByNumber` (the capture plane films by `CGWindowID`), `idByElement` (a notification
carries an element and nothing else), and `Record.element` (the write path sets frames through it, and a
stale element places on an invisible window).

**`AXMainWindowChanged`, registered on the app element.** `AXWindowCreated` fires once per tab and never
again, and `AXFocusedWindowChanged` did not fire for a tab switch in any run. This is the only notice
that the window standing for a group changed; it costs one dictionary lookup to dismiss when it names a
managed window. Without it the strip points at a backgrounded tab and every placement lands on an
invisible window.

## Observations

- Not run on a real desktop. 871 tests pass and the bundle builds, but the daemon that produced the
  four-column screenshot is the old binary; a rebuild is a new ad-hoc cdhash and therefore fresh
  grants.
- Inherited race the tests cannot express: if `AXUIElementDestroyed` for a closed tab beats the scan
  its successor triggers, the id is forgotten first and the group's column moves to wherever new
  windows go.
- The core still holds the title it met, so a group's column reads as whichever tab was selected when
  emira first saw it. Titles are frozen at first sight for every window, so this is not specific to
  tabs.
