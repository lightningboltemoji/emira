# Drop the move reports our own writes provoke

> Change `1791701442` — 2026-10-10

## Goal

`ASSESSMENT.md` P7. Each `setFrame` lands and the executor reads the frame back. The app also posts
`AXWindowMoved` and `AXWindowResized`, and `WorldWatcher.readFrame` turned those into one or two more reads,
each a position and a size, so 2–4 IPC per window. Each read then armed a 120 ms stillness wait, and its
`windowSelfPlaced` ran a placement pass that wrote nothing. The assessment counted ~16 of ~40 AX round trips
per four-window scroll as these echoes.

## Implementation

**Measured before deciding the shape.** An `axLanded` and the echo's `windowFrameChanged` arrive ~0.2 ms
apart in the trace. That fits reports which reached main during the write's lane job and queued their reads
behind it. Temporary logging of each `windowMoved` against an in-flight record confirmed it: over nine
commands on the 5K desktop, **43 of 44 reports arrived while the write was still out**. The one exception
reached main 0.1 ms after its landing. So the assessment's main proposal, a record of writes in flight, catches
nearly everything. Its fallback, a 1–2 ms debounce of moved and resized, was not needed.

**`FrameWrites`, `FocusIntent`'s shape for frames.** It is one instance per daemon. `AXExecutor` calls `begin`
for an app's group as it goes out on the lane and `end` when the landings come back. `WorldWatcher` drops a
`windowMoved` for a window that is still being written. It is a count rather than a set, because two batches
can name one window before the first lands.

**No grace period past the landing.** `FocusIntent` keeps a record for 0.5 s because focus echoes come back
by a second route. Frame echoes come back during the write itself. A report after the landing is the app
moving itself, which is P8's case and `windowSelfPlaced`'s reason to exist, so it is read as before.

**The registry's frame now comes from the landing.** `registry.noteFrame` was fed only by those echo reads.
It is the tab-succession join's corroborating rectangle, so the executor now notes each landed frame itself.

**Validated live**, A/B over the same nine-command drive (focus, `cycle-width`, `move-window`):

| | `axLanded` | `windowFrameChanged` | `windowSelfPlaced` |
| --- | --- | --- | --- |
| before | 27 | 33 | 24 |
| after | 28 | 1 | 1 |

Each dropped report was one or two AX reads, plus a placement pass that wrote nothing.

## Observations

- A report that loses the race to its own landing, ~1 in 44 here, is still read. It costs what every report
  did before.
- While a write is out, a user's drag of that same window loses its reports, for the length of one lane job.
  The next report after the landing restores the drag.
- Not tested live: an app that moves itself *during* our write, which the read-back captures, and an app
  that animates to a new frame after it.
