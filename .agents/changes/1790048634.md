# A hand on a pin's frame draws the band

> Change `1790048634` — 2026-09-21

## Goal

A pinned window could not be resized by its own frame. `grow`, `shrink` and `cycle-width` moved the
band; the resize handle did nothing, and the window snapped back on release.

The drag was seen the whole time. `driftedUnderHand` latches any on-screen window under a press, and
`World.isOnScreen` answers `true` for a pin, so the subject was latched correctly — measured through
the reducer, `Drag.subject` holds the pin from the first frame report. What declined it was
`adoptDraggedSize`, whose first guard is `participatesInTiling`: a pin is stored beside a float and
both mean *off the strip*, so the adoption read a pin as a window emira does not place. Then
`dragEnded`'s re-place wrote the band back from `metrics.pinFrames`. On a 1000 pt display with a
500 pt left band drawn out to 650, the batch that ends the drag carries `setFrame(pin, 0,0 500×800)`
— the drawn size explicitly taken back, not merely ignored.

`participatesInTiling` is the right question for a float, which emira declines to have an opinion
about, and the wrong one here: emira does place a pin, and `PRINCIPLES.md` already promises that the
handle "says exactly what `grow` says by another route". `grow` has said it to a band since pinning
existed.

## Implementation

**The branch is where the container is chosen, not inside the arithmetic.** `adoptDraggedSize` now
reads the gate, the subject and the observed frame, then sends a pin to `adoptPinnedWidth` and
everything else down the existing column path. A column and a band are the two things that hold a
width intent; asking which one owns a drawn rectangle is one decision and it is made once. Pushing
the pin case further in — a second lookup beside `workspaces.column(containing:)` — would have spread
that decision across the clamp, the height adoption and the viewport compensation, none of which a
band wants.

**The band's own record is the only new writing.** `PinPlacement` already carries a preset rung and an
override, which is what makes `grow`, `shrink` and `cycle-width` its width control with nothing behind
them; a drawn width is one more author of the same two fields. The preset survives beneath the
override for `adoptWidth`'s reason — the next `cycle-width` puts the band back on the ladder — and the
width is recorded as a share of `widthExtent`, the extent `pinWidth` resolves against and the same
extent a column's share is taken from.

**One clamp, not two.** The floor is `grow`'s, relaxed to the width the band already has, so an
adoption can stop short but never reverse. There is deliberately no ceiling: `LayoutMetrics.pinWidth`
clamps every read so the strip keeps a column's worth, and a bound here would be a second authority on
how wide a band may be. So a band drawn to the whole display records `.proportion(1.0)` as the intent
and resolves to 900 of 1000 — the intent is what the hand drew, the clamp is where it lands, and
widening the display later re-reads rather than re-clamps.

**Nothing else moves with it.** A column drag pays the viewport the width delta, because a column
grows rightward whichever edge is pulled and the offset is what keeps the moving edge under the
pointer. A band is nailed to the nominal area's own edge and grows inward from it, so the edge under
the hand is already where the hand left it, and `pinFrame` re-anchors the other one for free. What
does move is every column beside it, since the content area is narrower — arriving straight, with no
cover, exactly as the neighbours of a dragged column already arrive. Routing it through
`finishStructuralEdit` as `resizePin` does was the alternative and was rejected twice over: a cover
would film a window still draining a resize, and the hand path is deliberately outside the transition
machinery already.

## Observations

**An app that resizes its own pinned window still keeps the size**, which is now the opposite answer
from the hand on the same window. `standsWhereItPlacedItself` reads the same `!participatesInTiling`,
so `windowSelfPlaced` writes nothing for a pin and the band stays wrong until the next placement pass
happens by for another reason. It is the same conflation this change fixed one caller of, and it wants
the same one-word answer; it is left alone here because it is a different event with a different
subject, and nothing measured says how often an app moves a window it does not own the frame of.

**The hand on the glass is untested.** Everything above is measured through the reducer, which is
where all of the decision lives — the suite drives the same `dragBegan`/`windowFrameChanged`/
`dragEnded` sequence `WorldWatcher` emits. What no test can reach is the drag itself: the gate needs a
real button down, and a probe cannot press one.

**Two pins are untried.** `pinWidth`'s ceiling splits what is left evenly between them, so a drag on
one band is clamped by the other's presence and neither is a share of the other. The arithmetic is
unchanged by this and the clamp is the one already under `grow`, but no test draws a band with a
second one standing.
