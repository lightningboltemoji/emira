# A landing nobody could read back is not a landing

> Change `1788748011` — 2026-09-06

## Goal

Reported as emira very occasionally "losing track of a window's size": a window standing at one width
while the strip is laid out around another, in either direction — a column carrying space no window
fills, or a column whose neighbour begins inside it. No reproduction, and no correlation with any
verb.

`AXWindow.place(at:)` reports two independent facts, and the one that matters here is the second:
whether the window could still be read after the writes. It reads position and size back over the
same 250 ms messaging timeout the sets ran under, so an app that accepted both writes and then went
busy — which a resize is itself liable to provoke in a Chromium or JVM app — answers
`(accepted: true, actual: nil)`, or, when the busy spell begins after the corrective pass, answers with
the frame it read *before* it. The writes happened; where they left the window is unknown.

`AXExecutor.report` read only `accepted` for the verdict and sent `axLanded`. The frame
`Engine.writeTruthPlane` had written optimistically then stood as truth, `Engine.isAlreadyPlaced`
matched it, and the window was never asked again. With no `SizeCorrection` on file the column resolved
to the intent, so the strip was laid out around a width the window had refused — permanently, and with
nothing in the state saying why.

Nothing else catches it, which is what makes it survive rather than self-correct. Every other route
back to the truth runs through the window actually moving: `WorldWatcher` reads a frame because AX
posted `AXWindowMoved`/`AXWindowResized`, and an app that refuses a resize *without moving* — a window
already at its own minimum, in a column whose left edge did not shift — posts neither. The read-back
inside `place` is then the only witness there is.

## Implementation

One clause: a landing counts as landed when the write was accepted **and** a frame came back with it.
Otherwise it is `axFailed`, whose whole job is `World.unverified` — the mark that exists, in its own
words, because "a timed-out write usually can't be read back". `axFailed` also marks the landing, so
an unreadable window still cannot wedge a cover open, and it is not a retry: the mark makes
`isAlreadyPlaced` answer `false`, and the next placement pass asks again on its own.

`Event.axFailed` is widened to say so. It was "the write did not happen at all"; it is now the write
whose result the core may not believe, which covers a refusal, a timeout, and a set that went through
unreadably. The three are one fact where it is folded — the recorded frame is a guess — and giving the
read-back its own case would have added a second event with an identical fold.

The same principle cuts the other way one frame earlier, inside `place`. Its corrective pass fell back
to the frame read *before* those two writes when the read after them failed — and the writes exist
precisely to move the window, so a corrective pass that worked arrived as drift:
`placementCorrected(requested: 800, actual: 900)` for a window now standing at 800. That is the worse
half, because the fold believes it: `updateFrame` clears `unverified`, and `noteCorrection` files a
minimum the app never asserted, which `shrankOffQuestion` then makes unlearnable — every later request
*is* that fabricated answer, so no narrower truth the window offers can replace it short of an explicit
resize verb calling `forgetCorrections`. `place` now reports the read it could perform, or nothing.

Rejected: re-placing from the `axFailed` fold, so the window is re-asked in the same drain. That is
the retry `World.unverified` deliberately is not — an app that refuses every set would spin the pump
against it without bound, where the mark degrades to one extra set per real event.

Found by driving `Engine.reduce` against a model of apps that answer back. `EngineFix.settle` acks
every `setFrame`/`park` with a bare `axLanded`, so the whole refusal loop — the one machinery
`SizeCorrection` exists for — is closed by no test that does not construct its landings by hand, and
`(accepted: true, frame: nil)` was constructed by none of them.

## Observations

- Three further ways the allocation and the window can disagree came out of the same model, none of
  them addressed here, each reproducible:
  - `Layout.resolvedWidth` caps a learned answer at the content width. A window whose own minimum is
    wider than what is left beside a pin is allocated the cap and stands at its width, and the answer
    is re-learned and re-capped on every pass. A ⅔ pin leaves 504 pt of a 1512 pt display.
  - `Engine.shrankOffQuestion` declines a narrower answer whose request was not the question. From the
    moment a window has once refused to shrink, every later request *is* the previous answer, so no
    narrower answer it gives can ever be learned again — the column keeps a width the window has since
    stopped being able to reach.
  - In a stacked column only the window holding the widest answer is ever asked the question; the rest
    are asked *its answer*. When it leaves, the column collapses to the question with no record of what
    the remaining windows can actually do. On screen the next pass asks and repairs it; parked, the
    answer is discarded by design (`Effect.park`) and the column stays wrong until it is shown again.
- The height axis has the same read-back hole and the same repair, untested for the reason the width
  axis's was: no app on this desktop has been observed to leave a height set unreadable.
- `place` takes a live `AXUIElement`, so its two read-backs are reachable from no unit test. What the
  executor makes of an unreadable landing is covered; which of the two reads produced it is not.
