# Refuse the focus emira did not ask for, at one of three strictnesses

> Change `1785376482` — 2026-07-29

## Goal

Apps move focus to themselves at moments nobody chose. Dismissing Outlook's floating reminder is enough to
make Outlook raise a window of its own, and if that window is parked on another workspace the strip
faithfully follows it there: a snapped workspace switch, unasked for, away from what the user was typing
into. This is not a bug in the reveal — a focus emira did not cause is still one it must reveal, or the
user is typing into something they cannot see — it is that macOS lets an app decide, and emira was
obeying.

`[focus] system-events` makes that obedience a setting. Three escalating refusals, and the choice is how
much of macOS's own focus behaviour the user still needs: all of it (`respect`), clicking what they can
see (`on-screen`), or none of it (`ignore`).

The key is named for **what it gates**, not for the setting it is. A *system focus event* is a click on a
window, a Dock click, a Cmd-Tab, an app raising itself — which is exactly what `FocusOrigin.system` marks,
so the file, the event and the reducer's helpers all say the same word.

## Implementation

**The decision is the reducer's, because the question is about world state.** "Is that window on screen
right now" needs the layout, the live viewport offset and the workspace set. Deciding it in `WorldWatcher`
would mean the shell asking the core a geometry question and then issuing an AX write outside the effect
pipeline, which leaves `World.focusedWindow` describing a desktop that no longer exists.

**Refusing costs one effect and no state.** `refuseSystemFocusEvent` returns `[.focus(alreadyFocused)]` and
leaves `State` untouched, because the core's belief about focus never moved — re-asserting it *is* the
whole undo. Nothing reveals, nothing switches, no cover goes up. That is the point: the transition is
precisely what the user is trying to stop seeing, and a refusal that animated its way back would be a
second unasked-for motion answering the first.

**Provenance had to enter the event vocabulary.** The core cannot tell a Cmd-Tab from the echo of its own
`Effect.focus` — both arrive as `focusChanged` — so under `ignore` it would have refused every focus
command it issued. `WorldWatcher` already computes exactly that distinction to recognise its own stale
echoes (`FocusIntent.Verdict`) and was throwing it away; `Event.focusChanged` now carries a `FocusOrigin`
and `.expected` maps to `.ours`, `.external` to `.system`. Two alternatives were rejected. Re-deriving the
echo in the core would duplicate a ticket ordinal and a grace timer in a second place, and the core has no
clock. Splitting the echo into its own case would have left the 48 existing call sites untouched and put it
in the "effect feedback" section where it arguably belongs — but a case is not a dimension: someone adding
a third focus source would pick a case without ever being made to think about the policy, whereas a field
they must fill in asks them.

**The predicate is "on screen", which is deliberately not "on the strip".** Off the strip and off the
screen are different sets, and the difference is the whole of `isOnScreen`: a float is off the strip and
plainly visible, a minimized window is off the strip and in the Dock. So it tests the two facts that are
not about the strip first (minimized, `Cmd-H`), then treats anything emira does not place as visible, then
asks the ordinary `setFrame`-vs-`park` question of the rest. That last read is taken at
`viewportOffset.target` rather than `.current`, because `teleportBehindCover` moves the real windows to the
destination's frames the moment a cover is raised — mid-scroll, the target is where they actually are, and
`.current` would refuse a window the scroll is already travelling to.

The ladder is monotone by construction rather than by three independent tests: `ignore` is `onScreen`
minus the windows emira places, so `ignore ⊆ on-screen ⊆ respect` cannot come apart as the predicate
changes. `SystemFocusEvents` itself stays a dumb three-case enum in `Config.swift` — the choice in it is
policy, and policy lives in the reducer.

**Three things are admitted whatever the mode**, and each is load-bearing rather than defensive. Our own
echo, per above. A `nil` report, because it names no window and so cannot be judged — and because
refusing it would break ⌘N, where an app focuses its brand-new window before emira has adopted it and the
resulting `focusChanged(nil)` lands a moment before the creation. And a report with no focus of ours to
restore, because a desktop with no key window at all is worse than a focus nobody wanted. Before the first
`screensChanged` there is no geometry to judge against either, and no grounds to refuse is not a refusal.

**`ignore` still honours focus onto a window emira does not place** — a float, a dialog, a sheet. Not a
grudging exception: emira already declines an opinion about where a float *sits*, and policing focus onto
one is the same opinion. It is also what keeps a modal save sheet usable, since at this layer a sheet
taking focus and a Cmd-Tab are one indistinguishable notification, and bouncing focus off a save dialog
locks the user out of their own document.

`World.isAppHidden(of:)` is new, and `participatesInStrip` now reads the flag through it, so the two
questions that care about `Cmd-H` consult it in one spelling.

## Observations

Nothing here has been driven against a real desktop yet — the whole feature is exercised through the pure
reducer, which is the right place for the policy but says nothing about how the refusal *feels*. Three
things need watching:

- **How loud the refusal is.** By the time a focus report reaches us the offending app has already
  activated, so `.focus(ours)` re-activates our app behind it. The expected artifact is a menu-bar
  flicker; it could be worse.
- **Dock-clicking a minimized window.** If the app posts `AXFocusedWindowChanged` before
  `AXWindowDeminiaturized`, the report is refused and then the deminimize arrives and focuses the window
  anyway — the right outcome by a visible bounce. Which notification lands first is unmeasured.
- **Focus wars.** An app that re-asserts focus on losing it will ping-pong against the restore at AX
  latency. No damper was built: the loop needs an app that fights back, and pre-building a suppressor for
  a failure nobody has seen would be a mechanism with no measurement behind it.

`respect` remains the default, so none of this is reachable without asking for it.

Two things this deliberately does not touch. **A new window still takes focus in every mode** — an
arrival is not a focus report, and "a new window shouldn't steal focus" is a separate policy better spelled
as a window rule. And the mode is **config-only**: there is no command to change it at runtime, which
would want a `Command` case and a place for the CLI to read it back from.
