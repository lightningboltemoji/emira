# A veil that moved is an event

> Change `1789539018` — 2026-09-15

## Goal

Two columns at half width tile the viewport, so focus crossing between them scrolls nothing and raises
no cover: the veil is drawn by the standing scrim alone, and it cut. Two columns at 55% do not tile, so
the same keystroke scrolls a little, raises a cover, and `1789538233` fades the veil across the motion.
The same gesture on the same desktop, one instant and one smooth, decided by whether the columns happen
to add up to more than the screen.

## Implementation

`1789534267` turned Core Animation's implicit dissolve off on `ScrimWindow.cut`, and it was right to: a
mask repainted because our reading of the window server had gone stale is a **correction**, and a
correction that dissolves reads as the window deciding to become transparent by itself. But the dissolve
was never the problem — applying it to every repaint alike was. A repaint has two causes and they want
opposite treatment.

**So the plane names the cause and the window draws it.** `Scrims.apply` already computes the veil each
window is drawn at, per display; it now keeps that map from the last apply and compares. A veil that
moved is something the user did, and `setRegions(_:fading: true)` dissolves the mask over
`ScrimWindow.fadeDuration`. A rectangle that moved under unchanged veils is us catching up with the
window server, and it cuts. Per display, because a scrim is one screen's: a focus change on one is not an
event on the other, whose mask is only ever being corrected.

The veils rather than the rectangles is what makes the test hold up. The stack the mask is painted
against *does* change on a focus change — activating an app reorders the window server's list — so
"nothing moved" is not available as the signal, and `restack()`'s whole purpose is that something moved.
What separates the two cases is that a correction leaves every window at the veil it already had, which
is exactly the state `1789534267` measured its fix against: "the same state was diffed before and after
a forced re-apply that changed no binding and moved no window".

Cross-fading the mask's `contents` is the same mechanism Core Animation was applying on its own, asked
for deliberately and at a length we chose: the mask's alpha at a pixel *is* the veil there, so
interpolating it interpolates the veil. Nothing else about the scrim moves.

### Validation

The two columns cycled to half width so they tile exactly, confirmed uncovered by the absence of a
`capture:` line in the daemon's log. One region inside each window, same rects, same gesture both ways:

| | window losing focus | window taking it |
| --- | --- | --- |
| cut | 82.98 → 48.99 in **one frame** | 38.61 → 55.06, same frame |
| dissolve | 48.99 → 83.19 over **105 ms**, 7 frames | 55.41 → 39.10, same frames |

Same endpoints in both directions, so it is the same change drawn twice: once as a jump between two
consecutive frames, once as a ramp. 105 ms against the 120 ms asked for is frame quantisation at ~58 fps.

## Observations

- **The desktop photograph still swaps hard.** A refilm writes `host.contents` with no dissolve, so a
  wallpaper that changed under a scrim pops. It is throttled to once every two seconds and nobody has
  reported it; the same `fading` seam would carry it if anybody does.
- **A window closing or opening moves veils, so it fades.** Both also raise a cover, which hides the
  fade, so this is reasoning rather than measurement.
- **`ScrimWindow.fadeDuration`, `Reconstruction.veilDuration` and `refreshDuration` are all 0.12 s** and
  now all mean "how long a veil takes to change". They are three constants in two files because they are
  reached from different places, not because anybody wants them to differ.
