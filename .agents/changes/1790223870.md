# A window with no title bar that cannot resize is not a window

> Change `1790223870` — 2026-09-23

## Goal

Hovering Zoom's in-meeting toolbar tiled its popups — "Meeting security" (400×180) and "My Notes"
(300×277) — as columns, one per hover. Every question the classifier asks answered "window": role
`AXWindow`, subrole `AXStandardWindow`, `AXMain` settable, and each popup takes focus and main when it
opens. They sit at window level 0 beside real windows. Zoom keeps the window-server window and orders it
in and out, but the AX element is destroyed and re-created each time, so every hover is a fresh
`windowCreated`: a new `WindowId`, a new column.

A recording of every Zoom window over a session showed the rest of the app shares the shape under other
subroles — its "Menu window"s and "More meeting controls" (`AXSystemDialog`, level 99), a toast
(`AXSystemDialog`), a 600×324 `AXSystemFloatingWindow`, and one window whose subrole is the literal string
`AXSubrole`. Those floated rather than tiled, and paid the adoption cost `1785993114` describes on every
appearance. Its tooltips were already declined: they answer no role at all.

## Implementation

`WindowRole.init?` declines a window that has **no title bar and is not resizable**, whatever its subrole,
after the role and full-screen checks and before the subrole switch. "Resizable" is `AXSize`'s
settability; "title bar" is any of the close, minimize or zoom buttons, or `AXTitleUIElement`. Both are
autoclosures, as `canBecomeMain` is: resizability costs every window one round trip at first sight, and
the up-to-four title-bar reads are paid only by a window that cannot resize.

Zoom's shape reproduces in AppKit as `[.titled, .fullSizeContentView]` with a hidden, transparent title
bar and a `canBecomeMain` override: `AXStandardWindow`, main-capable, no buttons, no title element,
fixed size. A plain `.borderless` fixed window with the same override answers `AXUnknown` instead, which is
why the subrole cannot be the test — the same style of window reports differently depending on how the
title bar was hidden.

Each half alone was rejected in `1785993114`, and both reasons still hold, which is why this is a
conjunction:

- Fixed size alone drops Safari's Settings and every other titled, non-resizable window.
- No buttons alone drops a decorationless terminal (`[.borderless, .resizable]`), which must stay
  tileable.

The title bar test is two signals because neither one alone covers every title bar. A `.titled` window with
none of `.closable`, `.miniaturizable` or `.resizable` lists **no buttons at all** in AX — measured, all
three absent — while its title bar still shows its title, so `AXTitleUIElement` answers. A unified-toolbar
window (Safari, Ghostty) hides the title and answers no title element, but keeps its buttons.

Declined rather than floated. A float is still adopted per appearance and still enters
`World.window(at:)`, where it wins the `follows-mouse` hit test over whatever is under it; these popups are
the chrome that the find-bar change declined, reached by a different signal.

## Observations

Verified through the shipped path — a harness linked against the built `EmiraShell`, calling
`AXApplication.windows()` → `AXWindow.snapshot(bundleId:)` — over the live desktop and eight synthesized
style masks:

| window                                                  | result   |
| ------------------------------------------------------- | -------- |
| `[.borderless, .resizable]`, main override (terminal)   | standard |
| `[.titled, .closable]`, fixed (settings)                | standard |
| `[.titled]`, fixed, with and without override           | standard |
| `[.titled, .miniaturizable]`, fixed                     | standard |
| hidden title bar, all buttons hidden, resizable         | standard |
| hidden title bar, no buttons, fixed, override (Zoom)    | declined |
| `[.borderless]`, fixed, with and without override       | declined |

On the live desktop the change also declines windows that previously floated: macOS's `MenuBarAgent`, an
untitled `AXDialog` in Safari, and a window of `zip.tanner.bario` (`AXSystemDialog`). All are fixed-size and
bare. Worth confirming that none of them is something a user moves between workspaces.

Not verified end to end with the daemon running Zoom: an ad-hoc rebuild re-prompts for Accessibility.

The known false positive is a real window of this shape — a borderless, fixed-size game or emulator
window, or a frameless non-resizable Electron window. Declined, it belongs to no workspace, so it stays on
screen across switches and no rule can reclaim it, since rules run after classification. A window that
*becomes* resizable or titled after first sight is re-classified by any later scan of its app, and
reconciliation scans while it is on screen and unmanaged — three rounds, `reconcileInterval` apart — so
one that changes shape within about nine seconds is adopted; later than that waits for the app's next
scan.

That on-screen, unmanaged window buys its app a reconciliation scan for three rounds per appearance, as
Chrome's find bar already does. Bounded, and cheaper than the adoption it replaces.
