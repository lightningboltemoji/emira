# A focus emira did not cause moves the strip to its window rather than jumping

> Change `1785477519` — 2026-07-30

## Goal

Closing the focused window sometimes left the survivor standing in its final place instead of sliding
there. Reported as "closing the last window in the strip, when the remaining window doesn't need to
move much" — a window at 80% beside one at 25%, close the 25%.

The close itself was never at fault: fed `windowDestroyed` alone, the reducer opens a session and
springs the viewport 108 pt over 32 frames on that geometry. What eats it is the event *in front of*
it. AppKit hands key status to a replacement window synchronously and destroys the closing element
later, so `AXFocusedWindowChanged` normally arrives before `AXUIElementDestroyed`, and the watcher's
backfill filter — one `isAlive` probe on the closing app's own lane — can be answered while the element
is still valid. The report then reaches the core as an ordinary Cmd-Tab, which snapped the viewport to
reveal the survivor. That snap lands on *exactly* the offset the close was about to travel to, so the
`windowDestroyed` a beat behind it computes `start == end`, displaces nobody, and emits nothing at all.

The visibility of it tracked the geometry because `[focus] system-events = "on-screen"` decides
whether the backfill is admitted: a survivor still overlapping the viewport is on screen and the report
gets through, while one scrolled entirely out of view is refused and the close animates untouched. "It
only happens when the window doesn't need to move much" and "it only happens when the survivor was
still partly visible" are the same condition.

Answering that with a transition then exposed a second, older defect, which is the other half of this
change. `emitPlacements` wrote the truth plane at `viewportOffset.current`, and that number stops
describing the real windows the moment a cover goes up: `teleportBehindCover` has already put them at
`.target`, and `.current` is what the spring is feeding the layers. **Every click is a mouse-up**, so
`Event.dragEnded` landed tens of milliseconds inside the reveal that same click had just started and
dragged every real window to whatever fractional offset the animation had reached — one emitted
`setFrame(w1, x: -948.75)`. The cover then cross-faded onto a desktop scrolled part-way back: a click
animated over and jumped back, a slower release left the strip stranded mid-scroll, and a second click
found `start == end` and fixed it with a plain placement pass, which is why clicking twice worked.
Only a keyboard scroll could reach this before, and only if a click landed inside one.

## Implementation

`revealAcrossWorkspaces` sends a focus report for a window with a column through `scrollReveal` rather
than `reveal` — the same covered transition `focus left` opens. Both orderings now come out as one
scroll to one destination: the backfill aims a session at the survivor, and the destroy behind it
retargets that session instead of finding the viewport already at rest where it wanted to go. Off the
strip — a float, a dialog, a sheet taking focus — there is no column to frame on and nothing to scroll
to, so that case keeps `reveal`'s placement pass, which is also where the resting-offset clamp lives.

The cross-workspace branch goes with it, and the argument for keeping it a snap did not survive being
written down. "Two strips are a screen apart with nothing between them to animate" is a claim about the
*span*, and `handleFocusWorkspace` animates that exact span on demand — measured, not reasoned: from one
state, the verb opens a session over two captures and the identical report by Cmd-Tab emitted one bare
`setFrame`. So the axis was never who initiated the motion, and a desktop that glides when you press the
key and cuts when you Cmd-Tab to the same place is the two-window-managers complaint one axis over.
`revealAcrossWorkspaces` now reads the before-geometry `handleFocusWorkspace` reads and hands it to the
same `switchWorkspace` call, which is the whole diff — the animate-or-snap decision was already one
guard on that parameter, and there was never a second code path to keep in step. It costs a cover on a
Cmd-Tab across workspaces, on the same terms as everywhere else, and `[focus] system-events` is the same
answer it is for the horizontal case.

This retires "we made no motion, so we owe no animation" (`PRINCIPLES.md` §4a), on both axes. The rule was
about *obligation*, and obligation turns out to be the wrong axis: a reveal is a move of the strip whoever
asked for it, and a strip that jumps for one kind of move and glides for the other reads as two
window managers. The rule also could not compose, which is the actual defect — it treated a focus
report as a standalone event when it is routinely the first half of a structural change, and spent that
change's motion before its second half arrived.

`emitPlacements` became `reassertTruthPlane`, a router selecting on a new `MotionPhase` —
`TransitionSession.Phase` plus the case a session cannot represent, its own absence. Covered goes to
`teleportBehindCover`, capturing to nothing (no real window has moved yet, and the raise's own teleport
reads what this would have written), idle to the placement pass, which keeps the walk under the name
`placeAtRest`. The rename is the point of the split: two of the three answers emit no placement, so the
old name described only the branch that survived as `placeAtRest`. The phase is one value rather than
`isCovered` and `isTransitioning` tested in sequence because those two overlap, so a chain of them is
correct in only one order and nothing in the source says which — ask `isTransitioning` first and every
covered re-place silently emits nothing, which is a frozen desktop under a raised cover. Both booleans
stay as projections of the phase, most of their readers genuinely asking one yes/no question. The
routing sits in the function rather than at its call sites for three reasons: seven of them can be
reached mid-transition, `handlePlacementCorrected` and `reaimViewport` had both already grown this
routing inline (which is where the shape came from), and nothing about a mouse-up or a config reload
makes its handler the right place to remember that a cover might be up. The clamp inside `placeAtRest`
drops its `isTransitioning` guard, which the caller now establishes.

`World.placedOnScreen` is the same fact turned around for readers: which windows the last placement pass
put on the glass. `isOnScreen` reads it in place of `visibleWindowIds(at: viewportOffset.target)`, which
is true of the reals only *after* a raise. That predicate is how `[focus] system-events` judges a report,
and a refusal is an AX write rather than a shrug — through a reveal's capture head the old reading refused
windows still plainly on the glass and yanked focus back off the click that had just landed. Making every
reveal a transition is what turns that from a rare cost into the common one, so the two halves of this
change are the same change.

It is **recorded by the writers rather than derived**, which is the difference between answering the
question and answering it under `smooth` only. Every way of aiming runs ahead of the windows it aims:
`.current` is the spring's under a raised cover, and `snap` aims by writing *both* ends of the offset at
the open, so through a snapped capture head no animator still holds where the windows are. So the
placement pass ends by naming what it just wrote — which it is entitled to do and nothing else is, being
the only `setFrame`/`park` in the reducer. Deriving it instead (`isCovered ? target : current`) is right
only while a second, unwritten invariant holds — that nothing re-aims a raised cover without
re-teleporting — and only under the one mode whose `.current` has not already been spent.

**What is recorded is the `setFrame`-vs-`park` decision, not the offset behind it.** Recording the offset
is the obvious reading of "where the reals stand" and it is only half an answer: turning a number back
into "can the user see this window" needs the layout it was measured against, and a capture head is
exactly where those two come apart, being the one phase that restructures the strip without re-placing
anything. Measured on three full-width columns — open a head, close the leftmost column — the written
offset read against the strip as it now is points a screen past the end of it and reports an empty
desktop, so a click on the window physically filling the display is refused. That is the failure this
record exists to prevent, reproduced by the record. Keeping the decision freezes both inputs together,
and it is strictly less machinery: the predicate loses its `metrics` read, its workspace test and its
layout query, because a pass parks everything off the focused strip and membership already says all
three. It lives in `World` beside `unverified` rather than in `Motion`, being a fact about the real windows
and not an animated quantity — `Motion` holds three of those and a session, and this was never a fourth.

That also makes `refuseSystemFocusEvent` take its `State` by value. It reconciled only so the predicate
could read a window's workspace off the strips; with the strips out of the question it changes nothing at
all, and "a refusal is one `.focus` effect and no state change" stops being a comment.

That entitlement is load-bearing enough to be structural rather than observed, so the two writers became
one. `writeTruthPlane(at:)` holds the diffed emission, the optimistic `World` write and the record — which
covers every managed window, including the ones already standing correctly, where the effect stream is a
diff and names only what moved. `World.notePlaced(onScreen:)` is `internal` where its neighbours are
public, which is as structural as "one writer" gets here: the shell only reads core state, and every other
mutator on `World` folds an `Event` the shell has to be able to build.
`placeAtRest` and `teleportBehindCover` keep only what distinguishes them — the resting clamp and which
offset is the truth on the one side, arming the landing wait on the other, which is why `moved` is now
every window that needed a set and the scope filter sits at the caller. The loop was already duplicated
verbatim; what makes deduplicating it more than tidiness is that a second copy of it is a second place to
move a real window without saying so.

`holdTimeout` gained a `reassertTruthPlane` after its close. A session that times out in its capture head
never teleported anything, but closing it snaps the viewport to the destination regardless, leaving the
strip claiming a scroll no window performed and nothing scheduled to correct it. Free for the covered
case, which teleported at the raise and is already there. `CaptureService`'s own 0.25 s deadline resolves
every batch well inside the 1 s hold, so this is a guard rather than a live bug — but the reveal routes
every Cmd-Tab through it.

That is one of **four ways out of a capture head, and the capturing answer is a deferral owed by all of
them** — worth enumerating, because a head that exits without placing fails silently. The raise teleports;
`coverUnavailable` aborts and re-places; `holdTimeout` is the line above; and `abandonTransition`, reached
when a switch is handed no before-geometry, closes the session with `finishStructuralEdit` placing behind
it. Only the last discharges the debt from outside the function that incurred it, so it is the one that
can come apart without anything saying so, and it is now pinned by a test rather than by an argument.

That is also what retires `TransitionSession.didTimeout`, which existed to make the reducer "retry any
unlanded AX set" after a timeout and was never once read — the reducer had no such branch, and the case
that genuinely needed one is the capture head the line above now covers. The covered case wants no retry
at all: its sets are in flight on the app's own lane, not lost, which is why closing over them emits
nothing. A flag whose stated purpose turns out to be both unimplemented and unwanted goes with the change
that establishes it.

Chosen over hardening the filter in `WorldWatcher.resolveFocus`, which was the smaller diff and the
wrong shape. The question it asks — did the displaced window die? — is not answerable at the moment it
has to be answered, so any filter is a majority rather than a proof; making it a better majority (a
grace before believing a report, a window-server-list check instead of the AX probe) buys reliability
with latency on every genuine reveal and still loses sometimes. Animating removes the *consequence* of
losing rather than trying to stop losing, and the filter stays as it is: worth keeping, since a report
it lets through still scrolls the strip to a window nobody asked for, which is its own complaint.

## Observations

Verified in the reducer, both orderings, at two geometries. `EngineTests` gained
`aFocusBackfilledAheadOfTheDestroyLeavesTheCloseInMotion` for the ordering;
`aMouseUpMidTransitionDoesNotDragTheRealsToTheSpringsOffset`,
`aDragEndingMidTransitionSnapsBackToTheDestinationFrame` and
`aMouseUpInTheCaptureHeadDefersToTheRaisesTeleport` for the three phases;
`aHoldTimeoutInTheCaptureHeadStillPlacesTheWindows` and
`aWorkspaceSwitchAbandoningTheCaptureHeadStillPlacesTheWindows` for two of the four exits. In
`SystemFocusEventTests`, `aWindowStillOnScreenThroughTheCaptureHeadIsNotRefused` and
`aWindowStillOnScreenThroughASnappedCaptureHeadIsNotRefused` are the record's two modes, beside the
covered case already there; `aStructuralEditInTheCaptureHeadDoesNotStrandTheRecord` is what an offset
could not have answered, and asserts *both* readings — the viewport's, now empty, and the record's, still
right. `externalFocusRevealsUnderACoverWithoutEmittingFocus` replaces the test that asserted the
horizontal snap, and `WorkspaceCommandTests.externalCrossWorkspaceFocusAnimatesLikeTheWorkspaceVerbDoes`
the vertical one — that one drives the verb from the same state and compares capture sets, so it fails if
the two paths ever diverge again rather than merely if this one stops animating.

The branches that could have been silently deleted were confirmed by mutation: dropping the capturing
case leaves the whole suite green in the absence of the test named for it; restoring the
`viewportOffset.target` reading fails all three capture-head tests; restoring `animatingFrom: nil` fails
the cross-workspace test on all three of its claims.

Not verified on a live desktop: the premise that the probe really is answered "alive" during a close is
a macOS timing fact no test in this repo can observe, and the fix is deliberately built so that it does
not need to be true — it is an improvement to a race it does not have to win.

A Cmd-Tab, a Dock click or an app raising itself costs a capture batch and a cover **where it moves the
strip**, against one AX write per window before. Which reports those are is a config away from being all
of them: under `center-focused-column` every focus lands its column in the middle, so every click on a
different column scrolls, while without it `offsetToReveal` hands back the offset it was given for a
column already fully in view and the click stays free. Across workspaces there is no free case — a switch
always moves — so that is the one where the change is a straight new cost. Nothing bounds how often an app
may activate itself, so a badly-behaved one self-activating in a loop now raises covers in a loop — worst
under centering, and `[focus] system-events` is the existing answer either way.

`arriveOnWorkspace` is now the only caller left handing `switchWorkspace` no before-geometry, and it was
not re-examined here. Its case is genuinely different — a window a rule sends elsewhere has no old frame
to travel from, which is what that parameter seeds — but the *switch* around it is the same one that now
animates for a Cmd-Tab, so whether a rule-assigned window should arrive on a moving strip or a cut one is
an open question rather than a settled one.

The daemon logs a `transition:` line per cover, which is the cheapest way to tell these two paths
apart from the outside: a close that snaps leaves no line.

A drag that ends while a cover is up now snaps the window back to its frame at the scroll's end rather
than at the offset the strip is passing through, which is right — but it also means the cover is
animating a layer for a window whose still was captured before the drag. The layer is stale for the
rest of that transition; `refreshLayer` exists and nothing currently asks for one here.
