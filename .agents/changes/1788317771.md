# The animation nobody was allowed to see

> Change `1788317771` — 2026-09-02

## Goal

Closing TextEdit's Open panel with ⌘W snapped the column shut. ⌘Q on the same panel was perfect. Reported
as a render stall, and it is not one: the frames were all there, at rate, every time.

Measured over fifteen closes, emira's own report never varied — `43 frames in 366 ms (118 fps)`, no drop,
no long `dt`, no main-thread block. The spring was computed, committed and correct. What a second process
sampling `CGWindowListCopyWindowInfo` at ~4 kHz saw was something else entirely:

```
25197.7801  windowDestroyed          the close transition opens
25197.7924  panel alpha 1.000 → …    AppKit begins the window's close animation
25197.8348  coverOnScreen            the fence fires; the reals are teleported
25197.8422  axLanded ×2              Finder reports both windows moved
   ⋮                                 cover alpha as published: 0.000
25198.0545  ← everything at once     cover 0.999, reals at their new frames, panel destroyed
25198.1958  endTransition            the cover dissolves
```

**While an app runs a window-close animation, the window server can go on not showing what this process
commits.** For 216–500 ms the raise and every layer frame behind it were withheld and then published in a
single frame. `CADisplayLink` goes on firing throughout — the display is refreshing, it just is not
showing us — so the fence saw two callbacks, called the cover up, and the reducer teleported the real
windows and started the spring against a screen that was not taking them.
By the time anything was presented the animation had travelled 873 of its 890 points: the first visible
frame is **98% of the way through**, which is a column snapping shut, and on a shorter deferral it is the
tail end of a slide arriving from nowhere.

Three controls place it exactly. ⌘Q destroys the window outright with no animation, and the cover is
published 113 ms later — perfect, as reported. `NSAutomaticWindowAnimationsEnabled = false` makes ⌘W
behave identically to ⌘Q. And ⌘W on a Finder window — which animates its close just the same — defers
nothing, the cover landing 7 ms after the raise; whatever the panel's XPC hosting does on the way out, the
deferral is not a property of closing a window in general.

## Implementation

The fence gains a second half. The display link answers whether a frame has been shown since the raise;
the window server is asked whether ours was in it, through the alpha it has **published** for the overlay.
`CGWindowListCopyWindowInfo` opens by synchronizing this process's pending Core Animation commit, so the
question does not answer until the raise has been taken — one asking absorbs a deferral of any length, and
`publishGrace` bounds only the never-observed case of a server that keeps answering "not yet".

Measured cost of that read: **0.65, 2.8, 3.7 and 10.3 ms** while the desktop is publishing normally, and
**215.6 and 216.1 ms** while it is not. It is asked off the main thread, on the overlay's own serial queue.
The rule `1788313347` wrote down — this call costs what *we* have in flight — is what makes that safe here
rather than a repeat of what that change removed: nothing is painted while a cover is `.raising` (the
reducer drops those ticks), so the read contends with no frame commit of ours. Verified against the
external sampler: the fence now fires **7 ms after** the window server actually publishes the cover, so it
reports the deferral rather than extending it.

Nothing else needed changing, and that is the point — the phase machine already forbids everything that
went wrong. `.raising` writes no truth plane and consumes no motion; the whole defect was one report made
too early. After: the reals teleport 13 ms after the cover is published, the cover is up for 359 ms, and
the first visible frame is **2.4%** into the travel.

**`coverRaisedAt` moves to the fence.** The smoothness number is frames over the life of the cover, and
timing from the raise would charge a deferral to the animation — the same close read `43 frames in 576 ms
(75 fps)` before this moved and `43 frames in 347 ms (124 fps)` after, describing one transition twice.

**`Runtime.onReduce`** is kept for the reason `StallProbe` was. Off unless `EMIRA_TRACE=1`, it prints every
event with the effects it produced and a monotonic timestamp, which is the instrument that separated "emira
dropped frames" from "emira's frames were not published" — a distinction the frame counter cannot draw,
since it counts blits issued and this bug issued all of them.

**Rejected: `NSWindow.occlusionState`.** The obvious public signal, and it says nothing: the overlay is
ordered in permanently at alpha 0, so the server considers it visible from launch and posts exactly one
notification, at boot. No edge at the raise, none when the deferral lifts.

**Rejected: waiting for the closing window to leave the window server's list** before opening the
transition at all. It is the more principled statement — the window server is the authority on what is on
screen, and the destroy notification fires at the *start* of the close animation — and it would also take
the closing window's ghost out of the cover's base. But it is not the same wait: a Finder window stays
listed for 284 ms after its destroy while deferring nothing, so this would charge every close a delay the
defect does not justify, and on one measured run the panel was still listed after the deferral had already
lifted. The fence waits exactly as long as it must and no window close pays for another's.

## Observations

**The base still carries a ghost of the closing window.** The base is a photograph of the display with the
transition's *scoped* windows cut out, and a window that just closed is not scoped — it left `World` before
the batch was built. So a cover raised 44 ms into a close animation has the half-faded window baked into
it, frozen, for the length of the transition. Present before this change and unchanged by it; visible for
longer now, since the cover it sits on is no longer showing only the last 2% of the animation.

**The wait's cause is not established, only its shape.** It reproduces on TextEdit's XPC-hosted Open
panel and not on that app's own document window, a Finder window, or ⌘Q — 235 ms against 7–18 ms — and it
needs `NSAutomaticWindowAnimationsEnabled`. Nothing on our side is slow while it lasts: no
`CATransaction.commit` exceeded 3 ms, the capture head is 40 ms, and the main thread ticks throughout.
The fix does not depend on knowing: it waits for the server to say it is showing our cover, whatever was
stopping it.

**`publishGrace` has never fired.** Every fence measured answered `0.999` on its first asking. The retry
path exists for a server that answers short of the glass, which no measurement produced, and past the
grace the fence degrades to what it did before — a cover reported up on the display's word alone.
