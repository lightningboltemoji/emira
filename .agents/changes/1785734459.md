# What crosses between two displays, and what survives one leaving

> Change `1785734459` — 2026-08-02

## Goal

Four gaps a review of the landed multi-monitor work turned up, all of them in the two places the phases
never had a second display to try: a window handed **across** the desktop, and a display **departing**
from it.

`move-to-workspace` onto an address another screen was showing animated on neither screen. The
destination judged the edit invisible and hard-cut the arriving window into place; the source gave it a
layer and then never framed it, so it hung at its capture frame until the cover dissolved. §4 of the plan
tabulates that verb as raising two covers and change `1785729909` claims both covers draw the window
"where their own strip says it belongs" — neither was true, and nothing in the suite could see it.

A display that left lost its scroll position outright: `Motion.reconcile`'s own comment says the memory
outliving a display is the per-workspace offset `Workspaces` holds, and nothing ever wrote into it, so a
replug returned the workspace to the strip's origin. On the zero-display path the two containers
disagreed about *whose* state to keep — `Monitors` kept the focused display's address, `Motion` kept the
lowest-numbered survivor's viewport — so a lid close could come back showing the right strip in the wrong
place. And `unattached.shown`, chosen with care for exactly that moment, was then discarded by the
`detached` reclaim, which every departing display leaves an entry for.

## Implementation

**A crossing is one difference, computed once and read twice.** A structural edit animates `before −
after`, and each display's geometry answers only for the strips it holds — so a travelling window is
missing from the *after* side on the screen it left and from the *before* side on the one it reached,
and each display's own difference yields no move for it at all. That is the whole bug, in both
directions: no move means no displacement to animate, and on a destination with nothing else in motion
it also means nothing to raise a cover for. `Engine.crossing` reads the pair the displays cannot —
the frame the source snapshot holds, and the frame the display that now owns the workspace lays it out
at — which is well defined because natural frames on every display share one global space.

Seeding it **once** is not an optimization but the correctness condition: `Motion.displaceWindow`
accumulates onto an existing animator, and the animators are the desktop's rather than any display's, so
the obvious per-display patch (fill each side's missing frame, let `moves` pick it up) doubles the
journey and opens the layer a full screen past where the window was. Hence the crossing is computed
before the per-display loop, excluded from `moves`, and asked separately when each display decides
whether it has anything to cover — a window arriving on an otherwise-still screen being precisely the
case where it is the only answer.

**A cover has to name what it draws from elsewhere.** `emitLayerFrames` resolves against
`naturalFrames(among: owned)`, which cannot place a window that has left this display's strips, so the
departing layer had no frame emitted for it on any tick. `TransitionSession.carried` names it and the
frame is asked of the display holding it now — the same global number that display's own cover uses, so
both draw the identical journey and it reads as one window crossing rather than two cutting.

Rejected: making the fallback unconditional, so that *any* scoped window this display no longer holds is
drawn at its true home. One rule instead of a named set, and it needs no new field — but it also reaches
`move-workspace-to-monitor`, where a whole strip departs at once with no crossing seeded for any of it,
and the windows would jump a screen away on frame one instead of freezing. That verb's outgoing slide is
a deliberate deferral in change `1785729909`, and turning a freeze into a pop is not the way to close it.
Naming what actually crossed keeps the two verbs' behaviour separate, which is what they are.

**A reconfiguration is a workspace switch on every screen at once.** Which is the fix for the scroll, and
it is the switch's own two halves rather than anything new: `bankViewports` stores each display's scroll
against the address it is showing before the containers move, `resumeViewports` puts each display back at
the memory of whatever it shows afterwards. A display whose address did not change reads back the number
it just wrote, so the ordinary case is an identity; a departing display's number lives on in the address,
which is what a returning id reclaims. Banked at the scroll's **target**, since the same report closes
every cover and `closeTransition` snaps each viewport to exactly that — at rest the two are one number.

That subsumes the zero-display disagreement rather than patching it. The address memory is authoritative
on the way back in, so which viewport `Motion` happened to keep detached stops being able to contradict
`Monitors` about what the user was looking at. `Motion`'s own hand-off stays: it keeps that container
correct standing alone, and it is now the same number by construction.

The whole thing is skipped when the report describes displays `World` already holds — the exemption
`State.setMonitors` already had for closing covers, and for the same reason. Re-seating a viewport on a
redundant `screensChanged` would snap a spring mid-travel, which is the scroll's version of writing the
truth plane onto bare glass.

**The adoption outranks the reclaim.** In `Monitors.reconcile` the display that adopts the detached
desktop keeps `unattached.shown` instead of its own `detached` memory. Every display departing into a
zero-display state leaves a memory behind, so a reclaim that always won meant the address `unattached`
exists to choose never survived a lid close — the one case it was written for. A display whose address it
really was reclaims it in the same pass, and the adopter falls back through the ladder that was already
there, so nothing new can cascade.

**`StatusModel` says what the other screens are showing.** §7 of the plan asked for this and only its
first half landed. The title is one character and goes to the acting display; the rest follow it in the
tooltip. Empty on one display, so every string there is byte-identical to what it was.

## Observations

**Three of the four were invisible to the suite and one was invisible to it by construction.** The
crossing is a `setLayerFrame` stream, which no test read until this change added one; the scroll loss
needed two `screensChanged` events in a row, which nothing did. Both are now pinned by tests that were
confirmed to fail without the fix.

**The `move-workspace-to-monitor` source still does not slide away**, unchanged and deliberately — see
change `1785729909`. It is now the only verb whose hand-over is not drawn by both covers, and the shape
of the fix is this change's: name what the cover carries from elsewhere. What that verb hands over is an
*address* rather than a window, so what it needs is the address's windows resolved against the display
that took it, plus a seed per window, and the seeding-once argument above applies to every one of them.

**`reachable` is accretive, and D1 reads as though it were a partition.** `show` claims and never
releases, so the addresses a relative ref skips are the ones another display *visited*, not the ones it
holds windows on: two displays and enough browsing leave `focus-workspace next` stepping over a run of
empty addresses forever. Untouched here because it is a decision rather than a defect — either `show`
releases an empty address it leaves, or `reachable` is defined by occupancy — but it is the next thing to
try on a real two-screen desktop.

**Still owed: the visual check**, now for four phases' worth. Specifically: a window sent to the other
screen leaving one and arriving on the other as one motion; a display unplugged mid-scroll and plugged
back in; and the lid close on a docked laptop, which is the only way to reach the zero-display path at
all.
