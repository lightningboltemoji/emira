# Squeezing columns that do not fit beside a pin

> Change `1794881741` — 2026-11-16

## Goal

A pin narrowed where the strip could be drawn and left every width alone. That kept ½ meaning half the screen,
but it also meant a column wider than what the pin left could never be shown whole. Beside a ½ pin, two 100%
columns could be focused and scrolled between, and each one still ran off the display's edge. The strip
promises that a window is never clipped to fit, and pinning broke that promise without saying so.
`PinTests.aPresetWiderThanTheClearAreaIsStillTheWidthItAsksFor` described the old behaviour as intended.

The ask was fullscreen-like memory: squeeze the column into the room left, and give it back its natural width on
release.

## Implementation

**A bound applied when the width is read, not a mode.** `LayoutMetrics.squeezed` sits under the width stack in
`Layout.uncorrectedWidth`: `min(w, clear) + max(0, w − screen)`. What fits is untouched. What a pin made overflow
is cut to the clear width. Overflow the intent asked for (`width-presets = [1.5]`) keeps its distance past the
clear area, which a plain `min` would have thrown away. Nothing is recorded, so the memory comes free: unpinning,
moving the column to an unpinned display and adding a second pin need no code of their own. `fullscreen` stops
being a special case. It is now `.proportion(1.0)` of the nominal width, squeezed, which is exactly what it
previously resolved against `contentExtent` for. That made `contentExtent` dead, so it is gone.

**The real work is the writers.** A squeeze held only at read time stays invisible until something measures a
width on screen and stores it. Three places do that: `grow`/`shrink` (which measure from the resolved width on
purpose, to avoid a dead zone), `adoptWidth` after a hand resize, and `handlePin`, which seeds the band from the
column's resolved width. Each now stores `LayoutMetrics.unsqueezed`, the inverse, stated beside the formula it
inverts. Below the clear width it is the identity, and above it, it adds the overflow back. On the clear width
itself, where everything from the clear width to the screen's width lands, it keeps the width the column already
asks for when that width is in that range. So a `grow` against the clear width, or a drag outward, stores what was
there rather than 50%. Disabling the inverse fails exactly those three engine tests.

**`shrink` overwrites.** It drops below the flat part of the squeeze, so it is a width the user chose by looking
at the screen, and it stays after release. That was a decision, not a fallout.

**`cycle-width` passes over rungs that come out alike** (`PresetCycle.nextIndex(after:unlike:_:)`), comparing
each candidate's squeezed width against the column's resolved width. With the default ladder beside a ½ pin, ½
and ⅔ both give the clear width, so without the skip one press in three did nothing. With 1.0 on the ladder, two
in four did. The rule is about the width rather than the pin, so a ladder with a duplicate entry is now skipped
over too. A ladder whose every rung comes out alike still takes the plain step, keeping `resizeFocusedColumn`'s
contract that the stored rung moves.

**Rejected: a proportional squeeze** (every column scaled by clear ÷ screen). It would make ½ mean a quarter of
the screen beside a ½ pin, which is the re-proportioning the pin model exists to avoid.

**Rejected: a larger floor on the strip's width beside a pin.** `pinWidth` still guarantees the strip only
`minimumColumnWidth`. A pin that leaves 100 pt squeezes every column to 100 pt, and apps that refuse to go that
narrow overlap. That is the user's call when they draw a pin that wide.

## Observations

Verified in a Tart VM (macOS 27.2, 1760 pt display, `column-gap = 12`, ladder `[⅓, ½, ⅔, 1]`) on a release
build against a baseline built from `HEAD`, through `emira debug` and the window server's own frames. The
baseline reproduced the report: a ½ pin at 874 pt, with columns 1760 pt wide starting at 886. With the change,
those columns are 874 pt, exactly 886 to 1760, and the stored intent is still preset 3. A `grow 10%` left the
width at 874 and stored 1.0. A `shrink 10%` stored 0.401 (698 pt), which survived release. Release brought the
grown column back to 1760. A `cycle-width` from ½ beside the pin went to ⅓, skipping ⅔ and 1.

Pinning now resizes, not just moves, every column wider than the clear area, on every workspace the display
holds, including parked ones. Each one is asked a new width question, so each app re-lays out and answers
again. Growing or shrinking a pin does the same on every press. The resize rides the structural edit's existing
displacement, so no new animation was needed. The cost of the burst of AX writes on a display with many wide
columns has not been measured.

On film, a pin crossing the strip briefly shows wallpaper at the far edge, because the pin and the column it
swaps with move apart. The baseline shows the same strip of wallpaper for this arrangement, so the squeeze did
not introduce it, though a column that narrows as it slides can hold the gap a little longer.

`cycle-width` can no longer reach a rung that comes out alike while pinned. Beside a ½ pin, a column at ½ cannot
be cycled onto 100% to have it come back at 100% on release: it would be skipped as ½. Nor can `grow` do it,
since it stops at the clear width and keeps the ½ underneath. `fullscreen` is the one way to ask for the whole
screen while pinned. The pin's own `cycle-width` does not skip; its rungs only come out alike past
`pinWidth`'s ceiling.

`keepExistingWidth` (the launch scan) does not unsqueeze, since no pin survives a restart.
