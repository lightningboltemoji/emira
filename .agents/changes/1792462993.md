# Focus on nothing: the keyboard comes off a window emira has left

> Change `1792462993` — 2026-10-19

## Goal

`fn-b = "exec open /Applications/Fiber.app"` was meant to always reach Fiber, and did only conditionally. With
Fiber focused on workspace 1, `focus-workspace 2` onto an empty workspace set the core's focus to `nil` and told
macOS nothing, so Fiber stayed the active app with its parked window key. `open` on an app that is already
active activates nothing, posts no focus report, and emira never revealed it; a Dock click and Cmd-Tab fail the
same way. The same gap sent anything typed on an empty workspace into the parked window — `PRINCIPLES.md` §4's
"never focused on something you cannot see", broken on the keyboard. The conversation began as a `focus-app`
verb; reproducing the failure put the cause here instead, and this fixes every route to the app at once.

## Implementation

**Core.** `Effect.focusNothing(MonitorId)`, emitted by the `settleFocusOnNothing` post-pass when a **command**
takes focus from a window to `nil`: a switch to an empty workspace, the last window sent away, a move onto a
display showing an empty workspace. Departures are left to macOS on purpose. ⌘H reaches the core as
`windowMinimized` per window (`AppState.isHidden` is never fed), so the core cannot tell it from a minimize, and
after ⌘H or a quit macOS activates another app whose report is already in flight; an asynchronous sink landing
after that report would leave the core believing in a window while keys go to the sink. A `nil` report is not
answered either — that is focus on Spotlight, Raycast, a menu bar app. The `[focus] system-events` refusal with
no anchor (an empty workspace) now emits `.focusNothing` rather than nothing, since its own doc justified the
silence with "nothing here can unfocus a window". `State.owedFocus` widened from `WindowId` to `OwedFocus` so the
pin gate holds focus-on-nothing like any focus: otherwise the fence's activation of the pin's app lands after
the sink and leaves the keyboard on the pin. A debt of nothing is paid only while the core still focuses nothing.

**The sink is a second process, measured into being.** The plan was the daemon itself. A prototype with one
`.normal`-level window ordered to the back — standing in for `PeekPanel` — saw it raised above Ghostty the moment
the process was brought forward, and left there until another app activated. Moving peeks below `.normal` was
rejected: `Scrims` (`kCGWindowLayer == 0`), `StackProbe` and `DesktopCapturer` read layer 0, so a peek there loses
its veil, and proving otherwise needs two displays. A separate process can only raise its own invisible window,
and keeps taking keys while the daemon's main thread is blocked on AX (an active, blocked daemon would show a
beachball). It is the daemon's own executable run with `--focus-sink` rather than a second target, so packaging
is unchanged, there is one bundle identity, and `emira watch` names it as the app.

**Getting it to the front.** `NSApp.activate()` from a background accessory process was refused in the prototype
(front stayed Fiber); `AXFrontmost` written on the process's own app element, off the main thread, took the front
in ~4 ms. The shipped path is the daemon writing `AXFrontmost` on the sink's pid through its `AXClient` lane — the
route `AXWindowWriter.focus` already falls back to — so the sink needs no grant. `FocusIntent.request(nil)` puts
the request on the record: an earlier window's activation is dropped and its echo is stale, and a record whose
newest request was for nothing skips `onCleared`, whose read would otherwise name the parked window and reveal it
— undoing the verb, and bouncing back after half a second if the sink ever failed to come forward.

**The sink's window** is 1×1, alpha 0, at `normal − 1` (outside `WindowRegistry.windowLevels`, so reconciliation
never adopts it), on every Space so taking the keyboard never switches one, and swallows `keyDown`; with no main
menu ⌘Q and ⌘W do nothing. The first live run caught it taking the front **at launch**: `makeKeyAndOrderFront`
during launch is read as the launch asking for the front. It now orders in on `didBecomeActive` only. The daemon
starts it at boot (a fresh process cannot take the keyboard until it has checked in), sends `x y` lines on its
stdin, and its stdin closing ends it — verified by stopping the daemon. `AXExecutor.displays` now carries
`MonitorInfo` so the effect's display can be resolved.

**Validated live** on a `.build` daemon with the author's config, frontmost read by pid from `lsappinfo`: Fiber
focused on 1, `focus-workspace 2` → the sink in front; `open /Applications/Fiber.app` → workspace 1, Fiber
focused and in front, 53 ms capture head. A real fn-b from empty workspace 3 → the same. `focus-workspace 1`
from the sink → Fiber in front. System Settings pinned left, switch to empty 2 → the sink in front at 150 ms and
settled, the pin kept, `focus-pinned` reaching it. Under `system-events = "on-screen"`, `open` Fiber from empty
2 → refused, the desktop stayed on 2, the sink back in front within 400 ms. Measured: the sink's window at layer
−1, 1×1, centred on the display, alpha 0; three windows managed, the sink's not among them. The prototype logged
keystrokes arriving at the sink.

## Observations

- **Closing or minimizing the last window on a workspace still leaves the keyboard to macOS**, and an app with
  windows parked elsewhere hands one of them the keys. Fixing it needs ⌘H told apart from a minimize (an
  app-hidden event that feeds `AppState.isHidden`), then a sink for a same-app hole-fill only.
- Untested on two displays; the sink stands on the acting display's frame through `ScreenGeometry.current()`.
- Found in passing, not changed: the daemon itself becomes the frontmost app at launch from a terminal — the
  installed HEAD build too — so keys go nowhere until the user clicks something.
- Found in passing, not changed: a hidden (⌘H) app's windows return on the un-minimize path beside the current
  anchor, on the workspace the user is on, where `IMPLEMENTATION.md` *Window rules* says "position remembered".
- The `focus-app` verb is not built. `exec open -a` now covers the empty-workspace case; what a verb would still
  add is independence from `[focus] system-events`, no wait on the app's activation, and an answer for the
  hidden-app case above.
- A sink that dies is restarted by the next `focusNothing`, which itself is dropped: the new process has not
  checked in yet.
