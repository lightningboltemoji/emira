# Unfocused windows you can see through

> Change `1789528513` — 2026-09-15

## Goal

Make the window you are not working in look transparent, so focus reads off the desktop without a
border, a badge or a dimming wash.

macOS will not do it. Setting another app's window alpha is a SkyLight call and therefore SIP-off
(`PRINCIPLES` §2), and no public API comes near it. But the blend a transparent window performs is not
privileged — it is one line of arithmetic, and it is symmetric:

    drawn = v · backdrop + (1 − v) · window
    true  = (1 − v) · window + v · backdrop

Those are the same number. So a window of ours, standing exactly where the real one stands and holding
what is *behind* it at `v`, is not an imitation of transparency at `1 − v`; it is transparency at
`1 − v`, arrived at from the other side. Nothing here is approximate, which is why the feature can be
defended at all — the presentation plane's usual trade, a frozen still for smooth motion, is not being
made. What it *can* get wrong is never the blend. It is only ever the backdrop.

## Implementation

### The backdrop is the desktop, and that is a claim about what is behind a window

One photograph per display, taken with **every** window excluded — wallpaper, desktop icons, widgets,
nothing else (`DesktopCapturer`). Where a window sits directly on that, the photograph is exactly what
a transparent window would show.

Where another *window* is behind it, the photograph is a lie of the worst kind available here: it
replaces a real window with wallpaper, and the depth of the desktop reads inside out. This is not a
subtle failure. Photographed on a five-tile cascade at `v = 0.35`, the desktop icons along the right
edge appeared *through* all five windows, so the icons that are behind everything read as floating on
top of the pile.

So the rule the whole feature rests on: **a window is drawn see-through only where the desktop is what
lies behind it.** Its three consequences are one consequence.

- On the **strip** it is always satisfied, because `strip` promises windows never overlap
  (`PRINCIPLES` §1). That promise is doing real work here for the first time: it is what makes one
  photograph the true backdrop for every window on the surface.
- A **float** over a tile declines, and so does a tile with anything under it.
- A **cascade** declines almost everywhere, and that is the honest answer rather than a gap. A `stack`
  tile is backed by another tile; standing in for that needs a photograph per window, refilmed whenever
  anything behind anything redraws — a standing capture load the cover itself is careful not to carry.

The rejected alternative was to pay it: `SCContentFilter(display:excludingWindows:)` per window gives
an exact backdrop for each. It costs N full-display captures per focus change, on the window server's
serialized screenshot path — the ~25 ms-a-window cost the capture plane is built around avoiding — and
the pixels behind a window go stale the moment anything there redraws. One photograph, refilmed when
the desktop is quiet, is ~0 per focus change.

### Where the decision is split, and why that is not two opinions

The core names windows: unfocused, on `placedOnScreen`, at `1 − [focus] unfocused-opacity`. The shell
decides which of them the photograph can honestly back. That is the seam `capture` already sits on —
the core asks for a still, the shell reports it could not take one — and it is the right seam here for
a sharper reason: the physical stacking of the desktop *includes the windows emira never placed*, and
that is the window server's fact, not the layout's.

### One window per display, and the mask does the occlusion

The opposite shape to `HoistPanel`, for the opposite reason. A hoist must *take* the clicks that land
on it and the only region the window server routes on is a window's frame, so the frames have to be the
hoists. A scrim takes no clicks at all, so it is free to be one surface per display — and being one
surface is what makes the occlusion exact: the mask is painted **back to front** over the window
server's own ordering, so a window in front of a see-through one punches its own hole by being painted
after it. Nothing reasons about which rectangles overlap which.

Two details the first version got wrong and the tests now pin.

- **The veil lives in the alpha channel.** `CALayer.mask` reads alpha and nothing else. A grey mask
  with no alpha channel hides nothing, and the result is the entire desktop photograph drawn over the
  entire screen at full strength — which is what it did.
- **It is painted in `.copy`.** A painter's algorithm needs paint that covers; blending would leave a
  window in front half-veiled by the one behind it.

Per-window veils ride in the mask's grey levels, so the window itself stays at `alpha 1` and one
surface still serves any number of windows at any number of strengths.

### The display a scrim is backed by is a layout fact

`hoistBindings` asks `world.monitor(at: frame.center)`, and this reached for the same thing. A float
sits inside the screen it is on, so a centre answers for it. A **column** does not: the strip is
infinite and the viewport is a slice of it, so a column at the edge routinely hangs half off with its
centre in the parked region beyond — `monitor(at:)` returns `nil`, the binding is dropped, and the
effect vanishes for exactly the window a scrolling tiler leaves at the edge of the screen. Found by
running it: one of two on-screen windows was simply never scrimmed. A pin names its own display, a
window on a layout takes the display showing that layout's workspace, and only what is on neither is
asked where it happens to be.

### The cover has to carry the veil too

A cover is a photograph of the desktop it replaces, so a cover that draws every window opaque begins
every transition by making every unfocused window flash back to solid. Measured with a third-process
burst capture at ~20 fps across a `cycle-width`: the widget visible through the unfocused window
disappears at the frame the cover goes up and comes back when it comes down — a two-ended flash on
every covered transition.

On this plane transparency is simply transparency: these are layers we own, over a base that holds the
desktop, so `root.opacity` is the whole fix. It is read from `Scrims.veil(of:)` at the moment a layer is
built — the same moment, and for the same reason, as `LayerBinding.isFocused`. A stand-in stands for the
window as it was filmed, and the window as it was filmed had the desktop showing through it; the focus
change riding in this transition reaches it the way every other one does, through the cross-fade at the
end. Asking the scrim plane rather than deciding again is what keeps the two planes from forming two
opinions — one decision, read twice.

The alternative was a `veil` on `LayerBinding`, decided by the core. It needs the core to reproduce the
shell's decline or the cover and the desktop disagree, and it would have put the *new* focus on a
stand-in filmed under the old one.

### Calibration

`[focus] unfocused-opacity`, one number, `1` and off by default — a window manager must not start
altering how somebody's apps look. The veil is `1 − it`, clamped at 1 in the reducer because a `Bound`
spells floors and not ceilings.

The consistency question has a measurable answer. Since the drawn pixel is `v·B + (1−v)·W`, the change
a veil makes is `v·(B − W)`: **at a fixed veil the amount of effect is exactly the luminance distance
between a window and whatever is behind it.** So it varies with position over the wallpaper, and the
instrument (`measure` mode, mean |ΔL| per window in 0–255 luminance) says by how much. On a
high-contrast wallpaper, `v = 0.3`, one window over bright fog and one over dark forest:

| backdrop treatment | mean ΔL | spread |
| ------------------ | ------- | ------ |
| none               | 16.5    | 22.3   |
| blur 30            | 14.1    | 26.3   |
| flatten 0.5        | 29.0    | 10.6   |
| flatten 0.5 + blur | 29.1    | 10.2   |

**Blurring cannot even it out** — a blur keeps every low frequency it had, and the low frequencies are
the whole of the variation. Blending the photograph toward its own mean halves the spread, and at a
veil scaled back to match the mean effect it cuts it further. Neither is in this change: both give up
the property the design rests on, that the scrim is the same arithmetic as real transparency, and the
spread is a property of the wallpaper rather than of the setting. `0.7`–`0.75` reads well by eye.

## Observations

- **The photograph is refilmed only when the desktop is quiet** — at build, on a display change, and
  after a cover comes down, throttled to 2 s. Never on a focus change: the window server serializes
  screenshots, and a focus change is also a cover, whose batch is the one latency anybody can feel. A
  desktop *widget* therefore ticks late behind a window you are looking through, by up to the gap
  between transitions. A wallpaper changed while nothing transitions is not noticed at all.
- **The corner radius is the constant 12**, `Reconstruction.fallbackCornerRadius`'s value and its
  caveat. A standing scrim has no capture to measure one off. What a wrong radius costs is a
  corner-sized triangle of the window's own shadow lightened by the veil. `SurfaceCache` does hold a
  measured radius for any window a cover has ever filmed, if it proves visible.
- **The mask is a full-display bitmap rebuilt on every change** — 8-bit alpha at native scale, so
  ~8 MB on a 2× 1800×1169. Rebuilt on focus changes, not on frames, and never while a cover is up. Not
  measured; if it shows, the obvious move is to keep one context rather than allocate per repaint.
- **A cascade gets no effect**, by the rule above. Whether the per-window backdrop is worth its capture
  load is the open question, and it is the only route to `stack` having this at all.
- Untested: more than one display, and a window straddling two of them.
