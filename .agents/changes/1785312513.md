# Join each app against its own window list, and check the desktop on a heartbeat

> Change `1785312513` — 2026-07-29

## Goal

Windows were sometimes not adopted at boot — more often with many windows open, and never with a clear
pattern as to which. The suspicion was a truncated enumeration; it was not. `AXUIElementCopyAttributeValue`
on `AXWindows` returns the whole array (the paginated form is `AXUIElementCopyAttributeValues`, which we
do not use) and `CGWindowListCopyWindowInfo` returns the whole list in one call. Both sides of the join
saw everything. The losses were downstream, and there were two of them.

**One list read for a whole fan-out.** `enumerate(apps:)` fans out to every app in parallel, but `finish`
read `source.windowList()` once, when the *last* app answered. An app answering at 5 ms had its AX frames
joined against a list read at the slowest app's latency. The join matches on the frame within ±2 pt, so
any window that moved in that interval matched nothing and came back `.noCandidate`. At login, windows are
being restored and settling, so movement is the norm. This is why the symptom tracked total window count
rather than any property of the window that went missing: more windows meant a slower slowest app, which
meant a wider gap for *every other* app. Measured on a quiet desktop the fan-out spread is ~1 ms; the
whole point is that it is not quiet at boot.

**Nothing ever asked again.** Discovery was entirely edge-triggered. The bounded retry (three scans, 150 ms
apart) covers races measured in frames, and after it `onIncompleteScan` logs and no code path re-checks
anything. Two failures fell straight through it and were silent as well as permanent:

- `Report.unclaimed` counts only on-screen entries — correctly, since ordinary apps carry off-screen
  layer-0 oddments that are not windows. But a window on another Space or in the Dock that AX also failed
  to describe therefore set neither `unbound` nor `unclaimed`, so `isIncomplete` was false and no retry
  fired.
- An app absent from `applications()` at the boot instant — not yet `.regular`, or no `bundleIdentifier`
  yet — was never scanned, and could never be. `didLaunchApplicationNotification` does not fire for an
  already-running process, `windowAppeared` is gated on `apps[pid]`, and the retry deliberately reuses
  `report.apps` rather than re-asking the source. Its windows did not even count toward `unclaimed`,
  which filters on `scannedPids`.

## Implementation

`ScanAnswer` bundles one app's windows with the window list read beside them, and `WindowSource.windows(of:then:)`
delivers that instead of a bare `[ScannedWindow]`. `AXWindowSource` takes both reads on the app's lane,
back to back: `CGWindowListCopyWindowInfo` queries the window server rather than the app, so it is safe
off the main actor and safe concurrently across lanes, and taking it there also keeps the main-actor hop
out of the gap — under boot load that hop is itself worth tens of milliseconds. It costs ~2.5 ms per app.

`finish` therefore decomposes into a per-app `join`, aggregated into the same `Report`. This changes no
outcome, which is the argument for doing it: `bind` narrows candidates by owner before comparing frames
and a `CGWindowID` belongs to one process, so no window of one app could ever match, contest or displace
a window of another. The join was always per-app; it was merely fed a global list. Two consequences worth
naming. `available` is now filtered to the app's own entries, which makes the reliability test (`disagrees`)
exactly what its comment always claimed — previously it scanned every pid's entries and inserted foreign
pids into `unreliable`, harmlessly but confusingly. And the report is assembled in `apps` order rather than
answer-arrival order, so a scan is deterministic however the lanes race.

The retry now targets `Report.incompleteApps` rather than `report.apps`. `isIncomplete` is redefined as
`!incompleteApps.isEmpty`, which is exactly equivalent to the old `mayHaveMissedAnArrival || !undescribed.isEmpty`
— an app is incomplete iff it contributed a rejection, an unclaimed entry, or an undescribed window.
`mayHaveMissedAnArrival` is deliberately left as a whole-report property: it gates the succession wait in
`absorb`, and narrowing that to per-app is a change to the tab-succession path with its own risks, not
part of this.

Reconciliation is a `Heartbeat` seam alongside `DelayScheduler`, not a reuse of it. The two are different
in kind — a retry terminates, a heartbeat does not — and concretely, a repeating tick drained by the tests'
`fire()` loop would never let `theRetryIsBoundedRatherThanARepeatingScanOfTheUsersDesktop` finish. It is
optional on `WorldWatcher` and defaults to nil, so a test that isn't about reconciliation ignores it.
Every 3 s, `reconcile` reads the window list, takes the on-screen entries the registry does not know, and
scans their apps — resolving an unknown pid through `enumerator.applications()`, the question the retry
chain will not ask. Found windows are announced `alreadyOpen`, since by definition emira did not watch
them open. `maxReconcileRounds` caps attempts per window *number*: an on-screen layer-0 entry AX will never
describe is a real thing, and level-triggering on it without a cap is a scan of somebody's app every 3 s
forever. The budget is dropped as soon as a number stops being listed, because the window server reuses
numbers.

Rejected: a lower `maxScanAttempts`/`rescanDelay` tuning pass. The retry chain is the wrong instrument for
these failures — it is scoped to races that resolve in frames, and stretching it to cover an app that is
slow for seconds would delay every ordinary boot to pay for a rare one.

## Observations

The two AX-side failure modes remain unaddressed, both deliberately. `snapshot()` is seven round trips per
window, serially per app — the join needs only the frame, and deferring title/minimized to adoption would
roughly halve fan-out latency and the residual skew with it. And a permanent frame disagreement between AX
and the window server (suspected for Catalyst apps such as System Settings, unconfirmed) would still fail
every attempt identically; reconciliation would retry it three times and then stop, which is the correct
behaviour but not a fix.

Reconciliation is untested against a real desktop under load — the machine it was developed on had four
apps and two windows, well below the conditions that produce the bug. `scratchpad/probe.swift` is an
instrumented replica of the boot scan (same app filter, lanes, timeout, seven reads, join) that reports
per-attribute AX errors, both sides of every failed join, per-app latency and the answer spread; it is the
tool for confirming the skew fix on a desktop that actually reproduces the symptom.

One unreproduced observation worth recording: on the very first probe run against apps that had never been
AX-contacted by that process lineage, every window was dropped before the join, and this did not recur
across twelve subsequent fresh processes. If cold first contact really does behave differently, it would
sit upstream of everything here.
