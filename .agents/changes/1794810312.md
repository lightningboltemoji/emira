# A cover that stands in with stills seconds old

> Change `1794810312` — 2026-11-15

## Goal

`cover = "immediate"` raises on the base alone and stands in for each window with the still an earlier cover
left behind. The match is size alone, and size says nothing about content: a window that kept its size for ten
minutes while it was typed into fits a still ten minutes old, and that is what crosses the screen before its own
capture lands and cross-fades over it. In use that flash of something entirely different is distracting.
`immediate-fresh` keeps `immediate`'s head latency and bounds the stand-in's age to seconds.

## Implementation

**A third `CoverMode`, not a separate key.** The refresh only means something where a still may stand in, so
an interval beside `exact` would be a setting with no effect; the three read as one choice — wait, start stale,
start recent. Named `immediate-fresh` rather than a word of its own, because it is `immediate` with one
thing added, and a hyphen is how the config's values say so (`on-screen`); not `immediate-refresh`, because
`immediate` already refreshes, each layer sharpening as its own capture lands (`captureRefreshed`), and not
`immediate-async`, since every mode captures asynchronously. `CoverMode.standsIn` replaces every `== .immediate` (the core's `keptStills`, the capture
service's stand-in match, the daemon's `keepsStills`), and `refreshes` is `immediate-fresh` alone. The interval is a
constant (`CaptureService.refreshInterval`, 3 s), on the trackpad gain's reasoning: it wants use before it
earns a key.

**The core names the set; the shell films it.** What the next cover most likely scopes was already the core's
answer (`keptStills`, at `crossfadeDone`); it was emitted as one `keepStill` per window, which cannot say
"nothing" — a display switched to an empty workspace emitted no effect, and a refresher holding the previous
set would go on filming windows now parked on another workspace. So the effect became `keepStills(monitor,
[WindowId: Size])`, the whole set, empty included, and `CaptureStore.keep` takes it as a replacement. The
alternative, the shell re-deriving on-screen-ness from registry frames, is the second opinion about the
screen `PRINCIPLES` §1 rules out.

**The set gained a shoulder column either side** (`sweptWindowIds(from: o, to: o)` rather than
`visibleWindowIds`). A one-column focus move brings one on, and it is the stand-in the eye follows in. Under
`immediate` this costs nothing: the cover that just came down scoped those shoulders and filmed them at the
size they still have, so the top-up finds them fitting.

**The refresh lives in `CaptureService`** beside the top-up it extends, with the scheduler, the cache and
`isIdle` it needs already there. One global clock rather than one per display, keyed by each still's age
(`SurfaceCache.age(of:)`, off the `takenAt` the hole rule already kept): a window younger than half the
interval is left, which skips both a cover's fresh film and the last refresh's own (stamped a little after
the tick that asked for it, so a full-interval threshold would skip every other round). A per-display
clock reset by each `keep` was the other shape; it starves one display's refresh while the other is busy.

Films go **one at a time**, each through `film`, checking `isIdle` before the next and abandoning the round
when anything else is out: the window server serializes screenshots, and `SCKCapturer` measured one at
~25 ms alone against ~41 ms with another in flight, so a batch of five would hold a keypress's head behind all five. As built, a keypress landing on a refresh waits behind
at most the one film in flight. Nothing is filmed while input has sat for 30 s
(`CGEventSource.secondsSinceLastEventType(.combinedSessionState, …)`, which needs no grant — checked from an
unprivileged script): a standing capture cost with nobody watching is waste, and the next round after input
returns is at most 3 s away.

`transition = off` runs the shell as `exact` (`applyShellConfig`): with no cover nothing names a set, and one
left over from before the switch would be refilmed for nothing.

## Observations

Run on the desk (the built-in 3024×1964 display, two Ghostty windows, `cover = "immediate-fresh"` via `EMIRA_CONFIG`, input held warm by
a zero-distance synthetic mouse move, which `secondsSinceLastEventType` counts): a round of 2 windows took
105–163 ms, every ~3.3 s, so the window server is filming ~4–5% of the time while someone is at the desk.
Every cover raised on the base at 54–56 ms with both windows standing in (`2/2 standing`), against 150 ms for
the boot cover that had nothing kept. With input left alone the last round ran 28 s after the last input and
none after it. No keypress landed on a round in that run. One would cost up to the film in flight (50–80 ms a
window here), so `immediate-fresh` is not latency-free: it is `immediate`'s head ~95% of the time and a film slower
otherwise. The shoulder column went unexercised there (two windows, both on screen); the engine suite covers it.

- The first transition after coming back from more than 30 s idle can still stand in with a still as old as
  the absence. Waking the refresh on the first input after a lull would close it, at the price of an
  input observation the daemon otherwise only installs for `focus-follows-mouse` and `hide-cursor`.
- A refreshed still is reduced like any other, so `immediate-fresh` stand-ins are recent and soft. Filming the refresh
  at the cache's ratio directly would skip the full-resolution capture and its reduction, but would also
  read the corner off a quarter-scale image and overwrite a better reading at rest.
- Windows further than one column away, and other workspaces, still stand in from whenever a cover last
  showed them; a workspace switch is where `immediate-fresh` and `immediate` differ least.
- The settings preview (`Scenes.coverTrade`) draws `immediate-fresh` as `immediate`: it has no notion of a still's age.
- `animation.cover`'s help is the first to wrap in `config.example.toml`: naming three modes and saying the third
  retakes its stills in the background does not fit one comment line. `everySettingIsWrittenDown` matched each
  help as one unbroken string, which held every help to a line without saying so; it now reads them back across
  the wrap. Settings shows help on up to two lines, and this one takes two there, as the old one did.
