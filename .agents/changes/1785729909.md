# The eight verbs, and what a reference means with more than one display

> Change `1785729909` — 2026-08-02

## Goal

Phase 4 of the multi-monitor plan: the verbs that name a display, and the two resolution rules under
them. Phases 1–3 made the desktop hold several displays — each with its own strip, viewport, cover and
metrics — but the only way a window reached a second screen was `move-to-workspace` naming an address
that display happened to hold, and `focus-workspace` naming an address another display was *showing*
yanked it onto the acting monitor, because `Monitors.show` claims for whoever asked. That churn is
what D1 exists to fix, and it is visible the moment a second display tiles.

## Implementation

**`MonitorRef` is `WorkspaceRef`'s shape, and clamps for its reason.** `index` / `direction` / `next` /
`previous`, resolved on `State` because the spatial answer needs `World`'s frames and the enumeration
needs `Monitors`' records. A ref with nowhere to go resolves to the *acting monitor*, so "nothing that
way" is spelled the same as `next` at the end of the strip and every verb turns it into silence in one
place. A direction is the nearest frame centre in that half-plane — primary-axis distance, tie-broken
on the cross axis and then on enumeration order — which is what makes `focus-monitor down` different
from `focus-monitor next` on an L-shaped desktop. `focus-monitor 0` is a **syntax** error rather than a
clamp: reading a typo for `1` as `1` would make the off-by-one silent, and the spelling is a different
question from the resolution.

**D1 in one line.** `Workspaces.resolve` grows a `within:` set and `Monitors.reachable` supplies it —
the acting monitor's addresses plus every address no display holds. An absolute name ignores it, which
is the "just work" requirement; a relative motion stays inside it, because the monitor is the container
and cycling should not leave it. On one display "held here or held by nobody" is all 36 addresses, so
single-display behaviour is unchanged to the letter, and the alternative — a per-display *set* of
reachable names stored somewhere — would have been a second authority over ownership.

**Which display switches is the destination's to decide.** `switchWorkspace` moves `Monitors.focused`
to whichever display holds the address *first*, so every read after it is that display's own. Two
things had to come apart to make that work. The address focus is **leaving** and the address going
**off screen** are the same on one display and different on two, so the `lastFocus` write moved to the
top of the function (before the user travels) while the scroll write stayed beside `show`. And
`abandonTransition` moved *after* the focus move, since the cover that must not outlive its desktop is
the one on the display that is about to change. The same fix reaches `revealAcrossWorkspaces`: a
Cmd-Tab to a window living on another screen was the identical yank, arriving by another route.

**`finishStructuralEdit` takes a list of snapshots, one per display the edit changes.** This is the
widest part of the diff and the part most likely to break something. Each display decides for itself
whether it has anything to animate, so one may open a cover while the other lands its share at once,
and the `reassertTruthPlane` that used to sit in three early returns now runs once at the end if any
display snapped. One display is that list with one element — the dedupe in `snapshots(of:)` is what
keeps "one screen" the special case of "several" rather than a branch. Two behaviours fall out rather
than being written: a window that changed displays is in one side of the difference only, so no
displacement is seeded for it and both covers draw it where their own strip says it belongs; and
`move-to-workspace` to an address nobody is showing covers one screen, because the destination's
snapshot yields no moves and no scroll.

The one place a fiction was needed is `structuralSnapshot(travelling:)`. Invariant 4 says a workspace
never animates *between* displays — a hand-over is two independent switches — so the destination's
before-geometry has to place the arriving address one screen away, which it cannot do from ownership
alone, since it does not own it yet. Passing the travelling address makes both screens read it as
theirs for the length of the snapshot, and the destination's slide-in is then the ordinary vertical
switch. Without it `move-workspace-to-monitor` was a hard cut on both screens.

**`move-workspace-to-monitor` is `Monitors.show(name, on:)` and nothing else.** The claim already moves
`owned` with `shown` and already repairs the loser, so handing an address over needed no new mutator —
what it needed was a better fallback. §3's rule (nearest occupied among what the display still holds,
then nearest own-or-unassigned, then the existing third rung) replaces "the lowest address it owns",
and it needs occupancy, which only `Workspaces` can answer. That is plumbed as an argument on the two
mutators that can trigger a repair rather than stored, because a container holding a copy of occupancy
would be a second authority over it. `State.show` supplies it, which is what the join is for.

**Rejected: counting covers by verb.** §4 of the plan tabulates how many covers each verb raises, and
it is one short in one row — `focus-workspace` onto another display changes only that display's shown
address, so it is one cover, not two. Nothing was built to make the table true; the count is a
consequence of what each display's snapshot says, and asserting it separately would be a second
opinion about the same fact.

## Observations

**The source's departing workspace does not slide away.** When a display hands its workspace over, the
address is claimed by the destination immediately, so it leaves the source's `owned` — and a cover
draws `naturalFrames(among: owned)`, evaluated per tick. The source's outgoing windows therefore have
no position to travel to and their layers sit frozen at their capture frames until the cover dissolves,
which is exactly what a *departure* looks like today and is what D4 accepts in principle ("both covers
hold a still of workspace 2's windows"). What the plan wants is a slide, and getting it means the cover
knowing about an address its display no longer owns — one field on `TransitionSession`, set at
`openTransition` and read by `emitLayerFrames`. Deferred deliberately: it is a presentation refinement
to the most delicate type in the project, for one verb, and it is a thing only a running daemon shows.

**A source falling back to an *empty* address raises no cover at all.** Nothing arrives and nothing can
slide out (above), so the edit is judged invisible and snaps. The destination still covers.

**`focus-monitor` renumbers park ordinals.** `Monitors.shownWorkspaces` puts the acting monitor first,
and `placementOrder` hands out park slots in that order, so moving between displays re-parks the
off-screen columns of both strips. All of it is corner slivers and none of it is wrong, but it is N AX
writes for a verb that moves nothing. Making `shownWorkspaces` enumeration-ordered would remove it and
would also make nubs stable across a focus change — a phase 3 decision to revisit with a reason, not
here.

**A window closing on the display the user is *not* on still snaps.** `departFromStrip` reads the
acting monitor's strip, so a window elsewhere fails its guards and falls through to a plain placement.
Correct, and one display shorter than it should be; the fix is the same shape as this change's
(snapshot the display holding the window) but it drags `focused`, `successor` and the reveal with it.

**Still owed: the visual check.** Two displays, `move-workspace-to-monitor` both ways, and
`focus-monitor` onto an empty screen followed by ⌘N to prove the newcomer lands there.
