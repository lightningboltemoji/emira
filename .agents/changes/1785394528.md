# the schema gets its first consumer, and it is text

> Change `1785394528` — 2026-07-29

## Goal

The schema became a table so that four things could read it, and until one of them did, the claim that
it was general was untested. `emira config` is the cheap consumer, and it comes before the settings
window on purpose: if the table can drive a page of prose it isn't secretly GUI-shaped, and a mistake
in it shows up somewhere with no AppKit in the way.

```
emira config check              # parse the file; print the diagnostic or say nothing
emira config explain [<key>]    # what a setting is, what it may be, what it is now
emira config get <key>
emira config set <key> <value>
```

`set` is also the whole write path proven end to end for the price of a few lines: `ConfigDocument`
splices the value, the file is saved atomically, and the running daemon picks it up from its own watch.
Nothing on this path dials the socket.

## Implementation

**`config` is not a verb and must not become one.** It branches in `main.swift` before `Command.parse`
sees a word of it, because the config file is not a thing you ask the daemon to do — there is no request
to send and no reply to wait for. The same reasoning gives `--dry-run` a refusal rather than a shrug: it
prints the request that would be sent, and this sends none. Help learns the subcommands from
`ConfigCommand.usage`, which is to these what `Command.usage` is to the verbs — a second list beside it
rather than a fork of it, since the two vocabularies are answerable by different things.

**No sentence about a setting is written down in the CLI.** The label, the help, the legal values, the
default and the current reading all come off `ConfigSchema`, and `explain`'s two shapes are generated the
way the example file is: `Setting.explanation(in:)` and `ConfigSchema.summary(of:)` live in
`EmiraConfig` next to `ConfigExample`, which also makes them testable — an executable can't be imported,
so the tree's habit is that anything with logic in it lives a target down. What stayed in the executable
is what has no logic: argv, exit codes, and the disk.

**`set` parses a value from a word, and the codec does the refusing.** The word is built into the value
the setting's kind expects, and a word that can't be read that way is built into a *string* on purpose —
"must be a number, not a string" is already the right sentence and it is already written down. So the
bound is checked once, in the reader, and `emira config set layout.column-gap -5` gets the file's own
complaint. The one accommodation to the terminal is that a shell eats the quotes the file wants and
splits a list on its spaces: `adopt`, `"adopt"`, `[0.5, 1]` and `0.5 1` all arrive and all mean what they
look like. `ConfigSyntaxError` gained a `message` — the complaint without the line it names — because a
value that came from an argument has no line, and "line 0" would be a lie about where the number came
from. `ConfigLoadError` was already reaching for that string by cutting the prefix back off
`description`; it now asks for it.

**Setting something to its default unsets it**, which is `Setting.isDefault(_:)` rather than a rule the
CLI knows: an absent key already means the default, and writing it down pins it against ever changing.

**Refusing to write a file that doesn't parse** is task 2's rule arriving at its first caller, and it is
worth a sentence about *why* rather than only a diagnostic: an edit is a splice into text whose meaning
is unknown, and the rest of the file is the user's work.

The atomic save is `Data.write(.atomic)`, which *is* the temp-file-and-`rename(2)` dance — this is the
measurement that made the planned shared write helper not worth building yet. The sharable part is one
Foundation call plus "create the directory if it isn't there", and the second caller doesn't exist: the
settings window is to be handed a seam by the daemon rather than reaching for a path itself, so if a
helper is ever owed, it is owed to `EmiraShell` and the CLI, which have no module between them but the
two pure ones. `ConfigWatcher` was already built to survive an inode swap, so nothing on the daemon's
side had to change to notice the save.

The CLI regains a dependency on `EmiraConfig` that the extraction removed, and that is the point rather
than a regression: it was carried dead before — the whole TOML grammar linked into a binary that never
called it — and it is now the reason the binary can read the file at all. It still cannot see
`EmiraShell`, which is why `Config.defaultPath()` had to be the config's fact and not the shell's.

## Observations

`make test` is green at 1047, `EmiraConfigTests` at 123 — ten new, and the two that carry the change are
schema-driven rather than written per setting: every entry reads back whatever it prints (over its
default *and* over a value that isn't its default), and every entry explains itself in the schema's own
words. So a new setting is exercised by both without being named in either. The eleventh is in
`EmiraCoreTests` and guards the pitfall the branch creates: no verb may be spelled `config`, because the
CLI takes that word before `Command.parse` sees it and such a verb would be unreachable in silence.

The CLI itself is unreachable from the suite, so its exit codes were checked by hand against the table in
`main.swift`: `1` for a file that doesn't parse, `2` for anything wrong with the argument — including a
value the schema refuses, since that value came from the command line rather than from the file. The
fixtures were a good file, one with `column-gap = -5`, and a path with nothing at it. `check` on a
missing file exits `0` and says so on stderr: an absent file is every setting at its default, which is
what the daemon runs on, and silence about a file nothing is reading would be the wrong kind of quiet.

**`remove` leaves an empty `[table]` header behind** when the last key under it goes back to its default.
That is `ConfigDocument`'s existing behaviour, pinned by its tests, and it is legal TOML that reads as
`Config()` — but a file edited from a GUI for a while will collect them, so it is worth revisiting when
the window makes it common rather than now.

`emira config get` prints what `emira config set` reads, which is the property that keeps the two the same
vocabulary, and `TOMLValue.spelled` becoming public is what let that be true — the file's spelling is the
one a user can type back.

Nothing here was seen running: hot reload is `ConfigWatcher`'s, unchanged, and the daemon was not up.
Setting something the daemon reacts to, and watching it land with no `emira` command sent, is the one
check left.
