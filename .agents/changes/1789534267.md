# The correction moves behind the cover

> Change `1789534267` — 2026-09-15

## Goal

`1789533187` re-read the window server, but in the wrong place and over a quarter second. Passing
quickly through a column — `focus right` twice from Safari, so Font Book is only crossed — settled
*correct*, but the way it arrived was a flash: the window came to rest solid except for a strip down
its right edge, which was already see-through, and then the rest of it faded in behind.

## Implementation

Two faults, and the report separates them exactly. The strip that was already right is the old mask
still on the glass; the fade is the correction arriving as an animation.

**The correction was revealed rather than hidden.** `restack()` hung off `onCoverDismissed`, which
fires in the *completion* handler of the cover's cross-fade — so the cover uncovers a mask cut against
where the windows were, and only once it is fully down does anything repaint. It moves to the top of
`CompositingExecutor.dismiss`, before the cover starts moving. That is the same guarantee one moment
earlier: the transition closed because the AX sets landed, so the window server is already current,
and the cover is still on the glass, so the repaint happens where nobody can see it. `restack()` joins
`ScrimPlane`, which is where it should have been — the executor owns a cover's lifecycle and holds the
plane; the daemon's copy of the call is gone, so there is one site rather than two.

**A mask swap was a fade.** `ScrimWindow.cut` is a bare `CALayer`, not a view's backing layer, so
nothing returns `NSNull` from `actionForLayer:forKey:` and Core Animation's own default applied to
`contents`: every repaint dissolved the old mask into the new over a quarter second. That is what made
a correction legible as an event — the window appeared to *become* transparent on its own. It is
written with actions off now. A mask is geometry; the one fade a scrim owns is `fadeDuration`, on the
window's alpha, where it was put deliberately.

### Validation

Burst capture from a third process at ~31 fps through the reported gesture, each frame scored as mean
|ΔL| against the frame it finally settled to, in twelve vertical bands across the window's on-screen
width. The symptom is a **split**: the right band already at its final appearance while the body is
not. Before:

| t (s)     | 0.634 | 0.665 | 0.699 | 0.738 | 0.770 | 0.802 | 0.834 | 0.864 |
| --------- | ----- | ----- | ----- | ----- | ----- | ----- | ----- | ----- |
| body mean | 34.1  | 34.0  | 34.0  | 27.7  | 17.5  | 9.6   | 4.7   | 2.6   |
| right band| 9.2   | 7.3   | 7.3   | 6.0   | 3.8   | 2.1   | 1.0   | 0.6   |

Four frames — 0.104 s — where the right band is done and the body is 20-plus away, worst split 26.7,
and then the body decaying smoothly to zero: the quarter-second dissolve, caught mid-flight. After the
change the split never occurs at all, across four consecutive runs, and everything reaches its final
appearance together.

## Observations

- **What re-asks is still only a cover coming down**, so `1789533187`'s limit stands unchanged: a
  window server change that no transition caused — a dialog opening in front of a see-through window,
  a foreign window dragged across one — leaves the mask holding the previous reading until the next
  transition. An observer on the window server is the answer and is not here.
- The `holdTimeout` path closes a cover with AX sets still in flight, and those land after the restack.
  That mask is wrong until the next transition; it is the same gap as above, reached another way.
- **`ScrimBinding` array order is still unused.** Carried forward from `1789531974`.
