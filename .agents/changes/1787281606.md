# A float closing hands focus to the place it left

> Change `1787281606` — 2026-08-20

## Goal

Open three windows, float the third, close it: focus landed on the **first** window on the strip.
Reproduced against the running daemon on a strip of `[Safari][Ghostty]` plus a floated TextEdit —
closing the float put focus on Safari, two columns away from where the user was working.

Two independent faults, and it takes both to produce that.

`Engine.successor` answers "where does focus land when the window holding it leaves the strip" with two
positional clauses — a surviving stackmate, then whichever column now stands at the departed one's index
— and falls through to `layout.allWindowIds.first` when neither applies. A window that was already off
the strip when it closed has no column and no index, so *every* such departure took the fallthrough. The
strip's front is not a neighbour of anything; it is simply the leftmost thing there is.

`World.lastStripFocus` documents itself as "the last window focus rested on **that belongs to the
strip**", and only `remove` kept that promise. `setFloating` did not, so floating a window left the
memory naming a window that had just left the strip. `Engine.stripAnchor` re-validates at read time and
correctly declined it, which meant the one record of where the user had been working read as nothing at
exactly the moment something needed it. Live confirmation, mid-repro: strip columns `[[1],[2]]`,
`lastStripFocus = 5`.

The dialog case is the commoner one and had the same answer. A save sheet over the second column,
dismissed, sent focus to the first — sometimes invisibly, because macOS often backfills the parent
itself and the two answers raced. `PRINCIPLES` §4 claims that decision as emira's ("an app backfilling
focus after a window closes is macOS guessing... emira has already decided where focus goes"), so
racing the system to a worse answer is the wrong side of a promise already made.

## Implementation

**`successor` gains a third clause: `anchor`, which callers pass as `stripAnchor(s)`.** The ladder is
now stackmate → the index's new occupant → the last place focus held on this strip → the strip's front.
The first two clauses are the strip's own positional answer and stay untouched; the third is where a
placeless departure was falling through. Threaded as a parameter rather than read inside, because
`successor` takes a `Layout` and the anchor is a fact about `World` — and because the second call site
(`moveToWorkspace`, staying put) guards on a non-`nil` index, so it can never reach the clause and its
behaviour is provably unchanged.

**`World` keeps its own invariant.** `pruneStripFocus` clears `lastStripFocus` when it names a window
that no longer participates in the strip, and the four mutators that can break it — `remove`,
`setFloating`, `setMinimized`, `setAppHidden` — each call it. `remove`'s hand-written
`if lastStripFocus == id` is subsumed: a removed window fails `participatesInStrip` on the missing
record. `setAppHidden` has no `Event` routed to it yet and is included anyway; leaving one mutator out
is the shape of this bug.

**`departFromStrip` moves the memory when it cannot move focus.** It already computed the vacated
place's successor and used it only when focus was actually lost. When focus instead goes *off* the strip
with the window — which is exactly what `float` does, deliberately, because the window is still there to
look at — the same successor is the answer to "where was the user working on the strip", and
`World.noteStripFocus` records it without touching `focusedWindow`. The guard is `lastStripFocus == nil`,
which after the prune is true precisely when the departing window was the memory. This is the only moment
the vacated column and index are still known.

The two halves compose into the reported trace: floating C moves the memory to B, closing C finds no
column and no index and asks the anchor, which is B.

Two alternatives were dropped:

- **Geometric nearest — the column under the float's frame.** Tempting, because a float is the one
  off-strip window that is actually visible. But the viewport scrolls without focus moving, so "nearest"
  has no stable frame of reference, and a float's frame is the app's: emira declines an opinion about
  where a float sits and should not then read meaning back out of it. In the reported trace it agrees
  with the memory anyway, since the memory recorded at float time *is* the positional neighbour.
- **App provenance — hand a dialog back to a window of its own app.** Right for a save sheet, wrong the
  moment the user clicks to another window and back before dismissing it, and it needs app identity for
  a question focus history answers without it.

`RulesTests.theAnchorSurvivesTheFocusRace` changed with the behaviour. It floats the only window on the
strip and asserted `lastStripFocus == WindowId(1)` — the dangling value — as setup for its real claim,
that the rules read `lastFocus` instead. The strip is empty afterwards, so there is no place left to
name and the memory is now `nil`; the assertion is `nil` plus `lastFocus == WindowId(1)`, which states
the same thesis against the value that actually carries it.

## Observations

**The fix is validated by the suite, not against the daemon.** The bug was reproduced live on the
installed build; the fix was not, because seeing it live means `make install` over the user's running
window manager, and an ad-hoc signature's cdhash changes with every build, so macOS re-asks for
Accessibility and the WM is down until it is re-granted. `Engine.reduce` is a total function over
(`State`, `Event`) and the four new cases in `EngineWindowOpTests` drive the same events the daemon
folds, so the gap is the AX layer only. Worth a confirming pass on the next install.

**A float on a workspace the user has since left.** `stripAnchor` is constrained to the focused strip,
so it declines and the fallthrough stands. That is correct — restoring focus over there would switch the
desktop — but it means the far-left landing survives in that one case, and it is the case least likely
to be noticed.

**Seeding an empty memory from a departure.** The `lastStripFocus == nil` guard also fires when nothing
had ever focused a strip window (a boot enumeration, then a departure), so the memory is seeded with the
survivor rather than left empty. Both consumers — where a column opens beside, where a refused focus
report goes back — read that better than `nil`.

**`setAppHidden` is unrouted.** No `Event` folds it, so its prune is untested through the reducer and
covered only at the `World` level. When `Cmd-H` is wired up, a hidden app's window is a departure like
any other and should ride `departFromStrip`, which is what gives it the memory move for free.
