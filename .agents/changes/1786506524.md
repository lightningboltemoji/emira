# Keybindings in the settings window

> Change `1786506524` — 11 August 2026

## Goal

`[keys]` was one of the two surfaces the settings window did not edit, and the only one whose absence was
written down as a *reason* rather than chosen: a chord editor has to capture keystrokes rather than read a
value, and the field has to hold `⌘Q` and `⎋` without either reaching the app. That reason was accurate and
it was half the story. The other half was that `EmiraSettings` cannot name `Command`, so it could validate a
binding through the draft but could not **offer** one — no way to know that `focus` takes four words and
`grow` takes a number and a unit.

## Implementation

Nine pieces, each of which stands on its own.

**The vocabulary became a table.** `Vocabulary` is now a public top-level type in `EmiraCore` carrying every
`Verb`, and a verb carries its argument as a *shape* — `Verb.Argument`, five cases for twenty-one verbs,
`Setting.Kind`'s rule one vocabulary over: one case per shape of control, never per verb. Everything else
falls out of it. The printed grammar is derived rather than spelled beside the parser, so
`Grammar.direction = "<left|right|up|down>"` and `Direction(rawValue:)` stopped being two statements of one
fact; `takesRawTail` stopped being a third thing to remember and is now `if case .line`. `Verb.build` is
deliberately not public — the vocabulary is offerable outside the module, turning words into the reducer's
input is not. The one thing still spelled by hand is an address's grammar: `(next|prev)[-non-empty]`
compresses a set that also holds aliases and thirty-six one-character addresses, and listing it flat widens
every usage line by sixteen columns to say the same thing. `emira --help` is byte-identical, and a new test
pins all twenty-one signatures so it stays that way.

**`Key.virtualKeyCode` moved to `EmiraCore`,** as hex, with `Key(virtualKeyCode:)` derived from it. This
contradicts a written decision — "spelled `kVK_*` rather than hex so the table is checkable against Apple's
header" — and it had to buy something. It does: the package's hard rule is that nothing below imports a
framework, so a Carbon-spelled table cannot live where the recorder can reach it, and the alternative is a
second table in `EmiraSettings` re-creating exactly the silent transposition the old comment warned about.
Checkability moved from the spelling to `HotkeyTests`, which pins every entry against its `kVK_*` constant
and adds an injectivity check the spelling never gave us. A new target between `EmiraCore` and both consumers
was rejected: targets here exist to enforce boundaries, and sharing a table is not one.

**`ConfigDocument.rename(_:to:)`.** Retyping a chord was `remove` + `set`, which is two edits with two
failure modes nobody asked for: a refused second half leaves the binding *deleted*, and the insert relocates
the line to the end of the table's run, so editing line 2 of 12 moves it to line 12. Order carries no meaning
in `[keys]` — unlike `[[window-rules]]`, where it is precedence — but it is still the author's file.
`TOMLSpan` gained `key`, the range of the key expression's **last segment**, returned by `keyPath` rather
than found again afterwards. `Draft.Edit` gained `.unset` and `.rename`, because a `Setting` is never absent
and never renamed while a `[keys]` entry is both, constantly.

**The names in `[keys]` are the user's, and the editor asks what they are.** A row's edits are keyed by
`ConfigDocument.names(under: "keys")` — the file's own spelling — rather than by `KeyChord.description`. The two
part company constantly: modifier order is free, `control`/`option`/`opt`/`command`/`globe` are all accepted,
and a modifier may follow the key, so `cmd-alt-h` and `alt-cmd-h` are one hotkey and two TOML keys. Keyed
canonically, every edit to a file written any other way asks the document to change a line it does not carry,
and a document leaves a key it cannot find alone: ⊖ and a retyped chord do nothing at all, silently, and a
retarget writes a *second* line the schema then refuses as one hotkey set twice — naming a key that appears
nowhere in the file. `Catalog` parses the chord out of the take's key for the same reason. The whole suite
passed through this, because every fixture in it was spelled canonically; the schema's own documented example,
`cmd-alt-period = "center-column"`, is not.

**`ChordRecorder` is a local `NSEvent` monitor,** installed only while listening. Two things make it more
than a `modifierFlags` read. It strips fn from a function-class key — macOS marks the arrows, the F-keys and
home/end/page-up/page-down with that flag whether or not fn is held, and `fn-left` is a chord the file
refuses by name, so a naive recorder would hand the file something it will not read back. And it reports
modifiers held and released with nothing between them as the system's own. The decision is a pure function
of a keycode and a flag word, so every branch is testable without an event.

**`KeysEditor` is one `PanelRow` owning a list,** not a row per binding: the slab rebuilds rows only on
section change, so a list whose length moved under `show(draft)` would need a second callback into the slab
or would throw away the control under the cursor on every edit. It reconciles its own children — chord
first, then position, which is what makes a chord *retyped* one row rather than a row destroyed and a row
built at the moment the user is looking at it. Reconciling the *identities* is half of it and the stack is
the other, because taking a view out of the hierarchy ends any editing session inside it and `show` runs
after every edit anywhere in the panel — so a list rebuilt each time drops the field editor under the hand,
the same failure the matching prevents, one level down. `insertArrangedSubview` moves a view that is already
arranged without taking it out, so the stack is reordered rather than rebuilt and only departed rows are
removed. What that buys is a list whose *order* is free to move: the half-built row opens directly beneath
the button that made it, since a binding not yet in the file has no place in file order, and on commit it is
handed to `rows` before the edit travels — so reconciliation matches it by chord and the row the user filled
in is the one that takes its place among the bound ones, rather than a fresh one built where the file put it.
The one thing the editor decides rather than the draft is what may be *offered*: `cmd-alt-h` and `alt-cmd-h`
are two TOML keys and one hotkey, and letting that reach the draft produces one red sentence at the foot of
the slab a long way from either bubble, so it is caught canonically on `KeyChord` and both capsules are edged.

**The argument well is a fixed budget, and `rebuildArgument` is where that is enforced.** The bubble's width
comes from the row, so the two constraints the well installs are the whole of what stands between a control's
intrinsic size and a layout with a required constraint to break — and on a real panel it broke both ways. A
`.none` shape whose view still carried its autoresizing mask pinned the well to nothing and took 157 pt off
the bubble, stranding the ⊖ in open space; an address popup sizes itself to `previous-non-empty` whatever the
row is showing, which with a 44 pt field beside it wants around 200 pt of a 157 pt well, and it ran the
bubble 15 pt over the ⊖ — a workspace binding with no remove button on it at all. Guaranteeing the
precondition in the one place that installs the constraints beats five inits each remembering it, and the
control is told it may compress: a truncated word is a control that still works, a broken constraint is a row
whose remove button is somewhere else. Inside `AddressControl` the popup is named as the part that gives,
because an address is short and truncating it hides the whole answer where a truncated motion is still
readable in the menu it came from.

**Recording is a state the capsule wears, not one it disappears into.** The plan had the bubble replace
itself with `◉ Press a combination` while listening, and the first version did that — which foreclosed
building a chord by hand at exactly the moment the user first meets the feature. Recording is the shortcut;
the chips are the floor. So the controls stay up and stay live, listening is the edge breathing and the dot
filled, and the sentence under the row names both ways in. A hand on a chip or the popup ends the recording
rather than racing it: a press arriving afterwards carries whatever modifiers are physically held and would
overwrite what was just clicked, which reads as the control undoing itself. The popup has to be caught on
`mouseDown` rather than on its action — a menu tracks in its own event loop, so a recorder still installed
would swallow the arrow keys used to walk it.

Three visual decisions were measured against a real panel rather than settled on paper, and all three were
wrong the first time. The chord bubble is 296 pt because at 250 the record dot went behind the key popup.

The modifier chips are **all five spelled as text, coloured through `attributedTitle`**, and getting there
took two attempts. The fn key's keycap is 🌐, a colour emoji, which ignores whatever colour it is given — so
the first version drew it as an SF Symbol and tinted it with `contentTintColor`. That produced two rendering
paths whose colours are set two different ways, and they drifted immediately: `contentTintColor` reaches an
image and never a title, so on a dark panel the globe stayed at full strength while the four glyphs beside
it went dim. Spelling fn as `fn` collapses that to one path, which cannot drift, is legible at chip size,
and is the word the config file itself spells.

The inks took a third attempt, and the way the second one failed is the part worth keeping. Unheld moved
from `tertiaryLabelColor` to `secondaryLabelColor`, which was straightforwardly right: a modifier that is
not in the chord is still a label to be read, and tertiary over a dark chip on a dark panel is a glyph you
have to hunt for. Held was set to `controlAccentColor` — and **a recessed button in its on state is drawn
by AppKit with an accent-coloured fill**, so that painted an accent glyph onto an accent ground and the
held chips became solid blue rectangles with nothing legible in them. The fix is
`alternateSelectedControlTextColor`, the system's own answer to "text on an emphasized background". The
fill is what says a modifier is held, and it says it far louder than a hue did.

**That bug survived a screenshot**, which is the reason this is written down. The accent fill is only
painted while the app is **active**; inactive, AppKit draws the on state as a dim grey, against which an
accent glyph reads perfectly well. The verification harness never called `NSApp.activate`, so it captured
the one state in which the bug is invisible and pronounced the panel correct. The harness now activates,
and `KeysTests` asserts the held ink is *not* the accent — a claim a headless suite can make and a
screenshot cannot.

**`Catalog` demonstrates verbs.** A `[keys]` row resolves its chord to the binding's `spelling` and plays the
verb, badged with `Cue.command` — which already existed, is already spelled as literal config text, and is
already parsed back by `CueTests`. `Catalog.take(for: .keys)` stopped being dead code with a comment saying
nothing ever asks. The badge's down-beat is clamped inside the loop, because the pacing is not the badge's to
assume: a ladder is as long as the user's preset list, so `width-presets = [0.5]` is a 1.8 s take against a
1.1 s dwell, and a beat at or past `period` never plays — the badge would go up and be lowered by nothing,
cutting at the wrap rather than landing. A loop with no room for one at all is left unbadged.

**The rule is one rung out: every verb has a take or a written reason,** and `CatalogTests` will not let a
verb be added without one. Seven are demonstrated. Fourteen are on `notDemonstrableVerbs`, and the list is
the longer of the two on purpose: the mock is one display showing one workspace, so all eight workspace and
monitor verbs are genuinely undemonstrable on it, `exec` and `debug` happen off screen entirely, and
`consume-or-expel`, `float`, `close-window` and `center-column` each need a mock mechanism that does not
exist — membership, floating, removal, and scrolling the viewport without focusing something. The plan
expected the first and last of those four to be demonstrable; they are not, because no `Beat` expresses
them, and a take that mimed one would teach a picture the desktop cannot make. Each entry says what a take
would have had to invent, which is the discipline rather than the list.

## Observations

**The "this chord will never fire" diagnostic is the shape of the press and nothing more.**
`RegisterEventHotKey` returns `noErr` for chords the system owns — verified: `cmd-shift-4`, `cmd-space`,
`ctrl-up` and `cmd-tab` all register cleanly and never fire, because the window server consumes them first.
So `HotkeyManager.Outcome.rejected` catches only Carbon-vs-Carbon collisions and a pre-flight `bind` during
the suspend window would answer "fine" and be wrong. What ships is the recorder's modifiers-only tell, which
costs one branch and covers the common path: you press `⌘Space`, nothing arrives, and the bubble says so.

**The tell is a possibility and is worded as one**, because from inside a local monitor a chord the window
server ate and a hand that let go without pressing anything are the same two events in the same order. It is
narrowed to combinations carrying `⌘` or `⌃` — every chord macOS keeps is built with one of them, and a bare
`⌥` or `⇧` pressed and released is somebody resting a hand on the keyboard while deciding what to bind, which
is the commonest thing to do with this control open.
Two heavier options stay unbuilt. Reading `com.apple.symbolichotkeys` is real but partial — it stores
*overrides* (19 entries on this machine, mostly `enabled = 0`) and not the enabled defaults, so using it
means also carrying and maintaining a table of Apple's own defaults. Reporting `Outcome.rejected` back from
the daemon would be a fifth crossing of a boundary documented as four, and blind to exactly the case that
matters. If the diagnostic proves insufficient, the symbolichotkeys table is the next rung.

**Cancelling a recording is a click on the dot, on a control in the same bubble, or on another row's dot —
not a click anywhere.** A bubble also stops listening when another one starts (a static handle enforces one
live monitor) and when the draft tells it a chord. A click on the scrim with a recording open leaves it
recording. Closing that would want a global click monitor, which is a second monitor for a case the record
dot already answers.

**The row pitch is still the open question the plan flagged.** `ControlRow.height = 46` and
`visibleRows = 4.5` were derived for a label/help/well row, and a binding row is 57 pt with its summary, so
four of them fill a 234 pt viewport and the rest of a populated file is below the fold. The slab is one height
for every tab, so a per-tab viewport is a change to `ControlSlab`'s geometry rather than to this editor, and it
was left alone. What could not be left alone is the one control that *adds* a binding: under the list it was
226 pt past the bottom on eight bindings — the tab's whole subject, unreachable. It sits above the rows
instead, where the tab opens, and the half-built row it makes is stacked directly beneath it rather than at
the far end of a list the button would then have to scroll away from: that row opens *listening*, and one
below the fold is a user pressing keys at nothing. A pinned footer outside the scroller is the native answer
and remains the next rung; it costs the Keys tab a row of viewport, which is the trade the pitch question is
really about.

**A claim about objects is not a claim about the panel.** Both ways the argument well broke are invisible to
a suite that builds a `CommandBubble` per verb and never lays one out, and to a fixture of `focus`, `grow`
and `exec` — three shapes of the five, and neither of the two that break. What catches them is one binding
per shape, including the longest verb name and the address popup in the state that reveals its field, off a
laid-out slab: every row's command bubble ends in the same place, which is what the eye reads and what both
failures broke.

**Row identity was the wrong thing to assert about the stack.** A test that the row objects survive a reorder
and that the arrangement follows the file passes against a `restack` that tears the list down and rebuilds
it, because the objects do survive that. Only a live field editor tells the two apart, so the claim is made
off a real window and a real first responder — the one test in this suite that needs a window.

**The verb popup is 152 pt and its longest title wants about 242 pt of text alone**, so the five monitor
verbs are truncated in the closed popup. Widening it is a question about how the bubble divides between its
two halves, and both answers — a narrower chord bubble, a wider row — move a measurement taken against a real
panel.

**The 🌐 keycap appears nowhere.** Spelling fn as `fn` is right for the chip, but a chip's tooltip is
`KeyModifiers.canonical`'s word, so the fn chip's tooltip repeats its own title and the glyph on the physical
key is never shown. A tooltip carrying the keycap is the next rung, and it is the only one of the five whose
tooltip would say something its title does not.

**The repeated summary is the other half of the pitch.** Four `focus` bindings print one sentence four times:
it is the *verb's*, and the argument is what differs between the rows. It costs 27 pt of the 57 pt row to say
what the two popups beside it already say.

**A starter set is still open**, and it is a product call rather than a technical one: "bind the usual
eight" is the obvious affordance for the one tab that opens on nothing, and it cuts directly against the
stated reason for shipping zero bindings — which is the sentence the empty state now carries.

**Orphaned comments are unchanged.** `remove` takes a value line's trailing comment, which is right, but
leaves a `# window management` header above a deleted group describing nothing. The keys editor can now
produce that where before only `emira config unset` could.
