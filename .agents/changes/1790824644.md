# Native tabs survive a group emira has moved, and the boot cover's base cuts every window

> Change `1790824644` — 2026-09-30

## Goal

Two startup complaints. A window with several native tabs, adopted at launch, sometimes repositions when
a tab is switched — as if it were a different window — and almost never does once emira has been running a
while. And the boot transition feels slow and laggy next to any later one.

## Implementation

**A background tab does not stand where its group stands.** Measured on a synthetic `NSWindowTabGroup` app
and on Ghostty: an AX frame write moves the selected tab only, so every other tab keeps the frame it was last
shown at (Ghostty's sat on the previous run's quit cascade while the group was parked elsewhere). The tab
AppKit selects is given the group's frame — and **the first time a tab is ever shown, it is also fitted onto
the screen**: a group at x 2000, 900 wide on a 2560 display put a never-shown tab at 1660 and a once-shown
one at 2000; off the left edge it went to 0; a parked group (2559, 1400, 887×1374) put it at (1673, 66).
Reproduced under the daemon: selecting a never-shown tab in a peeking column was `windowDestroyed` then
`windowCreated` at the first preset's width. Startup is where both conditions hold — boot moves every group
away from where its tabs were last shown, and tabs restored at an app's launch have never been shown.

So `WindowIdentity.succeed` takes the screens (`WindowSource.screenAreas`, each display's frame and visible
frame) and accepts a successor on the departed rectangle *or on it slid onto a display*
(`WindowIdentity.slid`): same size, the one place AppKit would put it. A same-sized window anywhere else is
still a different window, so the rule stays on the frame.

**⌘W retired the group at once.** `vanish` only waits for a succession scan when something says a successor is
possible, and its witness — another entry of the app on the closing window's rectangle — assumed tabs share
the group's frame. After emira moves a group none do, so the id retired, and the next tab, arriving on the
exact rectangle 25 ms later, became a new window. Traced: AppKit makes the next tab main **before** it
destroys the closing one (`AXMainWindowChanged` 2.5 ms ahead of `AXUIElementDestroyed`), and an unknown main
window is already a `windowAppeared` scan. A scan of the app still out is now a third witness. Traced on a
plain window too: its app names the window left behind as main before the destroy, and that one is managed,
so a plain close starts no scan and still retires at once.

**The boot cover's base cut one window.** A head batch's base excludes that batch's windows, and the boot
scan adopts a window per event, so the core asks for a batch per window — all before the cover is up, with
only the first opening it. A dumped base from a six-window boot carried five windows at their pre-boot
spots, standing frozen under their own sliding layers for the whole animation. `SCKCapturer` now holds a
turn's batches until the turn ends (its grab was a `Task` anyway) and each opening batch's base cuts every
batch after it up to the next opening one (`baseCuts`). The redumped base is bare wallpaper.

Timing, six windows, five interleaved boots each, ms from `screensChanged` to `coverOnScreen`: baseline
median 308, this change 324 — inside the run-to-run spread. Rejected on the same harness: folding a turn's
batches into one serial grab (one content read, the base uncontended) put the first motion at 331–358,
since each still then waited on its own measuring and main-actor hop; pipelining those behind the captures
landed the last still no sooner (~317). Warming ScreenCaptureKit at launch was also dropped: a process's
first screenshot costs ~100 ms against ~30 for the next, standalone, but a 2×2 throwaway shot at startup
moved nothing measurable in the daemon (median 340).

## Observations

- The boot head is still ~250 ms for six windows against ~50 for a later transition. Boot has a cold cache,
  so `immediate` has no stand-ins and every window must be filmed (~25–40 ms each) before the cover can rise.
  Snapping the boot adoption instead would land the desktop in ~100 ms; that is a choice about what boot
  should look like, and is not made here.
- At 15 windows the boot head batch still misses its 250 ms deadline and the cover is abandoned for a snap.
- A 65–77 ms main-thread stall follows every boot cross-fade: `SurfaceCache.unpin` reduces every full-size
  still synchronously. Any cover pays it per fresh still; boot has the most.
- Not run against real Ghostty tabs: its AppleScript refused `new window` here, and the Ghostty tabs on this
  machine were in use. Ghostty's background tabs were measured stale; the selection and ⌘W behaviour were
  measured on AppKit's own tab group, which Ghostty uses.
- A close whose app names an unmanaged window as main — a panel emira declined — now waits one scan, bounded
  by `successionGrace`, where it used to retire at once.
- Untested: the slide on a second display, and against a visible Dock (this display's visible frame differs
  only by the menu bar, so frame-or-visible-frame is accepted rather than known).
- Unmeasured and left alone: for its first ~9 s (`maxReconcileRounds` reconciliations) an app with an
  on-screen window the join cannot place suspends every succession it has. Ghostty here had none.
- New tests: `NativeTabFirstShowTests` (right edge, parked, a same-size impostor, a group already on screen,
  `slid`), `aDestroyLandingWhileTheAppsArrivalIsBeingScannedWaitsForThatScan`, `BaseCutTests`. The three
  behavioural ones fail with the two tab fixes reverted.
