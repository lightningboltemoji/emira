# The veil travels with the strip

> Change `1789538233` — 2026-09-15

## Goal

`1789537146` took the veil out of the capture head, and the whole of it then landed in the dismissal
cross-fade — after the strip had already come to rest. Correct, and the slowest arrangement available:
the transition finishes, and then the desktop catches up. Two events where the eye expects one.

## Implementation

**Nothing was stopping it.** A stand-in's veil is `root.opacity` on a layer we own, so moving it during
the motion is one Core Animation property on the GPU — no capture, no AX write, no window-server round
trip, and nothing the blits in the same transaction do not already pay for. What made it wait was not
cost but availability: the shell's answer used to arrive at the *command*, which is too early to be
about this transition, so `Reconstruction` read it once when a layer was built and left the change to
the cross-fade. `1789537146` moved that arrival to the teleport — which is exactly the moment the motion
starts, with the shell's decline already folded in — and the reason to wait went with it.

So the cover asks again. `CompositingExecutor` calls `refreshVeils()` at the end of every scrim run;
`Reconstruction.refreshVeils` fades each stand-in's `root.opacity` to `Scrims.veil(of:)` over
`veilDuration`, geometry untouched, exactly as `refreshLayer` leaves it. It is a **pull through the seam
that already existed** — the `veil` closure the reconstruction holds — rather than a push carrying
values, so the scrim plane stays the one authority and the cover never forms a second opinion about what
a window looks like.

Read at build *and* asked again, not one or the other. The build-time read is what makes a raise
pixel-identical to the desktop it replaces; the ask is what carries the change after it. The fade starts
from the layer's **presentation** value rather than its model value, so a veil retargeted mid-flight —
two focus changes inside one cover — starts from what is on the screen instead of from where the last
one was headed.

The rejected alternative is the one `1789528513` already rejected, arriving by another road: put the
veil on `LayerBinding` and let the core animate it per frame. It needs the core to reproduce the shell's
decline, it puts a second opinion on the hottest path in the reducer, and it buys nothing — the shell's
answer is already correct and already arrives on time.

### Validation

Same drive as `1789537146`, five covered `focus` transitions per build, the screen filmed at ~58 fps and
scored in 24 bands. "Settled" is the last frame that changes at all, measured from the command:

| | motion ends | settled | veil arrives |
| --- | --- | --- | --- |
| cross-fade only | 583 ms | 703 ms | after the motion, as a 192 ms ramp |
| asked at the teleport | 381 ms | 474 ms | during the motion |

The shape is the part worth reading. A region inside the window whose veil changes, one run each, in ms
from the command:

```
cross-fade only   82 … 82 … 82 | 96 (sliding) … 91 … 91 … 91 | 91 → 52 over 522–714 ms
asked at teleport 82 … 82 … 82 | 82 → 53 over 167–346 ms, while the screen is still moving | 52
```

Before, the region sits at the wrong veil for ~200 ms after the strip stops and then ramps. After, it is
finished before the motion is. `1789537146`'s own measurement was re-run on the same films: the step
followed by motionless frames is still absent, 0 of 6.

## Observations

- **The cross-fade still carries a tail**, ~100 ms of small change in both builds. That is the cover
  dissolving into live pixels rather than the veil, and it is what a cover costs.
- **A window arriving mid-transition now takes its veil during the motion too**, which was a limit
  recorded in `1789537146`: it joins `placedOnScreen` at the teleport, so the set that names it is the
  set this asks against. Not separately measured.
- **`restack()` does not ask.** It re-reads the window server at `dismiss`, and a veil that changes
  there would be animating on a cover already fading out. Left alone rather than chased, on no
  measurement either way.
- **The base still shows a non-scoped window solid.** Unchanged by this, and still the open one:
  `1789537146`'s first observation.
