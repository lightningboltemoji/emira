# A focus read answers about the desktop it was queued on

> Change `1788415377` — 2026-09-02

## Goal

Rarely, and much more often on an M1 than an M5, a focus command did nothing: the guide came up, so the
chord had registered and the reducer had run, but the focused window did not change and no animation
played. The next press worked.

The command is fine; something undoes it. Focus reaches the core by two routes, and one of them is a
*read*. `NSWorkspace` says an app came forward and not which of its windows has focus, so that costs a
round trip on the app's serial AX lane — a lane also carrying the placement batch, the enhanced-UI
toggle, a frame re-read per moved window, and any scan. The read answers about the moment it was
queued. Under load that moment can be several hundred milliseconds before it lands, which is longer
than the gap between clicking into an app and pressing `focus left`.

So the answer arrives naming the window the command has just left. `FocusIntent`'s record covers the
app's *own* notifications and expires 0.5 s after the last request, and an external focus change was
never on it at all, so the report resolves `.external`, reaches the reducer as `.system`, and is
admitted — under `respect` unconditionally, under `on-screen` because the window just left is by
definition still on screen. `revealAcrossWorkspaces` then puts focus back and re-aims the live session
at the offset it started from.

That is the whole of the symptom. If the report lands inside the capture head, the session is re-aimed
before any real window has moved, so the cover raises onto a photograph identical to the desktop,
settles on the first tick and fades out invisibly. Meanwhile the `.focus` effect has already run
`makeKey` and the activation, so real keyboard focus *is* on the target — which is why the second press
works, and why the first looks like a chord that did nothing rather than a command that failed.

The M5 is not immune, it is fast: the read returns inside the capture head, and inside the grace.

## Implementation

**A queued read carries its position in request order, and an answer something overtook is dropped.**
`FocusIntent.newest` is a `Ticket` for *now* — no request issued, just the count read — taken as the
read leaves and checked with the existing `isCurrent` when it lands. Two call sites, both in
`WorldWatcher`: the activation read, and the liveness probe `resolveFocus` spends on the window a
report displaces. The probe was the same bug one hop further along: it decides whether a report is the
user or macOS backfilling a dead window, and its answer can land after a keypress exactly as an
activation's can.

**Order, not a clock.** The marker cannot expire, because a slow lane is not evidence against its own
answer — only a *newer request* is. That keeps the two mechanisms honestly separate: the grace bounds
how long `FocusIntent` remembers a window for the sake of the app's own notifications, and it still
does; the marker bounds nothing and only ever says whether something has been asked for since.
`theGraceDoesNotMoveTheMarker` pins that, against the tempting simplification of reusing the record.

**The activation read moved from `AXObservationSource` to `WorldWatcher`**, and `WorldObservation`
grew a pid: `.appActivated(pid_t)`. The source cannot stamp the read, because `FocusIntent` is
policy and `ObservationSource` is the decision-free half — so the read became
`focusedWindow(of:then:)`, a seam the watcher drives like `isAlive`. It answers `FocusedWindowRead`
rather than `WindowId?` for the reason the old code had a `guard let window` in it: an app that
cannot answer must not be read as "focus is on nothing", which would clear the core's focus every
time a busy app came forward. `.unreadable` says that in the type instead of in a comment.

**Only apps with something under management are asked.** The cursor half of the notification still
reaches the core for every app but us — an accessory app coming forward discards a background hide
just as a regular one does, which is why that half was never behind the `isRegular` filter — but the
window half is now spent only where the answer could name a managed window. The old `isRegular` test
was a proxy for that; `apps[pid] != nil` is the question itself, and it admits the accessory app that
`reconcile` has since adopted.

**Rejected: lengthening the grace.** It is the obvious knob and it is the wrong one twice over. It
does not cover the case at all — an external focus change is not on the record no matter how long the
record lives — and it trades directly against `focusIsNeverSuppressedForGood`, where a genuine
Cmd-Tab back to a window emira recently focused must reach.

**Rejected: refusing any system report while a session is open.** It would mask this and break the
case the reveal exists for: an app hands key status to a survivor *before* destroying the window it is
closing, so a focus report is routinely the first half of a structural edit, and a transition is what
the second half rides.

## Observations

**Diagnosed from the code, and the fix is not yet confirmed against the machine that shows the bug.**
The trace fingerprint to look for on the M1 is a `command(focus …)` line followed, in the same burst,
by `focusChanged(<the window focus just left>, origin: system)` ahead of any `coverOnScreen`. With
`EMIRA_TRACE=1` that burst is one block. What would confirm the fix is the absence of the second line
under the same provocation; what would refute it is the symptom surviving with no such line, which
would point at `axFailed` or `coverUnavailable` instead.

**One asynchronous focus hop is deliberately left unstamped.** `AXWindowWriter.focus` already drops a
superseded activation through the ticket it holds, which is the same rule reached by the other side
of the seam.

**The window server is still asked about a window that may have moved on.** `restoreFocus` reads
`CGWindowListCopyWindowInfo` on the main thread, and that call blocks for the length of another app's
window animation — the deferral `Overlay.confirmPublished` exists to survive, on a path that has no
fence. Untouched here, and worth its own look.
