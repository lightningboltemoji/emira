# Monitor-aware core, still one display

> Change `1785708535` — 2026-08-02

## Goal

The first of the multi-monitor phases: make the core able to *say* which display it is talking about,
with no user-visible change and still exactly one display managed. Three facts had no authority — which
monitor owns a workspace, which workspace a monitor shows, and which monitor the user is on — and the
third of them was silently answered by `Workspaces.focused`, a field that assumed there was only ever
one screen looking at anything.

## Implementation

**`Monitors` is its own container beside `Workspaces`**, joined to it by a `WorkspaceName` exactly as
`World` (windows) and `Workspaces` (strips) are joined by a `WindowId`. `Workspaces` loses `focused`
and every query that depended on it — `resolve`, `placementOrder`, `targetFrames`, `naturalFrames`,
`verticalOffset`, `reconcile` — takes the shown address as an argument instead. That is what keeps the
strip container a pure structure rather than a second opinion about which display is looking at what.

**The plan's own §1 sketch put `frame` and `struts` on `MonitorRecord`; they are not there.** The prose
two paragraphs later is the decision that was taken: `MonitorState` in `World` keeps what observation
refreshes, `Monitors` keeps the structure. Putting geometry in both would be the one thing the model
forbids — a fact held twice — and the split is already the `World`/`Workspaces` one, one level up.

**`Monitors.shown` is total, including with no display attached.** Every verb reads `State.layout`,
which is now a projection of `workspaces` at `monitors.shown`, so a `nil` there would be a crash at
boot rather than the no-op `metrics()` already gives. The launch state and every lid close are held in
an `unattached` assignment — read and written only while `records` is empty, which is the one condition
under which no record can answer. It is D12's detached bucket arrived at early, because the degenerate
case of it was needed anyway; the hot-plug policy on top of it is still phase 5.

Two invariants are kept structurally rather than checked. `show` is the only way to move `shown` and it
claims what it shows, so "a monitor showing an address it does not hold" is unrepresentable — including
for the *loser* of a claim, which `repairShown` re-homes in the same call.

**What the loser can take is a three-rung ladder, and the third rung is the one that matters.** Its own
addresses, then one nobody holds, then one another display owns but is **not showing**. The obvious
version stops at the second rung and looks safe — 36 addresses, so surely only a 37th display could
exhaust them — but that arithmetic assumes a display owns about one address, and `show` claims without
ever releasing. The acting monitor accumulates every address it has ever shown, so two displays and 36
switches strand the second one, showing an address the first now owns. Taking an address its owner is
not looking at costs that owner nothing visible and cannot cascade, and with it the "37 displays"
reading is true rather than merely plausible.

**Invariant 2 needed a mutator, not just a repair.** `reconcile` runs on `Event.screensChanged` and
nothing else, so "materialized ⇒ assigned" held only between display changes: `move-to-workspace 5`
without follow, and a window rule naming an address, both materialize a strip that `monitor(of:)` then
answers `nil` for. `Monitors.assign` is the other half of `show` — `show` claims what a display *shows*,
`assign` claims what a verb only materializes — and `State.move(window:to:insertingAfter:)` is where the
two containers are joined, for the same reason `State.setMonitors` exists: `Workspaces.move` gives an
address a strip and is deliberately unable to know about displays. An address some display already holds
keeps it, which is already phase 4's rule for an absolute reference and is what will let a window sent
to a workspace travel to whichever screen that is. `reconcile` still repairs what neither mutator saw:
orphans from a departed display land on the first survivor, and an address that lost its strip is
dropped unless it is the one being shown.

**`State.setMonitors` folds `Event.screensChanged` into all three containers in one call.** The first
version had the reducer do the three steps inline, and `GuideModelTests` immediately proved why that is
wrong: a test reaching `state.world.setMonitors` directly produced a desktop with geometry, no acting
monitor, and therefore no metrics at all. Ordering that has to hold is ordering that belongs inside one
method — the same argument `Workspaces.move(window:to:)` already makes.

**There are three such joins, not two, and the third is not one strip per call.** `State.show` is the
other half of a switch, and the obvious version — show the address, materialize the address — is wrong
for a reason only two displays surface: the claim dispossesses whichever display held that address, and
`repairShown` hands *that* display a fallback which may be an address nothing has ever materialized. So
what a switch owes a strip to is every address left on a screen. Shown ⇒ materialized is the invariant
`placementOrder(shown:)` and `targetFrames(shown:)` assume — both are handed the on-screen list, and a
name in it answering for no strip is a hole in the placement walk and a park ordinal spent on nothing.
`setMonitors` had been establishing it and `switchWorkspace` had been quietly not maintaining it.

**`Workspaces.move` is internal**, which is what makes `State.move` the way in rather than the way it is
supposed to be done. A doc comment saying "call the other one" is a rule somebody has to have read at
the moment they are looking somewhere else; `Layout.remove(window:)` is internal for the same reason one
level down, and there was exactly one caller to lose.

**D6: `struts` left `Config` entirely** rather than staying as the schema's one exemption. They are per
display and they move under a running daemon (the Dock changes edge), so they ride on `MonitorInfo`
beside the frame they inset. `ConfigSchemaTests.notKeys` is now empty, which is a stronger statement
than the list it replaces: every stored property of `Config` has a config story.

`allWindowIds` split into two queries. It had been answering both "which windows exist" and "in what
order do they stack", which one placement order could serve while there was one; a z-order now asks
`windowIds(inPlacementOrder:)` and says which addresses are on screen. `metrics()` stayed beside
`metrics(of:)` rather than being replaced by it: "the acting monitor's" is a well-defined query the
state can answer, not a stopgap, and phase 4 is where individual handlers start naming another monitor.

**`targetFrames` takes the same on-screen list the placement walk does**, rather than the single address
that tiles. Handing it one name and the walk the whole list gives two answers to "what is on screen"
that agree only while there is one, and the way they disagree is a park ordinal — a nub that renumbers
because the *other* screen switched, which is exactly the silent failure the single cursor exists to
rule out. The list's first entry is the one that tiles; another display's address parks with the rest,
because there is still one viewport and one metrics, and what being on screen buys it is its place near
the front of the run.

## Observations

Writing `MonitorsTests` found three real bugs in `reconcile`/`show` — a display arriving into a detached
desktop did not take the address that desktop was showing, the loser of a `show` was left showing an
address it no longer owned until the next reconcile, and a returning display lost what it had been
looking at. All three are silent on one screen, which is the whole reason the suite exists.

`Cascade.cascadeEffects` still lays the quit cascade out against the acting monitor's metrics alone;
§6 wants it once per monitor over that monitor's windows. Not blocking while one display is managed.

`Workspaces.targetFrames` and `naturalFrames` still take a single metrics and a single scroll offset.
The per-monitor supply they want needs `Motion.viewportOffset` to be per-monitor first, which is phase 3.

**A second display's shown address wanders as the first one switches**, because `focus-workspace 5`
claims 5 for the acting monitor wherever it lives and the loser then takes another address. D1 says an
absolute reference should go to the display holding it instead, which removes the churn — so this is
phase 4's to fix, not a bug to patch around here. It is invisible today (the other display shows an
empty workspace either way) and the ownership ladder above keeps it from stranding anyone.

`Workspaces.allWindowIds` has no caller left in `Sources/`. The membership/stacking split is real and
the query is the honest name for one half of it, but a public query only tests use is worth revisiting
once phase 4's verbs are in and can say whether they want it.
