# Mask against one reading, once the desktop has landed

> Change `1789630966` — 2026-09-17

## Goal

The veil fades cleanly for a float and not for a strip window, because the two reach the mask by different
routes. A float is never in the veil set, so releasing one writes nothing and the core sends one set. A strip
window's frame is in the set. `writeTruthPlane` stores the target (−606.92) before the move, `scrimBindings`
copies it into `ScrimBinding.frame`, and the app lands on whole points (−607). `settleScrims` compares exactly,
so every echo is a new set, and a set with unchanged veils is a correction. Painting a correction
(`repaint(from: nil)`) removes the running dissolve by name, which ends a fade-in partway through.

Underneath that, one mask was built from two moments. Veiled windows came from the core's targets, where the
windows were about to be. Occluders came from the window server read at `apply`, where they were then. Only a
covered transition ever re-read the window server afterwards (`Scrims.restack` in `CompositingExecutor.dismiss`).
An uncovered move (hand-resize adoption, float toggle, a self-placement written back, everything under `off`)
got its correction from the echoes alone. Under a cover the echoes were hidden but not free: each fractional
one cost a window list and a full-display mask on the main thread while the cover animated.

## Implementation

**Bindings carry no geometry.** `ScrimBinding` is window, monitor and veil. `Scrims.regions` takes the veiled
window's frame from the same `CGWindowListCopyWindowInfo` it already read every occluder from, so a mask is one
reading by construction and an echo changes nothing the core sends. Checked live before the change: at rest the
daemon's binding frames and the window server's bounds matched exactly, and after a placement `World` held
window 1 at x −1104.35 where the window server had −1105. `showing(_:at:)` still reads `World`'s frame to pick a
display for a window off every screen, which is a question about the layout and stays in the core.

**Every write is tracked until it lands, and an uncovered display's set waits for them.** `World.inFlight` maps
each written window to the displays its move touches: where it stood or where it was sent, by overlap. It is
filled by `World.noteWrite`, which `writeTruthPlane` now calls in place of `updateFrame` (still `internal`, for
`notePlaced`'s reason), and cleared by `axLanded`, `axFailed` and `remove`. Every write resolves: `AXExecutor`
fails a move for a missing record at once, and the lane always calls back, bounded by the 250 ms messaging
timeout. `settleScrims` holds a display that `!mayPlace` (the D8 hold) or that is uncovered with a write in
flight. A covered display is not held for its writes, because its stand-ins draw the veil from the core's
geometry and need the set at the teleport. The touched displays are geometric rather than the workspace's
owner, so a window leaving display A for B holds both. Owner-only would send A's set while the window still
stood on A, and B's landing would then cut A's dissolve short, which is the fault this change removes.

Rejected: keeping frames and comparing them within tolerance. That kills the echo sets but not the mixed
moment, since the first set of an uncovered move is still masked before anything has landed. Also rejected: a
shell-side wait for the window server to match the binding frames, as `HoistPanels` waits on `StackProbe`. It
needs frames in the binding, and it puts a second opinion of "settled" in the shell beside the core's landings.

**The core re-sends an unchanged set when the desktop settles, and `restack` is gone.** A set without geometry
cannot say the windows moved under it, so the post-pass sends the same set again (its `from:` state is what
tells) when every write touching a display has landed, or when a window emira will not write back stops where
it put itself. That is `windowSelfPlaced` for a float, or for a tiled window whose app already refused the
frame. `standsWhereItPlacedItself` is shared with the fold's own guard, so the two cannot drift apart. A tiled
window that stopped anywhere else is written back and re-sent when that lands. A tiled window that stopped
where the strip put it is our own echo, already re-sent at its landing, and sends nothing. Re-sending on every
`windowSelfPlaced` was rejected: most of them are those echoes (as `EngineSelfPlacementTests` states), so it
would cost a window list per moved window about 140 ms after every placement. An empty set is never re-sent,
since it has no geometry to recut.

**The re-send goes ahead of a dismissal in its batch.** Under `snap` the last landing closes the transition, so
the re-sent set and `endTransition` share a batch, and the post-pass appends. Executed in order, the dismissal's
alpha fade would start before the repaint. `settleScrims` inserts before the first `endTransition`, the way
`settleCoverClearing` runs early to stay in the fold's presentation run.

Tests. `ScrimTests` covers:
- an echo is not a set
- an uncovered scroll under `off` holds the veil through every landing but the last
- a write-back that moves no veil re-sends the set when it lands
- an echo that stops sends nothing
- a float that placed itself is re-sent at once
- a hand resize sets the veil down only after its re-tiled neighbour lands, not at `dragEnded`
- a `snap` transition's re-send comes before `endTransition`

`ScrimPlaneTests` replaces the restack test: the same set named again repaints where the window server now has
the windows, the veiled window included. Each rule in the post-pass was removed in turn: the in-flight hold,
the landing re-send, the self-placement re-send, and the insertion ahead of the dismissal. Each removal failed
exactly the tests written for it.

Three existing tests changed, and none of them was about the veil. Two `EngineRefusalTests` expected
`[.setScrims]` from a `placementCorrected`, which is the frame-only set this removes. They now expect nothing.
`EngineHoverTests.aCrossingIntoAFloatScrollsNothing` passed `EngineFix.settle` a state without the effects that
produced it, so its scroll never landed and the new hold correctly kept the veil. It now passes the effects.

## Observations

Checked live on this build with `EMIRA_TRACE=1`, on one 1710×1107 display:
- **`float on`** is uncovered. It wrote w1 and w2 and held the set, then sent it once at the second landing
  (4.4 ms). The echoes at 19 ms sent nothing.
- **`focus left` without a scroll** sent the set at once.
- **`focus left` with a scroll:** the set was held through the 97 ms capture head and sent at the teleport. It
  was re-sent at the landings 6 ms later, under the cover and 130 ms before `endTransition`. The echoes and
  `windowSelfPlaced` stops sent nothing.
- **Nothing in flight:** `inFlight` was empty after each command.

What the eye sees was not checked: whether a strip release now fades like a float's, and whether the repaint
under the cover is ever revealed. Neither hand paths nor multiple displays were exercised live.

**An existing redundant write, found in the trace.** Ghostty lands x −854.35 as −855, which is 0.65 pt off, past
`approximatelyEqual`'s 0.5. So the `windowSelfPlaced` that follows the echo writes the same target again, about
150 ms after every placement with such a coordinate, and nothing converges. That predates this change. What this
change adds is a re-send when that write lands, which repaints nothing because `setRegions` finds the regions
unchanged.

**A set is still one effect for the whole desktop.** A re-send or a change on display A repaints display B too,
against whatever B's in-flight writes have reached. The hold keeps B's bindings, not B's paint. This only
happens when two displays are writing within one landing time of each other, and it is the case for a
per-display effect that declares its own fade or cut.

**Chasing stops for an app animating its own window.** An app animating a veiled window's size is recut when
it stops or its write-back lands, where each frame report used to repaint it. That is the trade the hand lift
already makes.

**Windows emira never manages still never cause a recut** when they move. A dialog or Spotlight moving leaves
the mask as it was until the next set. The re-send is where such a trigger would go.

**`World.inFlight` and `TransitionSession.awaitingLanding` overlap.** The first is every write by display, the
second the scoped windows a cover waits on. A session's landing wait could probably be derived from the first,
but that is the D8 machinery, and this change leaves it alone.
