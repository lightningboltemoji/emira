# The core says dissolve or cut, and the mask stops being one image

> Change `1789705895` — 2026-09-18

## Goal

Two memories decided how a veil reached the glass, and neither was the one that knew why it had changed.
`Scrims` compared the veils it drew each display at last time against this time to sort a set into an event
or a correction; `ScrimWindow` read `isShowing` and a generation counter to decide what a repaint meant.
The core, which knows whether a hand lifted the veil, focus crossed, or the desktop merely settled under an
unchanged set, said only `lifted`.

And a set was one effect for the whole desktop, so a change on one display repainted the other against
whatever its own in-flight writes had reached, and one word — fade or cut — had to serve both screens.

Under that, the mask was a single alpha image the size of the display, so geometry and strength could not
move independently. Every repaint replaced the whole image, which is why a correction landing inside a fade
ended it (`repaint(from: nil)` removed the animation by name), and why a fade starting inside another fade
began from the previous target rather than from what was on the screen.

## Implementation

**A set is one display's** (`Effect.setScrims(MonitorId, [ScrimBinding], ScrimChange)`), as its photograph and
its surface already were. `ScrimBinding` loses `monitor` with it, and `State.scrims` becomes a set per
display, which is what the hold in `settleScrims` was already expressing by splicing. A held display is now
simply one that was sent nothing, and a display mid-move is not repainted by its neighbour's focus change.
`setMonitors` drops a departed display's set, beside `coverClearing` and for its reason.

**The core says how the mask gets there** (`ScrimChange`). A veil that moved with no hand on it is a
`dissolve`; a hand's lift and a set the desktop settled under are `cut`s. That deletes `Scrims.drawn`, the
`lifted` flag, `ScrimSurface.lift` and the plane's "first mask is a correction" case: a cut to an empty set
*is* the lift, and it neither rasterizes nor reads the window server, which is what `lift` existed to say.

**The mask is a layer tree.** One `CAShapeLayer` per see-through window, path for where it is, opacity for
how see-through it is. `Scrims.veils` builds each path as the window's rounded silhouette minus every other
window on the glass, so **the occluder and the decline are the same subtraction** and z-order decides nothing
— only the sheet rule still reads the walk. The whole `within:` mechanism, the back-to-front painting order
and `ScrimWindow.mask`'s rasterizer go with it.

This was measured before it was written, because the reason to keep the image was a Core Animation question
nobody had answered: whether repainting a mask ends an opacity fade. Offscreen, `CALayer.render(in:)` gives a
mask of shape layers exactly the alpha the image had (veil 0.5 → 128, 0.25 → 64, and a path carved by
`CGPath.subtracting` leaves the overlap at 0). On a real window sampled every 4 ms off `presentation()`, a
0.12 s fade from 0.5 runs linearly and **survives** a sibling's path being rewritten at 40 ms, its own path
being rewritten, a layer being added and one removed, and the mask layer's own contents being replaced; a
fade retargeted at 40 ms starts from 0.33 — where it had got to — and ramps back. Building the mask for six
windows at 3420×2214 costs 0.24 ms of paths against 2.13 ms of bitmap. `CARenderer` was tried first and drew
nothing at all in a plain command-line process, which is why the probe is a window.

**The gate stays, and the fade's end is Core Animation's to report.** The window flips to `alpha 1` the moment
there is a photograph and something see-through, and back when the transaction carrying the last fade
completes (`settled(keeping:)`), which reads the live state rather than the set that scheduled it — so a set
landing inside a fade is the one that decides, and the generation counter the old off-path needed is gone.
A `cut` closes the gate in its own transaction, since what a lift must not do is wait.

Tests. `ScrimTests` gains the display and the word: a set names one display and reaches no other, and each
re-send carries the change the core meant (`.cut` for a settle, a float that placed itself, and a covered
transition's re-send; `.dissolve` for a veil that moved and for a set-down). Both directions were mutated —
every change forced to `.dissolve`, then all to `.cut` — and each mutation failed the tests written for it.
`ScrimPlaneTests` moves from region lists to shapes: `shows(_:_:_:_:)` asks whether a point in core
coordinates is inside a window's path, which states the rule directly ("the desktop shows here, and not
there") where a list of rectangles stated its implementation. `ScrimMaskTests` is deleted — its claims are
those shapes now, except the two the rasterizer owned (the veil living in alpha, `.copy` clearing rather than
blending), which the layer tree does not have.

## Observations

Checked live on this build, one 1710×1107 display, `EMIRA_TRACE=1`:
- **`float on`** (no cover) held its set and sent it once at the landing, as a `cut` — nothing about the
  veil moved, only the rectangles.
- **A focus change on the glass** sent one `dissolve` naming display 1.
- **A scrolling focus change** sent a `dissolve` at the teleport and a `cut` at the landings, under the cover.
- **The veil renders.** The same 120×120 patch of a window reads mean luminance 36.8 focused and 27.4
  veiled, so the shape layers are masking the photograph on the glass and not only in `render(in:)`.

What was not checked live: a hand drag (the `cut` to nothing), a second display, and what any of it looks
like. The fades were measured on a probe window rather than on the scrim itself.

**A shape layer per window is a layer per window**, which is the shape `ScrimWindow`'s header argues against
for *windows*. The argument is about the window server — a window per window would take clicks and need
ordering — and layers inside one surface cost none of that. What they do cost is a `CGPath` boolean per pair
of overlapping windows per repaint, which is the 0.24 ms above and grows with the square of the windows on
one screen; a desktop with a hundred of them would want the rectangles sorted first.

**`CALayer.mask` with sublayers is the load-bearing fact**, and it is documented only by behaviour. If a
future macOS stops compositing a mask's sublayer tree, every scrim goes opaque at once rather than degrading.
The bitmap it replaces was the same kind of bet on `contents` being read as alpha.
