# Keep a still at the size a window rests at

> Change `1791701193` — 2026-10-10

## Goal

`ASSESSMENT.md` P2. Under `immediate` a kept still stands in for a window only at the size it was filmed at,
and the head batch films every window at its size *before* the transition. Any resize therefore left that
window with no stand-in for the next transition: `cycle-width`, `grow`, `fullscreen`, a column widening on a
departure, every arrival. The next head then waited on a fresh capture of it. The assessment's 256 ms
`move-window` raise was exactly this. P1 shortened that wait by filming the window first. This change removes
it.

## Implementation

**A new effect, `keepStill(monitor, window, size:)`, emitted at `crossfadeDone`.** It covers every window at
rest on that display, meaning the strip's visible windows and its pins, at the size the world records. It
is emitted only under `CoverMode.immediate`, the one mode that stands in by size. The preview guide reads
stills at any size, so it has no use for one. It is not emitted when a new cover has opened on the display
during the fade, the same `hasLayers` guard the pin's clearing already has. That cover's head batch is filming
what it needs.

**The core names rest sizes; the shell decides what to film.** `CaptureService.keep` films a window only when
stills are kept and `SurfaceCache` holds none at that size. The common case, where nothing was resized, films
nothing. The film goes through `film(_:on:then:)`, the hoist path. It is minted on the shared counter, recorded
unpinned, reduced off-main (change `1791700631`), and takes no base and owes no ack.

Considered and rejected:

- **Having the core track each session's capture sizes and emit only the resized windows.** That means more
  state in `Motion` to answer a question the cache already answers exactly.
- **Filming every scoped window at `crossfadeDone`.** That is 4–5 serialized captures (~250 ms of capture
  queue) per transition, and a keypress right after would queue behind them.

**Why `crossfadeDone`.** The capture plane is idle and the desktop is at rest. That is the same moment
`desktopMayHaveChanged` already refilms the scrim photograph. The assessment's objection to timer captures
does not apply: this is bounded per transition, and nothing runs at idle.

**Validated live** with the release daemon on the user's `immediate` config. The run was eight commands,
alternating `cycle-width` with focus moves. Every transition after a `cycle-width` stood all its windows in
and raised at the base: 67, 73 and 77 ms, reported as `3/3` and `4/4 standing`. The one raise past the base,
at 135 ms, was a fourth window entering scope for the first time, which no rule could have filmed ahead.

## Observations

- Shoulder windows, the columns just off the viewport that a scroll also scopes, are not named. They are
  rarely the ones resized, and naming them would film windows nobody is looking at. An arrival placed
  off-screen is the case this misses.
- A window resized *by its app* while no cover is up is not caught. It is refilmed only at the next cover's
  head, as before.
- `keepStill` and a head batch can overlap if a command lands right after `crossfadeDone`. Overlapping captures
  inflate each other (`SCKCapturer` header). The keep films are typically 0–1 windows, so the exposure is
  small, but it was not measured.
