# App chrome that carries an NSWindow is not a window

> Change `1785993114` — 2026-08-05

## Goal

Chrome's Cmd-F find bar is a full entry in `kAXWindowsAttribute`: role `AXWindow`, a frame, a title
("Find in page⏎…"). The classifier fell through its subrole switch to `default: .other`, so emira
adopted it — `emira debug` listed it alongside real windows.

`.other` does not tile, so nothing was ever laid out wrong, and it would be easy to call this
cosmetic. It is not. Adoption mints a `WindowId` per appearance, and a find bar is opened and closed
all day: toggling it three times minted ids 6, 7, 8, 9, each with a bind, an observer attach and a
destroy. Worse, `World.window(at:)` prefers floats over tiled windows by design, and `isOnScreen`
answers `true` unconditionally for anything emira does not place — so under `[focus] follows-mouse`
the find bar wins the hit test over the page beneath it, and `handlePointerEntered` emits `.focus`
at an element whose `AXMain` and `AXFocused` are both read-only. Focus lands on something that
cannot hold it.

## Implementation

`WindowRole.init?` gains a second failure direction: subrole is the literal `AXUnknown` **and**
`AXMain` is not settable ⇒ `nil`, dropped at the AX boundary exactly as an unrecognized role is.

Three candidate signals were measured against every window live on the machine, plus six synthesized
style masks, before this one was chosen. What the two losers miss is that **AppKit derives the subrole
from `canBecomeMain`**. Two windows built here with identical style masks (`.borderless, .resizable`),
differing only in an override, report:

| window                 | AXSubrole          | AXRoleDescription | AXMain settable |
| ---------------------- | ------------------ | ----------------- | --------------- |
| borderless, overridden | `AXStandardWindow` | standard window   | yes             |
| borderless, plain      | `AXDialog`         | dialog            | NO              |

So a decorationless Ghostty is safe for a reason that has nothing to do with its style mask: it must
override `canBecomeMain`/`canBecomeKey` to be typable, and reports `AXStandardWindow` for having done
so. Across every window sampled — ten of them — `AXStandardWindow ⟺ settable AXMain`, without
exception.

That correlation means the conjunction buys **no extra detection** on the AppKit path; it is one fact
read twice. It is kept anyway, as a false-positive belt for toolkits that grow their own AX tree
(Chromium, Electron, JVM), where `AXUnknown` is a habit rather than a statement and the settable
`AXMain` is the half worth believing.

`canBecomeMain` is a real AX round trip, so it is an `@autoclosure`: only the chrome arm evaluates
it, and a window that named its own subrole never pays. A test pins that, since it is a contract
rather than an implementation detail.

Rejected: keying on `AXSize` not being settable. It looks decisive — the find bar accepts position
writes and refuses size, so it can never be laid out — but it does not separate the classes. Safari's
Settings window refuses size writes too, and is a window we must keep. Non-resizability is a
consequence of this thing not being a window rather than evidence for it.

Rejected: keying on the absent stoplight buttons, and instructively. A borderless window exposes no
`standardWindowButton`s at all, so the test drops a decorationless terminal — precisely the case it
had to survive, and the same case that makes the subrole trustworthy.

Rejected: the broader "cannot be main" spelling without the `AXUnknown` half. It also swallows
`AXDialog`, and §6's tri-state `float` override exists so a user can tile a dialog.

## Observations

Verified against the running desktop without restarting the daemon — an ad-hoc rebuild re-prompts for
Accessibility (§12) — by linking a harness against the built `EmiraShell` and calling the shipped
`AXApplication.windows()` → `AXWindow.snapshot(bundleId:)` path directly. Find bar closed: four
windows, all `.standard`. Find bar open: the same four, plus `DECLINED (not a window)` for
"Find in page". Suite green at 1473 tests.

One Photos window with an empty title was declined in the same run and could not be reproduced in 65
subsequent polls, so its attributes were never captured. On the AppKit path `AXUnknown` implies
`canBecomeMain == false` implies borderless and non-resizable, which is a HUD or a drag proxy rather
than a document window — Photos' library window classifies `.standard` throughout — and the old code
adopted it as `.other`, so it is the same class as the find bar rather than a regression. Worth
confirming if it resurfaces.

Only Chrome's find bar was confirmed in the wild. Chrome's other auxiliary surfaces (the status
bubble that previews a link target, autofill dropdowns, the download bubble) were not observed and
may or may not be `NSWindow`s reaching `kAXWindowsAttribute`. `NSPanel`s are not the same problem:
six synthesized windows included two panels and **neither appeared in `kAXWindowsAttribute` at all**,
so AppKit-standard utility panels never reach the classifier.
