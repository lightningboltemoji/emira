# A way into the config file from the menu bar

> Change `1785471687` — 2026-07-30

## Goal

The config file is the whole interface, and nothing in the running GUI led to it. A user who installed
the `.app` and never opened a terminal had a menu bar item that could quit, could start at login, and
could tell them their file was broken on line 12 — with no way to go and look at line 12.

## Implementation

`ConfigFile.open(at:)` in the shell's `Config/` folder, and one menu item under **open at login**.
The path is the item's tooltip rather than its title: `$EMIRA_CONFIG` can make it arbitrarily long.
`MenuBarItem` takes the
path at init and the daemon passes `loader.path`, so the item opens the file the daemon actually read
rather than the one it would have read by default. Errors go out the existing `onError` channel, the
same shape as the login-item toggle — the menu item does the work and reports what failed.

There is nothing to configure about which editor, and the alternatives were all worse. `$EDITOR` is
not available to a daemon launched by launchd, and a `editor = "..."` setting would be a key you have
to edit the file to write. macOS types `.toml` as `public.toml`, which conforms to plain text, so
LaunchServices always resolves something: the user's TOML editor, or TextEdit when they've never said.
Measured, not assumed — `NSWorkspace.urlForApplication(toOpen:)` on a `.toml` returns TextEdit on a
machine with nothing registered. It returns *nothing* for a file that doesn't exist, and `open` then
returns `false`, which is the one real failure mode and the reason for the rest of this change.

So the file is created if it isn't there. That is not a workaround: a missing file is every setting at
its default and a perfectly good way to run emira, so "no file yet" is the likeliest state of the
machine whose user just asked to edit one. What goes in it is a two-line comment pointing at `emira
config explain` (`Config.starter`, beside `defaultPath()` — a fact about the config, not the shell).
Explicitly **not** `ConfigSchema.document`: that writes every setting out at its default, and a file
that writes a default down pins it against ever changing, which is the same judgement `config set`
makes when it *removes* a key set back to its default. The starter text parses to `Config()`, so the
watcher wakes on the new file, reads a config equal to the one it holds, and reports nothing — a test
pins that. An existing file is never touched, including one that won't parse, which is the file most
worth opening.

A `false` from `open` — nothing claimed the file — falls back to revealing it in Finder rather than
failing silently. Finder can always show a file that exists, and `Open With` is one right-click from
there.

## Observations

The item is `⌘,`, which only fires while the menu is open, the same as the existing `⌘Q`. When the
Settings window of M6.5 arrives it will want that equivalent, and this item should become something
like **reveal config file…** or move below it rather than compete.

`NSWorkspace.open` is not exercised by the suite — a unit test must not launch TextEdit. What is
tested is everything up to it: that a missing file is created, that its directory is created with it,
that its text parses to the defaults, that an existing file is left byte-for-byte, and that creating
one is not a reload.
