# The charter, and the knowledge base that carries it

> Change `1784863319` — 2026-07-23

## Goal

Determine whether a scrollable-tiling window manager can get fluid, compositor-grade motion on
macOS with SIP enabled, then record the architecture that follows from the answer.

## Implementation

Four throwaway prototypes tested the two risks.

- **Reconstruction fidelity.** A reconstruction assembled from ScreenCaptureKit stills and raised over
  a live window is indistinguishable from it. The one gap is the drop shadow, which is not part of a
  window's surface; a synthesized `CALayer` shadow travelling with the layer closes it.
- **Off-screen stashing.** An extreme off-screen coordinate is clamped to a ~40 px sliver. A precise
  position leaving ~1 px on screen is honored. Occlusion is binary, so a window with any visible pixel
  keeps rendering and parked columns do not freeze.

Both results are recorded in `PRINCIPLES.md` §4a and §6 as facts rather than as prototype output.
`PRINCIPLES.md` holds the SIP-on charter, the truth/presentation plane split, and the
layered-reconstruction loop. `IMPLEMENTATION.md` holds the functional-core architecture, the module
graph, and an M0–M7 roadmap whose completeness line is M5.

`.agents/README.md` defines the documentation rule: the two documents are present-tense ground
truth, and per-change history lives in `.agents/changes/`.

The prototypes are not retained.

## Observations

- No product code exists; everything below the charter is a plan.
- Fidelity is verified for three coordinated windows, not a full desktop.
- The strip is wider than the screen, so parked slivers accumulate at the screen edge. Their visual
  cost is unmeasured. A curtain overlay is the fallback.
- Static stills freeze window content for a transition's duration. Live ScreenCaptureKit streams are
  the escape hatch.
