# A veil stays cut to the window server through a slow write

> Change `1793851899` — 2026-11-04

## Goal

With a slow or hung app on the desktop, the veil was drawn over a window that had not got where emira sent it, and
left a clean rectangle somewhere else. The report was of a window that "should be placed but hasn't been yet"
being unveiled where it should be rather than where it is. The mask is cut from the window server, not from the
core's targets, so a mask in the wrong place meant a mask read at the wrong *moment*.

AX is served on the target's main run loop, so an app that holds its own main thread is slow AX on demand, and
`kill -STOP` is the hard version. Reproduced that way on a real daemon, filmed at 60 fps with the window list read on
every frame on `EMIRA_TRACE`'s clock:

- A placed window moved itself, then stalled: the neighbour's veil drew straight over it, focused, for as long as
  the stall (1.08 s for 1 s, about 5 s for 5 s), with no cut in between.
- A new window grew and moved after its cover had come down: veiled everywhere but a clean rectangle at the size
  it opened, for the 2 s between its two steps, or a hole left in the neighbour's veil where it had stood, for 1.3 s.
- A write that failed and then landed anyway: the hole stayed. 114 s on an idle desktop, until the next focus change.
- Focus moving while a write was out: the newly focused window stayed veiled for 3.8 s.

## Implementation

**Three things let the mask go stale, and each was a reasonable assumption about how long a write takes.** A set is
held while a write touches its display; a window's own move reports are dropped as echoes while a write to it is
out; the settle watch ends on quiet, reading that as the server having caught up. Between them nothing reads the
server for the length of a slow write, and a write was far longer than anybody thought.

**The 250 ms bound never reached a window.** `AXClient` set the timeout on each application element and said window
elements inherited it. Measured against a frozen app, calls through the application element took 260 ms and calls
through a window element 1.5 s. A timeout on `AXUIElementCreateSystemWide()` bounds them all at 260 ms, so it is set
once, there, and `AXApplication.setMessagingTimeout` is gone. Writes to a hung app are given up on in 1.03 s rather
than 4.8 s, or the 9.3 s of a run with focus's calls on the lane as well. `PinFence`'s grace was already sized for
three calls "at up to 0.25 s each", which is now true.

**The plane keeps reading while a write is out** (`Scrims.isWriting`, from `FrameWrites`), and past its settle yields
to the frame loop as an arrival watch does. Quiet still ends a stale frame on its old schedule: that is a claim about
the server, and `aStaleFrameStillEndsAtQuietWhileAWriteIsOut` pins that a window a write has not moved declines
again rather than being suspended for the length of the write.

**A move no write answers for tells the plane directly** (`WorldWatcher.onWindowMoved`, `FrameWrites.onBegin` →
`Scrims.expectMovement`, which `peeksChanged` became: it was the same operation). Ahead of the frame read, since
that read goes to an app that may have just stopped answering.

Rejected:

- **Re-sending the set on every `windowSelfPlaced` with nothing in flight**, which was the plan, and the one-line
  way to fix the late landing. `anEchoThatStopsIsNotARecut` pins the opposite on purpose: most of those are our own
  echoes stopping, and each set is a window-list read, under a cover if one is up. The rationale held. The shell
  reports the move instead, and a report under a cover reads nothing, so the core did not change at all.
- **A core effect for "watch this display".** `World.inFlight` knows the display exactly and `FrameWrites` does not,
  so a write on one screen keeps the other's watch reading too. It is a second of list reads against a new word in
  the vocabulary, and the shell already held the fact.
- **Releasing the held set.** Unmeasured, so left: it holds a focus change for at most 0.83 s now, from 3.8 s.

**Ruled out on the way.** The window server does not lead the glass for an AppKit app: stalled inside its own move
handler, the reading and the pixels changed on one frame. A stall before adoption was already right, the window a
stranger in front. The "ghost" at a target after a hold timeout is the cover's 220 ms cross-fade, gone by its end.

**The risk in tightening the bound** was a busy app that used to wait out 1.5 s now failing. Measured with stalls
across the scan's per-window reads, 0.3 to 2 s: every window adopted within 53 ms of its app recovering, and no scan
gave up. A setter that times out is forgiven by a read-back that answers (`AXExecutor.report`), so a slow-but-alive
app still lands. Ordinary transitions held 59–64 fps with nothing stalled.

**Checked on the glass with a throwaway harness**, left out of the repo as probes are. It asked four things of a
real daemon: a window that moved itself stands clear of its neighbour's veil, a write to a hung app is given up on
in under 2 s, a write landing after that leaves no hole, and a window landing late is not veiled past the frame it
opened at. Against the build before this change all four failed, 31 to 37 levels apart and 4.78 s to give up;
against this one all four passed on every run, at 0 levels and 1.03 s. The last one passed on the old build until
it sampled between the window growing and moving: a window's landing arrives with its last move, so that gap is
where the mask is stale, and a neighbour of the same app shares its lane and carries the mask's error whole.
Removing `isWriting` from the watch fails 15 expectations in the suite.

## Observations

- **A hole at a target the window never reached was not reproduced.** The nearest found is a window that reached it
  and left. It would take the server reporting a frame the glass does not show, which an AppKit move does not do and
  a stalled resize was only seen not to in frames. A Metal or Chromium window could differ.
- **Only the stalling test app was run**, never a real slow app, so a launch restoring a saved frame is the inferred trigger for
  the first symptom, not an observed one.
- **One display.** A write on one screen keeps every display's watch reading at 60 Hz, up to about a second, which
  nothing here measured. `MultiDisplayTests` passes, and a peek's change now takes the same path it did.
- **`transition = "off"`** starts a watch per write that it did not before, tracking windows through the teleport
  rather than cut after it. Not run live.
- A move a slow app reports long before it commits it could outlast the watch. Measured at 30 ms; the window is 67.
- A write that fails and never lands stays misplaced until the next event, by design. Why a timed-out write landed
  after a 5 s stall and not an 11 s one was not established.
- The AX timeout has no automated test, since proving it needs a frozen app. `AXClient`'s comment is what guards it.
