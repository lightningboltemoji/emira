# the config file becomes a document you can edit

> Change `1785391332` — 2026-07-29

## Goal

A settings window has to write the config file, and the file it writes to is hand-written. Its comments
explain choices, its blank lines group one table from the next, and the order of its `[keys]` block is
somebody's muscle memory. A `Config → TOML` serializer would have been a tenth of this change and would
have eaten all three the first time a checkbox was clicked — which makes the GUI hostile to exactly the
person who uses emira today.

So the reader stops throwing the source away. `TOML.swift` now records where every value was written,
and `ConfigDocument` changes one of them by splicing over the bytes it occupies. Nothing is reformatted:
not the spaces around a `=`, not the quote style, not whether a number two lines up was typed `8` or
`8.0`.

## Implementation

**Provenance sits on the value.** `TOMLValue` gains a `TOMLSpan` — two ranges, the value's own text and
the whole line carrying it, which are the two things an edit needs and they differ: `set` replaces the
first, `remove` takes out the second. It matches what the type already did with `line`, and the
alternative — a parallel map from dotted key to position — would have been a second structure to keep in
step with the first. `[table]` headers get the same treatment as `TOMLHeader`, whose `extent` is the
header line *plus every key line under it*: the parser knows which header it is inside, so it records the
run directly rather than leaving the writer to re-derive it from a flattened dotted path that has already
lost the shape.

**`config` is a `let`, and an edit replaces the whole document.** Splicing text invalidates every span
after the splice, so an edit has to either patch the parse or read it again. Patching is bookkeeping that
can fall out of step; reading again cannot, and it produces the new `Config` and the next edit's spans in
the same pass. A config file is a page long, so the cost of a re-read is not a cost. This is also why
`set` and `remove` throw where the sketched API didn't: the re-read runs the *schema*, so an out-of-range
value is refused with the file's own diagnostic — "must be at least 0", the same sentence, from the same
code — instead of needing a second validator in the GUI to drift away from the first. A refused edit is
an assignment that never happens, so the document is left exactly as it was.

The two readings cannot diverge because they are one reading: `Config.parse` split into
`TOMLTable.parse` and `Config(reading:)`, and the document runs the second over a *copy* of the table.
The schema consumes what it takes, and the uneaten original is where the spans live.

**Decisions worth naming.** A `remove` takes the line's trailing comment with it — a comment on a value
line describes that value, and leaving it behind leaves a sentence explaining a setting the file no
longer has. Line endings are per *file*, not per line: the terminator is whichever the text's first line
break is, so a CRLF file's inserted lines are CRLF. A new key joins the end of its table's key run, which
ends at the last key rather than at the blank line or the comment after it, so it lands in its table
rather than in the gap before the next one. A new table is appended after a blank line; where a *new
header* goes is the one placeholder here, and task 3's schema is what will let the file be ordered the
way the schema is.

`TOMLValue` is the one type this makes public, and only as far as five factories: `payload` and
`Quoting` stay internal, so a settings window can build a value to write without the grammar's value
model becoming API. `Quoting` exists so a regex goes back the way it came — `'literal strings'`, since a
`"…"` would double every backslash and `\d` isn't an escape this grammar admits at all — and falls back
to a basic string when the text carries a `'`, which a literal cannot hold. Escaping is per *unicode
scalar* rather than per character, because Swift reads `"\r\n"` as one grapheme and a raw one left inside
a value would split the line in two the next time the file was read.

The number spelling was the flagged smell: `ConfigSyntax`'s `spell` is now `TOMLValue.spell`, shared with
the writer, and it took the `abs < 1e15` guard from `SizeDelta.number` on the way — `String(Int(number))`
traps on a `Double` the writer could be handed, where the diagnostics that used to be its only caller
could only ever pass it a schema bound. `SizeDelta.number` stays where it is: it is `EmiraCore`'s, and
this task is `EmiraConfig`'s.

## Observations

`make test` is green at 1029 tests, `EmiraConfigTests` at 106 — 24 new, of which the load-bearing ones
are round-trip identity and reading-agreement over a corpus of eight file *shapes*. The corpus includes
Tanner's own `~/.config/emira/emira.toml`, embedded verbatim rather than read from `$HOME` so the suite
stays hermetic; it was diffed against the file on disk byte-for-byte, and it is the fixture that carries
the mixed `outer-gap` / `outer-gap-top` case and an `exec` line whose quoting is its own hazard.

**Array-of-table addressing is deliberately deferred.** `set("window-rules.2.app-id", …)` would work, and
is documented as not the API: the index is `takeArray`'s flattening detail, and task 6 needs to move whole
`[[window-rules]]` blocks to reorder them, which is not something a per-key `set` can express. No test
addresses a rule by index, so nothing here has to be unbuilt when that API arrives.

Two paths are unreachable through this schema and are here for the diagnostic rather than for the case: a
top-level key, which emira has none of, is inserted before the first header so that the *schema* names it
as unknown instead of the grammar complaining about an empty header first. `TOMLTable`'s speculative
top-level key-run tracking was removed for the same reason — nothing could reach it.

Nothing consumes any of this yet, so the daemon is untouched and there is nothing to look at in a running
emira. The first caller is task 5's window.
