# A close survives its app stalling

> Change `1793954925` — 2026-11-06

## Goal

`close-window` was lost for good if the app was stalled when it ran. `AXWindow.close` reads the close button and then
presses it, and `1793851899` took that read from 1.5 s to 0.25 s. A timeout read as a window with no button, so
nothing was pressed, and a close reports nothing, so nothing noticed. On a real daemon against a stalling fixture,
`close-window` during a 0.4 to 1.2 s stall closed the window 9 of 9 times before `1793851899` and 0 of 9 on `fea8804`.
The audit in `1793866083` and `1793950456` covered the reads that decide what the core believes. This one is in the
write path, so it was missed.

## Implementation

**`close` throws `AXUnanswered` for the read, and the writer says whether the app answered.** The retry is in
`AXExecutor.close`, not the writer: the registry says when the window has gone, and `ScriptedWriter` can drive it,
where a loop in `AXWindowWriter` needs a frozen app to test. It re-queues per attempt, so a write can get onto the
lane between them, under `WorldWatcher.maxUnansweredAttempts`, the one budget for a silent app.

**Only the read is asked again.** A read that timed out did nothing. A press that timed out is still in the app's
queue and lands when the app recovers, so sending another presses twice. `answered` is therefore about the button
read, whatever the press said.

| close during a stall of | before `1793851899` | `fea8804` | this change |
|---|---|---|---|
| 0 ms | 3/3 | 3/3 | 2/2 |
| 400 to 1200 ms | 9/9 | 0/9 | 6/6 |
| 3 s | 0/3 | not run | 2/2 |
| 4.5 s | not run | not run | 2/2 |
| 7 s, past the budget | not run | not run | 0/2 |

Each close that went through landed within a millisecond of the app recovering. Removing `!answered` or the registry
check fails an assertion, and removing the budget crashes the suite on the recursion it makes of the synchronous test
double. The AX half of this has no automated test, for the reason `1793851899` gives.

Rejected:

- **`AXClient.patientTimeout` on the read.** One line, and it covers 1.5 s where polling covers 5, with the lane held
  and that app's writes behind it for the whole wait.
- **Handing the close to `reconcile` past the budget**, as a frame or focus read is. Those repair a state that stays
  wrong until asked. A close firing a minute after it was given, on a window the user may have gone back to, is not
  repairing anything.
- **Holding the close button's element from adoption**, so a press could go straight out and queue like a click, with
  no polling at all. More registry state, for an element that can go stale. Reasoned, not run.
- **Repeating the press with the read.** See above.

## Observations

- **A stall past about 5 s still loses the close**, as silently as before and on purpose. It lost at 3 s before this.
- **Nothing is coalesced.** Each press of the key runs its own chain, so mashing close at a beachball puts several
  on one lane and stretches the budget, and each presses once the app recovers. A press on a window already gone
  does nothing. Reasoned, not run.
- **A press can still be dropped at send** with the app's port full, and is not asked again. It only goes out after
  a read has been answered, so the port should be near empty. Unmeasured.
- **`checkFullScreen` still drops an unanswered read**, the same shape as this. IntelliJ reported 5 of 5 entries and
  exits with that read at 56 ms at worst, and a stall aimed at it did not fire, so it stays unprovoked.
