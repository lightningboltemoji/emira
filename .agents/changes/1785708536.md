# N surfaces in the shell, one managed

> Change `1785708536` — 2026-08-02

## Goal

The second multi-monitor phase: build one of every display-shaped subsystem per attached display, and
move the `CATransaction` seam up so a frame is a frame across all of them. The core still runs one
transition session and only the first display holds workspaces, so what this buys is not a feature but
a proof — a second screen raises its own cover over its own desktop and dissolves it, with nothing on it.

## Implementation

**`CoverSurface` split into surface and plane.** A `CoverSurface` is one display's layer tree; a
`CoverPlane` is all of them plus the frame boundary. `beginFrame`/`endFrame` moved off the surface and
onto the plane, because with N surfaces a transaction that wraps one of them is not a frame at all —
two displays blitting inside two transactions are two frames, and the strips on them shear apart by
exactly one refresh. `Compositor` is the plane, and a composite of surfaces being a surface is what
leaves `CompositingExecutor` unchanged in shape.

**The two calls with an answer to give back are gated on every surface, not the first.** `coverOnScreen`
is what entitles the reducer to teleport a real window, so it is owed until the cover is up everywhere —
the conservative form of the quantified gate, and correct until a session can name its own monitor.
`crossfadeDone` waits for the last dissolve, because a cover half down is still a cover. Both use the
generation idiom `Overlay.fadeOut` already uses, so a fence from a superseded raise is dropped rather
than counted against the current one. A fence that never fires leaves the report unmade and the hold
deadline to rescue it, which is what the deadline is for.

**A base is per display; a window still is not.** `SCContentFilter(desktopIndependentWindow:)` is
display-independent, so a window is filmed once however many screens are covered — by the first
capturer, whose backing scale is the one the strip is laid out at. Every capturer is asked for its own
base, because a base is a photograph of one screen. Rule 2 generalizes to "no ack leaves a head batch
until every base it needs has landed", and a head batch that ends one base short abandons the whole
cover rather than raising one screen over its own black fill. Conservative deliberately: an instant,
correct placement on both displays beats a cover on one and a black rectangle on the other.

**Filming and excluding had to become separate instructions**, which is the one seam in this change
that is not just "N of it". `SurfaceCapturer`'s request list was doing both jobs — photograph these,
and cut these out of the base — and a fan-out that hands the list to the first capturer only leaves the
*second* display's base with the transition's windows still in it. A window reaching both screens then
appears twice on the second: frozen in the desktop and sliding on a layer above it, the exact artifact
the exclusion filter exists to prevent. So `capture` takes `filming` beside `includeBase`: every
capturer gets the requests, one is told to photograph them. The layer filter is deliberately
`intersects` rather than "belongs to", so a straddling window is drawn whole across the seam by a layer
on each side moving in lockstep under one untagged `setLayerFrame` — which only reads correctly once
both bases have the hole.

**Only a head batch reaches past the first capturer.** Bases are the only thing the others are for, and
a batch *growing* a cover takes none, so asking them bought nothing and cost an `SCShareableContent`
fetch each — a window-server round trip per extra display, at the head of every retarget that pulls a
window into scope, which is precisely the head cost §5 says to care most about.

**A departed display must cost its own screen and no other.** The shell's per-display objects are built
at launch and hot-plug is phase 5's, but *departure* is destructive rather than merely unhandled: a gone
display's `SCKCapturer` finds no `SCDisplay`, delivers no base, and the rule above then abandons every
cover — so one unplug puts the whole desktop on the `snap` path for the rest of the session. Its overlay
is worse still, fencing a raise on a display link for a screen that no longer refreshes, so
`coverOnScreen` never comes and the hold deadline pays for every transition. `CaptureService` and
`Compositor` each take a live `isAttached` and leave such a display out of a batch and out of a raise. A
dismissal is *not* gated that way: taking a cover down is always safe, and an overlay that was never
raised completes at once, so nothing can be left holding a stale photograph for a display that returns.
This is a guard, not the policy — no overlay, capturer or guide is built for a display that arrives.

**One *read* of the display set, too.** Moving the struts onto `Event.screensChanged` (D6) quietly turned
an agreement that had been structural into one that is temporal: the overlays are built from a
`geometry.monitors(screens)` at launch, and the core's copy had been a second call to the same function
at adoption. `NSScreen.visibleFrame` is live, so those are two independent reads — and adoption is held
back for as long as a broken config file takes to fix, which is how far apart they can drift. A Dock that
moved in between would leave the cover painting a working area the strip is no longer inside, which is
the one thing the unpainted chrome band is not allowed to be wrong about. The array is read once and both
sides get it.

**One reader for a display's identity** (`ScreenGeometry.displayId`). The daemon had been reading
`NSScreenNumber` a second time to build the capturers, with a *different* fallback than
`ScreenGeometry.monitors` uses — so a screen AppKit gave no number would have had the core keying a
strip on one id and ScreenCaptureKit filming another display entirely. The `MonitorId`, the
`CGDirectDisplayID` and the `NSScreen` are one number under three names, and that is now stated once.

**A surface builds a layer only for windows on its own display.** The bindings are the whole
transition's, so every surface is offered every window, and the still's own captured frame is the fact
that says which screen the window was on. Without the filter each display would hold a clipped copy of
the other's strip and the same `LayerId` would name N layers — which is the routing `Effect.setLayerFrame`
gets to skip by staying untagged (D11). This is the seam phase 3 replaces with the session's own monitor.

**The guide is per display and asks everything of its own monitor** — its metrics, the address it is
showing, and the strips that monitor *owns*. The last of those was a real leak: `naturalFrames` answers
for the whole workspace set, which is what makes a switch slide, and without the ownership filter a
second display's panel drew the first display's windows. `focused` in the trigger is scoped the same
way, so a screen that does not hold focus cannot summon a HUD because focus moved on the other one.

**One clock, on the fastest display attached** (D9). `dt` is real elapsed time and the springs are
analytic in it, so a 60 Hz screen fed at 120 Hz drops frames while a 120 Hz screen fed at 60 Hz is
visibly under-driven; picking the fastest means nobody is ever the latter. A strictly smaller change
than per-display ticks, and it buys the same smoothness.

## Observations

The multi-display capture tests found nothing, but they replaced something worse: `service.base == nil`
had been comparing a *method reference* against `nil` since `base` became `base(of:)` — it compiled,
because Swift promotes the function to an optional, and it silently asserted a tautology. Two store
tests had stopped testing anything.

`Reconstruction`'s display filter is the one load-bearing change here with no unit test, because
`Reconstruction` needs a window server. It fails safe in the direction that matters — a window is on
the display its capture was taken from, and macOS never lets one leave the screen entirely — but a hole
in a cover is what a wrong answer would look like, so it wants a running daemon on two displays.

`HoldTimer` is still single, and `Runtime.holdArmedFor` is still one generation: those become per
monitor with the sessions, in phase 3. `StatusModel.workspace` is still the acting monitor's alone.

**What a second display costs until phase 3, stated plainly, because it is a regression and not a
rough edge.** One core session covers every screen, so a transition *anywhere* raises an opaque cover
**everywhere** and holds it for the whole of it: a video playing on the other display freezes for the
length of every scroll. And the capture head roughly doubles — a base and an `SCShareableContent` fetch
per covered screen, with no sharing one, the type not being `Sendable`. Both are the conservative
reading of the quantified gate, both are the price of a session that cannot yet name its own monitor,
and both stop being paid when D7 lands. Anyone running two displays should expect to see this rather
than report it.
